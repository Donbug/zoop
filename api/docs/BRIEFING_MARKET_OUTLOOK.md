# 출근 전망 갱신·퇴근 관측 비교

브리핑 핵심 이슈 최대3개와 별도로 모든 적격 기업 자료를 회차 마감으로 고정해 시장 분석에 사용한다. 출근은 직전 퇴근 전망을 새 정보로 갱신하고 당일 목표 세션을 전망한다. 퇴근은 이번 실행에서 만든 출근 전망과 실제 관측을 비교하고 다음 거래일의 조건부 시나리오를 작성한다.

## 입력과 순차 실행

`briefing_market_outlook_run.py`는 기존 검증된 뉴스·공시/선정/문안/근거 상세/일별 지표/유료 호출 기록을 그대로 재사용한다. 입력 모집단은 시각 확인 자료 중 cutoff까지 적격인 전 기업 자료이며, body 전체가 아닌 정확한 앞600자/뒤300자 인용을 읽는다. 새자료와 기존배경은 나누고, 표본이 시장 전체를 대표한다고 주장하지 않는다.

각 회차의 생성·독립 검증 결과가 PASS일 때만 그 실제 결과 버전·SHA와 구조화 전망을 다음 회차의 입력에 전달한다. 없거나 보류된 이전 결과를 다른 과거 버전으로 대체하지 않는다. 최초 회차에 구조화 이전 전망이 없으면 새 전망부터 시작하며 과거 전망을 만들어내지 않는다.

거래 세션 달력과 대상일·종료시각·기준 종가가 있어야 가격 방향 전망을 만든다. 실제 일별 종가와 확인 가능한 은행 기준환율을 사용하며 장중 경로·수급·실제 뉴스 인과는 만들지 않는다. 조건이 미관측이거나 방향이 uncertain/기간미완료/정확한 대상일 관측없음이면 적중률을 계산하지 않는다. 출근09:20은 정상 거래일의 장초반이고 장전 실시간 분석이 아니다.

## 프롬프트와 검증

- 기존 `market-context/` v2는 그대로 보존한다.
- `market-context-v2.1-outlook/`은 최초 실제 실행의 prompt/schema 바이트를 보존한다.
- `market-context-v2.2-outlook/`은 사실을 여러 기업/수치로 묶지 않고 정확한 근거를 연결하며, 단정 수식어·기준일 혼동을 방지한다. 사실·해석·조건부 상방/하방 시나리오·이전 전망 갱신·관측 비교를 구분한다.

전망이 가능한데 단순 사실요약으로 끝나거나, 이전 전망이 있는 출근에 갱신이 없거나, 이전 출근이 있는 퇴근에 비교가 없으면 서버 검증이 거절한다. 생성과 별도 모델 검증의 전 문장이 통과해야 공개하고, 실패 기록은 성공으로 고치지 않는다. 버전별 허용 classpath prompt와 실제 요청 instructions가 같아야 한다.

## 저장·조회·화면

기존 public_snapshot에 `marketSummary.analysis`를 선택 필드로 저장한다. 검증된 claims/forecasts/forecastEvaluations, 이전 회차/버전, 기업 자료 범위만 공개하고 전체 raw 본문이나 모델 요청은 공개하지 않는다. 공개 OpenAPI와 생성 Swagger 모두 선택적 nullable 분석 필드를 포함한다. 이전 발행본은 기존 text 응답을 그대로 표시한다.

화면 D-BRF-01/02는 출근 전망 갱신, 퇴근 아침 예상·관측 비교, 대상 거래일, 조건과 반대 요인, 평가 불가 사유, 기업/자료 범위를 구분한다. 회차/edition/cutoff가 맞지 않는 분석은 숨긴다. 기존 원문 근거 상세와 개인화는 유지한다.

다른 실행의 파생 요약을 새 AI 결과로 복사하지 않는다. 유료 생성 없는 기존 파생 지표 표시 입력의 실행 승인만 새 layer로 결속하고 paid context/request/response는 변경하지 않는다. 재실행의 이전 유료 실패 기록은 outlookHistory의 원 bundle·request/response·usage·원문 위치를 다시 검증해 artifact와 회계 기록으로 보존한다. 같은 결과 재가져오기는 불변이다.

## 운영자 실행

독립 private baseline/output 및 명시적인 `--round YYYY-MM-DD-morning`/`--round YYYY-MM-DD-evening` 목록을 사용한다. 실행 플래그가 없으면 입력·모집단·달력·예산 계획만 검증한다. `--execute-authorized-generation`과 사용자 승인 참조·별도 private 키 파일이 있어야 새 유료 요청을 한다. 새 수집 HTTP는0이며 기존 완료 요청은 재사용하고 미응답 요청은 재전송하지 않는다.

호출 상한 기본400에는 기존 원 예약도 포함한다. 400초과 상한은 별도 사용자 승인 참조 `--budget-approval-ref`가 필요하며, 상한 확대 승인이 없으면 추가 실행하지 않는다. 승인 참조와 실제 사용량을 별도로 기록하며 승인된 최대 호출을 전부 소진할 필요는 없다. `--max-repairs 1`이면 회차마다 최대1회 같은 근거 안에서 보완하고 전체 예약 한도는 계속 적용한다.

현 단계 검증은 원발행시각 기준 과거 시뮬레이션이다. 당시 수집 가능성·본문 동일성·권리/운영 발행·예측 성과를 입증하지 않는다. 기존 발행 DB를 덮어쓰지 않고 별도 DB와 서버로 확인한다.

## 실제 순차 회차 검증 (2026-10-20)

보완 v2.2 프롬프트로 10/7 출근 → 퇴근 → 10/8 출근 → 퇴근을 순서대로 실행했다. 검증된 앞 회차의 결과 해시를 다음 회차가 참조했으며, 예전 실패 결과는 원형 보존했다.

| 회차 | 전체 적격 자료 | 생성·근거 검증 | 이전 회차 연결 |
|---|---:|---|---|
| 10/7 출근 |349|PASS|비교 가능한 직전 구조화 전망 없음을 표시하고 신규 전망부터 시작|
| 10/7 퇴근 |384|PASS|이번 실행의 10/7 출근 전망과 당일 종가를 비교|
| 10/8 출근 |452|PASS, 1회 보완|이번 실행의 10/7 퇴근 전망 2개를 새 정보로 갱신|
| 10/8 퇴근 |496|PASS|이번 실행의 10/8 출근 전망과 당일 종가 비교, 다음 거래일 10/12 전망|

전체 415회 한도 안에서 새 호출은 10회, 총 예약은 409회였다. 새 입력 4,338,653·출력 13,146토큰이며, 이전 완료 기록과 미응답2건을 그대로 보존했다. 같은 완료 실행을 재사용하면 새 호출은0회다. 10/8 출근 최초 문안의 근거보다 강한 이익 해석은 독립 검증에서 보류됐고, 지정 인용을 추가해 같은 회차의 고정 근거 안에서 보완했다.

`PASS`는 문안·근거 검증 통과다. `previousPublication.status`는 비교할 이전 브리핑의 가용성이고, `forecastEvaluations.status`는 조건부 전망의 평가 가능성이다. 이 세 상태를 합치지 않는다. 실제 두 퇴근 회차의 비교 문장은 저장된 아침 전망과 종가를 함께 설명하지만, 조건 충족 여부가 별도 관측되지 않아 적중/실패 판정은 하지 않았다. 이 실행을 예측 성과나 실시간 운영 검증으로 보고하지 않는다.

가져오기 서버도 기본 400회 제한을 유지한다. 더 큰 한도의 결과를 등록하려면 비공개 local replay 실행에 `zoop.briefing.replay.maximum-paid-calls=415`와 별도 `zoop.briefing.replay.budget-approval-ref`를 함께 지정한다. bundle이 스스로 한도를 올릴 수 없고, 승인 참조 누락·설정 상한 초과는 DB 쓰기 전에 거절한다. 승인된 확장은 비공개 manifest의 `budgetAuthorization`에 보존하며 공개 조회 권한을 확대하지 않는다.

## 연속 실행과 수정 전·후 목록 (2026-10-21)

실제 다음 실행은 현재 bundle을 입력으로 받고 별도 output/DB를 쓴다. `outlookHistory.bundleSha256` 체인을 최대8층까지 순회해 모든 이전 bundle 바이트·뉴스/회차·원문 인용·모델 요청/응답·영수증·직전 결과 연결을 검사한다. 일부 회차의 동일 입력 호출이 재사용되어 여러 층에 같은 receipt가 있으면 같은 내용일 때만 한 번 계산한다. 상충한 영수증·누락/위조·하위 원문 변조·깊이 초과는 거부한다. 각 이전 layer도 외부에서 설정한 승인 상한 안에서 검증한다. 기존한도400 기본은 유지한다.

`briefing_market_outlook_run.py`는 새 실행 전 history의 바이트 SHA·뉴스 동일성·receipt 목록 연결을 확인한다. 실제 요청은 원본 inputUserInboxRef 계보를 유지하고, 추가 유료 실행 승인·상한은 별도의 budgetApprovalRef/최대425 설정과 계획에 남긴다. 입력 폴더와 기존 DB/서버를 덮어쓰지 않는다.

완료 결과의 비교 목록은 `scripts/briefing_outlook_compare.py --baseline <기존 bundle-v2.json> --current <새 bundle-v2.json> --output <별도 private review 폴더>`로 만든다. 생성한 comparison.json/index.html은 같은 회차별 기존/새 버전·상태·문안·근거 수·조건/입력 문서 수를 나란히 보여준다. 실제 프론트 주소를 --old-url/--new-url로 지정한다. 보류 문안은 ‘비교용 보류 기록’으로 표시하며 발행으로 꾸미지 않는다. 이 도구는 모델 호출·DB 쓰기를 하지 않는 로컬 검토용이며 원문/키/로그 폴더를 HTTP 공개 루트로 쓰지 않는다.


## v2.4 역할별 사실/비교 검증·필수 전망 슬롯 (2026-10-21)

새 CLI 기본은 `market-context-v2.4-outlook`이다. 기존 완료 실행은 원래 `--prompt-version`과 output/plan으로 재사용한다. v2.3 기록을 새 버전으로 재명명하지 않는다.

v2.4는 사실의 독립 주장 단위와 비교/갱신의 요소 완전성을 구분한다. 생성 응답의 `requiredClaims`는 현재 target/직전 구조화 전망/직전 summary에 따라 필수 역할을 가진다. 첫 생성과 보완 모두 동일한 필수 슬롯·kind 검사를 통과해야 하며, Python/Java는 raw 응답을 동일한 순서로 투영한다. 서버 전망 삽입이나 기존 실패 판정 변경은 없다. 자세한 정의/반례는 `docs/development/briefing-outlook-quality.md`와 v2.4 생성/검증 prompt를 본다.

부분 회차 요청은 새 선행 결과로 입력이 바뀌는 후속 유료 회차를 포함한다. `requestedRoundIds`/`dependencyRoundIds`로 원요청과 추가 의존 회차를 구분한다. `plannedNewCalls`는 생성+검증 기본 수, `maximumNewCalls`는 `--max-repairs`를 포함한 상한이다. `minimumTotalReservations`, `maximumTotalReservations`, `additionalCeilingForMinimum/Maximum`은 기존 미응답까지 포함한 계획이며 승인 자체가 아니다. 미실행 계획은 현재 승인 상한이 부족해도 표시할 수 있지만 `--execute-authorized-generation`은 최소 예산 부족 시 어떤 호출/출력 생성도 하기 전에 거부한다.

10/7 출근·퇴근 +10/8 퇴근 요청에는10/8 출근이 추가돼4개를 순서대로 다시 연결한다. 실제424/425 기록 기준 신규8~16, 총432~440이 필요하다. 현재는 보완 코드/합성 검증만 실행했으며 기존 실제v2.3의1PASS/3WITHHELD·화면·DB는 보존한다. 새 실제 문안이 나와 검증된 뒤 별도 실행/DB/비교 목록에 등록한다.


## v2.5 역할 필드 제약과 부분 회차 재실행 기록

새 CLI 기본은 v2.5다. 기존 완료 실행은 반드시 원래 prompt-version/plan/output으로 재사용한다. v2.4에서 드러난 forecast_update의 counterFactors/target/direction 오입력을 필수 역할별 schema로 제한한다. 필수 forecast는 지정 target/방향·근거·반대 요인이 필요하고, update/comparison에는 새 forecast용 target/direction/counterFactors를 허용하지 않는다. 의미 검증을 완화하지 않는다.

440회 승인 범위 실제 실행: v2.4 4회차12회 후 v2.5의10/8 출근·퇴근4회를 별도 output에 보존했다. 최신4회차는2PASS/2WITHHELD이며 첫 실행3PASS/1WITHHELD도 조상으로 보존한다. 비교 도구는 새 품질flag와 raw requiredClaims의 반려 전망도 표시하고, 중간 실행의 실제 프론트가 없으면 --old-url/--new-url에 빈 문자열을 주어 다른 버전 화면으로 잘못 연결하지 않는다. 이전/중간/최신 문안·판정을 구분한다.

부분 회차 실행 layer는 이전 회차의 영수증을 유지할 수 있다. 전체 신규 토큰은 초기 원장의 requestDigest 집합을 제외한 실제 신규 고유 영수증으로 집계하며, 각 proof의 layer 토큰 합을 신규 호출 토큰으로 단순 합산하지 않는다. 완료 기록 재사용에는 추가 모델 호출이 필요하지 않다.
