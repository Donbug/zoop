# ZOOP AI 거버넌스 정책

문서 ID: ZOOP-AIG-001

버전: 0.3

작성일: 2026년 10월 13일

개정일: 2026년 10월 16일

적용 대상: ZOOP 금융 이슈·기업 관계 탐색 서비스

문서 책임 역할: 프로젝트 책임자

시행 조건: 팀 검토와 책임자 승인 후 적용

## 1 목적과 적용 범위

ZOOP은 뉴스·공시에서 시장 이슈와 기업 간 관계를 추출하고, 이를 관계 그래프·브리핑·근거 기반 답변으로 제공한다. 본 정책은 AI가 사용하는 데이터, 결과의 공개 조건, 사용자 질의의 처리 방법, 검증과 사고 대응 책임을 정의한다. 개발자와 운영자는 기능 구현 및 출시 판단에 이 정책을 사용한다.

챗봇은 사용자의 질문을 유형별로 분류하고, 해당 유형에 허용된 데이터와 도구를 사용하여 정해진 형식으로 답한다. 분류 결과만으로 응답을 확정하지 않는다. 사용자 권한, 대상 기업, 질문의 기간, 근거의 유효성, 출력 검증 결과를 함께 확인한다.

적용 범위는 데이터 수집과 정제, AI 사건·관계 추출, 자동 검증, 관리자 검수, 공개 버전 관리, 브리핑 생성, 챗봇, 모델과 프롬프트 변경, 로그 및 외부 모델 API 운영이다. 그래프와 브리핑에서 AI 결과를 보여주는 화면도 포함한다.

이 문서의 규정은 구현·운영 시 충족해야 할 목표다. 규정의 존재를 구현 완료나 검증 통과의 증거로 사용하지 않는다. 담당자 실명, 모델, 수치 기준, 보관 기간 및 외부 서비스 조건은 16장의 결정 기록에 따라 확정한다. 법령 준수나 금융업 관련 인허가 여부를 이 문서의 승인만으로 판정하지 않는다.

### 1.1 관련 계약의 적용

공개 API의 경로·필드·상태·오류는 [목표 OpenAPI](api/openapi.yaml), 현행 기능의 의미와 이행 기준은 [문서 연결 기준](system/links.yaml), 저장 제약은 [ERD v6](erd/zoop-core-erd-v6.md)를 따른다. ERD 변경 이력에서는 2026년 10월 13일의 ‘후보 allow 접수와 실행 분리’ 추가 변경을 적용한다. AI 내부 실행·검증·복구는 [AI 실행 계약](design/ai-system.md)과 [내부 HTTP 계약](api/internal-ai-openapi.yaml)을 따른다. 목표 설계, 현재 구현 관측, 팀 승인 여부는 각각 구분한다.

Q01~Q08은 이 문서가 제안하는 내부 질의 분류다. 기존 API 필드나 enum을 대체하지 않는다. 공개 계약의 확장이 필요한 복합 응답은 별도 변경과 검증을 거쳐야 한다. 본 정책과 관련 계약의 충돌이 발견되면 한쪽을 구현자가 임의로 덮어쓰지 않고 변경 기록과 담당자 검토를 남긴다.

## 2 서비스의 AI 활용 원칙

### 2.1 정보 제공 범위

ZOOP은 확인 가능한 자료를 설명하고 탐색을 돕는다. 기업·사건의 연결, 뉴스·공시의 핵심 내용, 특정 회차의 변화와 근거를 제공한다. 보유·관심 종목은 관련 정보를 찾는 필터로 사용한다.

개인의 자산 상황에 맞춘 매수·매도·비중 조정, 목표 수익률, 수익 보장, 확정적인 주가 예측, 주문 실행은 본 서비스의 허용 범위에 포함하지 않는다. 이는 ZOOP의 제품 운영 범위이며, 특정 법적 분류를 확정하는 문구가 아니다. 질문에 이러한 요청과 정보 탐색이 함께 있으면 투자 판단 부분의 한계를 알리고, 분리 가능한 사실 설명은 제공할 수 있다.

### 2.2 근거와 불확실성

기업·사건·수치에 관한 사실 주장에는 해당 주장을 뒷받침하는 근거를 연결한다. 출처가 있다는 사실만으로 내용을 확정하지 않는다. 보도에만 있는 주장은 보도 내용으로 표현하고, 추정·전망은 그 성격을 유지한다. 공시도 정정 여부와 효력 시점을 확인한다.

검색 결과가 없으면 ‘현재 조회 범위에서 확인되지 않음’으로 답한다. 이를 ‘사건이 없음’이나 ‘두 기업의 관계가 없음’으로 바꾸지 않는다. 모델의 내부 지식으로 최신 사건, 현재 가격, 공시 수치 또는 누락된 출처를 보충하지 않는다.

### 2.3 통제의 실행 위치

프롬프트에는 설명과 답변 규칙을 두고, 인증·인가·공개 상태 확인·도구 허용 목록·쿼리 범위·타임아웃은 서버 코드로 강제한다. 모델이 제시한 사용자 ID, 권한 또는 검수 상태를 신뢰하지 않는다. 사용자 입력과 수집 문서에 있는 명령은 정책이나 시스템 지시로 승격하지 않는다.

## 3 역할과 책임

소규모 팀에서는 역할을 겸임할 수 있다. 다만 고위험 변경이나 중대 사고 후 재개는 변경 수행자 외에 한 명 이상의 검토를 남긴다. 아래 역할에 실명을 배정하기 전에는 운영 승인 책임이 충족된 것으로 처리하지 않는다.

| 프로젝트 책임자       | AI 사용 범위, 정책 예외, 출시·재개 결정         | 정책 버전과 승인 기록             |
| AI 담당자             | 질의 분류, 추출·생성, 모델·프롬프트 관리        | 변경 내역, 평가 결과, 롤백 대상   |

## 4 전체 파이프라인과 공개 경계

### 4.1 데이터 생성과 공개

처리 순서는 다음과 같다.

1. 승인된 뉴스·공시 출처에서 데이터를 수집하고 출처 및 시각을 기록한다.
2. 정제·중복 제거·기업 식별을 수행하고 원문과 처리 결과를 연결한다.
3. AI가 사건·관계·요약 후보를 생성한다. 후보는 비공개 상태로 저장한다.
4. 자동 검증이 통과·보류·실패를 구분한다.
5. 보류 항목은 관리자 허용 결정 후 재검증한다. 데이터 결함의 수정·재수집은 기존 산출물을 덮어쓰지 않는 별도 버전·작업으로 처리한다. 챗봇 검증 실패의 재생성 금지는 7.4절을 따른다.
6. RDS 문서·벡터와 Neo4j 그래프 등 조회 자원의 준비 상태를 확인한다.
7. 모든 필수 자원이 같은 버전을 조회할 수 있을 때 공통 공개 버전을 전환한다.
8. 브리핑과 챗봇은 공개 버전을 지정하여 조회한다.

정상 결과는 자동 검증과 조회 준비 확인 후 공개할 수 있다. 모든 결과를 사람이 선검수하는 방식은 기본 조건으로 두지 않는다. 대신 위험 조건에 따른 보류와 공개 결과의 표본 검수를 운영한다.

위 순서는 개념상의 처리 단계이며 단일 DB/API 상태 enum이 아니다. `보류 → 관리자 허용 → 재검증 접수 → 실행 → 검증 결과`는 별도 경로다. 검수 결정은 `allow / reject`이며, `allow` 응답은 `revalidation_requested`와 작업 ID를 반환한다. 결정 요청 자체는 `publicChanged=false`이고, 재검증과 조회 준비를 통과해야 공개할 수 있다. 실패·반려·철회 결과는 공개 조회 대상에서 제외한다.

### 4.2 클라우드 구성과 책임의 연결

제공된 클라우드 설계에 따라 EC2-1은 API·인증·관리자 기능, EC2-2는 AI·수집·배치·검증, EC2-3은 Neo4j를 담당한다. RDS PostgreSQL과 pgvector는 문서·계정·검수·작업·공개 버전 관련 데이터를, 비공개 S3는 원문과 산출물을 보관하는 위치로 사용한다. 세부 필드와 물리 저장 위치는 구현 명세에서 확정한다.

EC2-1은 인증된 사용자 범위와 공개 버전을 EC2-2의 작업 요청에 전달한다. EC2-2는 요청이 내부 서버에서 왔다는 이유만으로 권한 검증을 생략하지 않는다. 외부 LLM 호출에는 10장에서 허용한 최소 데이터만 전달한다. 비밀값은 Secrets Manager 등 승인된 저장소에서 관리한다.

RDS와 Neo4j를 하나의 트랜잭션으로 갱신할 수 있다고 가정하지 않는다. 먼저 새 버전의 조회 자원을 준비하고, 준비 완료 기록을 확인한 후 활성 버전 포인터를 전환한다. 요청 시작 시 버전을 고정하고 응답 종료까지 사용한다. 일부 자원만 갱신되거나 전환에 실패하면 기존 공개 버전을 유지한다.

오류가 확인되어 철회된 근거는 과거 버전에 포함되더라도 새 답변에 사용하지 못하도록 별도의 철회 목록을 적용한다. 과거 기록의 보존과 사용자에 대한 재노출 허용은 서로 구분한다.

## 5 데이터 수집과 AI 추출 정책

### 5.1 출처 등록과 보관

데이터 담당자는 출처별로 제공자, API 또는 URL, 수집 항목, 이용·저장·재배포 조건, 외부 모델 전송 가능 여부, 갱신 주기, 정정 처리 방식, 담당자를 등록한다. 원문 전체 보관이나 외부 LLM 전송은 해당 이용 조건에 맞는 범위에서만 수행한다. 조건이 미확인인 출처는 공개 파이프라인에 투입하지 않는다.

원문에는 `source_id`, `document_id`, 원문 주소, 수집 시각, 원문 게시·수정 시각, 내용 해시, 언어, 이용 조건 식별자를 기록한다. 사건 발생 시각은 별도로 관리한다. 사건 시각을 모르면 ‘미상’으로 저장하고 수집 시각이나 게시 시각으로 대체하지 않는다.

같은 기사를 전재한 여러 매체와 같은 원문의 반복 수집은 중복 그룹으로 묶는다. 중복 문서 수를 독립 근거 수처럼 표시하지 않는다. 원문을 수정해서 덮어쓰기보다 수정본과 원본의 연결 및 변경 시각을 남긴다.

### 5.2 사건과 관계 추출

추출 결과는 정해진 구조를 따른다. 최소 항목은 사건 ID, 기업 ID, 관계 유형, 관계 방향, 근거 문서 ID와 근거 구간, 사건·유효 시각, 추출 모델 및 프롬프트 버전, 검증 상태다. 원문에 없는 관계를 매끄러운 설명을 위해 추가하지 않는다.

기업이 같은 기사나 사건에 등장했다는 사실은 공급·투자·계열 관계를 뜻하지 않는다. 공동 등장과 직접 관계를 별도 유형으로 저장한다. 여러 간선을 통과한 연결은 간접 경로로 설명하고 직접 계약 관계처럼 표현하지 않는다. 동명이인 기업, 약칭, 동일 티커 등 식별이 모호한 경우 보류한다.

### 5.3 자동 검증과 보류

| 검증 항목     | 통과 조건                                      | 실패 또는 보류 처리                  |
| ------------- | ---------------------------------------------- | ------------------------------------ |
| 구조와 식별자 | 필수 필드, 자료형, 기업·문서 ID 유효           | 구조 오류는 실패, 식별 모호성은 보류 |
| 근거 연결     | 원문에 접근 가능하고 주장에 대응하는 구간 존재 | 누락·무관한 인용은 공개 차단         |
| 사실과 표현   | 주체·대상·방향·부정·전망 여부가 원문과 일치    | 충돌·해석 불확실성은 보류            |
| 수치와 시점   | 단위·통화·기준일·비교 기간이 원문과 일치       | 불일치 항목을 수정하고 재검증        |
| 중복과 정정   | 중복 그룹 및 최신 정정 관계 반영               | 중복은 병합, 정정 영향은 재처리      |
| 콘텐츠 보안   | 문서 속 명령이 실행되지 않고 비밀값이 배제됨   | 의심 문서 격리 및 담당자 검토        |
| 조회 준비     | 동일 공개 버전의 문서·벡터·그래프 조회 가능    | 기존 버전 유지                       |

LLM을 검증에 사용하더라도 동일 모델의 자기평가만으로 통과시키지 않는다. 구조 검사, 원문 구간 대조, 단위·수치 검사, 참조 무결성 검사와 필요한 사람 검수를 함께 사용한다. 근거 문서가 여러 개라는 이유만으로 통과시키지 않는다. 하나의 명확한 공식 근거가 여러 중복 기사보다 충분할 수 있다.

검수 담당자는 허용·반려와 이유를 기록한다. 요청의 `expectedRevision`을 해당 대상의 현재 revision과 비교하여 오래된 화면에서 내린 결정을 거절한다. `allow`는 고정 후보의 재검증 요청이며 후보 본문을 수정하는 기능이 아니다. 수정이 필요하면 데이터 담당자가 별도 버전·후보 생성 경로와 이력을 정의하고 적용한다. 근거를 찾지 못한 항목을 설명만 고쳐 허용하지 않는다. 새 출처, 변경 모델, 정정 사건은 우선 표본 검수하며 비율과 주기는 출시 전에 결정한다.

### 5.4 관리자 재검증 큐

ERD v6의 최신 규칙에 따라 관리자 작업은 여러 `queued`를 접수하고 `scope=admin`의 `running`은 하나로 제한한다. 허용 결정·재검증 대기 작업·감사·멱등성 완료 기록을 같은 트랜잭션으로 저장한다. 다른 작업이 실행 중이라는 이유로 접수한 결정을 롤백하거나 결정 API에 `JOB_IN_PROGRESS`를 추가하지 않는다.

worker가 `requested_at/id` 순서와 실행 토큰·임대를 확인하여 실행권을 얻는다. `JobList.active`와 `JobLock`은 실행 중인 작업 기준이며 대기 작업만 있으면 `active=null`, `locked=false`, `jobId=null`이다. 허용된 재시도 역시 대기로 접수한다. 관리자 큐 규칙을 채팅에 적용하지 않는다. 채팅은 대화당 `queued/running` 작업 하나를 유지하며, 브리핑은 별도의 회차·시도 제약을 따른다.

### 5.5 문서 요약과 긍부정 판정

`DocumentSentiment`는 문서×기업 판정이고 `BriefingOutlook`은 발행 회차 판정이다. 라벨은 `positive / negative / mixed / undetermined`로 유지한다. `null`은 유효한 판정 산출물이 없다는 뜻이고, `undetermined`는 평가했으나 방향 근거가 부족하다는 뜻이다. 외부 호출 실패를 `undetermined`로 바꾸지 않는다. 확률·점수나 투자 수익률로 확장하지 않으며 이유·인용·판정 시각·모델·프롬프트 버전을 보존한다.

문서 요약과 기업별 판정은 독립 작업이다. 각 `analysisStatus`는 `not_requested / pending / failed / withheld / available`로 구분하고, 요약이 보류·실패했다는 이유만으로 유효한 기업별 판정을 지우지 않는다. Q03·Q06·Q08이 이 결과를 설명할 때도 대상 단위와 원래 라벨을 보존한다.

S1 문서 공개는 구조·정확 인용 검사와 생성기에서 분리된 의미 검증을 요구한다. 공개 사실·해석·제한 문장을 versioned claim/citation에 연결하고 의미 검증의 `supported / contradicted / insufficient` 판정을 적용한다. 인용 좌표는 고정 문서·텍스트 버전의 Unicode code point 기준 `[start,end)`이며 검증 시 임의 정규화하지 않는다. 의미 검증의 HOLD/REJECT 산출물은 내부에 보존하고 공개 응답은 사유와 null을 반환한다.

기존 회차 outlook의 `legacy-outlook-exact-1` 검증과 `validation.semantic=null`은 별도 의미 검증을 마친 문서와 구분한다. 이를 동일한 검증 수준으로 표시하지 않는다. 빈 회차는 모델 호출 없이 outlook을 null로 두고, 발행된 회차는 null을 포함하여 판정 결과를 고정한다.

## 6 챗봇의 질의 분류 정책

### 6.1 분류 구조

질의 분류는 ‘사용자가 알고 싶은 내용’을 식별한다. 정상 질의 유형과 처리 상태를 분리하여 저장한다. 예를 들어 관계 탐색 질문이라도 기업명이 불분명하면 처리 상태는 확인 질문이 된다. 정보가 없다는 이유로 서비스 안내 유형으로 바꾸지 않는다.

모든 챗봇 질문은 회원 전용이다. Q01~Q08의 유형과 관계없이 접수 전에 회원 세션과 대화 소유권을 확인한다. 비회원은 공개 그래프·기업·브리핑을 조회할 수 있지만 챗봇 질문은 할 수 없다. 개인 종목 조회에는 이 공통 조건 외에 본인 데이터 범위 검사를 추가한다.

정상 질의 유형은 다음 8개로 제안한다. 유형 ID는 내부 라우터·프롬프트·평가 세트·감사 기록에서 일관되게 사용한다. 공개 응답에 `intent` 등의 필드를 임의 추가하지 않는다.

Q02는 최신 금융 상황을 일반 지식으로 답하기 위한 우회 경로가 아니다. 현재 기업·가격·사건에 관한 주장은 Q03 등의 공개 데이터 조회를 요구한다. Q08은 모델의 내부 사고 과정이 아니라 기록된 근거와 규칙을 설명한다. 기록되지 않은 선정 이유는 생성하지 않는다.

#### Q02 일반 개념 답변의 현재 운영 기준

현재 ERD와 마이그레이션에는 용어 사전, 개념 문서, 지식 청크 또는 임베딩 전용 저장 구조가 없다. `articles`와 `article_versions`는 뉴스·공시를 대상으로 하며 이를 개념 지식 저장소가 이미 존재하는 것처럼 사용하지 않는다. 전용 지식 저장소를 구축하기 전의 MVP Q02는 다음 조건을 모두 만족하는 안정적인 일반 개념에 한해 일반 LLM의 설명 생성을 허용한다.

- 현재 기업 상태, 가격, 공시, 시장 점유율, 최신 표준, 전망 또는 투자 판단을 포함하지 않는다.
- 답변을 ‘공개 근거로 검증된 사실 답변’으로 표시하지 않고 일반 개념 설명임을 구분한다.
- 생성 모델과 별도의 호출을 포함한 모델 교차검토는 정책·관련성·내부 모순 탐지에 사용할 수 있으나, 비교할 권위 자료가 없으면 사실 검증 통과로 기록하지 않는다.
- 여러 의미가 가능한 약어·용어는 임의 확정하지 않고 `clarification`으로 처리한다.
- 안정적 개념 범위를 벗어나거나 안전한 설명을 만들 수 없으면 지원 범위를 안내한다. 향후 승인된 지식 검색에서 필요한 근거를 찾지 못한 경우에만 `insufficient_evidence`를 사용한다.
- 미지원·미식별 용어는 가명화된 빈도와 실패 유형을 품질 개선 자료로 집계할 수 있으나, 모델이 만든 정의를 자동으로 승인 지식에 추가하지 않는다.

위 조건을 통과한 일반 개념 설명은 `answered`로 저장할 수 있으며 `sources`와 `citations`에는 존재하지 않는 출처를 만들지 않고 빈 배열을 사용한다. 범위·정책·일관성 검사에 실패하면 `validation_failed`로 처리하며, 이를 근거 부족 성공 응답으로 바꾸지 않는다.

향후 용어·개념 지식 저장소를 도입하려면 출처, 문서 버전, 검토 상태, 검토자, 갱신 시각, 청크 위치와 임베딩 버전을 포함하는 별도 계약과 마이그레이션을 먼저 승인한다. 정적 용어 파일을 사용하는 경우에도 버전·해시·승인자를 기록하고, 일반 LLM 답변과 근거 기반 답변의 표시를 혼합하지 않는다.

#### Q02의 단계적 지식 저장소 도입

지식 저장소는 가능한 모든 금융·산업 용어를 미리 수집하는 완전한 백과사전을 목표로 하지 않는다. 일반 LLM만으로 안정적으로 처리되는 저위험 개념은 일반 개념 경로에 유지하고, 다음 조건 중 하나 이상이 실제 운영·평가에서 확인된 용어만 검토 지식으로 승격한다.

- 질문 빈도가 높거나 서비스 핵심 화면에서 반복 사용된다.
- 일반 LLM의 오답, 과도한 확정, 의미 혼동 또는 답변 변동이 반복된다.
- 약어·동음이의어 등으로 잘못된 분기가 자주 발생한다.
- 잘못된 설명이 투자 판단이나 사용자 행동에 큰 영향을 줄 수 있다.
- 출처 표시, 정확한 정의, 표준 변경 또는 갱신 이력 관리가 필요하다.

승격은 `미지원·오답 사례 수집 → 담당자 출처 선정·정의 검토 → 버전이 있는 지식 등록 → 고정 평가 세트 비교 → 승인` 순서로 수행한다. 사용자 질문이나 모델 답변을 자동으로 지식 저장소에 등록하지 않는다. 일반 LLM과 지식 검색 경로는 동일한 평가 질문에서 사실 정확성, 지원되지 않은 주장, 의미 일관성, 답변 가능 범위, p50·p95 지연, 모델·검색 비용을 함께 비교한다. 검색이 있다는 이유만으로 성능 향상을 가정하지 않으며 잘못된 청크·낮은 검색 품질·오래된 문서로 인한 저하도 평가한다.

승인된 지식이 있는 용어는 해당 지식 검색을 우선하며 사용한 문서 버전과 근거 수준을 표시한다. 필수 지식 검색이 실패하거나 승인 문서가 철회된 경우 검증 수준을 숨긴 채 일반 LLM 경로로 자동 전환하지 않는다. 일반 LLM으로의 fallback을 허용하려면 해당 용어가 여전히 저위험·안정적 일반 개념 범위에 든다는 별도 정책과 사용자 표시를 적용하고, 그렇지 않으면 `guidance`, `insufficient_evidence` 또는 실제 장애 상태로 처리한다.

### 6.2 작업 상태와 답변 결과

공개 `ChatJob.status`는 `queued / running / completed / failed / cancelled`를 사용한다. `ChatJob.outcome`은 결과가 없으면 null이고, 저장된 `ChatResult.outcome`은 `answered / clarification / guidance / insufficient_evidence` 중 하나다. 질의 유형, 작업 상태, 답변 결과와 HTTP 오류를 서로 대체하지 않는다.

| 상황                          | 현재 계약의 처리                                                     | 사용자 응답 또는 동작                     |
| ----------------------------- | -------------------------------------------------------------------- | ----------------------------------------- |
| 근거와 검증 조건 충족         | 저장 후 completed, outcome=answered                                  | 유형별 답변 제공                          |
| 기업·기간·대상 모호           | 확인 질문 저장 후 completed, outcome=clarification                   | 필요한 조건 확인, 선택지는 choices 사용   |
| 조건 부족 또는 지원 범위 안내 | 안내 저장 후 completed, outcome=guidance                             | reason과 필요한 action으로 다음 행동 안내 |
| 조회 성공 후에도 근거 부족    | 안내 저장 후 completed, outcome=insufficient_evidence                | 조회 범위와 부족한 부분 설명              |

| 소유권·접근 권한 위반         | 접수·조회 API의 접근 오류 또는 실행 중 ChatFailure.permission_denied | 정보 조회·노출 중단                       |
| 검증 실패 또는 기술 장애      | 해당 API 오류 또는 failed와 ChatFailure                              | 원인과 허용된 복구 방법 표시              |

위 상황은 기존 계약을 설명하는 분류이며 새 enum을 정의하지 않는다. 투자 판단 요청은 제한 이유와 지원 범위를 안내하고, 분리 가능한 사실 답변을 제공한다면 답변에 그 한계를 명시한다. 복합 질문의 부분 결과를 표현하는 별도 `PARTIAL` outcome은 현재 계약에 없다. 하위 결과·버전 등을 구조화하여 제공하려면 공개 계약을 먼저 확장하고 검증한다. 지원되지 않는 경우 범위를 좁히는 확인 질문이나 안내를 제공한다. 근거 부족과 장애를 구분하고, 외부 API 실패를 ‘관련 뉴스 없음’으로 표현하지 않는다.

### 6.3 분류와 실행 순서

1. 서버가 모든 유형에 회원 자격·대화 소유권·Origin/CSRF를 검사하고, 멱등성 및 대화당 활성 작업 하나를 확인한다. 최초 접수 시 질문·문맥·대상·기간·asOf·graphVersion과 접수 시각을 고정한다. 요청 추적 ID와 질문 작업 ID는 구분한다.
2. 입력 크기를 제한하고 외부 전송 전 불필요한 개인정보·비밀값을 제거한다. 명백한 권한 우회·비밀정보 요청을 점검한다.
3. 질문을 독립적인 하위 질문으로 나누고 각 질문의 유형, 기업, 기간, 회차 및 개인화 필요 여부를 식별한다. 분류 단계에서는 개인 데이터 조회를 실행하지 않는다.
4. 모호한 지시어·기업·기간을 해결한다. 모호성이 답변을 바꿀 경우 확인 질문을 한다.
5. 서버가 도구별 현재 접근 권한을 확인한다. 개인 데이터 조회에는 본인 범위 검사를 추가하며, 모델의 개인화 판정 누락에도 도구 자체가 접근 범위를 검사한다.
6. 각 하위 유형에 허용된 도구만 실행하고 공개 버전·기간·조회량을 고정한다.
7. 검색된 근거의 유효성과 충분성을 확인한 뒤 유형별 답변을 생성한다.
8. 근거·수치·정책·개인정보 출력을 검사하고, 검증된 결과를 내구 저장한 뒤 completed로 전환한다. 상태 조회와 결과 회수 시에도 회원·소유권·현재 근거 접근 권한을 재검증한다.

키워드 규칙은 명백한 표현과 범위를 식별하는 데 사용하고, 의미 분류는 여러 표현을 다루는 데 사용한다. 최종 실행 권한은 서버 정책이 결정한다. 모델의 자기보고 확신 점수를 확률처럼 취급하지 않는다. 평가 세트에서 오분류와 확인 질문 비율을 측정하여 임계값을 조정한다.

### 6.4 중첩과 복합 질문

‘내 종목 중 오늘 뉴스가 있는 회사를 찾아서 두 회사 관계도 설명해줘’는 Q07로 본인 종목 범위를 먼저 확정하고 Q03·Q04를 순차 실행한다. Q07의 개인 접근 조건은 후속 하위 작업에도 유지한다. 공개 기업 조회로 재분류하여 인증을 우회하지 않는다.

‘HBM을 설명하고 지금 어떤 주식을 사야 하는지 알려줘’는 Q02 설명과 투자 판단 요청을 분리한다. 허용된 개념 설명은 제공하고, 특정 매수 결론은 생성하지 않는다. 한 부분의 제한을 숨긴 채 전체 요청을 완료했다고 표시하지 않는다.

‘오늘 브리핑과 최신 그래프를 비교해줘’는 서로 다른 스냅샷을 비교하라는 요청이다. 현재 ChatResult의 단일 적용 버전으로 이를 숨겨 표현하지 않는다. 하위 답변별 스냅샷을 표현·검증할 계약이 갖춰진 뒤 지원하고, 그 전에는 기준 회차 또는 시점을 선택하도록 안내한다. 기간 비교 자체는 고정된 버전이 제공하는 자료 범위에서 수행할 수 있다.

질문 전체가 타인 정보 추출이나 시스템 우회를 위한 경우 관련 조회를 중단한다. 제한된 부분에서 얻은 정보를 허용된 하위 답변에 섞지 않는다. 반복 확인에도 대상을 정할 수 없으면 가능한 선택지를 안내하고 조회를 종료한다.

하위 질의 분기는 하나의 접수된 작업 내부에서 수행한다. 같은 대화에 여러 공개 질문 작업을 동시에 생성하여 활성 작업 하나 제약을 우회하지 않는다. 확인 질문은 저장된 완료 결과로 남기고, 사용자의 보충 입력은 새 질문 작업으로 접수한다. 완료 작업 재조회가 새 분류·생성을 실행하지 않도록 한다.

### 6.5 Multi-hop 실행과 오류 전파 통제

Multi-hop은 모델의 비공개 사고 과정을 노출하거나 자유로운 에이전트 실행을 허용한다는 뜻이 아니다. 서버가 승인된 순서로 `분류 → 대상 식별 → 조회 → 추가 조회 → 생성 → 검증`을 수행하는 오케스트레이션이다. 필요한 하위 단계만 실행하며 각 단계의 출력은 자연어 요약보다 기업 ID, 기간, 회차, 그래프 버전, 관계 ID, 근거 ID와 같은 구조화된 값으로 다음 단계에 전달한다.

첫 단계의 오분류·대상 오인이 뒤 단계로 전파될 수 있으므로 다음을 강제한다.

- 후보가 여러 개이고 선택에 따라 답변이 달라지면 실행을 계속하지 않고 `clarification`을 반환한다.
- 정책 기본값을 적용할 수 있는 기간은 실제 해석 범위를 표시하고, 기업·회차·권한은 기본값으로 추측하지 않는다.
- 각 단계가 받은 ID·버전·권한과 이전 단계의 고정 문맥을 서버에서 재검사한다.
- 단계 수, 그래프 경로 길이, 조회 문서 수, 시간과 비용에 상한을 두며 상한 도달을 전체 결과로 표현하지 않는다.
- 필수 단계가 실패하면 생성 모델이 누락 값을 보충하지 않고 실패·근거 부족·확인 질문 중 실제 상태로 종료한다.
- 내부 분기·도구·검증 이력은 감사 가능한 코드와 식별자로 기록하되 모델의 상세 내부 추론은 저장하거나 공개하지 않는다.

직접 관계와 간접 경로의 분리는 의미와 표시의 분리이지 반드시 별도의 LLM 호출을 뜻하지 않는다. 허용된 하나의 그래프 쿼리로 제한된 길이의 경로를 조회한 뒤 서버가 1-hop 직접 관계와 2-hop 이상 간접 경로를 구분할 수 있다. 비용이나 사용성 때문에 직접 관계를 먼저 조회하고 필요한 경우에만 간접 경로를 조회하는 구현도 허용한다.

## 7 유형별 답변과 도구 실행 기준

### 7.1 공통 답변 계약

사용자 답변은 먼저 질문에 대한 결론을 제시하고, 필요한 설명과 근거를 이어서 제공한다. 사건·기업 답변에는 대상, 조회 기간, 데이터 기준 시각, 출처를 표시한다. 회차 답변에는 회차 ID 또는 표시명과 발행 시각을 함께 제공한다. 문서 기반 개념·도움말 답변에는 해당 문서의 버전 또는 갱신 기준을 적용한다. 전용 지식 문서를 사용하지 않는 Q02 일반 LLM 답변은 모델·프롬프트·정책 버전을 내부 기록하고 사용자에게 일반 개념 설명임을 표시하되 존재하지 않는 문서 버전이나 출처를 만들지 않는다.

공개 응답은 목표 OpenAPI의 camelCase `ChatJob`과 `ChatResult`를 사용한다. `ChatJob`은 작업 ID·sessionId·status·outcome·고정 context·failure·result를 포함하며, result는 completed 전까지 null이다. `ChatResult`의 필수 필드는 `outcome`, `messageId`, `answer`, `reason`, `sources`, `citations`, `graphTargets`, `applied`, `choices`, `action`, `metadata`다. 각 필드의 required·nullable·배열 조건을 스키마 그대로 따른다.

실제 대상·기간·graphVersion·dataAsOf는 `applied`에, 요청 추적과 공통 응답 정보는 `metadata`에 둔다. 인용은 `evidenceId`, `articleId`, `articleVersion`, `quote`, `start`, `end` 및 출처 표시 필드로 연결한다. 내부 질의 유형·하위 유형, 라우터 버전과 검증 코드는 감사 기록에서 관리하며 기존 응답에 snake_case 필드나 별도 status를 추가하지 않는다. 개념·도움말 등 새 유형도 기존 필수 필드를 사실대로 채울 수 있어야 하며, 불가능하면 API 확장 전까지 미지원 안내로 처리한다.

인용 URL은 모델이 작성한 문자열을 그대로 사용하지 않는다. 서버가 승인된 문서 ID에서 생성하거나 허용된 주소인지 검증한다. 개인정보·비밀값·비공개 관리 화면 주소가 링크나 오류 메시지에 노출되지 않게 한다.

### 7.2 검색과 그래프 조회

공개 데이터 검색에는 공개 상태, 활성 또는 지정 버전, 철회 여부와 접근 범위 필터를 강제한다. 벡터 검색도 동일한 조건을 적용한다. 비공개 후보를 검색 후 모델이 알아서 제외하도록 맡기지 않는다.

그래프 조회는 허용된 쿼리 템플릿과 매개변수로 실행한다. 모델이 작성한 임의 SQL·Cypher를 운영 DB에 직접 실행하지 않는다. 조회 계정은 읽기 전용으로 제한하며 경로 길이, 노드·문서 수, 수행 시간을 제한한다. 상한에 도달하면 전체 결과를 찾은 것처럼 말하지 않고 조회 범위를 표시한다.

그래프의 연결 수나 시각적 크기는 활동량 또는 정의된 표시 규칙을 뜻한다. 이를 투자 매력도·수익 가능성·인과관계 점수로 설명하지 않는다. 간접 경로를 설명할 때는 각 단계의 근거와 관계 유형을 유지한다.

관계 근거는 해당 사건·관계의 주체, 대상, 유형, 방향, 범위 또는 유효 시점을 뒷받침하는 뉴스·공시 원문의 고정 인용 구간이다. PostgreSQL `evidence`는 `article_id`, `article_version`, `text_artifact_id`, 인용문, Unicode code point 기준 시작·끝 위치와 검증 artifact를 보관하고, Neo4j의 Issue·Relation은 해당 근거 ID를 연결한다. 실제 원문 텍스트는 `artifacts`가 가리키는 비공개 파일 저장소에서 읽는다.

사건이 추출된 문장과 관계 간선의 근거는 같을 수 있지만 의미를 동일시하지 않는다. 공동 행사 참여를 뒷받침하는 문장은 사건 또는 공동 등장 근거가 될 수 있어도 공급계약 간선의 근거가 되지 않는다. 직접 관계는 그 간선 자체의 유형과 방향을 뒷받침하는 근거를 요구한다. 간접 경로는 전체 경로를 직접 관계로 증명하는 하나의 문서를 요구하는 대신 각 단계의 간선에 해당 단계의 근거를 요구한다.

관계 생성·공개 단계에서는 입력 문서 결속, 문서 버전, 인용 위치와 원문 일치, 허용 관계 유형, 알려진 endpoint, 직접·간접 경로 구조, 방향·유효기간과 주장별 의미 지원을 검증한다. 모순은 반려하고 방향 반전·근거 부족 등은 보류할 수 있다. 챗봇 조회 단계에서는 이 검증을 매번 다시 생성하지 않고, 고정한 공개 그래프 버전에 간선이 존재하는지, `evidenceIds`가 공개·비철회 문서 버전과 실제 인용으로 해소되는지, 직접·간접 표시가 저장된 경로와 일치하는지를 자동 검사한다.

현재 관계 추출 파이프라인의 citation·검증 규칙, ERD의 `evidence`와 공개 API의 관계별 `evidenceIds` 계약은 존재한다. 그러나 S2 사건 추출·S3 관계 결과를 앱 PostgreSQL과 Neo4j의 공개 버전으로 수입하는 전체 운영 경로는 완료된 것으로 간주하지 않는다. 챗봇 관계 답변을 활성화하기 전에 이 수입·투영·철회 전파의 종단 시험을 통과해야 한다.

### 7.3 시점과 비교

‘오늘’과 상대 기간은 최초 요청 접수 시각의 Asia/Seoul을 기준으로 해석한다. 재시도 중 날짜가 바뀌어도 같은 요청의 기간은 바꾸지 않는다. 브라우저가 보낸 시간과 모델의 현재 시각 추측을 기준으로 삼지 않는다.

기업명이 ‘삼성’처럼 여러 회사를 가리키거나 ‘그 회사’의 대상을 확정할 수 없으면 확인한다. 화면에서 선택한 기업·사건을 문맥으로 쓸 때는 서버가 대상 ID와 접근 가능 여부를 검증하고 답변에 사용 대상을 표시한다. 현행 기준에서 ‘최근’의 기본 기간은 1개월이고 ‘작년’은 직전 달력 연도다. 질문에 명시한 조건을 선택 문맥보다 우선하며 실제 해석 기간을 고정·표시한다. 기본값 변경은 정책·명세·평가 사례를 함께 갱신하는 변경 절차를 따른다.

비교 대상의 통화·단위·관측 기준을 맞춘다. 차이·비율 등 산술은 서버에서 계산하고 LLM은 결과를 설명한다. 원본 값 또는 비교 기준이 없으면 수치를 생성하지 않는다. Q05의 ‘빠짐’은 선택된 데이터 창이나 회차에서 제외됐다는 뜻이며 사건 종료나 악재 해소로 단정하지 않는다.

### 7.4 출력 검증과 재시도

검증기는 인용 ID의 존재, 공개·철회 상태, 주장과 근거의 대응, 숫자·통화·날짜, 개인 접근 범위, 투자 판단 범위와 응답 구조를 검사한다. 챗봇 검증 실패는 `validation_failed`로 처리하고 자동 재생성하지 않는다. 검증 실패를 근거 부족 안내로 바꾸어 성공 처리하지 않는다. 질문 작업의 `ChatFailure.retry`는 서버가 결정한 `rerun / save_only / null`을 따르며, null이면 재시도를 제공하지 않는다.

데이터 생성·공개 검증과 챗봇 답변 검증은 구분한다. 사건·관계 추출의 보류 후보에는 관리자 검수가 개입할 수 있지만, 챗봇은 이미 공개된 버전만 조회하며 개별 답변마다 사람의 사전 승인을 요구하지 않는다. 챗봇 검증은 자동 실행하고, 사람은 출시 전 평가, 표본 품질 점검, 반복 실패 조사, 오류 신고와 사고 대응에 개입한다.

| 검증 대상        | 구현 기준                                                                                            | 실패 처리                                                      |
| ---------------- | ---------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 응답 구조        | OpenAPI·JSON Schema의 필수 필드, nullable, enum, 배열 조건 검사                                      | `validation_failed`                                            |
| 인용 존재와 결속 | `evidenceId`를 `evidence`에서 찾고 article/version/text artifact와 고정 문맥을 대조                  | `validation_failed`                                            |
| 인용 원문 일치   | 고정 텍스트의 `[start,end)` 구간과 quote를 Unicode code point 기준으로 비교                          | `validation_failed`                                            |
| 공개·철회·버전   | 문서 접근 상태, 분석 상태, graphVersion, 회차, 철회 목록과 현재 접근 권한 검사                       | 노출 차단 또는 `validation_failed`                             |
| 주장과 근거 대응 | 답변을 내부 주장 단위로 만들고 허용 citation을 결속한 뒤 구조·명칭·수치 검사와 독립 의미 판정을 결합 | contradicted는 실패, insufficient는 근거 기반 답변에 사용 금지 |
| 숫자·날짜·통화   | 구조화된 원본 값과 비교하고 산술은 서버에서 계산                                                     | `validation_failed`                                            |
| 그래프 관계      | 고정 Neo4j 버전의 endpoint·유형·방향·hop 수와 간선별 evidence ID 검사                                | `validation_failed`                                            |
| 시점 일치        | 질문의 고정 기간·asOf·회차와 `applied` 및 조회 결과 비교                                             | `validation_failed`                                            |
| 개인정보·권한    | 회원·대화 소유권, 본인 종목 범위와 출력의 타인 식별자 재검사                                         | 노출 차단, `permission_denied`                                 |
| 투자 판단·비밀값 | 규칙 기반 탐지와 보조 분류기를 사용하되 모델 자기평가만으로 통과시키지 않음                          | 답변 차단 또는 허용 범위 안내                                  |

Q02의 일반 LLM 답변은 권위 자료가 없는 상태에서 인용·주장 대응 검증을 통과했다고 기록하지 않는다. 이 경로의 후검증은 응답 구조, 일반 개념 범위, 최신 사실·수치·투자 판단 포함 여부, 관련성, 내부 모순과 명백한 오류의 교차검토다. 두 번째 LLM이 동의했다는 사실만으로 사실 정확성을 증명하지 않는다. 검사를 통과한 답변은 일반 개념 설명으로만 제공하고 Q03~Q08의 근거 기반 답변과 같은 검증 표식을 사용하지 않는다.

| 실패 또는 상태                              | 복구 규칙                                                 | 모델 호출                    |
| ------------------------------------------- | --------------------------------------------------------- | ---------------------------- |
| 챗봇 검증 실패·권한 오류·결과 소실          | 실패 사유 기록, 자동 재생성 금지                          | 자동 재호출 없음             |
| 검증 결과를 보존한 뒤 앱 저장 실패          | 원래 검증 산출물로 save_only, 현재 권한 재확인            | 없음                         |
| 서버가 재실행을 허용한 일시 장애            | 명시적 retry와 원래 고정 문맥 유지, 활성 작업 제약 재검사 | retry=rerun일 때만 허용      |
| 내부 worker 호출 결과 불명                  | reconciling / reconcile_only로 유지, 운영자 정산·확인     | 자동 재전송 없음             |
| 내부 worker 영수증 저장 후 산출물 저장 실패 | 저장 영수증·산출물로 검증·저장 복구                       | 이미 송신한 단계 재호출 없음 |
| worker ready 이후 앱 수입 실패              | 같은 job 결과를 읽어 수입·저장만 복구                     | 없음                         |

내부 worker의 ready는 산출물 준비 완료이며 공개 ChatJob의 completed와 다르다. 챗봇의 검증 결과를 시도별 불변 복구 산출물로 내구 저장하고, 앱 결과 저장과 completed 전환을 같은 트랜잭션으로 처리한다. 완료 결과·최초 문맥은 변경하지 않는다. 내부 worker의 resumeMode와 공개 ChatFailure.retry를 같은 enum으로 취급하지 않는다. 현재 S1 HTTP transport는 문서 세 stage와 기존 briefing-outlook 대상이며, 챗봇 HTTP 실행 계약이 이미 제공된다고 가정하지 않는다.

검증 전 생성 토큰을 사실 답변으로 스트리밍하지 않는다. MVP에서는 ‘자료 확인 중’과 같은 진행 상태만 먼저 전달하고 검증·저장이 끝난 본문을 반환한다. 창 닫기는 취소가 아니다. 취소·로그아웃·계정 전환 후 도착한 챗봇 응답은 서버의 상태·실행 토큰·전달 권한과 화면의 세션을 확인하여 유효하지 않은 결과를 폐기한다.

### 7.5 응답 문구 예시

아래 문구는 형식 예시이며 특정 사건의 실제 조회 결과가 아니다.

- 대상 확인: ‘삼성전자와 삼성SDI 중 어느 기업을 말씀하시나요?’
- 관계 설명: ‘조회 기간의 공개 자료에서는 두 기업이 이 사건에 함께 연결됩니다. 직접 공급계약을 확인할 근거는 현재 조회 범위에 없습니다.’
- 근거 부족: ‘선택한 기간과 공개 자료에서는 이 주장을 확인할 근거를 찾지 못했습니다. 기간을 넓히거나 다른 기업을 선택할 수 있습니다.’
- 투자 판단 제한: ‘특정 종목의 매수·매도 결론은 제공하지 않습니다. 해당 기업의 공개 이슈와 확인할 위험 요인은 근거와 함께 정리할 수 있습니다.’
- 일시 장애: ‘현재 자료 조회가 지연되어 답변을 완료하지 못했습니다.’ 이후의 재시도 또는 저장 복구 안내는 서버가 허용한 동작에 한해 제공한다.

### 7.6 챗봇 조회 자원과 질의 유형 매핑

pgvector는 PostgreSQL의 확장이지 별도 권위 DB로 간주하지 않는다. 현재 ERD v6에는 개념 문서 또는 일반 문서 청크·임베딩 테이블이 구체화되어 있지 않으므로 벡터 검색을 이미 구현된 기능으로 표시하지 않는다. 비공개 파일 저장소는 원문과 불변 산출물을 보관하지만 챗봇이 임의 탐색하지 않고 PostgreSQL의 `artifacts`와 권한 검사를 통해 특정 파일을 읽는다.

`chat_sessions`와 `chat_jobs`는 질문, 고정 문맥, 상태, 검증된 결과와 복구 정보를 저장한다. 최신 시세·재무는 전용 RDB 테이블이 아니라 승인된 외부 공급자 어댑터를 사용할 수 있으며 공급 실패를 0 또는 자료 없음으로 바꾸지 않는다.

## 8 브리핑과 관계 그래프 운영

브리핑은 공개 데이터의 지정 스냅샷으로 생성한다. 출근·퇴근 회차 ID, 생성 시작 시각, 발행 시각, 데이터 기준 시각, 지표별 관측 시각을 각각 저장한다. 예정 생성 시각을 발행 완료 시각으로 표시하지 않는다.

퇴근 브리핑은 같은 날 출근 회차와 비교하여 신규·이어짐·빠짐을 설명한다. 비교할 출근 회차가 없으면 비교 불가를 표시하고, 존재하지 않는 아침 내용을 만들어 채우지 않는다. 날짜·출근/퇴근 종류별 회차는 하나이며 회차당 발행은 한 번만 가능하다. 발행된 본문·근거·판정·스냅샷은 고정한다. 정정은 원문 밖의 별도 이력으로 추가하며 같은 회차의 새 판 발행이나 덮어쓰기를 허용하지 않는다. 재처리는 미발행 회차에 한정한다. 중대 오류가 있는 회차는 중단 이력을 기록하여 공개 접근을 제한한다.

핵심 이슈는 회차당 최대 3개이며 자료가 부족하면 억지로 채우지 않는다. 개인화는 같은 발행본의 항목과 본인 보유·관심 기업을 교차하여 표시하며 사용자별로 새로운 사건·판정·발행본을 생성하지 않는다. 생성 입력의 검수·규칙 revision을 고정하고 발행 시 현재 revision과 대조한다. 변경됐다면 오래된 생성 결과에 새 revision만 붙이지 않고 정해진 재검증·발행 절차를 수행한다.

브리핑 전체 상태는 미발행·생성 중·발행·실패·중단으로 관리한다. 지표별 정상·지연·사용 불가·실패는 전체 상태와 별도로 관리한다. 환율 등 한 지표가 실패해도 검증된 다른 내용은 유지할 수 있으며, 없는 값을 이전 값으로 대체할 때는 이전 관측 시각과 대체 사실을 명시한다.

이슈 선정 이유는 실제 실행된 규칙과 입력값에서 작성한다. 사건 시각 미상인 항목에 ‘사건 시각이 가장 최근’이라는 설명을 붙이지 않는다. 게시 시각을 대신 사용한 순위라면 게시 시각 기준임을 표시한다. 데이터 시점, 그래프 버전, 화면의 기준 시각이 서로 맞는지 발행 전에 검사한다.

자료의 브리핑 예정 생성 시각은 07:40·18:10 KST이며, 클라우드 계획의 개발 운영 시간은 평일 09:00~18:00다. 현재 승인 범위에서는 이 두 정기 실행을 보장하지 않는다. 개발·시연은 승인 시간 내 수동 실행 또는 시연 회차로 진행하고 실제 정기 운영과 구분한다. 정기 실행은 운영 시간·예산 변경과 작업 완료 시간을 승인받은 후 활성화한다.

## 9 보안과 프롬프트 공격 대응

수집한 뉴스·공시, 검색 결과, 사용자 질문에 포함된 ‘이전 지시를 무시하라’, ‘키를 출력하라’ 등의 문장은 처리 대상 데이터다. 시스템 정책, 도구 권한 또는 관리자 승인으로 해석하지 않는다. 검색 문서는 출처와 경계를 표시한 데이터 영역으로 전달한다.

챗봇의 도구는 정보 조회에 한정한다. 데이터 공개, 검수 승인, DB 수정·삭제, 사용자 권한 변경, 주문·결제는 챗봇 도구에 포함하지 않는다. URL 조회가 필요한 기능은 허용된 출처와 네트워크 목적지만 접근하고 내부 주소·클라우드 메타데이터 주소 등은 서버에서 차단한다.

정상적인 금융·보안 개념 질문에 공격 관련 단어가 있다는 이유만으로 일괄 차단하지 않는다. 요청한 행동, 접근 대상과 실제 실행 권한을 판단한다. 입력 필터와 출력 필터 외에도 도구 수준 접근 통제를 검증한다.

보안 시험은 문서 속 악성 지시, 여러 차례 대화에 나눈 우회 요청, 인코딩된 입력, 타인 ID 삽입, 거짓 관리자 주장, 외부 링크를 통한 정보 반출을 포함한다. 사용자에게 내부 프롬프트·키·상세 스택 추적을 노출하지 않고 지원용 요청 ID를 제공한다.

## 10 개인정보와 외부 모델 API

Q01~Q08의 회원 자격을 공통으로 확인하고, Q07은 세션에서 확인된 본인의 보유·관심 종목만 조회한다. 사용자 입력에 다른 사용자 ID가 있더라도 조회 주체를 바꾸지 않는다. 공개 근거로 답할 수 있는 하위 질문은 개인정보 조회 없이 처리할 수 있지만 챗봇 회원 조건은 유지한다.

외부 모델에는 답변에 필요한 기업 ID 또는 명칭과 최소 근거 구간을 우선 전달한다. 이메일, 실명, 연락처, 인증 토큰, 계좌 정보, 불필요한 보유 수량·매입 단가·자산 규모는 제외한다. 기업 목록만으로도 개인과 결합하면 민감한 맥락이 될 수 있으므로 가명 ID와 함께 보내는 것만으로 안전하다고 판단하지 않는다.

모델 제공자별 전송 데이터, 처리 위치, 보관·삭제 조건, 학습 이용 설정, 재위탁 조건, 계정 설정을 확인하여 기록한다. 확인되지 않은 조건을 ‘저장하지 않음’ 또는 ‘학습에 사용하지 않음’이라고 안내하지 않는다. 해당 조건을 확인하기 전에는 실제 개인 데이터의 외부 전송을 활성화하지 않는다.

운영 로그에는 최소한의 가명화된 메타데이터를 남긴다. 원문 질문·전체 답변·검색 문서 전문을 기본 로그로 무조건 저장하지 않는다. 품질 조사에 원문이 필요하면 목적, 마스킹, 접근자와 보관 기간을 정한 제한된 저장소를 사용한다. 사용자의 질문에 포함된 개인정보는 외부 모델뿐 아니라 오류 추적·분석 도구로의 전송에도 같은 기준을 적용한다.

운영 로그의 최소 수집과 서비스 대화 저장은 구분한다. 대화 조회·멱등성·복구에 필요한 질문·고정 문맥·검증된 결과는 chat_jobs 등 정해진 서비스 저장소에 권한과 보관 정책을 적용하여 저장한다. 관리자의 대화록 열람은 `transcript:read` 권한과 목적을 확인하고 마스킹·감사 저장을 완료한 뒤 반환한다. 마스킹 또는 감사 저장에 실패하면 원문을 반환하지 않는다.

보관 기간은 계정·종목, 대화 이력, 원문·근거, 감사 로그, 백업별로 정한다. 삭제 요청이나 보관 기간 만료 시 원본 DB, 벡터 색인, 캐시, 조사 사본과 외부 제공자 경로까지 처리 대상을 추적한다. 백업은 정해진 만료 정책을 따르며 복구 시 삭제·철회 기록을 재적용한다. 클라우드 자원의 견적상 보관 기간을 개인정보 보관 동의나 서비스 정책으로 대신하지 않는다.

## 11 품질 평가와 출시 기준

### 11.1 평가 세트

품질 검증 담당자는 Q01부터 Q08까지의 정상 질문과 경계 사례를 포함한 고정 평가 세트를 관리한다. 각 사례에는 기대 유형, 허용 상태, 필요한 권한, 기대 근거·기간, 금지 동작, 합격 조건을 기록한다. 모델이 생성한 기대 정답은 사람이 확인한다. Q02에는 안정적 개념, 최신 사실이 섞인 개념, 다의어, 미지원 용어, 잘못된 수치가 포함된 생성 답변과 생성·검증 모델이 같은 오류에 동의하는 사례를 포함한다.

평가에는 모호한 기업, 지시어, 상대 날짜, 한영 혼용, 복합 질의, 자료가 없는 경우, 정정·철회 문서, 서로 충돌하는 기사, 잘못된 그래프 경로, 로그아웃 후 응답, 외부 API 장애와 공격 입력을 포함한다. 대형 기업과 소형 기업, 자료가 많은 기업과 적은 기업을 나누어 확인한다. 자료량 차이를 기업의 중요성이나 투자 가치 차이로 해석하는지 점검한다.

전체 정확도와 함께 유형별 정밀도·재현율, 혼동 행렬, 잘못된 일반 유형 분류, 불필요한 확인 질문 비율을 확인한다. 근거 정합성은 인용이 존재하는 비율과 실제로 주장을 지지하는 비율을 나누어 평가한다. 성능 지표는 표본 수, 데이터 버전, 모델·프롬프트 버전과 함께 기록한다.

## 12 모델과 정책 변경 관리

모델, 라우터 규칙, 시스템·유형별 프롬프트, 도구 허용 목록, 임베딩 모델, 검색 설정, 관계 스키마, 검증 기준, 이슈 선정 규칙을 버전으로 관리한다. 모델 교체 시 같은 이름의 API라는 이유만으로 결과가 동일하다고 가정하지 않는다. 임베딩 변경 시 색인 재생성과 검색 품질도 검증한다.

변경 요청에는 목적, 영향 유형, 데이터 범위, 평가 결과, 알려진 실패, 승인자, 배포·롤백 방법을 기록한다. 개인정보 범위 확대, 새 외부 제공자, 도구 권한 확대, 투자 판단 범위 변경은 책임자와 해당 데이터·보안 담당자의 검토를 요구한다.

출시 전에 고정 평가 세트와 기존 실패 사례를 다시 실행한다. 제한된 환경에서 새 버전의 결과를 확인한 후 적용한다. 불합격이면 이전 코드·프롬프트·정책·데이터 조합으로 돌아갈 수 있어야 한다. 사용자 피드백을 즉시 자동 학습이나 정책 수정에 반영하지 않고 검토 후 평가 사례로 추가한다.

## 13 운영 감시와 감사 기록

챗봇 작업 단위로 요청 추적 ID와 작업 ID, 접수 시각, 가명 회원 식별자, 내부 유형·하위 유형, 작업 status와 outcome, 정책·라우터·모델·프롬프트 버전, 데이터 버전, 도구 실행 상태, 근거 ID, 검증 실패 코드, 수행 시간과 토큰 사용량을 기록한다. 비회원의 거절된 접근은 질문 작업으로 생성하지 않고 필요한 접근 보안 기록으로 구분한다. 상세 내부 추론이나 불필요한 원문은 감사 필수 항목으로 두지 않는다.

실제 모델 호출인 live, 저장된 응답을 사용하는 replay, 저장 복구인 save_only를 구분하여 집계한다. save_only를 새로운 모델 호출로 세지 않는다. 제공자가 보고하지 않은 토큰·비용은 null이며 0으로 바꾸지 않는다. 내부 worker의 호출 전 예산 예약과 호출 영수증은 재시작 이후에도 유지하고, 송신 여부가 불명인 호출의 예약을 임의 해제하지 않는다.

배치 단위로 출처, 수집 범위, 중복 수, 후보 수, 통과·보류·실패 수, 검수 결과, 공개 전환과 롤백 기록을 남긴다. 브리핑은 회차, 선정 규칙 버전, 근거 목록과 정정 이력을 연결한다. 실제 모델의 비결정성 때문에 완전히 같은 문장을 재생성할 수 있다고 보장하지 않되, 어떤 자료와 설정으로 결과가 만들어졌는지는 추적 가능하게 한다.

운영 대시보드는 유형별 요청량, 분류 변경, 확인 질문 비율, 근거 부족률, 검증 실패율, 보류 적체, 출처 지연, 응답 시간과 비용을 감시한다. 기준선 대비 악화와 보안·공개 경계 위반을 구분하여 알린다. 수치 경보 임계값은 부하·시연 시험으로 정하고, 중대 권한 위반이나 비밀값 노출은 단일 사건도 즉시 대응한다.

API와 개인화 결과를 공용 캐시에 저장하지 않는다. 캐시가 필요한 내부 기능은 사용자 범위, 정책·데이터 버전, 기간·회차를 키에 반영하고 로그아웃·철회·버전 변경에 따른 무효화를 검증한다. CloudWatch 등 운영 시스템의 로그 접근도 역할별로 제한한다.

일반 최신 조회에서 기존 유효 공개 버전을 유지하는 경우 오래된 자료임을 표시한다. 명시된 graphVersion·asOf·회차의 버전을 찾을 수 없으면 VERSION_UNAVAILABLE 등 정해진 오류를 사용하며 최신·다른 버전으로 대체하지 않는다. 철회됐거나 오류가 확인된 근거는 장애 대체 자료로 사용하지 않는다.

제출된 같은 AI 작업의 제공자·endpoint·모델·설정을 조용히 바꾸거나 자동 fallback하지 않는다. 다른 제공자를 사용하려면 현재 source grant의 전송 대상·목적·권한, 제공자 처리 조건과 품질 평가를 확인하고 별도 승인된 새 설정·작업으로 전환한다. 원래 작업의 호출 결과가 불명이면 먼저 영수증을 확인하여 중복 호출을 방지한다.

정정된 근거를 참조하는 그래프 간선, 브리핑, 캐시와 재사용 답변의 영향을 추적한다. 사용자 영향이 있는 오류는 영향 범위와 조치 사실을 안내하고, 법적 통지 여부는 실제 사고와 적용 기준에 따라 별도로 판단한다. 복구 후 원인, 대응 시각, 영향, 개선책과 담당자를 사고 기록에 남긴다.

## 15 구현 단계별 적용

### 15.1 MVP 필수 범위

MVP에는 Q01부터 Q08까지의 분류 계약과 미지원 유형 처리, 권한 검증, 공개 데이터 필터, 읽기 전용 도구, 근거 표시, 출력 검증, 버전 고정, 보류·재검증·공개 전환, 최소 감사 로그, 오류 신고와 중단·롤백을 포함한다. 유형별 실제 데이터나 도구가 준비되지 않았다면 해당 유형은 미지원 또는 이용 불가로 명확히 표시한다. Q02를 전용 지식 저장소 없이 활성화할 경우 6.1절의 제한된 일반 LLM 경로와 표시·평가 기준을 적용하며 이를 근거 검증 완료 기능으로 소개하지 않는다. MVP 출시를 위해 전체 용어사전 구축을 선행 조건으로 두지 않으며, 운영·평가에서 확인된 고빈도·고위험·오답 반복 용어부터 선택적으로 지식 저장소에 승격한다.

UI 고지에는 AI 생성·보조 결과라는 사실, 사건 답변의 기준 시점, 근거 확인 방법과 투자 판단 범위를 포함한다. 고지 문구만으로 검증·권한 통제를 대체하지 않는다. 모든 답변에 긴 경고문을 반복하기보다는 최초 안내와 해당 답변의 한계를 읽기 쉽게 표시한다.

### 15.2 출시 확인 순서

1. 담당 역할과 서비스 허용 범위를 승인한다.
2. 출처 이용 조건, 외부 모델 처리 조건, 개인정보 보관·삭제 방식을 확정한다.
3. 정상 유형·예외 상태·도구 범위·분류 우선순위를 구현 명세와 맞춘다.
4. 검증·검수·공개 전환과 회차 고정을 시험한다.
5. 11장의 평가와 보안·장애 시나리오를 실행하고 결함을 해결한다.
6. 운영 시간·비용·경보·복구 담당자를 확인한다.
7. 정책 버전, 구현 버전, 시험 결과, 미지원 기능과 승인자를 기록하고 공개한다.

자료에서 확인된 계약과 본 정책의 추가 요구사항을 구분한다. Q01~Q08 내부 분류, 복합 응답 확장, 출시 수치와 역할별 승인 절차는 설계 제안이다. 공개 응답 필드·상태·오류와 저장 제약은 관련 계약을 따른다. 와이어프레임의 기업·수치·사건이나 authored replay를 실시간 사실·실제 모델 품질·운영 성과의 증거로 사용하지 않는다. 정책 목표에 포함된 전체 철회 전파, 파이프라인 공개 연동 및 정기 운영의 구현 완료 여부는 별도로 확인한다.
