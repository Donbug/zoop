# 다음 작업 후보와 착수 기준

현재 완료한 S1 다음에는 **S2의 수집·문서 계보부터** 진행한다. 문서 요약·기업별 긍정/부정·별도 의미 검증·기존 브리핑 전망의 worker 이행은 다시 만들지 않는다. 이 문서는 다음 작업의 제안 순서이며 새 일정이나 담당자 배정, 전체 기능 완료 선언이 아니다. 일정은 WBS를 따른다.

## 기능 구현 순서

| 순서 | 사용자에게 생기는 변화 | 재사용·선행조건 | 완료를 확인할 장면 |
|---|---|---|---|
| **S2-1 수집과 문서 계보** | 어떤 수집 회차에서 들어온 원문인지 확인하고, 중단된 수집을 중복 없이 이어 간다. | 기존 PoC 수집·원장과 S1 version/citation/grant 계약을 재사용한다. 먼저 합성 HTML/PDF와 승인된 입력만 사용한다. | 같은 cursor 재처리 때 중복 문서가 생기지 않고, 변경된 본문은 새 버전이 된다. 정제 문장의 한글·emoji 인용이 원문 위치로 돌아가며, 중단 후 재개해도 누락되지 않는다. |
| **S2-2 사건과 주제 분리** | 동일 사건의 중복 기사와 여러 사건을 묶는 주제를 구별한다. | S2-1의 안정된 문서 버전, 기존 추출/SAME/outbox를 재사용한다. 사건 ID와 주제 ID는 별개로 둔다. | 중복 기사 추가가 사건 수를 부풀리지 않고, 한 주제의 서로 다른 사건은 독립 근거·시점으로 남는다. 목록·상세·그래프에서 같은 연결을 읽는다. |
| **S3 관계·영향·검수** | 공급·경쟁·투자 관계와 영향의 근거를 구분해 보고, 보류된 결과를 검수한다. | S2의 사건/주제·근거 연결, 현재 관리자 검수·발행 경계를 재사용한다. | 부적격 관계는 공개되지 않는다. HOLD 수정 후 재검증을 통과해야 발행되며, 그래프와 상세에서 같은 유형·근거를 확인한다. |
| **S4 철회와 공개 일관성** | 철회된 근거가 과거 화면·답변·브리핑을 통해 다시 노출되지 않는다. | 현재 문서 두 조회 경로의 deny를 전체 의존성으로 확장한다. S3까지의 관계를 포함한 의존성 추적이 필요하다. | 원문 철회 후 과거 pin, 직접 링크, 채팅, 브리핑, 캐시에서 공개가 차단된다. 복구 시 허용한 결과만 다시 공개하고 모델을 불필요하게 재호출하지 않는다. |
| **S5 기업·시장 요약과 브리핑** | 기업/시장 변화와 중요 이슈를 요약하고 전망의 근거를 확인한다. | S2–4의 근거·공개 상태, 기존 회차 생성과 불변 발행을 재사용한다. | 요약과 선정 이유가 근거로 연결된다. 회차 전망도 강화된 검증을 거치며, 이미 발행된 회차는 재생성·설정 변경으로 바뀌지 않는다. |
| **S6 실제 AI 채팅** | 질문 해석, 근거 있는 답변, 정보 부족 시 되묻기가 동작한다. | 현재 RuleEngine/예시 응답을 실제 AI로 오인하지 않는다. worker 작업 계약과 S4 공개 gate를 먼저 연결한다. | 같은 질문을 실제 작업→검증→답변으로 끝까지 실행한다. 근거 없는 답변은 공개하지 않고, 철회·실패·취소를 정상 답변으로 위장하지 않는다. |
| **S7 개인화와 평가** | 개인별 브리핑, 소유권, 평가·사용량을 일관되게 확인한다. | S5–6의 실제 결과, 현재 인증·설정·사용량 계약을 재사용한다. | 다른 사용자의 개인 결과에 접근할 수 없고, 피드백이 올바른 결과 버전에 연결된다. 재수입·캐시 사용이 비용을 중복 집계하지 않는다. |

S2-1과 S2-2는 기존 S2를 실행 가능한 두 단위로 나눈 것이며 범위를 줄인 것이 아니다. S4가 끝나기 전에는 S1의 문서 공개 차단을 전체 서비스 철회 보장으로 설명하지 않는다. 실제 유료 실행 전에는 승인된 출처·수신자·모델·추론 수준·호출 예산을 별도로 확정한다. 합성 재현은 운영 모델의 품질 평가를 대신하지 않는다.

## 함께 진행할 수 있는 후보

| 후보 | 권장 시점 | 범위와 완료 조건 | 외부 결정이 필요한 부분 |
|---|---|---|---|
| 상세 화면의 통합 동작 점검 | 각 S2–S3 데이터 연결 시 | 기업 전환, 세분화 타임라인, 관련 관계 요약, 주가의 동일 시점/기업 문맥을 실제 화면에서 확인한다. 이미 구현한 기능은 다시 만들지 않고 최신 상세 수용 기준의 미충족만 수정한다. | 원문 간 충돌은 정정 요청으로 남기고 작업자 안을 시연한다. |
| Figma 디자인 반영 | 해당 화면 기능이 안정된 뒤 | SUIT 유지, 컬러·노드·배치·상태를 고정 와이어프레임과 맞추고 디자인시스템 및 화면계획서를 함께 갱신한다. | 폰트 외 Figma 최종 기준은 이미 결정됐다. 새 디자인 승인을 다시 요구하지 않는다. |
| 기업 프로필·재무 API 연결 | S2 데이터 계약과 병행 가능 | OpenDART 등 기존 조사 후보 중 필요한 필드와 갱신 주기를 정하고 실제 응답→저장→기업 상세를 검증한다. 라이선스 미확정 데이터를 AI 입력으로 보내지 않는다. | 공급자 선택, 실제 키 등록, 저장·전송·표시 권리. 공개 API라는 사실만으로 허가를 추정하지 않는다. |
| 본개발 인수 패키지 | 기능 단위 완료 때마다 | OpenAPI, AI JSON Schema, 합성 계약 표본, 화면/명세/WBS 연결을 같이 넘긴다. Java/Spring BE와 다른 FE도 같은 계약을 구현할 수 있어야 한다. | 본개발의 FE/BE 스택·소유팀·배포 대상 선택. 프로토타입 코드 채택은 담당자 선택이다. |
| GitHub 원격 운영 완성 | 코드 반영 후 | 실제 CI 결과를 확인하고, 필수 체크·리뷰 책임·브랜치 규약의 운영 효과를 검증한다. | private PoC App 자격 증명 접근자의 trust 승인, 실제 GitHub handles, branch rules 등록. 푸시 승인이 이 등록까지 허용하지 않는다. |
