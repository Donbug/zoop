# 오늘 작업의 현재 기준과 순서 (2026-10-08)

이 문서는 사용자가 오늘 확정한 작업 권한과 해석 기준이다. [새벽 기록](overnight-2026-10-08.md)의 범위·승인·디자인·일정 가정 중 아래와 충돌하는 부분을 대체한다. 기능별 수용 기준 대조와 구현 완료 판정은 이 문서에 넣지 않는다.

## 원문과 유효 기준

| 항목 | 보존하는 원문·관측 | 현재 유효한 사용자 결정 |
|---|---|---|
| 요구 범위 | 명세의 `확정`·`보류`·`추가 제안 · 검토 전` 및 우선순위, WBS 원문을 그대로 보존한다. | 명세와 WBS의 모든 내용은 팀이 합의한 요구이며 구현 계획과 설계 대상에 포함한다. 갱신되지 않은 `검토 전` 표기로 FS074~FS081을 프로토타입 보류 범위로 제외하지 않는다. 이는 구현 완료나 비용·외부 실행 승인 기록이 아니다. |
| 프로토타입 권한 | 현재 코드와 기존 구현·실행 증거를 별도로 보존한다. | 프로토타입은 전권 범위이며 끝까지 완성한다. 기존 기능과 원본 PoC를 재구현하지 않고 재사용과 부족한 계약을 구분한다. 본개발에서 채택할지는 담당자가 선택한다. |
| 일정 | WBS 표지·요약·본문의 번호·일정·가중치 충돌을 보존한다. | 확정 일정은 WBS를 따른다. Notion 일정은 오래된 자료다. WBS 내부 충돌은 정정 요청으로 수집하며 범위 제외나 원문 자동 수정으로 해결하지 않는다. |
| 디자인 | 기존 UI 코드는 현재 구현 상태이고 화면계획서는 그 관측 자료다. | Figma는 폰트를 제외한 최종 목표 디자인이다. 기존 SUIT를 유지하며 기능을 먼저 완성하고 디자인을 뒤에 반영한다. Figma 원본은 10-08 고정본을 재사용한다. |
| 긍부정·모델 설정 | 긍정/부정/혼재/판단 보류, 모델·추론 수준의 `.env` 설정 정책을 유지한다. | AI 기능은 설계를 먼저 한다. 실제 모델·공급자 선택과 유료 호출 승인은 별개이고 live 예산은 아직 미정이다. 실제 `.env`나 키를 열람·변경하지 않는다. |
| API·충돌 | 목표 API와 저장된 BFF 관측본, 원본 의미 충돌을 구분한다. | 추가 외부 API는 조사한다. API 공통 규칙은 기존 잠정 채택/시연 기준이며 정식 구현 완료를 뜻하지 않는다. 오프라인 프로세스에 가짜 HTTP 엔드포인트를 만들지 않는다. 충돌은 근거 있는 작업자 안과 정정 요청을 남긴다. |
| 마이그레이션 | 현재 프로토타입의 React/Python은 현재 구현 사실이다. | 프론트·백엔드 언어와 프레임워크는 변경 가능하다. Java/Spring 백엔드는 유력 후보이지 확정 스택이 아니다. React/Python 재사용을 마이그레이션의 필수 전제로 강제하지 않는다. |

기계 판독용 유효 기준은 [`../system/links.yaml`](../system/links.yaml)의 `authority`다. 생성기는 원문 `catalog.yaml`과 이 결정의 `implementationScope`를 분리해 [`../system/out/effective-authority.json`](../system/out/effective-authority.json), 추적 xlsx 및 기능별 문서에 표시한다. FS074~FS081 원문 상태 8개는 별도 원문표기 시트에 남기되 유효 기준은 **팀합의요구/설계대상**이다.

전체 상세 정의별 원문 수용 기준과 기존 ID 단위 구현 판정은 [`../system/out/acceptance-matrix.md`](../system/out/acceptance-matrix.md)와 JSON, 추적 xlsx의 `수용 기준` 시트에 연결한다. 상세 정의를 한 행에 합치지 않으며 기준이 없으면 `없음`으로 표시한다. 이 문서 생성 작업에서 **현행 기능 실행 검증은 전부 미실행**이고 과거 판정·통과 수치를 현재 수용 기준 통과로 승격하지 않는다. 원문 ID/정의/요구 연결/추가 8개/WBS 표지·본문의 정정 요청은 [`../system/out/source-corrections.md`](../system/out/source-corrections.md)에 두 원문과 작업자 안을 함께 남긴다.

## 작업 순서

1. 새 사용자 결정을 기존 기준 문서·연결 메타데이터·생성기에 반영한다.
2. 전체 기능을 명세의 상세 수용 기준과 대조한다. 현재 구현과 미충족 항목을 구분한다.
3. AI 기능과 추가 외부 API를 조사하고 설계한다. 기존 계약의 재사용과 확장 경계를 정한다.
4. 기능을 구현하고 승인된 범위에서 검증한다. 기능 완성 후 Figma 목표 디자인을 반영한다.
5. 실행·사용·연동 설명서를 갱신한다.
6. 스택 독립 마이그레이션, 모노레포 구성, GitHub 연동을 준비한다. 후속 사용자 승인으로 누적 변경의 커밋·푸시는 허용됐다. 자격 증명·저장소 규칙 등록과 배포는 별도 승인 경계다.

## 입력과 실행 경계

- 명세/WBS는 `docs/evidence/raw/functional-spec_2026-10-08/`, `docs/evidence/raw/wbs_2026-10-08/`를, 요구사항은 `docs/evidence/raw/requirements-sheet_2026-10-06/`를 재사용한다. 고정본을 다시 다운로드하거나 수정하지 않는다.
- 현재 로컬 변경은 사용자의 작업으로 보존한다. 후속 사용자 승인 범위에서 검증한 누적 변경을 stage·commit·push할 수 있으며, 무관한 변경 되돌리기나 force push는 하지 않는다.
- `/Users/asqi/InvestMateLogicTest`는 읽기 전용이다. 실제 `.env`, 키, 개인정보는 열람하지 않는다.
- 승인된 저장소 커밋·푸시 외 외부 쓰기, 유료 모델 호출, 서비스 등록·배포, 새 의존성 추가는 하지 않는다. 예산 미정은 설계·로컬 구현을 제외할 이유가 아니라 실제 실행의 별도 승인 경계다.
- 이번 기준 갱신은 새 BFF 관측이 필요하지 않으므로 `docs/system/out/bff-openapi.json`과 `bff-observation.json`에 저장된 관측을 명시적으로 사용한다. 이는 현재 서버의 재검증이나 기능 동작 시험이 아니다.
