# 윤서진 담당 WBS와 10/12–10/18 개인 실행안

## 10/13 재확인: 오늘 적용할 우선순위

아래 기존 계획은 10/12 착수 전 기록이다. **현재 작업 순서는 이 절을 우선하며, 뒤의 ‘후속 구현’·옛 경로·Spring 후보 표현을 현재 상태로 읽지 않는다.** 팀 공유 WBS의 일정·담당·진행률은 이 문서에서 수정하지 않았다.

- 원격 `main`의 `72219db`까지 반영했다. `278b185`에서 AI 런타임과 Spring 호출 계층을 통합했고, `5cf208e`의 [원격 CI](https://github.com/Donbug/zoop/actions/runs/38226220631)는 8개 작업이 모두 통과했다. 이는 실제 모델 품질·운영 배포·사용자 인증부터 DB 저장까지의 전체 흐름을 검증한 결과가 아니다.
- S2-2 사건·동일성·주제 후보와 S3 관계·영향 후보/HOLD 재검증은 이미 오프라인 authored replay로 구현돼 있다. 다시 구현하지 않는다. 현재 경로는 `ai/pipeline`, `ai/worker`, `ai/service`이며, Spring 호출 계층은 `api/src/main/java/com/zoop/ai`다. 상세 범위와 실행 근거는 [AI 실행/공개 계약](../design/ai-system.md), 소비 계약은 [Spring 연동 안내](../../api/docs/AI_INTEGRATION.md)를 따른다.
- [공유 WBS](https://docs.google.com/spreadsheets/d/1aHJbxjXmvzgTXAlBd4mWTRDkcvD1S9vtHl1PR_bxn5c/edit?gid=136329476#gid=136329476)를 CSV로 다시 읽었다. 윤서진의 6.5.2는 10/14, 6.6.13–20은 10/15, 6.5.1·6.5.3·6.5.6·6.10.16은 10/16 종료다. 이 재확인은 WBS 한 탭에 대한 것이며 기능명세·Notion 전체의 최신화를 뜻하지 않는다.
- 오늘 구현 대상은 S4의 **원문·버전·권리 변경에 따른 AI 파이프라인 영향 대상 조회**다. 기존 S2/S3 저장 기록을 읽어 재검토할 후보를 찾는 기능부터 완결한다. 실제 권한 철회, GraphDB 비활성화, 과거 채팅·브리핑·캐시의 공개 차단까지 완료했다고 표현하지 않는다.
- ERD 피드백에서는 문서/문서 버전, 사건/주제, 분석 작업/결과, 공개 버전, 현재 권리의 연결과 저장 책임을 확인한다. 신규 인증 migration은 팀원 작업으로 보존하며, [migration 소유권](../development/api-migration-ownership.md)에 따라 다른 담당자의 테이블·Entity·정책을 임의로 확정하지 않는다. GraphDB 실행 책임은 WBS와 기능별 협업 설명을 함께 확인한다.

다음 순서는 영향 조회의 실제 CLI 실행 검증 → ERD 협의 → 확정된 소유권에 따른 앱 수입·GraphDB/공개 연결이다. 실제 공급원 권리·모델 비용·운영 배포가 필요한 작업은 별도 승인 경계를 유지한다.

**10/13 실행 결과:** `zoop-ai-dependents` 영향 대상 조회를 구현했고 pipeline 전체 208개 시험과 실제 CLI smoke가 통과했다. 원문·외부 모델 호출·원장 쓰기 없이 과거 문서/권리 버전의 의존성을 조회하며, 다른 고정 grant의 upstream은 연결 불명으로 표시한다. 전체 권한 철회·GraphDB 반영·공개 차단은 여전히 후속 범위다. 이 기록 당시 변경은 로컬 작업 트리에 있었고 커밋·푸시하지 않았다.

**10/13 후속 실행:** ERD와 독립적으로 S2 사건 추출·S3 관계 분석에 등록 전용 `submit`을 추가했다. 접수 시 분석 호출 없이 입력·권리·버전을 고정하고 이후 실행·취소할 수 있다. 전체 pipeline **228개 시험**과 네 CLI smoke가 통과했다. 이 기록 당시 S2/S3의 HTTP 연결은 없었고(이후 로컬 구현은 아래 1번 항목) 팀원 소유 DB·공개 API는 수정하지 않았다. 원격 반영도 당시에는 하지 않았다.

### ERD v6 동기화 후의 작업 순서

원격 `52b50d0`(PR #16)의 [ERD v6](../erd/zoop-core-erd-v6.md)와 변경 이력을 가져왔다. 오늘의 미커밋 pipeline 변경은 유지했다. 최신 설계는 v6(35개 테이블)이었고 당시 main의 인증 SQL은 v3.5의 3개 테이블 구조여서, 이미 병합된 migration을 고치지 않고 담당자가 후속 migration으로 이행해야 하는 상태였다. 현재 참조는 [migration 소유권](../development/api-migration-ownership.md)과 [AI 저장 책임 대조](../design/ai-system.md#erd-v6와-ai-저장-책임-대조)에 동기화했다.

**10/13 통합 갱신(main `91113ce`):** 위 서술은 `52b50d0` 기준이다. 이후 PR #18(`af2f0e3`)이 main에 병합돼 인증 스키마를 v6로 정렬하는 `V20261013000000`을 적용하고, AI 작업 식별·영수증·grant snapshot·검수 원천 버전 규칙을 v6와 공개 OpenAPI에 반영했다. 오늘의 변경을 이 main 위에 `ff-only`와 autostash로 통합했다. 충돌은 `api/README.md`와 `docs/development/api-migration-ownership.md` 두 문서뿐이었고, 업스트림의 적용 상태를 유지하면서 문서·근거·AI 저장 행과 인증 v6 이행 뒤 남은 결정만 이 저장소의 정리로 보존했다. 위 ‘미병합 분기’ 가정이 남아 있던 AI 문서는 병합된 기준으로 고쳤다. 병합은 `ai/`를 바꾸지 않았다.

다음은 작업자 제안 순서이며 아직 구현하지 않았다.

1. **S3 내부 HTTP → S2 내부 HTTP.** *(10/13 상태: S3 접수·검수·재검증과 S2 추출 job의 내부 HTTP, 실제 S2→S3 체인을 `ai/service`에 로컬 구현하고 `service-test` 461, `service-pipeline-test` 96, 실제 smoke로 검증했다. 호출자는 서버 사전 승인 요청의 digest만 참조하며 S2 결과가 S3 권한을 자동으로 넓히지 않는다. 커밋·푸시·원격 CI·배포는 없고 replay는 authored 응답이다. 아래 서술은 원래 계획이다.)* 기존 `ai/service`에 pipeline 전용 경로·응답 계약을 두고 설치된 CLI로 호출한다. S1의 상태·오류 파서를 그대로 재사용하지 않는다. S3는 완료된 S2 입력으로 접수→상태/결과→취소·복구부터 검증하고 관계별 HOLD 검수·재검증을 잇는다. S2도 범위에 유지하되 입력의 문서 관측·기업 목록·사건 snapshot과 서버 소유 replay 파일 고정 계약을 정해 연결한다. 앱 입력이 준비되기 전에는 운영자 합성 입력으로 실제 HTTP 흐름을 증명하며 앱 연동 완료로 보고하지 않는다.
2. **문서 저장 기반.** `artifacts`·`articles`·`article_versions`는 다른 담당의 회원/기업 FK 없이 먼저 만들 수 있는 후보다. 공유 `artifacts`의 쓰기 소유와 pipeline 문서/version→앱 문서/version 대응을 확정한 뒤, 새 migration·기존 DB 이행·문서 등록을 하나의 흐름으로 구현한다. ERD 정의만 옮긴 뒤 등록 기능까지 완료됐다고 보고하지 않는다.
3. **검수 접수와 실행 연결.** v6의 복수 queued·단일 running, allow=재검증 접수, 원천 version/revision 고정을 활용한다. `analysis_jobs`·`review_*` 담당, 공개 candidate와 S2/S3 후보의 대응, 앱 작업 ID와 AI jobId 결속을 먼저 맞춘 뒤 Spring 소비·검수 transaction·실행기를 연결한다. 앱 검수 revision과 S3 원천 revision은 서로 대체하지 않는다.
4. **분석 결과 수입·공개와 사용량.** grant 현재 권위, 검증 판정과 호출 기록의 구분, feature·replay 집계 의미를 맞춘 뒤 PostgreSQL 결과 수입→공개 gate→GraphDB 투영을 이어 간다. 과거 결과를 저장했다고 현재 공개 권한까지 생기는 것은 아니다.

HTTP 구현에서도 요청자가 파일 경로·fixture·실행 명령을 지정하지 못하게 하고, principal별 접근 통제를 유지한다. S1의 `--initial-only`와 같은 재시작 안전 장치가 pipeline에는 없으므로, 전송·실행 여부가 불명확한 작업을 자동 재실행하지 않는다. private PoC 의존성을 공개 의존성만 쓰는 service lock에 합치지 않으며, 새 자격증명 범위·배포·유료 모델 호출은 별도 승인 대상이다.

동기화 검증: `make public-check`에서 생성물 275개 차이 없음·하드 오류 0, 문서 검사 21개 통과. 수정한 주요 문서 5개의 로컬 링크 87개와 새 절 앵커를 확인했다. ERD SQL 제약·동시성은 실행하지 않았으며 이번 작업은 문서 동기화와 후속 순서 선정이다.

## 10/12 착수 전 계획 — 과거 기준

**월요일에는 이미 구현한 S1·S2-1을 다시 만들지 않고, 준비된 문서 한 묶음을 사건·이슈 후보와 근거까지 연결하는 S2-2 세로 흐름부터 진행한다.** 아래 일별 계획은 작업자가 제안한 개인 우선순위다. WBS 원본 날짜를 바꾸거나 다른 팀원의 업무를 재배정한 일정표가 아니다. 특히 FS074–081 전체의 원본 종료일 10/15와 현재 미구현 범위를 함께 보여 주며, 하루별 산출물을 전체 기능 완료로 표현하지 않는다.

## 4. 월요일 먼저 풀어야 할 의존성과 과밀한 납기

3. 문서·사건·분석 주제의 독립 ID와 mapping·claim/citation을 보존한다. 발생일 unknown, 서로 다른 기사, 같은 날의 다른 사건, 후속 사건을 구분하고 후보 상태로 저장한다. 준비 완료·model 응답·candidate 저장은 공개 완료가 아니다.

## 6. 팀에 넘길 최소 데모와 인수 계약

최소 데모는 다음 네 가지를 **실제로 구현·실행된 범위에서만** 제공한다. 화면이 없는 내부 흐름은 CLI/API evidence로 표시하고 UI 구현/완료를 가장하지 않는다.

1. **문서→사건/주제→근거:** 같은 사건의 두 보도를 별개 문서로 보존하고, 체결/해지·날짜 미상을 잘못 합치지 않는 후보와 exact span을 보여 준다. source/text/document/analysis version과 provenance를 표시한다.
2. **실패→허용 저장 복구:** receipt/검증 결과 보존 이후 저장만 실패한 사례를 기존 job으로 복구하고 model call/usage가 늘지 않음을 보여 준다. 검증 실패·결과 소실·권한 철회는 재생성 없이 보류/불가로 남긴다.
3. **관리자 조회→검수→공개 경계:** 후보의HOLD/REJECT/allow와 자동 검증·published를 분리하고 허용된 재처리만 표시한다. 앱/GraphDB 투영·공통 공개 전환이 없으면 ‘공개 미연결’이라고 안내한다.
4. **공동 검증용 정확한 전달:** 위 사례의 full commit 또는 working-tree 기준, 입력/corpus hash·schema version·예상/실제·로그/영수증·API/UI 증거 종류와 gap 목록을 전달한다. 미커밋 변경은 `69cc006` 원격 CI가 검증했다고 쓰지 않는다.

Spring이 본개발 앱 BE로 선택되는 경우 윤서진의 인수 범위는 AI **payload/버전/근거·권리/실행·영수증/오류·복구 계약과 golden 입력·출력**이다. Main이10/10 채택한 production 작업 설계는 앱→AI **내부 HTTP transport**이며 App SG만 허용하고 AI 포트는 인터넷에 노출하지 않는다. 현재 JSON CLI가 이미 그 HTTP 구현이라는 뜻은 아니다. 앱 BE는 transport·인증/소유권·transaction 수입·DTO·공개 gate를 구현하고 worker DB를 공유 쓰기하지 않는다. DB는 app/worker/ingestion/원장의 schema·쓰기 소유를 분리한다. GraphDB는 안정 ID·관계키·expectedVersion·projection/readiness/publication/withdrawal ack의 공동 경계를 확정한다. HOLD만 사람 검수 후 재검증하고 브리핑은 생성 방식에 맞는 검증 후 불변 자동 발행한다. MCP는 선택적 내부 읽기 도구다. 이 작업 설계는 코드 채택·스택 확정·AWS 가동/승인 완료가 아니며 계정·도메인·비용·credentials 없이 배포하지 않는다.

다음 주 성능 숫자와 배포 인수는 [별도 운영 계획](../development/release-verification.md#6-부하시간오류-측정-원본-기준과-작업자-실험값)을 사용한다. 로컬 수용안은 C1/5/10·warmup60초·측정300초×2, 일반읽기p95≤1초·graph/timeline≤2초·job접수≤1초·오류/timeout0·누락0이며 **작업자 제안·미실행**, NFS fact나 production SLO가 아니다. 실제 LLM 완료 목표·비용/권리·운영량은 미정이다. 이 개인 계획에서 full load를 수행하거나 안재현의10/19–23 WBS를 개인 작업으로 옮기지 않는다.
