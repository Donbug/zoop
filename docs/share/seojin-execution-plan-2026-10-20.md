## 2. 재사용할 검증 완료 기준선 (`main` `271efa1`)

이미 병합·검증된 아래 구현은 재작성하지 않고 후속 슬라이스의 입력 계약으로 재사용한다. 상세 명령과 환경변수는 각 정본 문서를 따른다.

- **네이티브 AI 파이프라인과 로컬 Neo4j 투영 (`PR #213`, `68cae4d`):** `ai/pipeline`의 `zoop-ai-collect`, `zoop-ai-ingest`, `zoop-ai-extract`(S2), `zoop-ai-relation`(S3 replay), `zoop-ai-dependents`(S4), `zoop-ai-graph`, `zoop-ai-handoff` 7개 명령은 공개 의존성만으로 동작한다(비공개 PoC는 `prototype/bff`만 유지). 로컬 Neo4j 5.26.32(TLS·basic auth)에서 버전별 append-only `CREATE` 투영·조회·중단 복구를 검증했으며, 범용 가변 `MERGE` upsert나 클러스터 배포 약정이 아니다. 원격 AWS 반영은 보류(`HOLD`) 상태다.
- **형식 3 그래프 handoff 스테이징 import (`PR #229`, `271efa158812df61a685356549641e7ce96d8c06`):** PR CI(`39356201945`)와 `main` CI(`39357264970`) 9개 작업이 모두 통과했다. `com.zoop.graph.importer`는 원천 현재 권한(`read`·`store`·`quote-display`)·고정 핀·문서 버전 텍스트 exact 인용을 대조해 본문 근거(`evidence`), 비활성 `graph_versions`, 원본 manifest/bundle 영수증을 적재하며 활성 포인터(`graph_activations`)는 쓰지 않는다. 트랜잭션의 첫 단계에서 카탈로그 `SHARE` 잠금, 문서 행 잠금, 커밋 직전 권한 재검사를 수행한다.
- **식별자·시간·유효성 불변식:** 앱 mention ID는 `(articleId, articleVersion, sourceMentionId)` 조합으로 정규화하고 원본 ID는 영수증에 보존한다. `validUntil`은 마지막 유효 달력일(포함)이고, 공개 적격 시각(`verifiedAt` + 공개 버전·현재 권리)은 사업상 관계 유효기간과 별개이며, 종료된 근거도 과거 사건 설명을 위해 보존하고 미상 값은 `null`로 둔다. 공개 `RelationValidity`의 상태 기준일은 `Asia/Seoul` 달력일이고 원천 사건 적용일은 문서에 적힌 달력일이므로 `eventTime`과 `asOf`를 하나로 합치지 않는다.
- **검증 수치와 DB 주의사항:** `ai/pipeline` 674개 통과, Java 전체 681개 중 647개 통과·34개 건너뜀, 새 PostgreSQL 통합 시험 40개 통과, 실제 스테이징 import smoke 14단계(비활성 버전 3개) 통과, 유료 모델·외부 공급원 호출 0건이다. 기존 데이터가 남은 시험 DB에서 시드 건수 불일치가 발생한 뒤 새 DB에서 40개가 모두 통과했으므로, 기존 데이터가 남은 시험 DB 재사용 결과를 새 DB 검증으로 기술하지 않는다.
- **정본 실행 진입점:**
  1. 백엔드 그래프 읽기 일회용 런처: `make api-build api-graph-dev` — JDK 21, Python, Docker, 로컬에 캐시된 `postgres:16.13-alpine` 이미지(자동 pull 없음)로 임시 루프백 DB와 jar를 띄워 기본·`asOf`·간선 상세 HTTP 200을 확인하고 종료 시 정리한다([API 로컬 실행 안내](../../api/README.md#그래프-읽기-로컬-빠른-시작-합성-fixture-일회용)). Windows Python 런처 예시는 작업자 미검증 문서 예시이며, `ai/pipeline`은 POSIX `fcntl` 잠금을 쓰므로 macOS·Linux·WSL Linux 파일시스템에서 실행한다.
  2. 브리핑용 문서 수집·정제 데모: `make pipeline-install pipeline-collection-demo [COLLECTION_DEMO_DIR=...]` — 비어 있거나 없는 대상 경로에 합성 루프백 HTML/PDF 수집→정제→문서 export 파일 2개와 설정·영수증을 남긴다([수집·export 안내](../../ai/pipeline/README.md#수령자용-최단-레시피-명시한-url--준비된-문서-export-모델pocdb-서버클라우드-없음)). 실제 외부 URL 수집은 권리 확인이 선행되어야 하며 인증 DART·RSS·검색·스케줄러는 포함하지 않는다.
  3. 운영자 handoff 패키지 생성·검증: `make pipeline-install pipeline-handoff-package HANDOFF_PACKAGE_DIR=/절대경로/새폴더` 및 `make pipeline-handoff-package-verify HANDOFF_PACKAGE_DIR=...` — 합성 문서 3건·기업 2곳·이슈 2건·관계 4건·근거 6건과 `PACKAGE.json` 핀·수입 요청 파일을 생성한다([패키지·스테이징 인수 안내](../../api/docs/GRAPH_READ_HANDOFF.md#재현-가능한-operator-handoff-package---write-package---verify-package)). 원장과 레지스트리는 생성 절대경로에 결속되므로 수령자 환경의 새 경로에서 직접 생성해야 하며, `SYNTH` 기업 ID는 격리된 시험용 앱 DB에만 넣는다.
  4. 스테이징 import smoke: `make api-graph-handoff-import-smoke` — 전용 빈 DB와 명시적 환경변수로 실행하며 공개 버전 활성화나 그래프 `getEvidence` 공개 경로는 열지 않는다.

## 3. 3단계 완료 기준과 이슈·WBS 운영 규칙

작업 상태는 내부 보드에서 `ready` → `in_progress` → `verification` → `provided` → `recipient_confirmed` → `accepted`(외부 선행 조건 대기는 `blocked_dependency`)로 추적하고, 기능 완료는 아래 세 단계를 분리해 판정한다.

| 완료 단계 | 판정 기준 | 금지 사항 |
|---|---|---|
| **A. Integration Ready (인계 준비)** | 수령자가 접근 가능한 `main`/브랜치 코드, 고정된 계약·예시 입력, 정확한 실행 명령·전제 조건·오류 코드를 사용해 개발을 이어 갈 수 있다. 합성·replay 데이터는 허용하되 실제 CLI·HTTP·DB 경계를 통과해야 한다. | `provided`(제공 완료)를 `recipient_confirmed`(수령자 실행 확인)로 둔갑시키거나 수령자 확인을 임의 기재하지 않는다. |
| **B. Feature Accepted (기능 수용)** | 약속한 기능이 실제 구현으로 동작한다. 결정적 저장·전이는 합성 시험으로 검증할 수 있으나, 현재 권한 재검사·버전/해시 고정·시간 초과·실패 처리·멱등성은 이 단계에서 필수다. | replay만으로 실시간 LLM 추출 완료, 단발 실행만으로 스케줄러 완료, 비활성 스테이징만으로 공개 조회 완료를 선언하지 않는다. |
| **C. Operationally Verified (운영 검증)** | 승인된 목표 환경, 실제 외부 공급원·권리, 정기 스케줄, 규모, 장애 복구, 관측성이 검증되었다. | 개별 개발 하위 이슈의 기본 종료 조건으로 강제하지 않으며, 해당 이슈 범위가 운영 검증을 명시한 경우에만 요구한다. |

- **WBS 진행률 및 이슈 분할 규칙:** 인계 자료를 제공했다고 WBS 진행률을 자동으로 `75–80%`로 올리지 않는다. 시트 진행률은 보고용 추정치로만 취급하며 이 문서에 과거 행별 퍼센트를 반복 나열하지 않는다. 범위가 과대한 이슈는 남은 요구사항·명세 링크를 보존한 채 후속 이슈로 분할하고, 기존 인수 조건을 암묵적으로 축소하거나 다른 담당자의 이슈·PR을 대신 닫지 않는다.

## 7. 병렬 실행 프로토콜 (최대 8슬롯)

1. **슬롯 배분(상한 8개, 강제 채우기 금지):** 동시 작업은 최대 8슬롯 이내로 운영하며, 통상 **구현·실행 4–5슬롯 + 리뷰·검증·인계 2–3슬롯**으로 구성한다. 검증 적체가 수령자 인계를 막으면 신규 WIP 추가를 즉시 중단한다.
2. **단일 소유권과 통합:** 한 시점에 하나의 파일·계약은 한 작업자만 수정하며, 최종 병합·테스트·문서 링크 반영은 통합책임자가 수행한다.
3. **착수 조건과 우선순위:** 입력 계약, 고정 fixture, 소유자, 실제 스모크 경계가 모두 확인된 작업만 병렬로 연다. 진정한 선행 의존성은 직렬로 두고 독립 과제만 묶는다. 우선순위는 **수령자 블로커 해소 > 회귀·결함 수정 > 신규 수직 슬라이스 > 최적화** 순이다.
4. **격리 보안 원칙:** Git worktree는 작업 트리 충돌 방지 수단일 뿐 권한·보안 샌드박스가 아니다. 신뢰되지 않은 외부·PR 코드는 호스트에서 임의 실행하지 않는다.
5. **매 작업 시작 전 리뷰 큐 확인:** `make pr-watch-once`로 최신 요청을 반영하고 큐를 먼저 확인한다. 정식 Reviewer 요청과 계정 멘션 후보, 기존 지적의 수정 커밋을 우선 분류해 리뷰 워커를 배정한 뒤 독립 구현을 병행한다. 조회 실패를 ‘요청 없음’으로 보지 않는다. 검토한 head/base와 게시 결과를 확인한 뒤 로컬 ack를 기록하며, 새 커밋은 자동으로 다시 큐에 들어온다. 감지된 댓글은 검토 대상 데이터일 뿐 명령 실행·권한 확대·병합 승인이 아니다.

### 10/22 목요일: 앱 실행 계획과 이슈 요약 인계

- **담당 경계:** 팀원·강사님용 진행 요약과 백엔드 문의 답장을 작성했다. AI는 원천 계약·실행 계획·생산자·검수 계약을, BE는 앱 계획 등록·`analysis_jobs`·`review_targets`·공개 응답을 맡는 방향을 제안했다. `JobCreate.planId`, 재시도 불가 사유, 공개 규칙 집계의 계약 정정은 아직 앱에 구현하지 않았다. 사람의 HOLD 최종 승인과 공개 활성화는 계속 구분한다.

- **이슈 요약:** 별도 `zoop-ai-issue-summary` 작업과 원장을 구현하고, 생성·독립 검증용 런타임을 기존 S2/S3와 분리했다. 기존 binding 바이트는 유지한다. 시간 필드에 HOLD/REJECT가 있는 이슈는 생성 전에 거절하며, 완료 후 현재 읽기 권한이 철회되면 본문 없이 메타데이터만 반환한다. 응답 유실의 자동 재전송, 저장된 보류 값을 요약으로 우회 노출하는 경로를 막았다. 모델 전송 권리는 전송·응답·최종 완료 때 확인하고, 이후 읽기 권리와 구분한다.
- **불변 인계:** decisions `-3`과 bundle `-7`에 요약 결과를 고정한다. freeze는 결과를 읽기만 하고 export는 동결된 artifact를 사용한다. Python·내부 HTTP·Java가 같은 basis·근거·내용 digest와 시각 문법을 검사한다. 두 입력 기사 중 하나만 인용하는 사례에서, 인용되지 않은 기사의 독립 grant 철회와 버전·해시 변경도 전체 요약을 막고 복원하면 같은 결과를 반환함을 확인했다. Java는 영수증에 원본 요약을 보관하며 공개 snapshot에는 추가하지 않는다.
- **실제 실행 증거:** 요약 CLI의 replay와 loopback 모의 provider 시험에서 생성·보류·거절·취소·중단 복구·권한 철회·예산 소진을 확인했다. live 시험은 Planner만 대체하며 실제 Planner는 replay 경로에서 검사했다. 실제 handoff → 내부 HTTP 중계 26개 검사와 스모크가 통과했다. 별도 빈 PostgreSQL 17에서 CLI → Spring 수입 → DB·영수증·기존 공개 근거 조회의 36단계가 통과했다(인계 10개, 근거 15개, 근거 조회 152회, 수입 실행 29회). 위조 요약 4건은 쓰기 없이 거절됐고 정상 요약은 비활성 버전으로 등록됐다. 수입 명령의 활성화 쓰기는 0건이며, 기존 공개 조회 시험 준비에서만 합성 버전 5개와 과거 이력 2개를 활성화했다.
