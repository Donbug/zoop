### 2. 직접/구조적 관련 필터

<!-- block: 9d86adab-2612-444b-a1ab-080f72e4a0f9; type: text -->
대상: listEvents → EventSummary.relationTypes

<!-- block: 2f1e7256-cf7c-451a-a071-04c4eea1304c; type: bulleted_list -->
- 필수 배열 필드를 추가했다.

<!-- block: afea89d4-3376-4576-bb1c-fb4f43870721; type: bulleted_list -->
- INVOLVES: 직접 관련, STRUCTURALLY_RELATED_TO: 구조적 관련.

<!-- block: 2b6389d0-ab8b-463e-95ef-8ba2f464c9db; type: bulleted_list -->
- 요청 companyId와 각 사건 사이의 승인된 관계를 백엔드에서 조회한다.

<!-- block: 825e044d-9e19-41de-9d74-9e8a4c28efbb; type: bulleted_list -->
- 두 타입이 모두 있으면 중복 없이 함께 반환한다.

<!-- block: 472a8903-8b8c-4f61-82cb-3d3e6f5c64b4; type: bulleted_list -->
- companyId가 없거나 해당 기업과 사건 사이에 해당 연결이 없으면 빈 배열을 반환한다.

<!-- block: b6fba05b-92ec-45ce-b1dc-503b10118c77; type: bulleted_list -->
- items와 unknownTimeItems에 동일하게 적용한다.

<!-- block: 9f69a956-cd9d-4569-be59-4d5278e6aaca; type: bulleted_list -->
- 다른 기업을 거쳐 연결된 사건을 임의로 직접/구조적 관련으로 분류하지 않는다.

<!-- block: 3a497fb6-648f-4dd2-b4ac-4bcb99abdc71; type: bulleted_list -->
- 프런트는 별도 그래프 조회 없이 relationTypes로 필터링한다. 전체 필터에서는 빈 배열인 사건도 포함한다.

<!-- block: 77471d37-c9c5-41ab-92ec-8353458e85d1; type: sub_header -->
### 3. 상단 최신 시세와 차트 시점 분리

<!-- block: ae1ba0cb-ed51-4456-9b4a-772965d86e4e; type: text -->
대상: getCompanyQuote

<!-- block: cf06d4c8-672f-413c-a7da-7882471b5dde; type: bulleted_list -->
- 요청 query 필드 graphVersion, asOf를 삭제했다.

<!-- block: fd1d738c-84bb-4566-b129-67535d8d7d19; type: bulleted_list -->
- 공급자 기준 최신 시세를 반환하고 차트의 선택 기간·시점과 독립적이라고 명시했다.

<!-- block: f66872c2-d803-4761-b114-6b2043296c7d; type: bulleted_list -->
- 응답 quote.asOf는 실제 시세 관측 시각이므로 유지했다.

<!-- block: e6e48fa3-9af2-472f-bc16-2b150a3fb9b9; type: bulleted_list -->
- getCompanyPrices와 다른 API의 시점·버전 조건은 변경하지 않았다.

### 4. 소셜 로그인 제공자 확정

<!-- block: a6123bd4-22bf-4779-9c54-86911fc595f9; type: text -->
대상: listSocialProviders, authorizeSocialLogin, completeSocialLogin, SocialProvider, SocialProvidersResponse

<!-- block: eca96f41-88b6-4d9d-909c-50686f634c22; type: bulleted_list -->
- Google의 ID는 google, 카카오의 ID는 kakao로 확정했다.

<!-- block: 87f74363-9766-44ff-81f7-ea8386e57921; type: bulleted_list -->
- 인증 시작·콜백의 provider 경로 필드와 SocialProvider.id를 google/kakao 열거형으로 제한했다.

<!-- block: ce861b15-e779-412c-8d7f-970cd12c0a16; type: bulleted_list -->
- 제공자 목록에도 두 제공자를 명시했다. 기존 페이지네이션은 유지했다.

<!-- block: fd70baf2-5414-4530-8a6a-df5f9c96d7f7; type: bulleted_list -->
- 소셜 제공자를 미확정으로 적은 문구를 정정했다. 관리자 인증 섹션에 반복된 같은 문구도 정리했다.

<!-- block: 6fe6aba2-6bbb-485d-82ea-675642dc5f9e; type: bulleted_list -->
- 계정 연결 정책과 관리자 SSO·권한 관련 기존 미결정 사항은 유지했다.

### 반영 범위와 확인

<!-- block: 59789924-34c6-4d70-b567-ecba265f1d22; type: text -->
위 네 가지 및 관련 설명의 정합성 수정 외 기존 계약은 유지했다. 관계 탐색 등 다른 API의 변경이나 새 엔드포인트 추가는 하지 않았다.

<!-- block: 1a04d7d4-efd7-4a9b-a3a5-306b4e257f97; type: text -->
원본 Downloads 파일은 보존하고 별도 수정본을 작성했다. 원문이 정본으로 안내한 openapi.yaml은 제공되지 않아 수정하지 않았다. 이 Markdown을 다시 생성하기 전 같은 변경을 openapi.yaml에 반영해야 한다.

<!-- block: 62fee9d4-e330-4573-bfef-0bec0bed9ca0; type: text -->
변경 비교와 구조 검증으로 네 가지 반영, quote.asOf 응답 유지, getCompanyPrices 및 관련 없는 API 계약 유지, 기존 문서 앵커 유지를 확인했다. 서버 코드 변경이나 실행 검증은 포함하지 않는다.

# 줍 기능 명세서·와이어프레임 비교 보고서

**검토 대상**

- 줍_기능·비기능명세서_상세형_v1.2.xlsx

**기준과 범위**

명세서 v1.2를 요구사항 기준으로 삼아 PDF v2.1(2026-10-06)의 본문과 화면 코드를 대조했다. zoop-trace의 `추적표`, `화면→기능→API`, `변경·제안` 정보를 ID·화면 연결을 확인했다. API 문서는 권한·상태·운영 계약을 보조하는 자료로만 활용했다. PDF 8쪽에 인쇄된 페이지 번호는 16~77쪽 구간을 참조한다. 자료에서 프로토타입 또는 목표 계약으로 표시한 내용은 구현 완료의 근거로 보지 않았다. 원본 파일은 수정하지 않았다.

## 요약

로그인·온보딩·그래프 탐색·기업 상세·브리핑·AI 질문으로 이어지는 핵심 사용자 여정과 관리자 주요 화면은 PDF에 대체로 담겼다. 다만 다음 항목은 개발 전에 정리해야 할 **확정 충돌 또는 명확한 표현 차이**다.

1. **개인화 그래프의 보유 범위:** FS017은 보유·관심 상태와 전체/보유/관심 필터를 정의하지만, PDF 24쪽 D-GRP-01b의 설명은 “필터 깊이 1”로 범위를 제한한다. 명세는 기준 종목 및 관련 기업·이슈를 함께 표시하도록 한다. 이 깊이 제한이 제품 규칙인지 프로토타입 가정인지 확인하고 일치시켜야 한다.
2. **그래프 노드 의미:** PDF 23~24쪽은 “크기=활동”으로 범례를 정하지만 동시에 거리·크기를 인과나 중요도로 해석하지 말라고 안내한다. 명세 FS017/FS018은 노드 크기를 정의하지 않는다. 사용자에게 서로 다른 의미로 읽힐 수 있는 표현이다.
3. **파이프라인 추가 요구:** 명세의 신규 제안 FS074~FS081 8개는 수집, 문서 정제/버전, 이슈 추출, Entity Linking, 관계 추출, 근거 검증, GraphDB 공개 버전 반영, 증분 갱신/복구까지 규정한다. PDF 65쪽 A-ADM-03은 후보 검수·공개 버전·작업 관제의 개략 화면만 보여 주며, 단계별 결과·오류·버전 복구의 상세 흐름은 표현하지 않는다. zoop-trace에는 이 8개 ID가 추적표와 화면→기능 매핑에 없다.
4. **AI 복구 화면:** FS052-01(후속 질문)과 FS052-02(패널 닫기/재열기)는 분리된 요구다. PDF 51~52쪽 D-AI-02/02b는 저장 대화 회수와 조회 오류의 차이를 글로 설명하지만, 캡처된 실제 화면은 되묻기 상태라 조회 실패·재시도 동작을 시각적으로 검증할 수 없다.
5. **공통 누락:** FS074~FS081의 세부 단계 화면뿐 아니라 PDF에는 명세서 NFS001~NFS012의 공통 실패·접근성·성능 조건을 검증할 별도 상태가 없다. PDF 설명 텍스트가 일부 상태를 명시하더라도 화면·수용 기준까지 모두 확인된다는 뜻은 아니다.

반면 초기 관심종목 0개 허용, 가상계좌 건너뛰기, 브리핑 회차 불변, 비회원 접근 범위 등은 명세서의 제안·확인 시트와 PDF가 대체로 맞는다. 충돌로 잘못 분류하지 않도록 확정 사실과 미결정을 아래에 따로 기록했다.
