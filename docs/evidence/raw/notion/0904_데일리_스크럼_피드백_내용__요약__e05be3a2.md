# 회의록
## 1. 회의 개요: 주제 및 목적
- **주제:** 금융상품 추천형 AI 챗봇의 데이터 구조, 검색/RAG 아키텍처 및 개인화 적용 방안 검토
- **목적:** Vector RAG, Graph RAG, OpenKB, PageIndex 등을 활용한 검색 정확도 개선 방안을 검토하고, 금융상품(예적금) 추천 서비스의 개인화·라우팅·데이터 연계·AI 거버넌스 관점에서 향후 설계 방향을 구체화한다.
## 2. 주요 논의 사항
### 2.1 금융상품 추천을 위한 검색 및 지식관리 구조
**00:02 ~ 01:54 / 참석자 1**
- 금융상품 추천 답변의 품질을 높이기 위한 방안을 크게 세 가지로 구분하여 제안함.
  1. **Vector RAG + Graph RAG**
    - 질문과 상품 간 유사도 탐색
    - 상품 조건과 사용자 조건 간 관계 파악
  1. **OpenKB + PageIndex**
    - 금융상품 설명서, 약관, FAQ 등의 비정형 문서를 AI가 활용하기 좋은 형태로 사전 구조화
    - 문서 구조와 목차를 반영하여 검색 정확도 향상
  1. **DB 직접 조회**
    - 구조화된 필드로 확인 가능한 사실성 질의는 RAG보다 DB 직접 조회를 우선 적용
- 초기 단계에서는 개인화 요소를 제외하고 검색 품질 자체를 테스트한 뒤, 데이터 확보 및 상세 데이터 플로우를 구체화하는 방향을 제안함.
### 2.2 OpenKB 및 PageIndex의 역할과 기존 RAG와의 차이
**07:32 ~ 17:48 / 참석자 2, 참석자 4**
- 참석자 2가 OpenKB가 기존 Vector RAG와 어떤 차이가 있고 어떤 역할을 담당하는지 구체적인 설명을 요청함.
- 참석자 4는 금융상품 데이터가 PDF, PPT, 이미지 등 다양한 형식과 규격으로 존재하기 때문에 이를 그대로 활용할 경우 전처리 비용과 검색 정확도 문제가 발생한다고 설명함.
- OpenKB는 이러한 원본 문서를 AI가 탐색하기 쉬운 **위키/Markdown 기반 구조화 지식 형태로 사전 변환·관리**하는 역할로 설명됨.
- PageIndex는 고정 길이 Chunk 검색보다 문서의 목차 및 계층 구조를 활용하여 문서 내부를 트리 형태로 탐색하는 방식으로 설명됨.
- Vector 검색을 통해 관련 문서를 찾은 후, OpenKB/PageIndex를 통해 해당 문서의 전체 문맥을 추가 탐색하는 구조를 고려함.
- 질의 시마다 원문 전체를 다시 변환하는 방식이 아니라, 초기 단계에서 문서를 구조화해 두고 이를 반복적으로 활용하는 방식으로 이해를 정리함.
- 결과적으로 다음 세 종류의 데이터를 운영하는 방향이 논의됨.
  - 원본 데이터
  - OpenKB 기반 Markdown/구조화 데이터
  - Vector DB 데이터
### 2.3 검색 라우팅 및 RAG 선택 기준
**18:25 ~ 24:50 / 참석자 2, 참석자 4**
- 사용자 질문이 입력되었을 때 Vector RAG, Graph RAG, OpenKB, DB 등 **여러 검색 수단 중 어느 경로로 보낼 것인지에 대한 라우팅 로직**이 아직 구체화되지 않았음을 확인함.
- 참석자 4는 질문의 성격에 따라 Vector RAG 또는 Graph RAG 사용 여부를 판단하고, 여러 검색 결과를 종합할 필요가 있다고 설명함.
- 참석자 2는 핵심 문제가 특정 RAG 기술을 선택하는 것보다 **여러 검색 대상 중 어떤 경로를 선택하고 어떤 순서와 기준으로 검색할 것인지**라고 지적함.
- 모든 검색 경로를 동시에 실행하는 전수검사 방식은 성능 저하가 발생할 가능성이 있으므로 적절하지 않으며, 질의 의도 분류 및 라우팅 로직이 필요하다는 의견이 제시됨.
- 향후 구현 시 다음 사항을 추가 설계해야 한다는 데 의견이 모임.
  - 질의 의도 분류
  - 검색 엔진 선택 기준
  - 복수 검색 결과의 조합 및 가중치
  - LLM 사용 시점
  - 검색과 추론/답변 생성의 역할 분리
### 2.4 금융상품 추천 범위 및 사용자 질문 시나리오
**27:37 ~ 33:54 / 참석자 1, 참석자 2, 참석자 4**
- 서비스 방향은 우선 **금융상품 추천**으로 좁혀 검토하기로 함.
- 초기 대상 상품으로 예금·적금 중심의 범위를 고려함.
- 사용자가 “돈을 모으고 싶다”와 같이 모호한 질문을 입력할 경우, 단순 Vector 유사도 검색만으로는 적합한 결과를 얻기 어려울 수 있다는 의견이 제시됨.
- LLM을 활용하여 사용자의 질문 의도를 “예금/적금” 등 구체적인 금융상품 영역으로 보정하거나, 추가 질문을 통해 조건을 수집하는 방식이 검토됨.
- 답변 품질을 높이기 위해 실제 사용자의 질문 유형과 시나리오를 충분히 확보하고 이를 기반으로 테스트해야 한다는 의견이 제시됨.
- 실제 산업 환경에서는 기존 챗봇 질문/답변 로그를 활용해 **Golden Set**을 구축하고, 이를 KPI 기준으로 평가하는 방식이 필요하다는 의견이 제시됨.
### 2.5 개인화 금융추천의 필요성과 데이터 활용
**35:12 ~ 51:01 / 참석자 1, 참석자 2, 참석자 4, 참석자 5**
- 단순 금융상품 검색과 달리 “나에게 맞는 상품 추천”을 제공하려면 사용자 개인 정보가 필요하다는 의견이 제시됨.
- 개인화 요소로 다음과 같은 정보를 고려할 수 있음.
  - 계좌 정보
  - 자산 및 잔액
  - 소득 및 소비 내역
  - 투자 성향
  - 기존 대화 이력 및 사용자 성향
- 참석자 5는 **사용자 계좌를 연동하여 소비내역과 수입 등을 기반으로 답변을 제공하는 방식**을 개인화 방향으로 제안함.
- 참석자 2는 개인화 요청 시 단순히 계좌 데이터 하나를 조회하는 것이 아니라 다음과 같은 단계가 추가된다고 설명함.
  1. 해당 질문이 개인화가 필요한 질문인지 판단
  1. 어떤 계정계/API를 호출할지 판단
  1. API 요청 파라미터 결정
  1. 여러 응답 필드 중 질문에 필요한 데이터 추출
  1. 결과 데이터를 AI가 활용할 수 있는 형태로 정제
- 개인화 질의가 일반 질의보다 처리 비용 및 응답 속도 측면에서 부담이 크므로 모든 질의를 개인화 경로로 보내는 방식은 적절하지 않다는 의견이 제시됨.
- 일반 추천과 개인화 추천을 탭 또는 명시적인 서비스 모드로 분리하는 방안도 검토됨.
- 단, 탭을 분리하지 않고 질의 중 개인정보가 필요한 시점에 동의를 요청하는 방식도 제안되었으나, 이 역시 개인정보 필요 여부를 판별하는 로직이 선행되어야 한다는 점이 지적됨.
### 2.6 금융 서비스 관점의 AI 거버넌스
**03:29 ~ 06:20 / 참석자 2**
- 실제 End User가 사용하는 금융 AI 서비스라면 검색 정확도뿐 아니라 **AI 거버넌스 관점의 설계**가 필요하다는 의견이 제시됨.
- 주요 관리 항목으로 다음 내용이 언급됨.
  - 데이터 품질 관리
  - 보안 관리
  - 접근권한 관리
  - 리스크 관리
  - Hallucination 관리
  - 운영 관리
- 단순히 사용자의 질문에 답하는 기능만 구현하는 것이 아니라 금융 서비스 환경에서 실제 운영 가능한 수준까지 고려했다는 점을 보여줄 필요가 있다는 의견이 제시됨.
### 2.7 서비스 형태 및 운영 구조
**37:14 ~ 40:30 / 참석자 2, 참석자 4**
- 서비스는 별도의 **웹 기반 금융 챗봇** 형태로 구현하는 방향이 논의됨.
- 개인화 기능을 제공하는 경우 로그인·인증이 필요할 가능성이 높으며, 다음과 같은 운영 기능도 고려해야 한다는 의견이 제시됨.
  - 사용자 인증
  - 질문/답변 이력 관리
  - 사용자별 상태 및 정보 관리
  - 관리자 기능
  - 데이터 업데이트 및 개선 관리
- 일반 질문과 개인화 질문을 기능적으로 구분하는 방식이 구현 난이도 및 정확도 측면에서 유리할 수 있다는 의견이 제시됨.
### 2.8 실제 금융 API를 고려한 Mock 데이터 설계 필요
**48:09 ~ 55:57 / 참석자 2, 참석자 4**
- 실제 은행 계정계에서는 사용자 정보가 단일 테이블이나 하나의 API로 정리되어 있지 않고 다양한 API와 데이터 구조로 분리되어 있을 가능성이 높다는 점이 논의됨.
- 따라서 개인화 구현 시 다음과 같은 문제를 고려해야 함.
  - 어떤 API를 선택할 것인지
  - 어떤 식별자 및 조회 파라미터를 사용할 것인지
  - 반환되는 다수의 컬럼 중 어떤 정보를 사용할 것인지
  - 반환 데이터가 AI가 바로 활용하기 좋은 형태가 아닐 경우 어떻게 정제할 것인지
- 프로젝트에서도 단순한 임의 JSON을 만드는 방식보다 **실제 금융권 API에서 제공하는 구조를 조사한 후, 가능한 한 실제와 유사한 Mock API 및 가상 데이터를 구성할 필요가 있다**는 방향이 제시됨.
- 데이터 조회부터 응답 정제까지의 전체 흐름을 실제 금융서비스에 가깝게 구현하는 것이 프로젝트의 기술적 가치와 완성도를 높일 수 있다는 의견이 제시됨.
## 3. 결정 사항 (Conclusion)
1. **서비스 방향은 금융상품 추천형 AI 챗봇으로 유지한다.**
  - 우선 예금·적금 등의 금융상품 추천을 중심으로 구체화한다.
1. **검색 아키텍처는 단일 RAG 방식이 아니라 복수 검색 기술을 결합하는 방향으로 검토한다.**
  - Vector RAG
  - Graph RAG
  - OpenKB
  - PageIndex
  - DB/API 직접 조회
1. **OpenKB와 PageIndex는 기존 RAG를 완전히 대체하는 기술이 아니라 지식 구조화 및 문맥 탐색을 보완하는 계층으로 활용하는 방향으로 검토한다.**
1. **질문마다 모든 검색 시스템을 실행하는 전수검사 방식은 지양하고, 질의 의도에 따른 라우팅 구조를 설계한다.**
1. **개인화는 프로젝트의 주요 차별화 요소로 고려한다.**
  - 단, 개인화 여부를 판단하는 라우팅과 사용자 데이터 조회 구조를 먼저 설계해야 한다.
1. **실제 금융권 데이터/API 구조를 조사한 후 이를 참고하여 Mock API와 가상 데이터를 설계한다.**
  - 단순 임의 데이터가 아니라 실제 금융 API의 요청/응답 구조와 최대한 유사하게 구성한다.
1. **금융 AI 서비스 특성상 AI 거버넌스 항목을 별도로 정의한다.**
  - 데이터 품질, 보안, 접근통제, Hallucination, 리스크, 운영관리 등을 포함한다.
1. **서비스 형태는 웹 기반 챗봇을 우선 고려하며, 개인화를 적용할 경우 로그인 및 사용자 관리 기능을 함께 검토한다.**

### 우선순위가 높은 단기 과제
**① 실제 금융 API 및 데이터 구조 조사→ ② Mock 금융 데이터/API 설계→ ③ 사용자 질문 시나리오 정의→ ④ 질의 라우팅 구조 설계→ ⑤ RAG/OpenKB/PageIndex 상세 데이터 플로우 설계**
현재 단계에서는 특히 **“실제 금융권에서는 어떤 API에서 어떤 데이터를 어떻게 제공하는가”를 먼저 확인하고, 이를 기반으로 개인화 데이터 흐름을 설계하는 것이 핵심 선행 과제**로 정리된다.
