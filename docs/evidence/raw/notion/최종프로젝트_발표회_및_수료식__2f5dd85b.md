## 🎯 **오늘 멘토링 핵심 요약**

1. 암호화는 목적과 사용 위치에 따라 방식이 달라지며, 성능 저하와 검색 불가능성까지 고려해야 함
1. Kubernetes의 Deployment / ReplicaSet / Service 역할을 구분해서 이해해야 배포 구조를 설명할 수 있음
## 💡 **멘토님 주요 코멘트 / 피드백**
> 도메인별로 나누면 나중에 정리하기 쉬워짐
### ✅ 주제/서비스 방향성
- 지금은 무리하게 비동기 구조부터 설계하기보다 동기 방식으로 먼저 전체 흐름을 완성하는 게 우선
- Kafka는 요청/응답용이라기보다 데이터 흐름 분리와 장애 대응에 적합한 구조
- 알림처럼 실시간성이 낮은 기능은 DB 상태를 보고 배치처럼 처리하는 방식도 가능
### ✅ 기술 스택 관련 조언
- Kafka는 “요청하면 바로 답을 받는 구조”가 아니라 메시지를 적재하고 소비하는 흐름으로 이해해야 함
- Future 기반 비동기 응답 처리도 학습 필요
- Prometheus, Elasticsearch, Fluent Bit, Kibana는 오후에 가볍게라도 확인해보면 좋음
- 암호화는 무조건 적용보다 “왜 암호화하는지”와 “어디에 쓰이는 데이터인지”가 중요
### ✅ 시스템 구조 / 아키텍처 피드백
- Deployment는 Pod 배포와 버전 관리를 담당
- ReplicaSet은 Deployment가 만든 Pod의 개수와 버전을 관리
- Service는 Pod에 접근하기 위한 네트워크 진입점 역할
- Service는 Pod가 바뀌어도 안정적으로 접근할 수 있게 해줌
- ClusterIP / NodePort / LoadBalancer 타입 차이 이해 필요
- Ingress는 외부 요청을 Service로 라우팅하는 역할
### ✅ 일정 / 스프린트 관리
- 우선 동기 방식으로 기능을 완성하고, 이후 병목 구간만 비동기 전환
- 모니터링/로그 수집은 핵심 기능 이후 적용 가능
- Kubernetes 배포 구조는 기본 개념부터 정확히 이해하고 적용
### ✅ 리스크 요소 및 주의점
- Kafka를 무조건 쓰면 구조가 복잡해질 수 있음
- 암호화는 검색 성능 저하와 속도 문제 발생 가능
- JWT나 토큰에는 민감 정보나 불필요한 정보를 넣지 않아야 함
- Kubernetes 리소스 역할을 헷갈리면 배포/서비스 연결 구조 설명이 어려워짐
