# 데이터의 형식화 방식
크게 3개 분류(유저정보·포트폴리오 / 주식 종목 및 분야 / 뉴스 및 실시간 정보)에 따라 다른 데이터 정규화 방식을 사용, GraphDB에 관계를 연결.
### 1. GraphDB 연계 및 노드 스키마
종목(Stock)과 섹터(Sector)를 중심 허브 노드로 두고 3개 도메인을 매개체 형태로 연결.
| 핵심 속성 (Properties) | 주요 노드 | 분류 | 관계 정의 (Relationships) |
| userId, portfolioId | User, Portfolio | **유저 · 포트폴리오** | (User)-[:OWNS]->(Portfolio)
(Portfolio)-[:HOLDS {qty, avgPrice}]->(Stock) |
| ticker, name, market | Stock, Sector | **주식 종목 및 분야 (허브)** | (Stock)-[:BELONGS_TO]->(Sector)
(Stock)-[:SUPPLIES_TO]->(Stock) |
| newsId, sentimentScore, pubDate | News | **뉴스 및 실시간 정보** | (News)-[:MENTIONS {sentiment}]->(Stock)
(News)-[:COVERS]->(Sector) |
### 2. 핵심 그래프 탐색 경로
- **보유 종목 악재 실시간 탐지**: (User) -> (Portfolio) -> (Stock) <- [:MENTIONS] - (News)
- **섹터 기반 2차 파급 효과 분석**: (News) -> (A 종목) -> (Sector) -> (내 보유 B 종목)
### 3. 저장소 역할 분리 기준
- **GraphDB**: 엔티티 식별자(ticker, newsId), 노드 간 관계, 탐색/필터링용 메타데이터만 적재
- **RDB / DocDB**: 뉴스 본문 전문, 유저 상세 정보 저장
- **TSDB (시계열)**: 실시간 주가 틱 및 차트 시계열 데이터 저장
### 4. AI(LLM) 기반 데이터 수집 및 형식화 자동화
동일 분류 내 데이터는 구조적 패턴을 공유하므로, LLM의 구조화 출력 기능을 활용해 수집 및 전처리를 자동화.
| LLM 자동화 역할 | 분류 | 원천 데이터 형태 | 최종 적재 데이터 |
| 보유 종목, 수량, 평단가 등 핵심 엔티티 파싱 | **유저 · 포트폴리오** | 자연어 텍스트, 비정형 자산 메모 | 정형 JSON (ticker, qty, avgPrice) |
| 공급망(고객사·협력사) 식별, 테마/섹터 자동 분류 | **주식 종목 및 분야** | 기업 공시, 증권사 리포트 | 노드 속성 및 관계 엣지 (SUPPLIES_TO, BELONGS_TO) |
| 연관 종목 NER 추출, 감성 점수(-1.0 ~ 1.0) 채점 | **뉴스 및 실시간 정보** | 비정형 뉴스 기사 본문, 속보 | 뉴스 메타 및 연결 엣지 (MENTIONS {sentiment}) |
### 5. LLM 파이프라인 처리 흐름
- **1단계 (수집)**: 크롤러, RSS, API를 통해 기사 및 공시 원문 텍스트 인입
- **2단계 (엔티티 정규화)**:
  - LLM을 거쳐 비공식 명칭 표준화 (예: '삼전', '삼성' → 티커 005930 매핑)
  - 사전 정의된 JSON Schema 규격으로 변환
- **3단계 (GraphDB 자동 적재)**:
  - 파싱된 엔티티와 관계를 바탕으로 Cypher MERGE 쿼리 생성 및 실행
  - 기존 Stock, Sector 노드에 신규 News 노드 및 관계 실시간 바인딩

  ## 강사님께 설명할 스토리
  “처음 저희가 구상했던 서비스는 개별 종목이나 시장 이슈를 분석해서 보여주는 형태였습니다. 예를 들어 삼성전자 주가가 왜 움직였는지, 특정 이슈가 어떤 기업에 영향을 주는지를 뉴스와 함께 설명하는 방식이었습니다.
  그런데 이 방향을 구체화하면서 한 가지 문제를 발견했습니다. 분석 대상이 모든 사용자에게 동일하다면, 결국 기존 증권 서비스나 금융 뉴스 플랫폼과 비슷한 ‘정보 전달 서비스’에 머물 수 있다는 점이었습니다.
  그래서 저희는 서비스의 중심을 ‘시장 정보’에서 ‘사용자의 실제 자산’으로 바꾸었습니다.
  사용자가 증권 계좌를 읽기 전용으로 연결하면, 보유 종목과 비중을 가져오고, 그 종목들이 어떤 기업·산업·시장 이슈에 노출되어 있는지를 관계 그래프로 보여주는 방향입니다.
  예를 들어 사용자가 삼성전자와 SK하이닉스를 각각 보유하고 있다면, 표면적으로는 서로 다른 두 종목을 가진 것처럼 보입니다. 하지만 실제로는 AI 데이터센터 투자, HBM 수요, 메모리 가격, 미국의 대중 규제, 원·달러 환율과 같은 공통 요인에 동시에 노출되어 있을 수 있습니다.
  저희 서비스가 보여주고 싶은 것은 단순히 ‘삼성전자 관련 뉴스가 나왔습니다’가 아닙니다.
  ‘이 뉴스에서 추출된 이슈가 어떤 기업과 연결되고, 그 연결이 사용자의 포트폴리오에 어떤 경로로 도달하는가’를 보여주는 것이 핵심입니다.”
  ## 서비스의 핵심 가치
  > 뉴스와 공시에서 발견한 기업·산업·이슈의 관계를 GraphDB에 축적하고, 사용자의 실제 포트폴리오를 출발점으로 개인화된 금융 지식 지도를 제공한다.
  이를 사용자 관점에서 더 간단히 표현하면 다음과 같습니다.
  > “내가 가진 종목은 실제로 무엇에 영향을 받고 있으며, 서로 얼마나 같은 위험에 노출되어 있는가?”
  단순히 뉴스를 모아서 보여주는 것이 아니라, 뉴스 속 관계를 구조화해 사용자의 자산과 연결한다는 점이 차이입니다.
  ## 그래프 구조를 어떻게 설계하려는가
  현재는 사용자에게 보이는 노드를 크게 세 종류로 구분했습니다.
  | 노드 유형 | 예시 | 의미 |
  | 포트폴리오 종목 | 삼성전자, SK하이닉스 | 사용자가 실제 보유한 자산 |
  | 외부 기업 | NVIDIA, Micron, CATL | 보유 종목과 관련된 경쟁사·고객사·공급사 |
  | 이슈 | HBM 수요, 중국 EV 수요, 환율 | 뉴스와 공시에서 추출한 산업·정책·거시 요인 |
  이 세 종류의 노드 사이에서 출발점과 도착점을 기준으로 3×3, 총 9개의 관계 범주를 표현하려고 합니다.
  - 포트폴리오 종목 → 포트폴리오 종목                                                       
  - 포트폴리오 종목 → 외부 기업
  - 포트폴리오 종목 → 이슈
  - 외부 기업 → 포트폴리오 종목
  - 외부 기업 → 외부 기업
  - 외부 기업 → 이슈
  - 이슈 → 포트폴리오 종목
  - 이슈 → 외부 기업
  - 이슈 → 이슈
  다만 이 9개는 GraphDB의 실제 관계명을 단순하게 9개로 제한한다는 뜻은 아닙니다. 사용자에게 그래프를 설명하기 위한 상위 분류에 가깝습니다.
  GraphDB 내부에서는 더 구체적으로 관계를 정의할 수 있습니다.
  - SUPPLIES_TO: 공급한다
  - COMPETES_WITH: 경쟁한다
  - CUSTOMER_OF: 고객사다
  - BELONGS_TO: 산업에 속한다
  - AFFECTS: 영향을 줄 가능성이 있다
  - MENTIONS: 뉴스가 기업을 언급한다
  - EXPOSED_TO: 특정 이슈에 노출된다
  - CO_MOVES_WITH: 주가가 함께 움직이는 경향이 있다
  - HOLDS: 포트폴리오가 종목을 보유한다
  각 관계에는 방향뿐 아니라 관련도, 근거, 최신성, 신뢰도를 함께 저장하려고 합니다.
  ```
삼성전자
  └─ EXPOSED_TO
       └─ 메모리 가격 반등

관련도: 0.89
방향: 긍정 가능
근거: 뉴스·공시 9건
최근 관측: 오늘 14:30
```
  ## UI에서는 어떻게 보여줄 것인가
  현재 프로토타입은 사용자의 보유 종목을 중심으로 그래프를 펼치는 형태입니다.
  사용자가 노드를 누르면 노드 종류에 따라 다른 정보를 보여줍니다.
  - 포트폴리오 종목을 누르면 보유 비중, 수익률, 가격 영향 후보, 투자 시점 이후 달라진 이슈를 표시합니다.
  - 외부 기업을 누르면 보유 종목과의 경쟁·고객·공급망 관계를 표시합니다.
  - 이슈를 누르면 해당 이슈가 영향을 줄 가능성이 있는 보유 종목과 외부 기업, 전파 경로를 표시합니다.
  - 간선을 누르면 두 노드가 왜 연결되었는지, 근거 뉴스는 무엇인지, 관련도와 최신성은 어느 정도인지 보여줍니다.
  따라서 사용자는 그래프를 단순한 시각 자료로 보는 것이 아니라, 노드와 간선을 탐색하면서 금융 관계를 이해하게 됩니다.
  ## 최종적으로 만들고 싶은 ‘금융 지도’
  “현재 프로토타입은 사용자의 포트폴리오를 중심으로 주변 관계를 보여주고 있지만, 최종적으로는 GraphDB에 축적된 금융시장 관계를 하나의 지도처럼 표현하는 것이 목표입니다.
  그래프에서 가까운 노드는 단순히 화면상 가까운 것이 아니라, 산업·공급망·뉴스 이슈·가격 동조성 등의 관계가 강하다는 의미를 가지게 됩니다.
  예를 들어 삼성전자와 SK하이닉스는 같은 반도체 산업, HBM 수요, 메모리 가격이라는 여러 관계를 공유하기 때문에 가까이 배치될 수 있습니다. 반면 삼성전자와 셀트리온은 산업적으로 거리가 멀기 때문에 기본적으로 멀리 배치됩니다.
  다만 환율이나 글로벌 정책 같은 공통 이슈가 발생하면, 평소에는 멀리 있던 기업들도 해당 이슈를 중심으로 새롭게 연결될 수 있습니다.
  그래서 그래프의 구조가 고정된 것이 아니라, 뉴스와 시장 상황에 따라 관계 강도와 중심 이슈가 달라지는 형태를 구상하고 있습니다.”
  여기서 “GraphDB를 그대로 화면에 출력한다”고 말하기보다는 다음 표현이 더 정확합니다.
  > GraphDB에 저장된 전체 관계 중 사용자의 보유 자산과 현재 선택한 이슈에 필요한 부분을 추출하여, 관계 강도와 유형을 반영한 금융 지도로 시각화한다.
  전체 DB를 그대로 보여주면 노드와 간선이 지나치게 많아져 사용할 수 없기 때문에, 실제 UI에서는 사용자 중심의 부분 그래프를 추출해야 합니다.
  ## 그래프의 거리에는 어떤 기준을 사용할 것인가
   “가깝고 멀다는 것을 어떻게 계산할 것인가?”
  그래프의 거리는 한 가지 기준이 아니라 여러 신호를 조합해 계산합니다.
  - 직접적인 공급망·경쟁·고객 관계
  - 같은 산업이나 테마에 속하는 정도
  - 동일한 뉴스에서 함께 언급되는 빈도
  - 공통으로 연결된 이슈의 수
  - 일정 기간 주가 동조성
  - 관계를 뒷받침하는 출처의 수와 신뢰도
  - 관계가 최근에도 유효한지에 대한 최신성
  예시는 다음과 같습니다.
  ```
관계 강도 =
기업 구조 관계 35%
공통 이슈 관계 25%
뉴스 동시 언급 15%
가격 동조성 15%
최신성·출처 신뢰도 10%
```
  이 값이 높으면 그래프상 가까이 배치하고, 낮으면 멀리 배치합니다. 다만 이 점수는 주가 인과관계를 증명하는 수치가 아니라, 그래프 탐색을 위한 관련성 점수라는 점을 명확히 해야 합니다.
  ## 7명·2개월 프로젝트에서의 현실적인 범위
  서비스가 화면만 보면 단순한 그래프처럼 보일 수 있지만, 실제 개발 범위는 그래프 뒤의 데이터 파이프라인에 있습니다.
  - 뉴스·공시 수집
  - 기업명과 종목코드 정규화
  - 뉴스 속 기업·이슈 추출
  - 동일 이슈 중복 제거와 군집화
  - 기업 관계 식별
  - 관계 방향과 유형 분류
  - 관련도·감성·신뢰도 산정
  - GraphDB 스키마와 적재 파이프라인 구현
  - 사용자 포트폴리오와의 연결
  - 부분 그래프 탐색 쿼리 구현
  - 그래프 레이아웃과 상호작용 UI 구현
  - 노드와 간선의 근거 데이터 표시
  - AI가 만든 잘못된 관계를 검증하는 장치
  따라서 2개월 MVP에서는 전체 시장을 완성하려 하기보다 다음 범위가 현실적입니다.
  1. 국내 대표 산업 2~3개 선정
  1. 포트폴리오 표시 대상 15~20개 종목 선정
  1. 외부 연관 기업은 필요에 따라 추가
  1. 핵심 이슈 유형 5~8개 정의
  1. 관계 유형과 관련도 계산 방식 구현
  1. 노드·간선 탐색이 가능한 그래프 UI 완성
  1. 실제 계좌 연동이 어렵다면 샘플 계좌나 파일 업로드 방식으로 대체
  “모든 상장사를 정확하게 분석하겠다”가 아니라, “제한된 산업과 종목에서 데이터 수집부터 개인화 그래프까지 전체 구조를 증명하겠다”는 것이 MVP로 더 설득력 있습니다.
