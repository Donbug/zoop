# 📝 회의록: 금융 챗봇(예·적금) LLM + RAG/그래프 기반 설계 논의
## 1. 회의 개요: 주제 및 목적
- 본 회의는 **은행권 금융상품(예·적금 중심) 챗봇**을 대상으로, **LLM 기반 응답 정확도 향상 방법**과 **RAG(레그)·그래프/벡터 DB 구축 난이도, 개인화 범위, 운영/개선 프로세스**를 논의하는 것을 목적으로 한다.
- 특히 “단순 상품 추천”을 넘어 **사용자 목표/수익 시나리오**까지 대응하려면 필요한 데이터·구조화·검색 전략을 정리한다.
## 2. 주요 논의 사항
### 2-1. 금융상품 범위·데이터 소스·가명화/개인화 접근
- (참석자 1, 00:01~01:38)
  - 금융상품 범위를 **예·적금(은행권 앱의 예금/적금 중심 구성)**으로 제한해 서비스 설계를 시작.
  - 공식 금융상품 정보는 은행 앱/사이트에서 확인 가능하나, 그 자체만으로는 불충분하다고 판단.
  - 개인정보는 API로 처리하기 어렵다고 보고, **데이터를 직접 설정(목 데이터 구성)**하며 **표준 JSON 형식(아이 데이터 표준 참조)** 등을 활용해 **가명화된 사용자 빅데이터** 구성 방안을 검토.
  - 은행이 제공하는 금융상품을 검증하기 위해 **“가상의 은행 시스템”을 가정한 출발 방식**을 논의함.
- (참석자 2, 02:01~02:35)
  - 기존 챗봇에서 “정확하지/상세하지 않다” 이슈의 원인을 **매크로/키워드 기반으로는 자연어 상세 설명을 이해하지 못해 무응답이 발생**하는 문제로 전제(후속 설명에서 3번 항목에서 구체화됨).
  - 추천/정확도 향상을 위해 데이터 기반이 무엇을 바꾸는지 질문.
- (참석자 4, 13:17~14:45)
  - 개인정보 처리에 대해 “내 정보에 대한 질의 허용” 수준의 **개인화**를 검토.
  - 초기 우선순위는 **예·적금 상품 질문에 대한 응답**이며, 이후 개인화 확장 시 고려.
  - 개인화가 들어오면 “현재 금리 기반 더 좋은 상품 추천” 또는 “해약 시 얼마/미래 목표(결혼 시점 금액 등)” 같은 개인 상황 기반 질문이 발생.
  - 따라서 개인화 질문 여부를 **분기/판단하는 설계**가 핵심 허들로 제시.
### 2-2. LLM 도입만으로는 정확도 보증 불가 → RAG/도구/레그 필요
- (참석자 3, 03:17~04:22)
  - 실제로 사용자가 자연어로 자세히 설명해도 **의도 파악/이해가 안 되어 답을 못 주는 경우가 빈번**했고, 사용성(체감 만족)이 낮다는 문제 제기.
  - 해결책으로 **LLM을 활용하되**, 정확성 보증은 LLM 단독으로 어렵기 때문에 **문서 기반 RAG(레그) + 추가 데이터 + 툴 연계**가 필요하다고 설명.
- (참석자 2, 04:22~05:55)
  - 기존에 적용된 사례가 있어도 “원치 않는 답변” 개선은 필요하며, 그 과정에서 **레그가 사실상 전제**라고 봄.
  - 다만 **레그 구축 자체가 쉽지 않음**이 최대 감소 포인트로 지적.
### 2-3. RAG(레그) 구축의 핵심 난제: chunking/표 분할·overlap·정제
- (참석자 2, 04:53~07:25)
  - 예·적금은 “상품명 추천”으로 끝나지 않고,
    - 목표 수익률 달성에 필요한 예치금,
    - 미래 시점(예: 결혼 계획 시점)까지의 목표 금액 산정
    - 등 **상품 정보 외 형태의 요구**가 등장할 수 있음.
  - 레그를 구성할 때 핵심 실패 케이스로
    - 문서 chunking이 적절히 되지 않아
    - 특히 **테이블이 잘리는 문제**
    - overlap(중복) 비율 산정 실패
    - chunk 크기/길이 제약 초과로 정확도 하락
    - 이 발생함.
  - 이를 보완하기 위한 방법이 필요하다고 정리.
- (참석자 3, 07:32~09:12)
  - 금융 서비스에서 레그가 어려운 이유를 2가지로 요약:
    - 사용자 입력이 정제되지 않음
    - 레그로 찾아야 하는 데이터 역시 정제되지 않음
  - 데이터 정제를 “전부 사람 손으로” 하기 어렵고, “AI/벡터 인덱싱만으로”는 정확도 한계가 있다고 설명.
  - 해결 시도로 **오픈 KB(오픈 소스 라이브러리)**처럼 PDF/Word/Markdown 등 파편화된 문서를 **정형화된 지식 데이터 형식으로 변환**하는 접근을 확인.
- (참석자 2, 09:49~10:38)
  - 변환·정형화 작업은 양이 많고 리소스가 크며, 실무에선 단기간을 위해 임베딩을 우선하는 선택이 많다는 현실적 제약 언급.
  - 또한 entity 추출/정제에 **휴먼 프로세스**가 들어갈 수 있으며, 하루 적재량·속도·비용 문제로 범위 설정이 필요.
### 2-4. 의도 분류(분기)·멀티턴 설계: 추천 vs 개인화, 벡터/그래프 조합
- (참석자 2, 10:38~12:19)
  - 챗봇 흐름에서 **의도 파악 후 설계에 따라** LLM/DB/벡터/그래프 등 경로가 달라짐.
  - 레그 내부의 전수검사로만 의도 분기를 대체하기 어렵고, **분류 체계는 데이터 구조/구축 단계에서 정의**가 필요하다고 봄.
  - 벡터 레그 정확도는 검색 실험 기준으로 충분히 높지 않을 수 있으며(대략 60~70 수준 언급),
    - “계약으로 연결되기까지”의 신뢰성 관점에서도 단순 매칭은 부족하다고 판단.
- (참석자 2, 14:30~16:01)
  - 개인화는 “질문 워딩이 달라질 수 있어” 의도 분류/분기 로직이 크게 바뀌는 영역.
  - 개인화까지 포함하려면 분기 및 데이터 처리(계정계/기관계 등)까지 은행권 업무 영역이 되며, 외부 연동 난이도가 커서 “빼야 할지”를 검토.
- (참석자 2, 16:34~18:55)
  - 예시로 오픈뱅킹 기반 계좌 잔액 등은 연동이 상대적으로 쉬울 수 있으나, 사용자 질문이 깨끗하지 않아 **의도 분류 정확도가 중요**하다고 강조.
  - 벡터만 쓰면 예금/적금 혼동 등 **관계없는 결과 확률**이 존재.
  - 그래서 **그래프까지 포함**해 상위 후보를 가져오고, LLM이 “1차 해석 → 2차 확인(추가 질문 유도)” 같은 **방어형 멀티턴**을 수행하는 방식이 언급됨.
  - 결과적으로 사용자에게 “혹시 이거야?” 식의 반복 확인이 발생할 수 있어, 사용자 관점에서의 수용성 설계가 필요.
### 2-5. 운영(사후 개선/AI Ops/LLM Ops): 로그 기반 업데이트 프로세스
- (참석자 2, 25:48~31:58)
  - 서비스 오픈 후 1~3개월 단위로 **로그 데이터 분석**을 통해 정확도/만족도가 낮으면 개선이 필요.
  - 개선을 “막연히 업데이트”가 아니라,
    - 1차: 프롬프트 변경
    - 2차: 파이닝(정교화)
    - 3차: 데이터셋 교체
    - 등 **단계별 판단 기준과 의사결정 구조**가 필요하다고 제시.
  - 사람(Human)이 판단하되, **어디까지 자동화할지**도 포함해야 함.
  - 모델 버전/프롬프트 버전/모델 교체 등 **운영 프로세스(AI Ops/LLM Ops 성격)**까지 설계해야 한다는 결론.
### 2-6. 확장 아이디어(참고 제시): 추천의 범위 vs 리서치 에이전트/그래프DB/데이터 레이크
- (참석자 2, 19:55~23:30)
  - 본 회의의 5가지 전달 내용 중 “추천”보다 발전시킨 아이디어로
    - 벡터/그래프 레이크 + Prompt Engineering
    - Knowledge Graph 형태 시각화
    - 이벤트/기사를 연결해 자동 리서치 보고서 생성(“AI 금융 리서치 에이전트”)
    - 데이터 레이크(주가·재무공시·환율·금리 등 통합) 기반 분석(텍스트-to-SQL 정확도 한계 등)
    - 그래프/도메인 온톨로지로 보완
    - 를 제시.
  - 단, 본 논의의 중심인 “금융상품 챗봇 추천/개인화”와 차이를 비교하며 확장 방향으로 공유.
## 3. 결정 사항(Conclusion)
1. 금융상품 챗봇에서 **LLM 도입만으로는 정확도 보증이 어렵고**, **문서 기반 레그(RAG) + 데이터/툴 연계**를 함께 구축하는 방향이 필요하다는 데 공감.
1. RAG 구축에서 가장 큰 리스크는 **chunking(특히 테이블 분할), overlap 산정, 데이터 정제/정형화 난이도**이며, 이를 보완하기 위한 접근(정형화 라이브러리 검토 등)과 **범위 설정**이 필요하다는 점이 확인됨.
1. 서비스 설계에서 **의도 분류/분기(추천 vs 개인화)**가 핵심이며, 개인화는 데이터/분기 난이도가 커서 **포함 여부 및 적용 범위는 신중히 판단**해야 함.
1. 오픈 이후에는 **로그 기반 성능(정확도/만족도) 점검**과 함께, **프롬프트/파이닝/데이터셋 교체 등 단계별 개선 프로세스** 및 **모델·프롬프트 버전 관리 포함 운영 설계(AI Ops/LLM Ops)**가 필요함.
