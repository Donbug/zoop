### 아이디어 1 : 금융 다마고치
**“계좌 거래내역으로 성장하는 금융 다마고치”**로 발전시키면 꽤 강한 프로젝트가 됩니다. 캐릭터와의 대화, 소비 분석, 금융상품 추천이 하나의 경험으로 자연스럽게 연결돼요.
다만 핵심은 캐릭터를 단순한 장식이 아니라 **사용자의 금융 상태를 시각화하는 인터페이스**로 만드는 것입니다.
## 핵심 사용자 흐름
```
계좌 연동
  ↓
거래내역 자동 수집·분류
  ↓
소비 습관과 금융 상태 분석
  ↓
캐릭터 상태 및 개인 퀘스트 생성
  ↓
캐릭터와 대화하며 원인·해결책 확인
  ↓
실제 행동 변화
  ↓
캐릭터 성장
```
예를 들어:
- 배달 지출이 평소보다 40% 증가→ 캐릭터가 지치는 것이 아니라 “배달 몬스터 출현”
- 이번 주 예산을 지킴→ 몬스터 처치, 경험치 획득
- 자동이체 저축을 실행→ 캐릭터 집이나 마을이 성장
- 사용하지 않는 구독을 해지→ 매달 생산되는 골드 증가
- 비상금 목표 달성→ 새로운 지역 개방
이렇게 만들면 사용자가 돈이 적다고 불이익을 받는 게임이 아니라, **자신이 설정한 목표를 달성하면 성장하는 게임**이 됩니다.
## 캐릭터와의 대화
캐릭터는 일반적인 AI 챗봇이 아니라 사용자의 금융 데이터를 이해하는 동반자입니다.
> 사용자: 이번 달에 왜 돈이 부족해?
> 캐릭터: 지난달보다 배달비가 8만 4천 원 증가했고, 연간 구독료 6만 원이 결제됐어. 남은 고정비를 고려하면 이번 달 자유롭게 사용할 수 있는 돈은 약 12만 원이야.
> 사용자: 다음 달부터 20만 원씩 저축하려면?
> 캐릭터: 배달 횟수를 주 4회에서 2회로 줄이면 약 11만 원, 사용하지 않는 구독을 정리하면 3만 원을 확보할 수 있어. 부족한 6만 원을 다른 항목에서 찾아볼까?
중요한 점은 AI가 답을 지어내지 않고, 먼저 분석 서버가 계산한 숫자를 받아 **사람이 이해하기 쉽게 설명하도록 설계하는 것**입니다.
## 금융상품 추천도 가능하지만
가능합니다. 다만 처음부터 예금·카드·대출·투자를 전부 추천하면 범위가 너무 커집니다. MVP에서는 **적금이나 예금 상품 하나에 집중**하는 것이 좋습니다.
예를 들어 사용자가:
> “6개월 뒤 여행비 120만 원을 모으고 싶어.”
라고 하면 시스템이:
1. 거래내역으로 월 저축 가능 금액 계산
1. 월 20만 원 저축 목표 설정
1. 조건에 맞는 적금 상품 필터링
1. 금리뿐 아니라 중도해지, 가입 조건, 우대조건 비교
1. 추천 근거를 캐릭터가 설명
하도록 만들 수 있습니다.
단순히 “이 상품이 좋아요”라고 추천하면 안 되고 다음과 같이 근거를 보여주는 것이 중요합니다.
> 월 20만 원을 6개월간 납입할 수 있고, 급여이체 우대조건을 충족할 가능성이 있어 이 상품을 추천했어. 단, 중간에 해지하면 우대금리가 적용되지 않을 수 있어.
학교 프로젝트에서는 실제 금융 자문처럼 표현하기보다 **상품 비교 및 정보 제공 서비스**로 정의하는 편이 안전합니다.
## 프로젝트의 기술적 강점
- 오픈뱅킹 API 또는 샌드박스를 통한 계좌 연동
- 거래내역 자동 카테고리 분류
- 사용자별 소비 패턴 및 이상 지출 탐지
- 목표 달성 가능성 예측
- 개인화 퀘스트 추천 알고리즘
- 금융상품 조건 기반 필터링 및 랭킹
- 사용자 데이터 기반 RAG 챗봇
- 계산 기능과 AI 대화를 연결하는 Function Calling
- 추천 이유를 제시하는 설명 가능한 AI
> 어려운 금융관리를 숫자와 그래프가 아닌, 사용자의 행동에 따라 성장하는 캐릭터와 세계로 경험하게 한다.
## “예쁜 가계부”가 되지 않게 하는 장치
가장 중요한 차별점은 **보는 서비스가 아니라 행동하게 만드는 서비스**라는 것입니다.
단순 기능:
> 이번 달 식비는 35만 원입니다.
프로젝트의 기능:
> 식비가 목표보다 7만 원 높습니다. 앞으로 8일 동안 하루 1만 5천 원 이하로 사용하면 목표를 회복할 수 있습니다. ‘냉장고 탐험’ 퀘스트를 시작할까요?
사용자가 퀘스트를 수락하면:
- 진행 상황 자동 측정
- 캐릭터 반응
- 성공 가능성 갱신
- 성공 시 성장 보상
- 다음 난이도 자동 조절
까지 이어져야 합니다.
## 추천 MVP
처음에는 다음 범위가 적당합니다.
1. 가상 계좌 또는 거래내역 CSV 연동
1. 거래내역 자동 분류
1. 저축 목표 설정
1. 소비 패턴에 따른 주간 퀘스트 생성
1. 퀘스트 결과에 따른 캐릭터 성장
1. 캐릭터와 금융 데이터 기반 대화
1.  적금 상품 5~10개 비교 및 추천
여유가 생기면 실제 계좌 연동, 캐릭터 꾸미기, 친구 기능, 금융 사기 탐지 등을 추가하면 됩니다.
프로젝트 이름은 **통장키우기**, **머니펫**, **뱅크몬**, **월렛메이트**, **FinPet**, **모아몬** 같은 방향이 잘 어울립니다. 한 문장으로는 다음처럼 정의할 수 있어요.
> **사용자의 실제 금융 행동으로 캐릭터와 세계를 성장시키는 AI 금융 습관 코칭 서비스**
### 프로젝트 아이디어: 다른 사람의 투자 판단에 투자하는 금융 시뮬레이션
[https://judgment-market-demo-hyun.hongfamilychat25.chatgpt.site/](https://judgment-market-demo-hyun.hongfamilychat25.chatgpt.site/)
과거 금융사건을 배경으로, 당시 공개된 정보만 보고 투자 결정을 내리는 서비스입니다. 사용자는 자신의 투자 근거를 작성하고, 다른 사람의 판단을 읽은 뒤 믿을 만한 판단에 가상 포인트를 배분합니다.
예를 들어 코로나 폭락이나 채권시장 불안 상황에서 “지금은 매수 기회다”와 “현금을 보유해야 한다”는 의견 중 누구의 논리를 믿을지 선택합니다.
**서비스 진행 방식**
1. 사건에 입장해 당시 뉴스·공시·가격을 확인합니다. 이후 정보는 숨깁니다.
1. 투자할 자산과 비중, 판단 이유, 예상 위험을 작성합니다.
1. 판단에 검증 가능한 전망과 확률을 붙입니다.예: “30일 후 지정된 채권지수가 현재보다 높을 확률은 70%”
1. 다른 이용자의 판단이 익명 카드로 공개됩니다.
1. 설득력 있다고 생각하는 카드에 가상 포인트를 배분합니다.
1. 시간이 진행되면 새로운 정보를 보고 판단을 유지하거나 수정합니다.
1. 종료 후 투자 성과, 전망 정확도, 판단 근거에 대한 피드백을 확인합니다.
수정한 판단은 새 버전으로 남으며, 이전 판단과 포인트 배분 기록은 보존합니다.
**차별점**
일반 모의투자가 “어떤 종목을 살 것인가”에 집중한다면, 이 서비스에서는 **“누구의 논리를 믿을 것인가”도 선택**합니다.
이용자의 투자 의견 자체가 콘텐츠가 되고, 그 의견에 대한 신뢰를 포인트로 표현합니다. 단순 추천·좋아요보다 선택의 결과를 직접 경험할 수 있습니다.
**평가는 어떻게 하는가?**
평가의 공정성을 위해 결과 계산과 AI 피드백의 역할을 구분합니다.
| 담당 | 평가 내용 | 구분 |
| 가격 데이터＋계산 코드 | 실제 수익률과 손실 | 투자 성과 |
| 확률 채점 공식 | 미리 작성한 확률과 실제 결과 비교 | 전망 정확도 |
| RAG＋LLM | 공시·뉴스와 주장이 일치하는지 확인 | 근거 검토 |
| 계산 규칙＋기록 비교 | 투자 비중·손실 한도·이후 행동의 관계 확인 | 판단 일관성 |
**포인트는 AI의 주관적인 종합 점수로 정산하지 않습니다.** 카드에 명시한 전망과 실제 결과를 사전 공개한 공식으로 비교합니다. 구체적인 지급 비율은 게임 설계 과정에서 조정할 예정입니다.
AI는 다음처럼 근거 있는 피드백을 제공합니다.
> “전체 자산의 80%를 투자하고 해당 자산의 15% 하락을 예상했다면, 전체 자산 손실은 12%입니다. 본인이 설정한 손실 한도 5%와 일치하지 않습니다.”
공격적 투자 자체를 감점하지 않으며, 불확실한 해석은 ‘판단 유보’로 표시합니다. 전망이 맞았다고 그 논리까지 입증됐다고 보지는 않습니다.
**예상 기술스택**
| 적용 위치 | 기술 |
| 사건 화면, 차트, 판단 카드, 포인트 배분, 결과 화면 | React·TypeScript |
| 회원, 사건 진행, 가상 매매, 판단 버전, 포인트 정산 | Spring Boot |
| 가격·문서 메타데이터·판단·거래·포인트 원장 | PostgreSQL |
| 해당 시점까지 공개된 관련 문서 검색 | pgvector＋Vector RAG |
| 기업→사업→보증 관계를 따라 관련 공시·뉴스 탐색 | 관계 탐색·Graph RAG |
| 사용자 주장 구조화, 근거 대조, 피드백 생성 | Spring AI＋LLM |
| 수익률, 손실 가정, 확률 채점, 정산 | 계산·규칙 엔진 |
| 실행 환경 통일과 자동 검사·배포 | Docker·GitHub Actions |
Graph RAG는 예를 들어 건설사 → 채무보증 → 개발사업 → 자금조달 문제를 연결해, 기업명 검색만으로 놓칠 수 있는 정보를 제공하는 데 사용합니다.
**데이터와 검증 계획**
- 공시·정책 발표·당시 뉴스·가격으로 사건 자료를 구성합니다.
- 한국은행 보고서는 사건 배경과 위험 분석, 종료 후 회고에 활용 용등 is 합니다.
- FinanceBench·FinQA는 금융 문서 이해와 계산 능력을 검증하는 보조 자료입니다. 투자 판단의 정답 데이터는 아닙니다.
- 사건별로 숫자 오류, 잘못된 인용, 미래정보 사용, 계산 모순 등의 평가 사례를 만들어 AI가 제대로 찾아내는지 검증합니다.
- 전문적인 해석이 필요한 항목은 별도 검토하며, 확인되지 않은 종합 판단 점수를 제공하지 않습니다.

과거 금융 사건을 당시 공개된 정보만으로 체험하면서, 단순히 수익이 났는지가 아니라 **어떤 근거로 선택했고 새로운 정보에 어떻게 대응했는지**를 복기하는 투자 판단 훈련 서비스입니다.
사용자가 막연한 확신이나 타인의 의견에만 의존하지 않고, **근거와 위험을 검토해 스스로 결정하는 능력**을 기르도록 돕습니다. 체험을 통해 자신의 판단에서 빠진 부분을 발견하고, 다음 선택에 적용할 기준을 가져갈 수 있습니다.
### 강사님 아이디어 - 뉴스 분석
솔직하게 말하면 **강사님이 설명한 전체 Financial Market Intelligence Graph는 그대로는 구현하기 어렵습니다.** 하지만 범위를 강하게 줄이면 프로젝트 수준에서 충분히 구현할 수 있습니다.
핵심은 “전 세계 금융시장을 실시간 분석한다”가 아니라:
> **AI 반도체 뉴스 한 건을 분석해 기업·제품·공급망 관계를 그래프에 추가하고, 관련 국내외 기업을 근거와 함께 보여준다.**
까지 만드는 것입니다.
# 구현 가능한 MVP
## 범위 제한
- 산업: AI 반도체 하나
- 기업: 국내외 10~15개
- 뉴스: 미리 수집한 기사 100~300개
- 이벤트: 5종
- 그래프 탐색: 최대 2단계
- 실시간: 제외, 버튼을 눌러 수집하거나 일정 주기 실행
- 포트폴리오: 가상 보유 종목 입력만 지원
- 자동매매: 제외

```
NVIDIA
AMD
TSMC
삼성전자
SK하이닉스
Micron

Amazon

```
실적 발표

규제·정책
```

    "AI GPU",
    "HBM"
  ],
  "event": {
    "type": "SUPPLY_CONTRACT",
    "subject": "NVIDIA",
    "direction": "positive"
  },
  "relations": [
    {
      "from": "TSMC",
      "to": "NVIDIA",
      "type": "PRODUCES_FOR"
    },
    {
      "from": "SK하이닉스",
      "to": "NVIDIA",
      "type": "SUPPLIES_TO"
    }
  ]
}
```
LLM에게 자유롭게 설명하도록 하는 게 아니라 정해진 JSON 형식으로 출력하게 하면 구현 난도가 많이 낮아집니다.
## 3. 기업명 정규화
완전한 AI 모델을 만들지 않고 별칭 테이블을 사용합니다.
```
{
  "SK Hynix": "SK하이닉스",
  "에스케이하이닉스": "SK하이닉스",
  "000660": "SK하이닉스",
  "엔비디아": "NVIDIA",
  "Nvidia": "NVIDIA"
}
```
모든 기업을 처리할 수는 없지만 지원 기업 15개만 대상으로 하면 충분합니다.
## 4. GraphDB 저장
```
NVIDIA —[USES]→ HBM
SK하이닉스 —[PRODUCES]→ HBM
NVIDIA —[PRODUCED_BY]→ TSMC
```
Neo4j를 사용하면 관계 검색을 비교적 쉽게 구현할 수 있습니다.
예:
```
MATCH path = (company:Company {name: "NVIDIA"})-[*1..2]-(related)
RETURN path
```
NVIDIA로부터 두 단계 안에 연결된 기업·제품을 반환합니다.
## 5. 화면에 그래프 표시
```
          TSMC
            │
       PRODUCES_FOR
            ↓
SK하이닉스 → NVIDIA → AI GPU
     ↑
  PRODUCES
     │

```
노드를 클릭하면:

- 관계 종류
- 관련 뉴스
- 관계를 추출한 문장
- 정보 기준일
- AI 신뢰도
를 보여줍니다.
## 6. AI 질문
사용자가:
> NVIDIA와 관련된 국내 기업만 보여줘.
라고 물으면 AI가 다음 함수 조건으로 바꿉니다.
```
{
  "startCompany": "NVIDIA",
  "country": "Korea",
  "maxDepth": 2
}
```
서버가 Neo4j를 조회하고 결과를 AI가 설명합니다.
```
NVIDIA와 2단계 안에서 연결된 국내 기업은
SK하이닉스와 삼성전자입니다.

SK하이닉스는 HBM 공급 관계,
삼성전자는 파운드리 및 메모리 경쟁 관계로 연결됩니다.
```
# 어디까지가 진짜 기술인가
최소한 다음 하나는 실시간으로 보여줘야 합니다.
```
새 뉴스 입력
→ AI가 기업과 이벤트 추출
→ 그래프에 새로운 노드·관계 추가
→ 화면 그래프 갱신
```
처음부터 그래프를 전부 하드코딩해 놓고 보여주면 단순 시각화 프로젝트로 보입니다.
반대로 기본 공급망은 수동하게 구축해도 괜찮습니다.
```
기본 기업·공급망 관계
= 팀이 검증해 미리 구축

새로운 뉴스 이벤트
= AI가 자동 추출해 동적으로 추가
```
이 혼합 방식이 가장 현실적입니다.
# 구현하면 안 되는 부분
## 실시간 전 세계 뉴스 분석
뉴스 API, 중복 제거, 다국어 처리, 속보 처리까지 필요하므로 제외해야 합니다.

대신:

라고 표현합니다.
## AI 주가 예측
수익률 검증까지 들어가면 프로젝트 초점이 흐려집니다.
## 실제 자동매매
증권사 API와 규제 문제가 추가되므로 제외합니다.
## 모든 산업 지원
AI 반도체 하나를 제대로 구현하는 편이 훨씬 낫습니다.
# 현실적인 시스템 구조
```
React
  │
  ├── 그래프 화면
  ├── 뉴스 입력
  ├── 기업 상세
  └── AI 채팅
        │
Spring Boot 또는 FastAPI
        │
  ┌─────┴─────┐
  ↓           ↓
Neo4j      LLM API
그래프 저장   개체·이벤트 추출
  │
  ↓
뉴스 원문·근거 저장
```
팀이 Spring Boot에 익숙하면 굳이 FastAPI로 바꿀 필요 없습니다.
- 백엔드: Spring Boot
- AI 파이프라인: Python 또는 LLM API 직접 호출
- 그래프: Neo4j
- 프론트엔드: React
- 시각화: Cytoscape.js
- 문서 저장: PostgreSQL 또는 간단한 JSON
- 임베딩 검색: 시간 남으면 추가
벡터 DB, Kafka, 데이터 레이크는 MVP 필수 요소가 아닙니다.
