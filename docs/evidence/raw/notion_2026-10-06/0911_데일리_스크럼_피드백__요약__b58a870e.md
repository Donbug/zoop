# 회의록
## 1. 회의 개요
**주제:** 개인 자산 포트폴리오 기반 Financial Market Intelligence Graph 서비스 구체화 및 중간발표 준비
**목적:** 기존 프로토타입의 금융 도메인 적합성과 개인화 요소를 강화하고, **그래프 DB·자산 데이터·뉴스 데이터·AI 챗봇을 어떻게 연결할지 기술적 범위와 MVP 구현 방향을 검토**함.

### 2.3 보유 종목 변경에 따른 Graph DB 확장 문제
**03:17 ~ 07:39 | 참석자 1, 2, 4, 5, 6**
- 사용자의 실제 포트폴리오는 계속 변경되므로, **사전에 구축하지 않은 신규 종목이 포트폴리오에 들어왔을 때 어떻게 처리할 것인지**가 주요 쟁점으로 제기됨.
- 예를 들어 MVP가 20개 종목의 관계 데이터만 가지고 있는데 사용자가 그 외 종목을 보유하게 될 경우:
  - 신규 종목 관련 뉴스와 데이터를 자동 수집하여 Graph DB를 확장할 것인지,
  - 아니면 MVP에서는 지원 종목을 20개로 제한할 것인지 결정 필요.
- 최종 서비스에서는 신규 종목을 지속적으로 추가하는 것이 바람직하다는 의견이 있었으나, **자동 데이터 수집·관계 생성 방법은 아직 구체화되지 않음**.
- 참석자 1은 2개월 프로젝트의 시간·비용을 고려하면 **지원 종목을 제한하는 방식도 현실적인 선택**이라고 제안.
- 단, 지나치게 제한할 경우 서비스가 빈약해 보일 수 있으므로 팀 차원의 추가 검토가 필요함.
### 2.4 그래프와 자산 변동 정보의 연결
**07:39 ~ 09:16 | 참석자 1, 2, 4**
- 단순히 종목·뉴스 관계를 그래프로 보여주는 것만으로 충분한지 검토.
- 사용자의 **자산 규모 및 자산 변동량과 시장 이벤트를 어떻게 연결할 것인지**에 대한 추가 고민이 필요하다는 의견이 제시됨.
- 주가 또는 자산가치 자체를 직접 예측하는 기능은 현재 고려하지 않고 있음.
- 다만 “향후 자산이 오른다/내린다”는 직접 예측보다는 **시장 변화가 내 포트폴리오에 어떤 영향을 줄 수 있는지를 분석하는 형태**의 기능은 검토할 가치가 있다는 의견이 제시됨.
- 그래프가 서비스의 중심이라는 기존 방향은 유지.

### 2.6 Graph RAG 기반 답변과 Hybrid 검색 필요성
**10:15 ~ 11:46 | 참석자 1, 6**
- “삼성전자 주가 영향 요인을 알려줘”와 같은 질문을 단순히 외부 LLM API에 전달한다면 **Graph DB를 구축한 의미가 약해진다**는 지적.
- 이에 따라 챗봇은 내부 Graph DB에 구축된:
  - 보유 종목
  - 관련 기업/산업
  - 뉴스/이슈
  - 관계 데이터를 기반으로 답변하는 **Graph RAG 구조**를 고려.
- 다만 참석자 1은 Graph 검색만으로는 충분하지 않을 가능성이 있으며 **Vector RAG 등과 결합한 Hybrid RAG 구조**를 검토할 필요가 있다고 지적.
- 특히 개인 자산 질문은 Graph DB가 아니라 원천 자산 데이터/API를 조회해야 하므로 단일 Graph RAG로 모든 질문을 처리하기 어렵다는 의견.
### 2.7 통합 챗봇의 Intent Classification 및 Routing
**11:46 ~ 14:57 | 참석자 1, 4**
통합 챗봇에서는 사용자의 질문 유형에 따라 **조회 대상과 처리 방법을 분기하는 구조가 필요**하다는 점이 핵심 기술 과제로 제시됨.
예상되는 질문 유형은 크게 다음과 같음.
| 질문 유형 | 예시 | 예상 처리 방식 |
| 시장/관계 질문 | “삼성전자 주가 영향 요인은?” | Graph DB / Graph RAG |
| 뉴스 질문 | “삼성전자 최근 이슈는?” | 뉴스 검색 / Vector RAG |
| 개인화 질문 | “내 삼성전자 보유 비중은?” | 개인 자산 DB/API |
| 자산 조회 | “내 현재 주식 잔액은?” | Open Banking/증권 API 또는 Mock API |
| 복합 질문 | “최근 반도체 이슈가 내 포트폴리오에 어떤 영향을 줘?” | Graph + 뉴스 + 개인 자산 데이터 결합 |
- 따라서 챗봇 앞단에 **Intent Classification/Query Routing 계층**이 필요.
- 간단한 MVP 방법으로 사용자가 `개인화`, `뉴스` 등의 Chip/Button을 직접 선택하게 하는 방식도 제안됨.
- 개인화 질문에서도 질문 종류에 따라 잔액조회, 보유종목 조회 등 서로 다른 API를 선택해야 함.
- API 호출에 필수 파라미터가 부족한 경우 **Multi-turn 대화로 추가 정보를 수집하는 구조**까지 고려해야 함.
- 서비스가 처리할 질문뿐 아니라 **지원하지 않는 질문을 어떻게 제한·거절할 것인지**도 사전에 정의할 필요가 있음.

# 3. 결정 사항 (Conclusion)
1. 서비스의 핵심 기능은 **사용자의 보유 자산을 중심으로 기업·산업·뉴스·이슈 등의 관계를 Graph DB로 구성하고 시각화하는 것**으로 유지한다.
1. 챗봇은 단순 LLM 질의 기능이 아니라 **서비스 내부 데이터와 연결된 통합 질의 인터페이스**로 설계하는 방향으로 검토한다.
1. Graph DB만으로 모든 질문을 처리하기 어렵기 때문에 **Graph RAG + Vector RAG + 개인 자산 데이터/API를 결합하는 Hybrid 구조**를 추가 검토한다.
1. 개인화 질문을 지원하기 위해서는 질문의 **Intent Classification 및 데이터 소스/API Routing 구조**가 필요하다.
1. 매매 과정 자체를 구현하기보다는 **현재 보유 종목·잔고 등 결과 데이터를 기준으로 서비스를 구성**한다.
1. 주가 또는 자산가치에 대한 직접적인 예측 기능은 현재 MVP 범위에는 포함하지 않는다.
1. **지원 종목을 사전 정의된 범위로 제한할지, 신규 종목까지 동적으로 확장할지는 아직 미확정**이며 팀에서 구현 난이도와 서비스 완성도를 고려해 결정한다.
1. 다음 주 중간발표를 위해 **주제 선정 이유, 서비스 구조, 핵심 기능 및 구현 결과물 중심의 발표자료를 사전에 준비·공유**한다.
