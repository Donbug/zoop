## 1. 회의 개요: 주제 및 목적
Graph DB와 AI를 활용한 종목별 금융 뉴스·영향 관계 분석 서비스의 범위와 구현 방향을 검토하였다. 사용자 시나리오, 데이터 수급, 자연어 관계 검색, AI 활용 방안과 프로젝트 검증 기준을 구체화하는 것을 목적으로 진행했다.
## 2. 주요 논의 사항
### 2.1 서비스 기능과 프로젝트 규모
- **참석자 1 (00:00~01:37)**
  사용자가 자연어로 특정 종목의 영향 요인, 과거 거래량, 주가 변동 관련 정보를 요청하는 기능을 제안했다. 현재 제시된 단일 화면만으로는 7~8명이 수행할 프로젝트로서 규모가 작아 보일 수 있으므로, 전체 사용자 여정과 부가 기능을 함께 설계해 실제 개발 범위를 확인해야 한다고 설명했다.
- **참석자 1 (00:30~01:37)**
  단순히 주식·지수·가상자산과 관련 **뉴스를 제공하는 것만으로 금융 도메인의 특성을 충분히 보여줄 수 있는지 검토**해야 한다고 지적했다. 금융정보를 이용해 사용자가 무엇을 판단하고 어떤 결과를 얻는지 명확히 해야 한다고 강조했다.
### 2.2 사용자 시나리오와 업무 흐름도 작성
- **참석자 1 (02:18~03:31)**

- **참석자 1 (02:18~03:31)**
  전체 서비스 구조를 구체화하기 위해 다음 산출물을 작성할 것을 제안했다.
  - 사용자 여정 및 화면 흐름
  - 유스케이스
  - 데이터 처리 업무 흐름도
  - 필요시 시퀀스 다이어그램
  - 프로젝트의 핵심 기능과 솔루션 구조

### 2.4 데이터 갱신 시점
- **참석자 5 (05:43)**
  실시간 데이터를 계속 수집하기보다 장 마감 이후 데이터를 일괄 처리하는 방안을 언급했다.
- **참석자 2 (12:37~14:02)**
  데이터 수급의 어려움을 고려해 장 마감 후 하루 동안 발생한 이슈를 정제하고 최종 그래프와 리포트를 제공하는 방향을 제안했다.
- **참석자 1 (12:47~13:51)**
  데이터 수집이 어렵다는 이유만으로 프로젝트 방향을 변경하기보다, 공식 API 외에도 사이트별 데이터 제공 방식과 대체 경로를 조사해야 한다고 말했다. 다만 데이터 제공 조건과 접근 제한을 고려한 현실적인 수집 주기 설계가 필요하다고 보았다.
- **참석자 1 (14:27~16:31)**
  사용자의 거래를 실시간으로 유도하는 서비스라면 장중 데이터가 필요하지만, 정보 전달과 학습이 목적이라면 장 마감 후 또는 새벽에 배치 방식으로 분석해도 무방하다고 설명했다. 데이터 갱신 주기는 서비스의 최종 목적에 따라 결정해야 한다고 정리했다.
### 2.5 대상 기업 20개의 MVP 적정성
- **참석자 6 (08:08~08:23)**
  하나의 기업에서도 많은 관계가 파생되는 점을 고려해 지원 기업을 약 20개로 제한했다고 설명했다.
- **참석자 1 (08:23~09:21)**
  20개 기업은 기술 가능성을 확인하는 MVP 범위로 적절하다고 평가했다. 각 기업에 연결되는 속성, 사건, 기업 및 관계를 포함하면 전체 그래프는 수백 개의 노드와 관계로 확장될 가능성이 있다고 설명했다.
- **참석자 1 (09:21~10:11)**
  다음과 같은 단계적 개발 방식을 제안했다.
  1. Graph DB 또는 Graph RAG로 특정 기업의 관계 시각화 가능성을 검증하는 PoC 수행
  1. 약 20개 기업을 대상으로 MVP 구축
  1. 향후 새로운 기업을 검색·등록하면 그래프가 자동으로 생성되는 구조로 확장
### 2.6 자동 그래프 구축의 한계와 자연어 검색
- **참석자 1 (08:23~10:11)**
  궁극적으로는 삼성전자나 SK와 같은 기업을 등록하면 관련 속성과 관계가 자동으로 구축되는 형태가 바람직하다고 설명했다.
- **참석자 1 (10:11~11:28)**
  새로운 기업의 속성과 관계를 완전히 자동으로 생성하려면 정보의 정확성과 관계의 적절성을 사람이 검증해야 하므로 MVP에서 완전 자동화는 어렵다고 판단했다.
- **참석자 1 (10:11~11:28)**
  이미 구축된 20개 종목을 대상으로 자연어 관계 검색을 제공하면 제한된 데이터 범위에서도 Graph DB의 장점을 충분히 보여줄 수 있다고 평가했다. 완전한 자연어 처리가 어렵다면 룰 기반 검색조건 변환도 가능하다고 제안했다.
### 2.7 AI·클라우드 지원과 수행계획서
- **참석자 1 (11:28~12:14)**
  AI와 클라우드 자원을 지원받을 가능성이 있으나, 프로젝트 수행계획서가 확정된 이후 사용할 수 있을 것으로 보인다고 안내했다. 팀이 프로젝트 방향과 활용 계획을 조속히 정리해 담당 매니저에게 전달해야 한다고 설명했다.
- **참석자 1 (06:29~08:01)**
  프로젝트는 단편적인 기능 구현이 아니라 다음 절차를 경험하는 과정이라고 강조했다.
  ```plain text
  목표·목적 정의
  → 벤치마킹
  → 사용자 시나리오
  → 요구사항 정의
  → 구현
  → 테스트
  → 목표 대비 검증
  ```
### 2.8 분석 결과 검증과 KPI
- **참석자 1 (14:27~15:51)**
  종목의 정확한 수익률을 예측하기는 어렵더라도 상승·하락 방향을 분석하고, 실제 결과와 비교해 정확도를 리포트하는 방안을 제안했다.
- **참석자 1 (15:28~15:51)**
  Graph DB에 저장된 영향 요인을 근거로 상승·하락을 판단하고, 일주일 또는 한 달 단위로 결과를 검증하면 서비스 신뢰도를 높일 수 있다고 설명했다.
- **참석자 7 (15:48)**
  반드시 실시간 예측일 필요는 없다는 의견을 제시했다.
- **참석자 1 (18:17~19:22)**
  분석이나 추천 기능을 제공한다면 정량적인 KPI가 필요하다고 강조했다. 예시로 상승·하락 판단 정확도를 제시했으며, 목표 수치 달성을 위해 다음 요소도 함께 정의해야 한다고 설명했다.
  - 그래프 데이터의 정확성
  - 관계 추출 검증 방법
  - 평가 데이터셋
  - 테스트 절차
  - 목표 정확도
  - 분석 실패 및 오류 처리
  단, 구체적인 목표 정확도 수치는 이번 회의에서 확정되지 않았다.

  ## 3. 결정 사항(Conclusion)
- Graph DB와 AI를 활용한 종목별 뉴스·영향 관계 분석 방향을 프로젝트 주제로 계속 구체화한다.
- 약 20개 기업을 대상으로 하는 범위는 MVP로 적절하다고 판단했다.
- 특정 기업의 관계 데이터를 시각화하는 Graph DB·Graph RAG 기술 검증을 먼저 수행한다.
- 완전히 새로운 기업의 관계를 실시간으로 자동 구축하는 기능은 검증 부담이 크므로 초기 MVP 범위에서는 제한한다.
- 구축된 기업 데이터를 대상으로 자연어 또는 룰 기반 관계 검색 기능을 추가하는 방향을 검토한다.
- 실시간 데이터 제공 여부는 확정하지 않았으며, 서비스 목적에 따라 결정한다.
  - 거래 의사결정 지원: 장중 또는 짧은 주기 데이터 필요
  - 정보 제공·학습: 장 마감 후 배치 분석 가능
- 단순 뉴스 제공을 넘어 금융 도메인의 특성과 사용자가 얻는 가치를 구체적으로 정의해야 한다.
- Google Finance, Gemini 연계 사례 등 유사 서비스를 벤치마킹하고 차별점을 도출한다.
- 사용자 여정, 업무 흐름도, 데이터 처리 과정과 핵심 기능을 수행계획서 작성 전에 구체화한다.
- 분석 결과를 평가하기 위한 KPI와 검증 데이터셋을 설계한다.
- 상승·하락 분석 및 정확도 리포트는 아이디어로 제시됐으나 핵심 기능으로 확정되지는 않았다.
- 다음 날까지 진행한 내용을 통합해 진척 사항을 공유한다.
