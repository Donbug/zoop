## 💡 멘토님 주요 코멘트 / 피드백
> 도메인별로 나누면 나중에 정리하기 쉬워짐
### ✅ 주제/서비스 방향성
- 원격 결제 기능은 보안 관점에서의 해결 방안까지 함께 제시하면 좋음
- 카드 추천/최적화 기준이 무엇인지 명확한 평가 기준 필요
- 사용자 결제 데이터를 기반으로 추천 알고리즘이 지속적으로 개선되는 구조를 설명하면 좋음
- 실제 카드사 데이터 연동에는 한계가 있으므로, 최종 발표에서는 카드사 시뮬레이터(Mock PG)를 활용하는 이유를 함께 설명하는 방향 추천
- 실적 데이터는 이룸페이 내부 사용 데이터를 기준으로 관리하는 방향으로 정리
- 공공 마이데이터 활용 시, 사용자의 약관 동의를 기반으로 카드 데이터 연동 가능성 존재
### ✅ 기술 스택 관련 조언 (AI / LiDAR / 백엔드 / 프론트)
- Redis는 휘발성 데이터 처리 및 캐싱에 적합하며 속도가 빠름
- DB는 영구 저장 및 거래 이력 관리에 적합
- JWT 토큰, QR 유효시간 등의 데이터는 Redis 활용이 적절함
- QR 거래 이력 및 결제 추적 데이터는 DB 저장이 필요하며 Redis와 병행 사용 가능
### ✅ 시스템 구조 / 아키텍처 피드백
- MSA 선택 기준을 보다 명확하게 설명하는 것이 중요
- Saga 패턴과 도메인 분리 기반 설계 방향에 대한 설명은 긍정적인 평가를 받음
- 서비스 규모가 작더라도 “MSA 구조를 직접 경험하고 설계해보기 위해 선택했다”는 방향의 답변도 설득력 있음
- 2PC(Two-Phase Commit)는 서비스 결합도를 높이기 때문에 MSA 환경에서는 일반적으로 지양됨
- 대신 Saga 패턴 기반의 보상 트랜잭션 설계가 적절함
### ✅ 일정 / 스프린트 관리
- QR 데이터 기준 및 유효시간 정책 정의 필요
- 결제 실패 및 재시도 시나리오를 포함한 테스트 항목 구체화 필요
- 보상 트랜잭션 및 장애 대응 시나리오 추가 학습 필요
### ✅ 리스크 요소 및 주의점
- 카드사 승인 완료 이후 PG 내부 장애 발생 시 PG 측 책임 처리 방안 필요
- 결제 승인 후 데이터 적재 실패 시 재조회 및 재처리 로직 필요
- 보상 트랜잭션 처리 시 사용자 리스크 최소화 방안 고려 필요
- 외부 데이터 연동(공공 마이데이터 등)은 정책 및 실제 활용 가능 범위 검토 필요
