## 1. 회의 개요
금융 시장 및 기업 관련 데이터를 활용한 **AI 기반 금융 정보 탐색·분석 서비스의 구체적인 사용자 흐름과 데이터 파이프라인을 정의**하고, 데이터 수집 방법 및 금융 도메인 특성을 강화할 수 있는 방향을 논의하였다.
특히 **뉴스·기업·시장 데이터 수집 → 데이터셋 구축 → 자연어 질의 및 의도 분류 → 관련 데이터 검색·분석 → 그래프/차트 등 시각화 및 AI 답변 제공**으로 이어지는 서비스 구조를 구체화하는 데 초점을 맞췄다.

# 2. 주요 논의 사항
### 2.1 데이터 수집 방안 및 뉴스 데이터 확보
**00:13 ~ 03:36**
**참석자 1**
- 기업 정보 및 공시 데이터는 **OpenDART**에서 확보할 수 있음을 확인.
- 시세·종목·시장 관련 데이터는 **KRX 등의 데이터 소스**를 활용할 수 있을 것으로 파악.
- 뉴스 데이터의 경우 네이버 API 활용 가능성을 확인했으나, 원문 전체가 아닌 요약 정보 중심으로 제공되는 문제가 있음.
- 해외 뉴스 역시 실시간성이 떨어질 가능성이 있어 추가 검토가 필요함.
- 뉴스 데이터를 기반으로 기업, 인물, 원자재 등의 **키워드 및 관계 정보를 추출**하는 방향을 고려 중.
**참석자 2**
- 프로젝트가 실제 상용 서비스가 아닌 개발·테스트 목적이라는 점을 고려하여 네이버 뉴스 데이터를 활용하는 방안도 테스트할 것을 제안.
- 네이버 뉴스에서 제공되는 출처 링크를 활용해 **원문 페이지를 크롤링하고 자체 데이터셋을 구축**하는 방안을 제안.
- 크롤링한 뉴스에서 필요한 키워드를 추출하고 이후 **KG(Knowledge Graph) 구축 등에 활용하는 흐름**을 검토할 것을 제안.
- 뉴스 데이터의 실시간성 여부보다 **데이터의 기준 시점(Data Timestamp)을 명확히 정의하는 것이 중요**하다고 강조.

### 2.2 '실시간 서비스'의 정의 및 데이터 기준 시점
**02:44 ~ 04:52**

- 크롤링한 시점을 기준점으로 설정하고 사용자에게 데이터가 어느 시점 기준인지 명시하는 방안을 제안.
- 해외 뉴스처럼 하루 정도 지연되는 데이터는 실시간 서비스에 사용하기에는 한계가 있을 수 있음을 언급.
- **데이터 자체의 실시간성**과 **사용자가 서비스를 실시간으로 검색**하는 것은 서로 다른 개념이므로 이를 구분할 필요가 있다고 설명.
**참석자 1**
- 완전한 실시간 데이터 확보는 어렵기 때문에 몇 분 또는 몇 시간 전 데이터임을 표시하는 형태를 고려.
- 수집된 데이터에서 AI 분석을 통해 기업·인물·원자재 등의 태그를 추출하고 관계도를 구성하는 방향을 설명.

### 2.3 최종 서비스 형태 및 사용자 흐름 구체화
**04:52 ~ 07:09**
**참석자 2**
- 현재 가장 중요한 부분은 **최종적으로 사용자가 어떤 방식으로 서비스를 이용할 것인지 정의하는 것**이라고 강조.
- 사용자가 삼성전자·SK하이닉스 등 미리 정의된 기업을 선택하는 방식과 **자연어로 직접 질문하는 방식**은 구현 구조가 크게 달라진다고 설명.
- 자연어 검색을 지원할 경우 다음과 같은 파이프라인을 고려할 수 있다고 제안.
`데이터 크롤링 → 데이터 정제/적재 → 데이터셋 및 KG 구축 → 사용자 자연어 질의 → 질문 의도 분석/분류 → 적절한 DB·그래프·벡터 검색 → 관련 Context 구성 → LLM 답변 생성 → 시각화`
- 전체 사용자 여정(User Journey)이 정해져야 필요한 데이터, 기술 및 역할을 구체적으로 결정할 수 있다고 강조.
**참석자 1**
- 현재는 **사용자가 자연어 질문을 입력하는 방식**을 우선적으로 생각하고 있다고 설명.

### 2.4 금융 도메인 특성 강화
**07:30 ~ 12:05**
**참석자 1**
- 주식과 관련된 기업·산업 등의 관계를 그래프로 표현하면 사용자가 투자 관련 인사이트를 얻을 수 있으므로 금융 서비스의 특성을 가질 수 있다고 설명.
- 단순 정보 제공을 넘어 사용자의 투자 판단에 도움을 주는 방향도 검토.
**참석자 2**
- 단순히 데이터를 수집·정제하고 질문에 따라 시각화하는 것만으로는 **금융 도메인의 특성이 충분히 드러나지 않을 가능성**이 있다고 지적.
- 단순 LLM API 호출로 투자 리포트를 생성하는 형태라면 프로젝트 팀이 직접 구현한 기술적 역할이 약해질 수 있다고 설명.
- 반면,
  - 투자에 필요한 데이터를 직접 크롤링하고,
  - 데이터를 적재·구조화하고,
  - 질문 의도에 따라 적절한 데이터를 검색하고,
  - Context를 구성한 뒤,
  - 이를 기반으로 LLM이 답변하도록 하는 구조라면
    **프로젝트의 기술적 차별성이 충분히 확보될 수 있다**고 평가.
- 개인 자산관리 서비스보다는 **사용자가 금융시장 자체를 이해하고 투자 판단에 필요한 정보를 탐색할 수 있도록 지원하는 서비스**로 포지셔닝하는 방향도 가능하다고 제안.
- 금융 도메인 적합성에 대해서는 팀 내부 논의와 함께 **다음 멘토링 전 멘토에게 서비스 방향을 사전 공유하고 피드백을 받을 것**을 권고.

# 3. 결정 사항 (Conclusion)
1. 서비스는 단순 기업·종목 선택 방식보다는 **자연어 질의를 중심으로 하는 방향을 우선 검토**한다.
1. 금융 및 뉴스 데이터는 외부 데이터 소스/API와 **크롤링을 병행하여 자체 데이터셋을 구축**하는 방향으로 진행한다.
1. 뉴스 데이터는 완전한 실시간성을 보장하기보다 **데이터 수집·갱신 기준 시점을 명확하게 관리하고 사용자에게 표시하는 방향**을 검토한다.
1. 수집된 뉴스·기업·시장 데이터에서 **기업, 산업, 인물, 원자재 등의 핵심 Entity 및 관계를 추출하여 KG/관계도 구축에 활용**하는 방향을 검토한다.
1. 서비스의 핵심 흐름은 다음 구조를 기반으로 구체화한다.
`데이터 수집 → 정제/적재 → 데이터셋·KG 구축 → 자연어 질의 → 의도 분석 및 검색 분기 → 데이터 검색 → Context 구성 → AI 답변 생성 → 그래프/차트 등 시각화`
1. 단순 LLM API 호출 형태를 지양하고 **데이터 수집·정제·검색·분기·Context 구성 등 자체 데이터 파이프라인 구현을 프로젝트의 핵심 기술 요소로 강화**한다.
1. 금융 도메인은 단순한 '주식 정보 시각화'보다는 **금융시장 이해 및 투자 판단에 필요한 정보와 관계를 탐색할 수 있도록 지원하는 서비스** 방향으로 구체화한다.
1. 전체 개발에 앞서 **크롤링, 데이터셋 구축, 검색, 의도 분류/분기 등 핵심 기능에 대한 소규모 PoC를 먼저 진행**한다.
1. 최종 서비스 형태를 명확하게 하기 위해 **화면 기획 및 와이어프레임을 작성**한다.
1. 구체화한 서비스 방향과 금융 도메인 적합성은 **다음 멘토링 전에 멘토에게 사전 공유하여 피드백을 받는 방향**으로 진행한다.

다음 회의까지 가장 우선적으로 정리해야 할 부분은 **① 사용자 시나리오, ② 화면 와이어프레임, ③ 전체 데이터/AI 파이프라인, ④ 금융 도메인 차별화 포인트**이다.
특히 현재는 기술 요소를 추가하는 것보다 **"사용자가 어떤 질문을 입력하고 → 시스템이 어떤 데이터를 찾고 → 어떤 분석을 수행한 뒤 → 최종적으로 어떤 화면과 답변을 보여주는가"**를 하나의 구체적인 시나리오로 확정하는 것이 우선되어야 한다.
