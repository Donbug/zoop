    # 결제/통신/보안 관련 회의 요약본
    ## 1. 타임아웃 및 결제 처리 방식
    ### 핵심 개념
    - 결제 요청을 오래 붙잡고 있는 **블로킹 방식**은 타임아웃 문제가 발생할 수 있음
    - 특히 결제 승인 과정이 길어지거나 트래픽이 몰리면 응답 대기 중 타임아웃 발생 가능
    - 따라서 실무에서는:
      - 요청 즉시 `PENDING` 상태 응답
      - 이후 상태 업데이트 방식으로 처리하는 구조를 많이 사용함
    ### 처리 방식 비교
    ### 폴링(Polling)
    - 클라이언트가 일정 주기로 서버에 상태를 반복 조회
    - 구현은 단순하지만 요청이 많아질 수 있음
    - 예:
      - “처리 완료됐나요?”
      - “아직 안 됐나요?”
      - 반복 조회
    ### 웹훅(Webhook)
    - 요청 후 즉시 응답 반환
    - 처리 완료 시 서버가 다시 콜백 호출
    - 불필요한 반복 조회 감소 가능
    ### 결론
    - 웹훅 + 폴링을 혼합 사용하는 경우가 많음
    - 결제 프로세스에서는 상태 기반 비동기 처리 구조가 중요
    ---
    ## 2. 타임아웃 관련 정리
    ### 타임아웃 발생 원인
    - 오래 걸리는 작업을 하나의 요청에서 계속 대기
    - 과도한 데이터 처리
    - 트래픽 증가
    - 프론트와 백엔드 전체 응답 시간 누적
    ### 실무 방향
    - 서버 간 타임아웃은 짧게 설정
    - 프론트는 상태 기반으로 처리
    - 장시간 작업은 비동기 처리 후 상태 조회
    ### 흐름 예시
    1. 결제 요청
    1. 서버 즉시 응답 (`PENDING`)
    1. 실제 결제 처리 진행
    1. 완료 후 상태 변경
    1. 프론트가 상태 확인 후 UI 업데이트
    ---
    ## 3. HTTPS / TLS / SSL 정리
    ### HTTPS 동작 방식
    - 클라이언트 ↔ 서버 구간 암호화 통신
    - TLS 인증서를 사용해 안전한 통신 수행
    ### TLS 핵심
    - 서버가 인증서를 전달
    - 클라이언트가 서버 신뢰 여부 확인
    - 공개키(Public Key) 기반 암호화 수행
    ### SSL vs TLS
    - 실무에서는 혼용해서 사용
    - 현재는 TLS가 최신 개념
    - HTTPS는 TLS 기반 통신이라고 이해하면 됨
    ---
    ## 4. MSA 환경에서의 통신 구조
    ### 일반적인 구조
    - 외부(클라이언트 → API Gateway):
      - HTTPS 사용
    - 내부 서비스 간:
      - 보통 HTTP 사용
      - 내부망은 신뢰 가능한 구간으로 판단
    ### 이유
    - 내부 서비스마다 인증서 처리 시 오버헤드 증가
    - 따라서:
      - Gateway까지만 HTTPS
      - 내부는 HTTP
구조를 많이 사용
    ### 추가 보안이 필요한 경우
    - Zero Trust 구조에서는 내부도 HTTPS/mTLS 적용 가능
    ---
    ## 5. TLS / mTLS / 인증서 피닝
    ### TLS
    - 서버 인증 중심
    - 클라이언트가 서버를 신뢰하는 방식
    ### mTLS (Mutual TLS)
    - 서버와 클라이언트가 서로 인증
    - 양방향 인증 구조
    - 금융/보안 환경에서 활용
    ### 인증서 피닝(Certificate Pinning)
    - 모바일 앱에서 많이 사용
    - 앱 내부에 서버 인증서 정보를 미리 저장
    - 서버 인증서와 비교 후 통신 허용
    - 위변조 및 중간자 공격 방지 목적
    ### 특징
    - 웹에서는 구현 어려움
    - 모바일 앱에서 주로 사용
    ---
    ## 6. 개인정보 암호화 및 키 관리
    ### 추가 암호화 필요성
    - TLS만으로도 통신 구간 보호 가능
    - 하지만 주민번호/전화번호 등 민감정보는:
      - 별도 암호화(E2E 성격) 추가 가능
    ### 방식
    - 특정 키로 데이터 자체를 암호화 후 전송
    - 서버에서 동일 키로 복호화
    ### 키 관리
    - 키 유출 시 복호화 가능하므로 중요
    - 주기적 키 교체 필요
    ### AWS KMS
    - 키 관리 시스템
    - 암호화 키 생성/보관/교체 지원
    - 실무에서 많이 사용

    ## 7. 네트워크 및 포트 정리
    ### 대표 포트
    - HTTP → 80
    - HTTPS → 443
    ### HTTPS 강제 전환
    - HTTP 접속 시 HTTPS로 리다이렉트
    - 예:
      - `http://` 접속
      - → `https://` 로 자동 이동
    ### 내부/외부 네트워크
    - 퍼블릭 IP:
      - 외부 인터넷 접근 가능
    - 프라이빗 IP:
      - 내부 서버끼리만 통신 가능
    ### MSA 내부 구조
    - EC2 간 내부 통신은 프라이빗 IP 사용
    - 외부 접근은 Gateway 중심으로 처리

## 💡 **멘토님 주요 코멘트 / 피드백**
> 도메인별로 나누면 나중에 정리하기 쉬워짐
### ✅ 주제/서비스 방향성
- 결제 시스템은 단순 요청/응답 구조보다 상태 기반 비동기 처리 구조로 설계하는 것이 실무적
- 이벤트 기반 아키텍처(Event Driven Architecture)에 대한 이해 필요
- 대규모 트래픽 및 비동기 이벤트 처리를 위해 Kafka 활용 가능성 검토
- 결제 시스템은 안정성·재처리·상태 관리가 핵심 요소
### ✅ 기술 스택 관련 조언 (AI / LiDAR / 백엔드 / 프론트)
### Kafka / 메시지큐
- Kafka는 대표적인 메시지큐(Message Queue) 시스템
- 과거에는 RabbitMQ를 많이 사용했으나 현재는 Kafka 사용 비중이 높음
- Kafka는 데이터를 삭제하지 않고 저장하며 Offset 기반으로 읽기 위치를 관리
- 동일 Topic 데이터를 여러 Consumer Group이 독립적으로 소비 가능
- AWS 환경에서는 MSK 사용 가능하지만 비용 부담 존재
- 프로젝트 단계에서는 Docker 기반 Kafka 구축도 충분히 가능
### Docker / Jenkins / ECR
- Jenkins는 GCP VM 위에 Docker 기반으로 설치 가능
- Jenkins 자체도 컨테이너로 운영 가능
- Docker Hub뿐 아니라 AWS ECR 사용 경험도 중요
- CI/CD 환경 구성 경험 자체가 중요하다는 피드백
### 보안 / 인증
- HTTPS는 TLS 기반 암호화 통신 구조로 이해
- 실무에서는 SSL/TLS 용어를 혼용하지만 현재는 TLS가 최신 개념
- 모바일 환경에서는 인증서 피닝(Certificate Pinning)을 많이 사용
- 금융 서비스 수준 보안에서는 mTLS 및 추가 데이터 암호화 고려 가능
### ✅ 시스템 구조 / 아키텍처 피드백
### 결제 처리 구조
- 결제 승인 과정을 하나의 요청에서 오래 대기하는 블로킹 구조는 타임아웃 위험 존재
- 따라서:
  1. 요청 즉시 `PENDING` 상태 반환
  1. 실제 처리 진행
  1. 완료 후 상태 업데이트
구조를 많이 사용
### Polling / Webhook
- Polling:
  - 클라이언트가 반복적으로 상태 조회
  - 구현은 단순하지만 요청 수 증가 가능
- Webhook:
  - 처리 완료 시 서버가 콜백 전달
  - 불필요한 조회 감소 가능
- 실무에서는 Polling + Webhook 혼합 구조 사용 사례 많음
### Kafka 구조
- Kafka 내부에는 여러 Topic 존재
- Topic 안에 데이터가 계속 적재되는 구조
- Consumer는 Group ID 기준으로 메시지를 읽음
- Offset을 통해 어디까지 읽었는지 관리
- 동일 Topic이라도 Group ID가 다르면 처음부터 독립적으로 소비 가능
### Partition 구조
- Partition은 병렬 처리 단위
- 같은 Group ID 내에서는 하나의 Partition을 동시에 하나의 Consumer만 처리 가능
- Partition 수보다 Consumer 수가 많으면 일부 서버는 유휴 상태 발생 가능
- Partition과 Consumer 수 설계가 성능 및 확장성에 영향
### MSA 네트워크 구조
- 외부(Client → Gateway)는 HTTPS 사용
- 내부 서비스 간 통신은 HTTP 사용하는 경우 많음
- 내부망은 신뢰 가능한 네트워크로 판단하는 경우가 많기 때문
- Zero Trust 환경에서는 내부도 HTTPS/mTLS 적용 가능
### ✅ 일정 / 스프린트 관리
- 우선순위를 정해서 핵심 인프라 기술부터 단계적으로 학습 필요
- 실제 서비스 수준보다는 “구조를 이해하고 구현해보는 경험” 자체가 중요
- 초기에는 Docker 기반 로컬 환경 구축 후 점진적으로 클라우드 확장 권장
### ✅ 리스크 요소 및 주의점
### 비동기 처리 리스크
- 비동기 구조에서는 일반적인 트랜잭션 롤백이 어려움
- 실패 시 보상 트랜잭션(Compensation Transaction) 설계 필요
### Kafka 운영 리스크
- Partition 수를 과도하게 늘리면 운영 복잡도 증가 가능
- MSK 사용 시 비용 부담 존재
### 보안 리스크
- TLS만으로는 민감정보 자체 보호가 부족할 수 있음
- 주민번호/전화번호 등은 별도 암호화 고려 가능
- 키 유출 시 복호화 가능하므로 키 관리 중요
- AWS KMS 등을 활용한 키 관리 필요
### 타임아웃 리스크
- 장시간 블로킹 요청은 타임아웃 발생 가능
- 상태 기반 비동기 처리 구조 필요
