# ZOOP AI 거버넌스 정책

문서 ID: ZOOP-AIG-001

버전: 0.8

작성일: 2026년 10월 13일

개정일: 2026년 10월 21일

적용 대상: ZOOP 금융 이슈·기업 관계 탐색 서비스

문서 책임 역할: 프로젝트 책임자

시행 조건: 팀 검토와 책임자 승인 후 적용

## 1 목적과 적용 범위

ZOOP은 뉴스·공시에서 시장 이슈와 기업 간 관계를 추출하고, 이를 관계 그래프·브리핑·근거 기반 답변으로 제공한다. 본 정책은 AI가 사용하는 데이터, 결과의 공개 조건, 사용자 질의의 처리 방법, 검증과 사고 대응 책임을 정의한다. 개발자와 운영자는 기능 구현 및 출시 판단에 이 정책을 사용한다.

챗봇은 사용자의 질문을 유형별로 분류하고, 해당 유형에 허용된 데이터와 도구를 사용하여 정해진 형식으로 답한다. 분류 결과만으로 응답을 확정하지 않는다. 사용자 권한, 대상 기업, 질문의 기간, 근거의 유효성, 출력 검증 결과를 함께 확인한다.

적용 범위는 데이터 수집과 정제, AI 사건·관계 추출, 자동 검증, 관리자 검수, 공개 버전 관리, 브리핑 생성, 챗봇, 모델과 프롬프트 변경, 로그 및 외부 모델 API 운영이다. 그래프와 브리핑에서 AI 결과를 보여주는 화면도 포함한다.

이 문서의 규정은 구현·운영 시 충족해야 할 목표다. 규정의 존재를 구현 완료나 검증 통과의 증거로 사용하지 않는다. 챗봇의 초기 모델 역할·임계값·실행 상한은 6.3.3절의 설계 결정값을 사용한다. 담당자 실명, 정확한 배포 모델 버전, 보관 기간 및 외부 서비스 처리 조건처럼 실제 조직·계약 정보가 필요한 항목은 16장의 결정 기록에 따라 출시 전에 승인한다. 법령 준수나 금융업 관련 인허가 여부를 이 문서의 승인만으로 판정하지 않는다.

### 1.1 관련 계약의 적용

공개 API의 경로·필드·상태·오류는 [목표 OpenAPI](api/openapi.yaml), 현행 기능의 의미와 이행 기준은 [문서 연결 기준](system/links.yaml), 저장 제약은 [ERD v6](erd/zoop-core-erd-v6.md)를 따른다. ERD 변경 이력에서는 2026년 10월 13일의 ‘후보 allow 접수와 실행 분리’ 추가 변경을 적용한다. AI 내부 실행·검증·복구는 [AI 실행 계약](design/ai-system.md)과 [내부 HTTP 계약](api/internal-ai-openapi.yaml)을 따른다. 목표 설계, 현재 구현 관측, 팀 승인 여부는 각각 구분한다.

Q01~Q08은 이 문서가 제안하는 내부 질의 분류다. 기존 API 필드나 enum을 대체하지 않는다. 공개 계약의 확장이 필요한 복합 응답은 별도 변경과 검증을 거쳐야 한다. 본 정책과 관련 계약의 충돌이 발견되면 한쪽을 구현자가 임의로 덮어쓰지 않고 변경 기록과 담당자 검토를 남긴다.

## 2 서비스의 AI 활용 원칙

### 2.1 정보 제공 범위

ZOOP은 확인 가능한 자료를 설명하고 탐색을 돕는다. 기업·사건의 연결, 뉴스·공시의 핵심 내용, 특정 회차의 변화와 근거를 제공한다. 보유·관심 종목은 관련 정보를 찾는 필터로 사용한다.

개인의 자산 상황에 맞춘 매수·매도·비중 조정, 목표 수익률, 수익 보장, 확정적인 주가 예측, 주문 실행은 본 서비스의 허용 범위에 포함하지 않는다. 이는 ZOOP의 제품 운영 범위이며, 특정 법적 분류를 확정하는 문구가 아니다. 질문에 이러한 요청과 정보 탐색이 함께 있으면 투자 판단 부분의 한계를 알리고, 분리 가능한 사실 설명은 제공할 수 있다.

### 2.2 근거와 불확실성

기업·사건·수치에 관한 사실 주장에는 해당 주장을 뒷받침하는 근거를 연결한다. 출처가 있다는 사실만으로 내용을 확정하지 않는다. 보도에만 있는 주장은 보도 내용으로 표현하고, 추정·전망은 그 성격을 유지한다. 공시도 정정 여부와 효력 시점을 확인한다.

검색 결과가 없으면 ‘현재 조회 범위에서 확인되지 않음’으로 답한다. 이를 ‘사건이 없음’이나 ‘두 기업의 관계가 없음’으로 바꾸지 않는다. 모델의 내부 지식으로 최신 사건, 현재 가격, 공시 수치 또는 누락된 출처를 보충하지 않는다.

### 2.3 통제의 실행 위치

프롬프트에는 설명과 답변 규칙을 두고, 인증·인가·공개 상태 확인·도구 허용 목록·쿼리 범위·타임아웃은 서버 코드로 강제한다. 모델이 제시한 사용자 ID, 권한 또는 검수 상태를 신뢰하지 않는다. 사용자 입력과 수집 문서에 있는 명령은 정책이나 시스템 지시로 승격하지 않는다.

## 3 역할과 책임

소규모 팀에서는 역할을 겸임할 수 있다. 다만 고위험 변경이나 중대 사고 후 재개는 변경 수행자 외에 한 명 이상의 검토를 남긴다. 아래 역할에 실명을 배정하기 전에는 운영 승인 책임이 충족된 것으로 처리하지 않는다.

| 프로젝트 책임자       | AI 사용 범위, 정책 예외, 출시·재개 결정         | 정책 버전과 승인 기록             |
| AI 담당자             | 질의 분류, 추출·생성, 모델·프롬프트 관리        | 변경 내역, 평가 결과, 롤백 대상   |

## 4 전체 파이프라인과 공개 경계

### 4.1 데이터 생성과 공개

처리 순서는 다음과 같다.

1. 승인된 뉴스·공시 출처에서 데이터를 수집하고 출처 및 시각을 기록한다.
2. 정제·중복 제거·기업 식별을 수행하고 원문과 처리 결과를 연결한다.
3. AI가 사건·관계·요약 후보를 생성한다. 후보는 비공개 상태로 저장한다.
4. 자동 검증이 통과·보류·실패를 구분한다.
5. 보류 항목은 관리자 허용 결정 후 재검증한다. 데이터 결함의 수정·재수집은 기존 산출물을 덮어쓰지 않는 별도 버전·작업으로 처리한다. 챗봇 검증 실패의 재생성 금지는 7.4절을 따른다.
6. RDS 문서·벡터와 Neo4j 그래프 등 조회 자원의 준비 상태를 확인한다.
7. 모든 필수 자원이 같은 버전을 조회할 수 있을 때 공통 공개 버전을 전환한다.
8. 브리핑과 챗봇은 공개 버전을 지정하여 조회한다.

정상 결과는 자동 검증과 조회 준비 확인 후 공개할 수 있다. 모든 결과를 사람이 선검수하는 방식은 기본 조건으로 두지 않는다. 대신 위험 조건에 따른 보류와 공개 결과의 표본 검수를 운영한다.

위 순서는 개념상의 처리 단계이며 단일 DB/API 상태 enum이 아니다. `보류 → 관리자 허용 → 재검증 접수 → 실행 → 검증 결과`는 별도 경로다. 검수 결정은 `allow / reject`이며, `allow` 응답은 `revalidation_requested`와 작업 ID를 반환한다. 결정 요청 자체는 `publicChanged=false`이고, 재검증과 조회 준비를 통과해야 공개할 수 있다. 실패·반려·철회 결과는 공개 조회 대상에서 제외한다.

### 4.2 클라우드 구성과 책임의 연결

제공된 클라우드 설계에 따라 EC2-1은 API·인증·관리자 기능, EC2-2는 AI·수집·배치·검증, EC2-3은 Neo4j를 담당한다. Neo4j는 AI 파이프라인의 관계 투영·검증 저장소이며, 사용자에게 공개되는 그래프는 handoff로 수입·활성화한 앱의 불변 스냅샷(`graph_versions`)이다. 공개 그래프 API와 챗봇은 Neo4j를 직접 읽지 않는다. RDS PostgreSQL과 pgvector는 문서·계정·검수·작업·공개 버전 관련 데이터를, 비공개 S3는 원문과 산출물을 보관하는 위치로 사용한다. 세부 필드와 물리 저장 위치는 구현 명세에서 확정한다.

EC2-1은 인증된 사용자 범위와 공개 버전을 EC2-2의 작업 요청에 전달한다. EC2-2는 요청이 내부 서버에서 왔다는 이유만으로 권한 검증을 생략하지 않는다. 외부 LLM 호출에는 10장에서 허용한 최소 데이터만 전달한다. 비밀값은 Secrets Manager 등 승인된 저장소에서 관리한다.

RDS와 Neo4j를 하나의 트랜잭션으로 갱신할 수 있다고 가정하지 않는다. 먼저 새 버전의 조회 자원을 준비하고, 준비 완료 기록을 확인한 후 활성 버전 포인터를 전환한다. 요청 시작 시 버전을 고정하고 응답 종료까지 사용한다. 일부 자원만 갱신되거나 전환에 실패하면 기존 공개 버전을 유지한다.

오류가 확인되어 철회된 근거는 과거 버전에 포함되더라도 새 답변에 사용하지 못하도록 별도의 철회 목록을 적용한다. 과거 기록의 보존과 사용자에 대한 재노출 허용은 서로 구분한다.

## 5 데이터 수집과 AI 추출 정책

### 5.1 출처 등록과 보관

데이터 담당자는 출처별로 제공자, API 또는 URL, 수집 항목, 이용·저장·재배포 조건, 외부 모델 전송 가능 여부, 갱신 주기, 정정 처리 방식, 담당자를 등록한다. 원문 전체 보관이나 외부 LLM 전송은 해당 이용 조건에 맞는 범위에서만 수행한다. 조건이 미확인인 출처는 공개 파이프라인에 투입하지 않는다.

원문에는 `source_id`, `document_id`, 원문 주소, 수집 시각, 원문 게시·수정 시각, 내용 해시, 언어, 이용 조건 식별자를 기록한다. 사건 발생 시각은 별도로 관리한다. 사건 시각을 모르면 ‘미상’으로 저장하고 수집 시각이나 게시 시각으로 대체하지 않는다.

같은 기사를 전재한 여러 매체와 같은 원문의 반복 수집은 중복 그룹으로 묶는다. 중복 문서 수를 독립 근거 수처럼 표시하지 않는다. 원문을 수정해서 덮어쓰기보다 수정본과 원본의 연결 및 변경 시각을 남긴다.

### 5.2 사건과 관계 추출

추출 결과는 정해진 구조를 따른다. 최소 항목은 사건 ID, 기업 ID, 관계 유형, 관계 방향, 근거 문서 ID와 근거 구간, 사건·유효 시각, 추출 모델 및 프롬프트 버전, 검증 상태다. 원문에 없는 관계를 매끄러운 설명을 위해 추가하지 않는다.

기업이 같은 기사나 사건에 등장했다는 사실은 공급·투자·계열 관계를 뜻하지 않는다. 공동 등장과 직접 관계를 별도 유형으로 저장한다. 여러 간선을 통과한 연결은 간접 경로로 설명하고 직접 계약 관계처럼 표현하지 않는다. 동명이인 기업, 약칭, 동일 티커 등 식별이 모호한 경우 보류한다.

### 5.3 자동 검증과 보류

| 검증 항목     | 통과 조건                                      | 실패 또는 보류 처리                  |
| ------------- | ---------------------------------------------- | ------------------------------------ |
| 구조와 식별자 | 필수 필드, 자료형, 기업·문서 ID 유효           | 구조 오류는 실패, 식별 모호성은 보류 |
| 근거 연결     | 원문에 접근 가능하고 주장에 대응하는 구간 존재 | 누락·무관한 인용은 공개 차단         |
| 사실과 표현   | 주체·대상·방향·부정·전망 여부가 원문과 일치    | 충돌·해석 불확실성은 보류            |
| 수치와 시점   | 단위·통화·기준일·비교 기간이 원문과 일치       | 불일치 항목을 수정하고 재검증        |
| 중복과 정정   | 중복 그룹 및 최신 정정 관계 반영               | 중복은 병합, 정정 영향은 재처리      |
| 콘텐츠 보안   | 문서 속 명령이 실행되지 않고 비밀값이 배제됨   | 의심 문서 격리 및 담당자 검토        |
| 조회 준비     | 동일 공개 버전의 문서·벡터·그래프 조회 가능    | 기존 버전 유지                       |

LLM을 검증에 사용하더라도 동일 모델의 자기평가만으로 통과시키지 않는다. 구조 검사, 원문 구간 대조, 단위·수치 검사, 참조 무결성 검사와 필요한 사람 검수를 함께 사용한다. 근거 문서가 여러 개라는 이유만으로 통과시키지 않는다. 하나의 명확한 공식 근거가 여러 중복 기사보다 충분할 수 있다.

검수 담당자는 허용·반려와 이유를 기록한다. 요청의 `expectedRevision`을 해당 대상의 현재 revision과 비교하여 오래된 화면에서 내린 결정을 거절한다. `allow`는 고정 후보의 재검증 요청이며 후보 본문을 수정하는 기능이 아니다. 수정이 필요하면 데이터 담당자가 별도 버전·후보 생성 경로와 이력을 정의하고 적용한다. 근거를 찾지 못한 항목을 설명만 고쳐 허용하지 않는다. 새 출처, 변경 모델, 정정 사건은 우선 표본 검수하며 비율과 주기는 출시 전에 결정한다.

### 5.4 관리자 재검증 큐

ERD v6의 최신 규칙에 따라 관리자 작업은 여러 `queued`를 접수하고 `scope=admin`의 `running`은 하나로 제한한다. 허용 결정·재검증 대기 작업·감사·멱등성 완료 기록을 같은 트랜잭션으로 저장한다. 다른 작업이 실행 중이라는 이유로 접수한 결정을 롤백하거나 결정 API에 `JOB_IN_PROGRESS`를 추가하지 않는다.

worker가 `requested_at/id` 순서와 실행 토큰·임대를 확인하여 실행권을 얻는다. `JobList.active`와 `JobLock`은 실행 중인 작업 기준이며 대기 작업만 있으면 `active=null`, `locked=false`, `jobId=null`이다. 허용된 재시도 역시 대기로 접수한다. 관리자 큐 규칙을 채팅에 적용하지 않는다. 채팅은 대화당 `queued/running` 작업 하나를 유지하며, 브리핑은 별도의 회차·시도 제약을 따른다.

### 5.5 문서 요약과 긍부정 판정

`DocumentSentiment`는 문서×기업 판정이고 `BriefingOutlook`은 발행 회차 판정이다. 라벨은 `positive / negative / mixed / undetermined`로 유지한다. `null`은 유효한 판정 산출물이 없다는 뜻이고, `undetermined`는 평가했으나 방향 근거가 부족하다는 뜻이다. 외부 호출 실패를 `undetermined`로 바꾸지 않는다. 확률·점수나 투자 수익률로 확장하지 않으며 이유·인용·판정 시각·모델·프롬프트 버전을 보존한다.

문서 요약과 기업별 판정은 독립 작업이다. 각 `analysisStatus`는 `not_requested / pending / failed / withheld / available`로 구분하고, 요약이 보류·실패했다는 이유만으로 유효한 기업별 판정을 지우지 않는다. Q03·Q06·Q08이 이 결과를 설명할 때도 대상 단위와 원래 라벨을 보존한다.

S1 문서 공개는 구조·정확 인용 검사와 생성기에서 분리된 의미 검증을 요구한다. 공개 사실·해석·제한 문장을 versioned claim/citation에 연결하고 의미 검증의 `supported / contradicted / insufficient` 판정을 적용한다. 인용 좌표는 고정 문서·텍스트 버전의 Unicode code point 기준 `[start,end)`이며 검증 시 임의 정규화하지 않는다. 의미 검증의 HOLD/REJECT 산출물은 내부에 보존하고 공개 응답은 사유와 null을 반환한다.

기존 회차 outlook의 `legacy-outlook-exact-1` 검증과 `validation.semantic=null`은 별도 의미 검증을 마친 문서와 구분한다. 이를 동일한 검증 수준으로 표시하지 않는다. 빈 회차는 모델 호출 없이 outlook을 null로 두고, 발행된 회차는 null을 포함하여 판정 결과를 고정한다.

## 6 챗봇의 질의 분류 정책

### 6.1 분류 구조

질의 분류는 ‘사용자가 알고 싶은 내용’을 식별한다. 정상 질의 유형과 처리 상태를 분리하여 저장한다. 예를 들어 관계 탐색 질문이라도 기업명이 불분명하면 처리 상태는 확인 질문이 된다. 정보가 없다는 이유로 서비스 안내 유형으로 바꾸지 않는다.

모든 챗봇 질문은 회원 전용이다. Q01~Q08의 유형과 관계없이 접수 전에 회원 세션과 대화 소유권을 확인한다. 비회원은 공개 그래프·기업·브리핑을 조회할 수 있지만 챗봇 질문은 할 수 없다. 개인 종목 조회에는 이 공통 조건 외에 본인 데이터 범위 검사를 추가한다.

정상 질의 유형은 다음 8개로 제안한다. 유형 ID는 내부 라우터·프롬프트·평가 세트·감사 기록에서 일관되게 사용한다. 공개 응답에 `intent` 등의 필드를 임의 추가하지 않는다.

| ID와 유형                  | 질문 예시                              | 허용 데이터와 도구                                                                                   | 답변의 필수 구성                                                   |

Q02는 최신 금융 상황을 일반 지식으로 답하기 위한 우회 경로가 아니다. 현재 기업·가격·사건에 관한 주장은 Q03 등의 공개 데이터 조회를 요구한다. Q08은 모델의 내부 사고 과정이 아니라 기록된 근거와 규칙을 설명한다. 기록되지 않은 선정 이유는 생성하지 않는다.

#### Q02 일반 개념 답변과 범용 용어 사전 미구축 원칙

현재 ERD와 마이그레이션에는 범용 금융·산업 용어 사전, 개념 지식 청크 또는 임베딩 전용 저장 구조가 없다. `articles`와 `article_versions`는 뉴스·공시를 대상으로 하며 이를 범용 개념 지식 저장소가 이미 존재하는 것처럼 사용하지 않는다. ZOOP은 MVP 및 현재 목표 설계에서 범용 용어 사전을 런타임 선행 조건이나 fallback으로 구축하지 않는다. 일반 금융·산업 개념은 다음 조건을 모두 만족할 때 일반 LLM으로 설명한다.

- 현재 기업 상태, 가격, 공시, 시장 점유율, 최신 표준, 전망 또는 투자 판단을 포함하지 않는다.
- 답변을 ‘공개 근거로 검증된 사실 답변’으로 표시하지 않고 일반 개념 설명임을 구분한다.
- 생성 모델과 별도의 호출을 포함한 모델 교차검토는 정책·관련성·내부 모순 탐지에 사용할 수 있으나, 비교할 권위 자료가 없으면 사실 검증 통과로 기록하지 않는다.
- 여러 의미가 가능한 약어·용어는 임의 확정하지 않고 `clarification`으로 처리한다.
- 안정적 개념 범위를 벗어나거나 안전한 설명을 만들 수 없으면 Q03~Q08의 근거 조회로 재분류하거나 지원 범위를 안내한다. 존재하지 않는 범용 용어 사전 검색을 시도하거나 `insufficient_evidence`를 가장하지 않는다.
- 미지원·미식별 용어는 가명화된 빈도와 실패 유형을 품질 개선 자료로 집계할 수 있으나, 모델이 만든 정의를 자동 지식으로 등록하지 않는다.

위 조건을 통과한 일반 개념 설명은 `answered`의 `general_knowledge` 구간(`ChatResult.sections`)으로 저장할 수 있으며, 그 구간에는 존재하지 않는 출처를 만들지 않고 근거를 연결하지 않는다. 일반 개념만 답한 결과의 `sources`와 `citations`는 빈 배열이다. 범위·정책·일관성 검사에 실패하면 `validation_failed`로 처리하며, 이를 근거 부족 성공 응답으로 바꾸지 않는다.

범용 용어 사전을 없애는 결정은 ZOOP 고유 정책·화면 명세·도움말까지 제거한다는 뜻이 아니다. ‘중요 이슈’, ‘직접 관계’, ‘내 종목’, 선정 규칙처럼 서비스가 정의한 개념은 승인된 ZOOP 정책·서비스 명세를 조회한다. 이 문서는 일반 금융 용어의 백과사전이 아니라 서비스 동작의 권위 자료이며, 문서 ID·버전·승인 상태를 기록한다. 해당 문서가 없거나 철회되었으면 일반 LLM이 ZOOP 내부 규칙을 만들어내지 않고 `guidance` 또는 실제 장애 상태로 종료한다.

### 6.2 작업 상태와 답변 결과

공개 `ChatJob.status`는 `queued / running / completed / failed / cancelled`를 사용한다. `ChatJob.outcome`은 결과가 없으면 null이고, 저장된 `ChatResult.outcome`은 `answered / clarification / guidance / insufficient_evidence` 중 하나다. 질의 유형, 작업 상태, 답변 결과와 HTTP 오류를 서로 대체하지 않는다.

| 상황                          | 현재 계약의 처리                                                     | 사용자 응답 또는 동작                     |
| ----------------------------- | -------------------------------------------------------------------- | ----------------------------------------- |
| 근거와 검증 조건 충족         | 저장 후 completed, outcome=answered                                  | 유형별 답변 제공                          |
| 기업·기간·대상 모호           | 확인 질문 저장 후 completed, outcome=clarification                   | 필요한 조건 확인, 선택지는 choices 사용   |
| 복합 요청이 예산을 초과하거나 기준이 양립 불가 | MCP 호출 전 completed, outcome=clarification                 | 우선할 범위·기간·대상을 선택하도록 안내   |
| 조회 결과가 체크포인트의 개수 조건을 넘음 | 다음 단계 호출·답변 생성 전 completed, outcome=clarification | 실제 조회된 대상으로 만든 choices에서 선택 |
| 허용 답변과 금지된 투자 판단 요청이 함께 있음 | 허용 부분이 완결되면 completed, outcome=answered              | 허용 답변과 `limitations`의 `investment_advice` 항목 |
| 조건 부족 또는 지원 범위 안내 | 안내 저장 후 completed, outcome=guidance                             | reason과 필요한 action으로 다음 행동 안내 |
| 조회 성공 후에도 근거 부족    | 안내 저장 후 completed, outcome=insufficient_evidence                | 조회 범위와 부족한 부분 설명              |
| 유효 세션 없음                | HTTP 401 AUTH_REQUIRED, 질문 미접수                                  | 로그인 안내                               |
| 비회원 세션의 질문            | HTTP 403 MEMBER_REQUIRED, 질문 미접수                                | 회원 로그인 안내                          |
| 소유권·접근 권한 위반         | 접수·조회 API의 접근 오류 또는 실행 중 ChatFailure.permission_denied | 정보 조회·노출 중단                       |
| 검증 실패 또는 기술 장애      | 해당 API 오류 또는 failed와 ChatFailure                              | 원인과 허용된 복구 방법 표시              |

위 상황은 기존 계약을 설명하는 분류이며 새 enum을 정의하지 않는다. 투자 판단 요청은 제한 이유와 지원 범위를 안내하고, 분리 가능한 허용 요구를 완결된 형태로 답할 수 있으면 `answered`로 저장하되 제한된 요구와 이유를 `limitations`에 기록한다. 이는 실행 도중 일부가 누락·실패한 `PARTIAL`을 뜻하지 않는다. 허용된 필수 요구를 예산·모호성·도구 부재 때문에 수행하지 못하면 완료 답변으로 가장하지 않고 답변 생성 전(계획 시점 또는 6.3.4절의 선언된 체크포인트) `clarification` 또는 실제 상태에 맞는 `guidance`를 사용한다. 복합 질문의 부분 실행 결과를 표현하는 별도 `PARTIAL` outcome은 현재 계약에 없다. 하위 결과·버전 등을 구조화하여 제공하려면 공개 계약을 먼저 확장하고 검증한다. 근거 부족과 장애를 구분하고, 외부 API 실패를 ‘관련 뉴스 없음’으로 표현하지 않는다.

`answered` 결과에서 답하지 않은 요구는 공개 `ChatResult.limitations`의 항목(`kind`, `label`, `message`)으로 기록한다. `kind`는 `investment_advice`(투자 판단), `precondition_unmet`(6.3.4절 체크포인트 미달), `results_truncated`(조회 상한 도달), `evidence_insufficient`(조회는 성공했으나 해당 요구의 근거 부족), `out_of_scope`(지원하지 않는 하위 요구) 중 하나다.

- 제한 여부는 서버가 결정한다. 투자 판단 gate, 체크포인트 판정, 도구 결과의 `truncated`, 해당 요구의 유효 citation 부재가 근거이며 모델이 스스로 요구를 제한으로 돌릴 수 없다. `message`는 `kind`별 서버 템플릿으로 만든다.
- 출력 검증은 모든 필수 요구가 본문에서 근거와 함께 답한 요구와 `limitations` 항목 중 정확히 하나에 속하는지 검사하고, 어느 쪽에도 없거나 본문이 제한된 요구를 답한 것처럼 쓰면 `validation_failed`로 종료한다.
- `limitations`는 정상 실행에서 나온 결정만 담는다. 도구 timeout·장애·권한 오류는 limitation이 아니라 `failed`와 `ChatFailure`이며, 이 구분으로 `PARTIAL`을 만들지 않는다.
- `limitations`는 `answered`에서만 비어 있지 않을 수 있다. 답한 요구가 하나도 없으면 `answered`가 아니며 전체 이유는 `reason`에 둔다(금지된 투자 판단만 → `guidance`, 모든 요구 근거 부족 → `insufficient_evidence`).

### 6.3 분류와 실행 순서

1. 서버가 모든 유형에 회원 자격·대화 소유권·Origin/CSRF를 검사하고, 멱등성 및 대화당 활성 작업 하나를 확인한다. 최초 접수 시 질문·문맥·대상·기간·asOf·graphVersion과 접수 시각을 고정한다. 요청 추적 ID와 질문 작업 ID는 구분한다.
2. 입력 크기를 제한하고 외부 전송 전 불필요한 개인정보·비밀값을 제거한다. 명백한 권한 우회·비밀정보 요청을 점검한다.
3. 질문을 독립적인 하위 질문으로 나누고 기업, 기간, 회차, 최신성 및 개인화 필요 여부를 구조화한다. 분류 단계에서는 개인 데이터나 업무 DB를 조회하지 않는다.
4. 챗봇 라우터용 TypeSafe Jev가 정제된 질문과 고정된 Q01~Q08 정의를 받아 각 유형의 해당 여부를 typed 판정으로 반환한다. 초기 계약은 유형별 독립 Noul 질문과 확률을 사용한다. 이어서 버전이 고정된 논리 기능 목록에서 질문 해결에 필요한 기능 후보를 typed 판정으로 반환하며, 자유 문자열 유형이나 실제 MCP 도구명·인자를 생성하게 하지 않는다.
5. 서버는 사용자가 명시한 하위 요구를 필수 요구로 고정하고, 승인된 임계값을 통과한 Q 유형과 논리 기능을 후보 계획으로 만든다. 유형 수를 세 개로 자르거나 확률 순위만으로 명시적 요구를 제거하지 않는다.
6. 답변 생성 호출과 분리된 Luna 커버리지 검증 stage가 원문 질문, 구조화된 하위 요구, Jev의 Q 유형·기능 후보와 확률, 후보 도구 계획을 입력받아 `coveredRequirements`, `missingRequirements`, `unnecessaryCapabilities`, `requiresClarification`을 정해진 스키마로 반환한다. 초기 구현은 승인된 같은 Luna 배포를 사용하되 별도 프롬프트·JSON Schema·source grant·호출 영수증으로 분리한다. 이 결과는 계획 보완·축소·확인 요청의 신호이며 직접 실행 권한이 아니다.
7. 서버가 커버리지 검증 결과와 결정론적 규칙을 결합하여 최종 도구 계획을 확정한다. 앞 단계 결과가 다음 단계 입력인 계획은 단계(stage)와 6.3.4절의 체크포인트로 선언한다. 모호한 지시어·기업·기간 때문에 서로 다른 실행 결과가 가능하고 조회 없이 회원이 답할 수 있으면 MCP 호출 전에 `clarification`을 반환한다. 검증 LLM이 허용 목록 밖 기능을 추가하거나 명시적 요구를 근거 없이 제거하지 못하게 한다.
8. 서버는 선택된 논리 기능을 승인된 읽기 전용 MCP 도구로 매핑한다. Jev와 검증 LLM은 MCP를 직접 호출하지 않는다. 서버가 도구 레지스트리, 입력 스키마, 권한, 공개 상태, 중복, 조회량, 전체 호출 수·시간·비용 예산을 검사한 뒤 실제 호출을 승인한다.
9. 승인된 MCP 조회를 필요한 만큼 수행하고 기업 ID, 기간, 회차, graphVersion, evidenceId 같은 구조화된 `BranchContext`를 만든다. 서로 독립적인 조회는 병렬화할 수 있으며, 단계가 끝날 때마다 서버가 선언된 체크포인트를 평가한다. 1차 결과가 필수 요구를 충족하지 못할 때만 승인된 범위에서 보충 라운드를 실행한다. Q07의 본인 범위와 공통 인증·보안 검사는 모델 선택으로 제거할 수 없는 필수 gate다.
10. 유형별 `BranchContext`를 Luna 답변 생성 stage에 전달한다. Luna는 제공된 도구 결과와 허용된 일반 지식 범위 안에서 하위 답변을 만들고, 서로 다른 버전·대상을 하나로 숨겨 합치지 않는다.
11. 근거·수치·정책·개인정보·응답 구조를 결정론적으로 검사하고, 통과한 경우에만 근거 구간의 claim에 생성과 분리된 Jev 의미 검증을 수행한다(6.3.3절). 검증된 결과를 내구 저장한 뒤 completed로 전환하며 상태 조회와 결과 회수 시에도 회원·소유권·현재 근거 접근 권한을 재검증한다.

키워드 규칙은 명백한 표현과 범위를 식별하는 보조 수단이고, Jev는 Q01~Q08 다중 분류와 논리 기능 선택 신호를 제공한다. Jev의 확률·confidence와 검증 LLM의 동의는 정답률 보증이 아니며 운영 임계값은 고정 평가 세트로 보정한다. 최종 실행 권한과 MCP 호출 여부는 서버 정책이 결정한다. 요구 분해·Jev 판정·커버리지 검증·도구 매핑·MCP 호출·Luna 생성·후검증은 각각 버전과 영수증을 남긴다.

#### 6.3.1 Q 유형과 MCP 도구 계획

아래 이름은 목표 논리 도구 ID다. 실제 MCP 서버·도구가 등록되기 전에는 구현 완료로 표시하지 않으며, 등록 시 입력·출력 스키마와 읽기 전용 권한을 별도 승인한다.

| Q 유형 | 허용할 논리 MCP 도구 계획 | Luna에 전달할 최소 결과 |
| ------ | ------------------------- | ------------------------ |
| Q01 | `help.search`, `screenSpec.read`, `zoopPolicy.read` | 도움말·화면·정책 문서 ID와 버전 |
| Q02 | 일반 개념에는 MCP 없음. ZOOP 고유 개념만 `zoopPolicy.read` | 일반 개념 범위 또는 승인된 내부 문서 버전 |
| Q03 | `document.search`, `company.read`, `issue.read`, `evidence.resolve` | 기업·사건·기간·공개 문서·근거 ID |
| Q04 | `graph.path.read`, `evidence.resolve` | 고정 graphVersion, 직접·간접 경로와 간선별 근거 |
| Q05 | `graph.version.diff`, `period.compare` | 비교 기간·버전·신규·유지·제외 집합 |
| Q06 | `briefing.read`, `briefing.evidence` | 발행 회차·dataAsOf·포함 이슈·근거 |
| Q07 | `portfolio.scope.read` 후 선택된 공개 조회 도구 | 서버가 확인한 본인 종목 ID와 공개 결과 |
| Q08 | `selectionRule.read`, `evidence.resolve` | 실제 적용 규칙 revision·입력 요인·공개 근거 |

한 하위 질문이 여러 유형에 해당할 수 있으며 Q01~Q08은 배타적인 단일 enum이 아니라 실행 능력 태그로 사용한다. Jev는 Q 유형과 허용된 논리 기능을 독립 판정하고, 커버리지 검증 LLM은 사용자의 모든 명시적 하위 요구가 후보 계획에 포함됐는지 확인한다. 유형이나 기능 개수에 고정 상한을 적용하지 않되 동일 목적의 중복 도구는 제거하고, 전체 호출 수·시간·비용·문서 수·그래프 경로 길이는 서버 예산으로 제한한다. 보안·권한·개인정보·투자 판단 제한은 분류 후보가 아니며 항상 실행되는 결정론적 gate다.

#### 6.3.2 현재 구현과 목표 설계의 경계

현재 저장소의 네이티브 Jev 어댑터는 S1 `semantic-verification`에서 고정 claim을 `supported / contradicted / insufficient`로 판정하는 용도다. 현재 구현은 챗봇 Q01~Q08 라우팅, MCP 도구 선택·호출, Luna 챗봇 답변 생성을 제공하지 않는다. 본 절의 라우터는 별도 stage·요청 계약·모델 목적·source grant·호출 예산·평가 세트가 필요한 목표 설계다.

기존 S1 검증용 Jev 요청·임계값·영수증을 라우터에 그대로 재사용하지 않는다. 라우팅 Jev와 후검증 Jev를 모두 사용하더라도 `router`와 `semantic-verification`의 질문 집합, 정책 버전, 수신 목적, 비용과 실패 상태를 분리한다. MCP 도구 호출 결과는 Luna에 전달하기 전에 서버가 스키마·권한·버전·공개 상태를 검증한다.

#### 6.3.3 초기 구현 결정값

다음 값은 v0.7의 초기 구현 기본값과 v0.8의 단계·체크포인트 규칙이다. 임의의 런타임 환경 변수로 조용히 바꾸지 않고 11장의 고정 평가 세트와 12장의 변경 절차를 거쳐 버전을 올린다.

**Jev 선택 기준**

- 사용자가 명시적으로 요구한 유형·기능은 결정론적 요구 분해기가 `required=true`로 고정하며 Jev 확률로 제거하지 않는다.
- Noul 확률 `p >= 0.70`은 자동 선택 후보로 포함한다.
- `0.35 <= p < 0.70`은 검토 후보로 Luna 커버리지 검증에 전달한다.
- `p < 0.35`는 기본 제외하되 명시적 필수 요구이거나 커버리지 검증이 누락 요구를 발견한 경우 allowlist 안에서 다시 포함할 수 있다.
- 보안·권한·개인정보·투자 판단 gate는 위 임계값을 적용하지 않고 항상 실행한다.

**커버리지 검증과 생성 모델**

- 커버리지 검증은 승인된 Luna 모델의 `coverage-verifier` stage를 사용한다. 답변 생성 `answer-generator`와 모델 배포는 같아도 프롬프트·출력 스키마·목적·영수증·평가 지표를 분리한다.
- 커버리지 검증은 최초 1회와 서버가 계획을 보완한 뒤 재확인 1회까지 허용한다. 두 번째 확인에서도 필수 요구가 해소되지 않으면 도구를 호출하지 않고 `clarification` 또는 `guidance`로 종료한다.
- 최종 답변 생성은 Luna 1회만 허용한다. 출력 검증 실패 시 자동 재생성하지 않는다.
- 근거 기반 고정 주장에 필요한 별도 Jev 의미 검증은 최대 1회이며 라우터 Jev와 다른 stage·질문 집합·정책 버전·영수증을 사용한다.
- 출력 검증은 결정론적 검사 다음 의미 검증 순서다. 결정론적 검사(스키마, 요구 커버리지, 인용 실재·원문 일치·철회, 구간 규칙, 수치·날짜, 그래프, 버전·회원 범위, 투자 표현 규칙)에 실패하면 Jev를 호출하지 않고 `validation_failed`로 종료한다.
- 의미 검증 대상은 `evidence_grounded`·`zoop_documented` 구간의 claim과 그 인용 원문이다. 모든 claim(최대 20개)을 한 번의 호출로 보내 claim마다 `supported / contradicted / insufficient`와 Noul(`prohibitedAdvice`, `unsupportedCausality`)을 판정한다. `general_knowledge` 구간은 비교할 권위 자료가 없으므로 사실 판정(Choice)을 하지 않고 Noul `prohibitedAdvice`만 판정한다. 이는 투자 권유 차단용이며 사실 검증 통과로 기록하지 않는다. 따라서 `answered` 결과는 일반 개념만 답한 경우에도 의미 검증 Jev를 1회 호출한다.
- 하나라도 `contradicted`이거나 Noul이 예이면 답변 전체를 `validation_failed`(retry 없음)로 종료한다. `insufficient`이거나 Noul이 불확실한 hold claim이 있으면 그 claim이 속한 요구의 구간을 서버가 결정론적으로 제외하고 `evidence_insufficient` limitation으로 기록한다. 남은 답변 요구가 없으면 `insufficient_evidence`다. 이 제외는 재생성이 아니며, 이를 위해 각 답변 구간은 내부적으로 하나의 요구에만 속하고 여러 요구를 잇는 통합 문장은 별도 구간으로 두어 관련 요구 중 하나라도 제외되면 함께 제외한다.
- Jev 모델 불일치·응답 형식 오류는 응답을 받은 확정 실패이므로 원문 응답을 영수증으로 먼저 저장하고 재시도 없이 `failed`(`transient`, `provider_error`, retry=`rerun`)로 닫는다. 송신 후 timeout·연결 끊김으로 응답 여부를 모르면 `failed`(`transient`, `response_unknown`, retry=null)로 닫고 호출은 `unknown`·`reconcile_only`로 남긴다(6.3.3절 한도 초과 분류). 의미 검증을 건너뛰고 결과를 저장하는 경로는 없다.
- 판정 임계값은 S1 의미 검증의 잠정 공학값(Choice 승리 확률 ≥ 0.90 그리고 confidence ≥ 0.80, Noul ≥ 0.90 예 / ≤ 0.10 아니오, 그 사이 불확실)으로 시작한다. 이 값은 보정되지 않았으며 D15 출시 승인 전에 챗봇 고정 평가 세트로 보정한다.

**시간 기한과 한도 초과 처리**

| 단계 | 잠정 상한 |
| --- | --- |
| Jev 라우터 | 4초 |
| Luna 커버리지 | 회당 6초(최대 2회) |
| MCP 단계 | 10초(개별 3초) |
| Luna 답변 생성 | 25초 |
| Jev 의미 검증 | 6초 |
| 결정론적 검사·저장 등 서버 처리 | 3초 |

- ChatJob 실행 기한은 계획 확정 때 실제로 실행할 단계의 상한만 더해 정하며 최대 60초다. 예: Q02 단독(라우터·커버리지 1회·생성·의미 검증·서버 처리) 44초, 근거 조회를 포함한 단순 조회 54초, 커버리지 재확인까지 포함한 복합 질문 60초. 모든 경로의 단계 상한 합은 60초를 넘지 않게 정한다. 기한은 `running` 시작부터 검증된 결과 저장까지이며 polling 전달 시간은 포함하지 않는다.
- 각 모델 단계를 시작하기 전에 남은 기한이 그 단계와 이후 남은 필수 단계(생성·의미 검증·서버 처리 등) 상한의 합보다 적으면 호출하지 않고 종료한다. 다음 단계 하나만 보면 생성 비용을 쓴 뒤 의미 검증 직전에 기한이 끝날 수 있기 때문이다. 커버리지 재확인도 이 조건을 만족할 때만 실행한다. 실행 lease는 시작 시각에 기한과 여유 시간을 더해 정하고 기한이 지난 실행의 늦은 완료는 owner token 검사로 거부한다.
- 위 시간 상한은 성능 목표가 아니라 비용·남용 차단선이며 실측 근거 없는 잠정값이다. 출시 전(D11) 고정 평가 세트에서 단계별 p95를 측정해 상한을 p95의 1.5배로 다시 정한다. Luna 커버리지의 reasoning effort를 낮추는 방안은 이때 함께 검토한다.
- 실행 중 한도 초과는 같은 고정 문맥으로 다시 실행했을 때 결과가 달라질 수 있는지로 구분한다.

| 상황 | 처리 | 재시도 |
| --- | --- | --- |
| 계획 시점 예산 초과, 체크포인트 fan-out 초과 | `clarification` | 해당 없음 |
| 보충 라운드가 호출 상한 때문에 불가 | 해당 요구를 `results_truncated` 또는 `evidence_insufficient` limitation으로 기록 | 해당 없음 |
| 모델 송신 전 실패: 시작 전 잔여 기한 부족(`deadline_guard`), 연결 실패·처리하지 않았음이 명시된 공급자 오류(429·503 등)·응답을 받았으나 형식·모델이 맞지 않음(`provider_error`) | `failed`·`transient` | `rerun` |
| MCP 단계·개별 상한 초과(`tool_timeout`) | `failed`·`transient`, 호출은 `unknown`으로 기록 | `rerun` |
| 모델 송신 후 단계 상한 초과·연결 끊김·게이트웨이 timeout으로 응답 불명(`response_unknown`) | `failed`·`transient`, 호출은 `unknown`·`reconcile_only` | 없음(retry=null). 운영자 정산 대상 |
| 압축 후에도 Luna 입력 상한 초과(`context_too_large`), 답변이 출력 상한에 닿아 미완성(`output_limit`) | `failed`·`budget_exceeded` | 없음. 범위를 좁힌 새 질문 안내 |

- 괄호 안의 값은 `ChatFailure.reason` 코드다. UI 문구와 관리자 집계는 이 코드를 기준으로 한다.
- `rerun`은 공급자가 요청을 처리하지 않았거나 응답을 받아 실패가 확정된 경우에만 허용한다. 모델 송신 후 응답 불명은 공급자가 이미 처리·과금했을 수 있어 같은 job을 다시 실행하면 중복 호출이 되므로, 7.4절의 내부 worker 결과 불명 규칙과 같이 자동 재전송과 공개 재실행을 모두 막고 영수증·운영자 확인으로 정산한다. 정산 뒤에도 끝난 job의 `retry`는 바꾸지 않으며 회원은 새 질문으로 진행한다.
- MCP 도구는 앱 내부의 읽기 전용 조회라 다시 실행해도 외부 상태나 과금이 바뀌지 않는다. 그래서 `tool_timeout`은 원 호출을 `unknown`으로 남긴 채 새 실행에서 다시 조회하는 `rerun`을 허용한다.
- `rerun`은 작업당 실행 3회(`runs` ≤ 3)까지 허용하며 이후에는 `retry=null`이다. 모델을 호출하지 않는 `save_only`는 이 횟수에 포함하지 않으므로, 세 번째 실행이 검증까지 마친 뒤 저장에만 실패해도 검증된 결과를 복구할 수 있다. 재실행은 이전 실행 종료와 현재 권한을 확인한 뒤 최초 질문·고정 문맥으로만 수행한다.
- 진행 중 작업은 공개 `ChatJob.phase`(`planning`, `retrieving`, `writing`, `verifying`)로 현재 단계를 알린다. 검증 전 생성 본문은 계속 노출하지 않는다.

**공개 응답과 Q02 표시**

- MVP에서는 `PARTIAL` outcome이나 하위 결과 배열을 추가하지 않는다. 여러 스냅샷·독립 실패를 구조적으로 표시해야 하는 질문은 범위를 선택하도록 `clarification`한다.
- `answered` 본문은 근거 수준별 구간 `ChatResult.sections`(`basis`, `text`, `evidenceIds`)로 구성한다. `basis`는 `general_knowledge / zoop_documented / evidence_grounded` 중 하나이고, 서버가 구간 text를 순서대로 이어 `answer`를 만든다. `answered`가 아니면 구간은 비어 있다.
- 공개 `ChatResult.answerBasis`는 서버가 구간에서 계산한다. 구간 basis가 한 종류면 그 값, 두 종류 이상이면 `mixed`, 구간이 없으면 `none`이다. 모델의 자기평가나 UI 추측으로 설정하지 않는다.
- Q02 일반 개념은 `general_knowledge` 구간에만 담는다. 이 구간의 첫 문장은 서버가 `일반 개념 설명입니다. 최신 기업·시장 사실은 별도 조회가 필요합니다.`로 붙이며 모델이 쓰지 않는다. 구간의 `evidenceIds`는 빈 배열이고 현재 가격·기업 사건·시장 점유율·최신 표준·전망·개인 투자 판단을 포함하지 않는다.
- `evidence_grounded`·`zoop_documented` 구간의 사실 주장은 그 구간의 근거에만 연결한다. 모든 `evidenceIds`는 `citations`에 있어야 하며(ZOOP 도움말·정책 인용은 `sourceKind=zoop_doc`과 문서 ID·버전·구간을 갖는 같은 형식의 항목이다), 일반 개념 구간과 근거 구간을 한 구간으로 섞지 않는다. 일반 개념만 답한 결과의 `sources`와 `citations`는 빈 배열이다.
- ZOOP 고유 개념은 Q01 또는 Q08의 승인 문서를 조회하고 문서 버전과 근거를 표시한다. 약어·다의어를 확정할 수 없으면 `clarification`한다.

#### 6.3.4 단계와 체크포인트

앞 단계 결과가 다음 단계의 입력이고 결과에 따라 대상이 달라지는 질문(예: ‘내 종목 중 오늘 뉴스가 있는 두 회사의 관계’)은 회원이 조회 전에 답할 수 없으므로 MCP 호출 전 `clarification`으로 처리하지 않는다. 서버는 계획 확정 때 다음을 typed 값으로 선언한다.

- `stages[]`: 단계 순서와 각 단계의 논리 기능·의존 단계. 같은 단계 안의 독립 호출은 병렬 실행한다.
- `checkpoint`: 평가 대상 단계, 개수 조건(`exactly(n)`, `atLeast(n)`, `atMost(n)`), 0개·조건 미달·초과 때의 처리. 조건은 요구 분해 결과(‘두 회사’ → `exactly(2)`)에서 정하며 Jev·Luna 출력이나 실행 중 모델 판단으로 정하지 않는다.

| 체크포인트 결과 | 처리 | outcome |
| --- | --- | --- |
| 조건 충족 | 다음 단계 진행 | 이후 결과에 따름 |
| 초과 | 다음 단계를 호출하지 않는다. 실제 조회된 대상으로 선택지를 만들고(조합 6개 이하, `kind=scope`), 넘으면 자유 입력을 받는다 | `clarification` |
| 조건 미달(1개 이상) | 조회된 대상에 대한 요구는 답하고 의존 요구는 `precondition_unmet` limitation으로 기록한다 | `answered` |
| 0개이고 `truncated=false`·오류 없음 | 해당 대상이 없음을 조회 범위·기준 시각과 함께 답한다 | `answered` |
| 0개이고 `truncated=true`·오류 없음 | 없다고 표현하지 않는다 | `insufficient_evidence` |
| 단계의 도구 호출이 timeout·장애·권한 오류로 끝남 | 개수 조건을 평가하지 않고 근거 부족으로 저장하지 않는다 | `failed`(`ChatFailure`) |

- `clarification`은 답변 생성 전, 즉 계획 시점이나 선언된 체크포인트에서만 반환한다. 체크포인트에서 멈추면 Luna 답변 생성을 호출하지 않으며 생성 뒤의 결과를 `clarification`으로 바꾸지 않는다.
- 선택지는 실제 도구 결과로만 만들고 choice id는 서버가 다시 해석할 수 있는 불투명 값이다. 회원의 선택은 `resolves`를 담은 새 작업으로 접수하며 새 작업은 원 작업의 asOf·graphVersion을 복사한다. 같은 결과가 재현되도록 조회 도구는 고정 asOf 이후 자료를 제외한다.
- 확인 질문 사슬은 최대 2회다. 루트 질문 작업의 깊이는 0이고 확인 답 작업의 깊이는 원 작업 깊이 + 1이다. 깊이 0·1 작업만 `clarification`을 반환할 수 있다. 깊이 2 작업에서 계획 시점 모호·예산 초과나 체크포인트 초과가 생기면 다음 단계와 답변 생성을 호출하지 않고, 대상·기간·범위를 구체적으로 적은 새 질문을 안내하는 `guidance`로 끝낸다. 근거 부족이나 장애로 표현하지 않으며 `route_summary`에 `clarification_depth_exceeded`를 기록한다. 확인 답 작업은 루트 질문과 사슬의 답(선택지 또는 자유 입력)을 순서대로 합쳐 요구 분해부터 다시 실행하고, 고정 문맥은 루트 작업의 것을 그대로 쓴다. 같은 확인 질문에 다시 답하는 분기는 횟수를 제한하지 않는다. 분기마다 새 작업이며 대화당 활성 작업 하나와 작업별 예산이 그대로 적용된다.
- fan-out 단계(`atLeast(n)`)는 단계별 fan-out 상한을 넘으면 그 체크포인트에서 범위를 좁히는 `clarification`을 반환한다.
- 체크포인트 판정·선택지 생성 근거·중단 단계는 `route_summary`에 기록하고 이미 실행한 호출은 `chat_tool_calls`에 남긴다.

### 6.4 중첩과 복합 질문

‘내 종목 중 오늘 뉴스가 있는 회사를 찾아서 두 회사 관계도 설명해줘’는 Q07로 본인 종목 범위를 먼저 확정한 뒤 Q03·Q04를 실행한다. Q03과 Q04 사이에 데이터 의존성이 없으면 병렬 실행하고, 앞 단계의 결과가 다음 단계 입력인 경우에만 순차 실행한다. Q07의 개인 접근 조건은 모든 후속 하위 작업에 유지한다. 공개 기업 조회로 재분류하여 인증을 우회하지 않는다. ‘두 회사’는 Q03 결과에 대한 `exactly(2)` 체크포인트로 선언한다. 해당 회사가 셋 이상이면 Q04를 호출하지 않고 실제 조회된 회사 조합으로 `clarification`하고, 하나면 그 회사의 뉴스를 답하며 관계 요구는 전제 불충족 제한으로 명시하고, 0개이며 결과가 잘리지 않았으면 해당 종목이 없음을 근거와 함께 답한다(6.3.4절).

‘HBM을 설명하고 지금 어떤 주식을 사야 하는지 알려줘’는 Q02 설명과 투자 판단 요청을 분리한다. 허용된 개념 설명을 완결되게 제공하고 특정 매수 결론은 생성하지 않는다. 이 경우 `answered`의 본문은 제공한 범위를 답하고 거절한 요구는 `investment_advice` limitation으로 기록하며 `PARTIAL` 실행 성공으로 기록하지 않는다. 금지된 투자 판단만 요청한 경우에는 사실 답변을 억지로 만들지 않고 지원 범위 `guidance`를 제공한다.

‘오늘 브리핑과 최신 그래프를 비교해줘’는 서로 다른 스냅샷을 비교하라는 요청이다. 현재 ChatResult의 단일 적용 버전으로 이를 숨겨 표현하지 않는다. 하위 답변별 스냅샷을 표현·검증할 계약이 갖춰진 뒤 지원하고, 그 전에는 기준 회차 또는 시점을 선택하도록 안내한다. 기간 비교 자체는 고정된 버전이 제공하는 자료 범위에서 수행할 수 있다.

Jev 후보가 여러 개라는 이유만으로 유형을 잘라내지 않는다. 명시적 요구를 충족하는 데 필요한 유형과 최소 충분 논리 기능·MCP 도구는 커버리지 검증 및 서버 승인을 거쳐 실행한다. 유형 수에는 고정 상한을 두지 않지만 같은 목적의 중복 조회와 답변에 쓰이지 않을 조회는 제거한다. 예상 호출이 승인된 시간·비용·조회량 예산을 초과하거나 서로 양립할 수 없는 기준 시점·권한·대상을 요구하면 일부를 조용히 생략하지 않는다. 현재 계약에는 `PARTIAL` outcome이 없으므로 MCP를 호출하기 전, 또는 조회 결과가 기준이 되는 경우 선언된 체크포인트에서 답변 생성 전에 범위를 좁히는 `clarification`을 반환한다. 향후 부분 결과를 제공하려면 하위 결과별 상태·버전·실패를 표현하는 공개 계약을 먼저 추가한다.

질문 전체가 타인 정보 추출이나 시스템 우회를 위한 경우 관련 조회를 중단한다. 제한된 부분에서 얻은 정보를 허용된 하위 답변에 섞지 않는다. 반복 확인에도 대상을 정할 수 없으면 가능한 선택지를 안내하고 조회를 종료한다.

하위 질의 분기는 하나의 접수된 작업 내부에서 수행한다. 같은 대화에 여러 공개 질문 작업을 동시에 생성하여 활성 작업 하나 제약을 우회하지 않는다. 확인 질문은 저장된 완료 결과로 남기고, 사용자의 보충 입력은 새 질문 작업으로 접수한다. 완료 작업 재조회가 새 분류·생성을 실행하지 않도록 한다.

### 6.5 Multi-hop 실행과 오류 전파 통제

Multi-hop은 모델의 비공개 사고 과정을 노출하거나 자유로운 에이전트 실행을 허용한다는 뜻이 아니다. 서버가 승인된 순서로 `요구 분해 → Jev 분류·기능 선택 → 커버리지 검증 LLM → 필수 gate·서버 승인 → MCP 조회 → 필요 시 추가 조회 → Luna 생성 → 검증`을 수행하는 오케스트레이션이다. 필요한 하위 단계만 실행하며 각 단계의 출력은 자연어 요약보다 요구 ID, Q 유형 ID, 논리 기능 ID, 논리 도구 ID, 기업 ID, 기간, 회차, 그래프 버전, 관계 ID, 근거 ID와 같은 구조화된 값으로 다음 단계에 전달한다.

첫 단계의 오분류·대상 오인이 뒤 단계로 전파될 수 있으므로 다음을 강제한다.

- 기업·회차·기간·지시 대상 후보가 여러 개이고 어느 대상을 선택하는지에 따라 사실 답변이 달라지면 실행을 계속하지 않고 `clarification`을 반환한다. 실행 중에는 모델 판단이 아니라 선언된 체크포인트에서만 멈추며 답변 생성 뒤에는 `clarification`으로 바꾸지 않는다. 여러 Q 유형이나 논리 기능이 동시에 필요한 것만으로 확인 질문을 만들지 않는다.
- 정책 기본값을 적용할 수 있는 기간은 실제 해석 범위를 표시하고, 기업·회차·권한은 기본값으로 추측하지 않는다.
- 각 단계가 받은 ID·버전·권한과 이전 단계의 고정 문맥을 서버에서 재검사한다.
- 단계 수, 그래프 경로 길이, 조회 문서 수, 시간과 비용에 상한을 두며 상한 도달을 전체 결과로 표현하지 않는다.
- 필수 단계가 실패하면 생성 모델이 누락 값을 보충하지 않고 실패·근거 부족·확인 질문 중 실제 상태로 종료한다.
- 내부 분기·Jev 분포·선택·제외 사유·MCP 도구·검증 이력은 감사 가능한 코드와 식별자로 기록하되 모델의 상세 내부 추론은 저장하거나 공개하지 않는다.

직접 관계와 간접 경로의 분리는 의미와 표시의 분리이지 반드시 별도의 LLM 호출을 뜻하지 않는다. 허용된 하나의 그래프 쿼리로 제한된 길이의 경로를 조회한 뒤 서버가 1-hop 직접 관계와 2-hop 이상 간접 경로를 구분할 수 있다. 비용이나 사용성 때문에 직접 관계를 먼저 조회하고 필요한 경우에만 간접 경로를 조회하는 구현도 허용한다.

## 7 유형별 답변과 도구 실행 기준

### 7.1 공통 답변 계약

사용자 답변은 먼저 질문에 대한 결론을 제시하고, 필요한 설명과 근거를 이어서 제공한다. 복합 질문은 구조화된 명시적 요구마다 본문 답변 또는 `limitations` 항목(제한·근거 부족) 중 하나가 대응되게 구성하고, 허용된 요구를 조용히 누락하지 않는다. 사건·기업 답변에는 대상, 조회 기간, 데이터 기준 시각, 출처를 표시한다. 회차 답변에는 회차 ID 또는 표시명과 발행 시각을 함께 제공한다. ZOOP 정책·도움말 답변에는 해당 내부 문서의 버전 또는 갱신 기준을 적용한다. Q02 일반 LLM 답변은 모델·프롬프트·정책 버전을 내부 기록하고 사용자에게 일반 개념 설명임을 표시하되 존재하지 않는 범용 용어 사전, 문서 버전 또는 출처를 만들지 않는다.

공개 응답은 목표 OpenAPI의 camelCase `ChatJob`과 `ChatResult`를 사용한다. `ChatJob`은 작업 ID·sessionId·status·outcome·고정 context·failure·result를 포함하며, result는 completed 전까지 null이다. `ChatResult`의 필수 필드는 `outcome`, `messageId`, `answer`, `reason`, `sources`, `citations`, `graphTargets`, `applied`, `choices`, `action`, `metadata`다. 각 필드의 required·nullable·배열 조건을 스키마 그대로 따른다.

실제 대상·기간·graphVersion·dataAsOf는 `applied`에, 요청 추적과 공통 응답 정보는 `metadata`에 둔다. 인용은 `evidenceId`, `articleId`, `articleVersion`, `quote`, `start`, `end` 및 출처 표시 필드로 연결한다. 내부 질의 유형·하위 유형, 라우터 버전과 검증 코드는 감사 기록에서 관리하며 기존 응답에 snake_case 필드나 별도 status를 추가하지 않는다. 개념·도움말 등 새 유형도 기존 필수 필드를 사실대로 채울 수 있어야 하며, 불가능하면 API 확장 전까지 미지원 안내로 처리한다.

인용 URL은 모델이 작성한 문자열을 그대로 사용하지 않는다. 서버가 승인된 문서 ID에서 생성하거나 허용된 주소인지 검증한다. 개인정보·비밀값·비공개 관리 화면 주소가 링크나 오류 메시지에 노출되지 않게 한다.

### 7.2 검색과 그래프 조회

공개 데이터 검색에는 공개 상태, 활성 또는 지정 버전, 철회 여부와 접근 범위 필터를 강제한다. 벡터 검색도 동일한 조건을 적용한다. 비공개 후보를 검색 후 모델이 알아서 제외하도록 맡기지 않는다.

그래프 조회는 허용된 쿼리 템플릿과 매개변수로 실행한다. 모델이 작성한 임의 SQL·Cypher를 운영 DB에 직접 실행하지 않는다. 조회 계정은 읽기 전용으로 제한하며 경로 길이, 노드·문서 수, 수행 시간을 제한한다. 상한에 도달하면 전체 결과를 찾은 것처럼 말하지 않고 조회 범위를 표시한다.

그래프의 연결 수나 시각적 크기는 활동량 또는 정의된 표시 규칙을 뜻한다. 이를 투자 매력도·수익 가능성·인과관계 점수로 설명하지 않는다. 간접 경로를 설명할 때는 각 단계의 근거와 관계 유형을 유지한다.

관계 근거는 해당 사건·관계의 주체, 대상, 유형, 방향, 범위 또는 유효 시점을 뒷받침하는 뉴스·공시 원문의 고정 인용 구간이다. PostgreSQL `evidence`는 `article_id`, `article_version`, `text_artifact_id`, 인용문, Unicode code point 기준 시작·끝 위치와 검증 artifact를 보관하고, Neo4j의 Issue·Relation은 해당 근거 ID를 연결한다. 실제 원문 텍스트는 `artifacts`가 가리키는 비공개 파일 저장소에서 읽는다.

사건이 추출된 문장과 관계 간선의 근거는 같을 수 있지만 의미를 동일시하지 않는다. 공동 행사 참여를 뒷받침하는 문장은 사건 또는 공동 등장 근거가 될 수 있어도 공급계약 간선의 근거가 되지 않는다. 직접 관계는 그 간선 자체의 유형과 방향을 뒷받침하는 근거를 요구한다. 간접 경로는 전체 경로를 직접 관계로 증명하는 하나의 문서를 요구하는 대신 각 단계의 간선에 해당 단계의 근거를 요구한다.

관계 생성·공개 단계에서는 입력 문서 결속, 문서 버전, 인용 위치와 원문 일치, 허용 관계 유형, 알려진 endpoint, 직접·간접 경로 구조, 방향·유효기간과 주장별 의미 지원을 검증한다. 모순은 반려하고 방향 반전·근거 부족 등은 보류할 수 있다. 챗봇 조회 단계에서는 이 검증을 매번 다시 생성하지 않고, 고정한 공개 그래프 버전에 간선이 존재하는지, `evidenceIds`가 공개·비철회 문서 버전과 실제 인용으로 해소되는지, 직접·간접 표시가 저장된 경로와 일치하는지를 자동 검사한다.

현재 관계 추출 파이프라인의 citation·검증 규칙, ERD의 `evidence`와 공개 API의 관계별 `evidenceIds` 계약은 존재한다. 그러나 S2 사건 추출·S3 관계 결과를 Neo4j 투영·검증을 거쳐 handoff로 앱 공개 스냅샷에 수입·활성화하는 전체 운영 경로는 완료된 것으로 간주하지 않는다. 챗봇의 그래프 도구는 공개 그래프 API와 같은 읽기 경로(버전 고정 → 불변 스냅샷 → asOf 필터 → 현재 공개 제외 결정 적용)만 사용하며, Neo4j나 AI 내부 그래프 읽기 API를 호출하지 않는다. 챗봇 관계 답변을 활성화하기 전에 handoff 수입·활성화·챗봇 조회·철회 반영의 종단 시험을 통과해야 한다.

### 7.3 시점과 비교

‘오늘’과 상대 기간은 최초 요청 접수 시각의 Asia/Seoul을 기준으로 해석한다. 재시도 중 날짜가 바뀌어도 같은 요청의 기간은 바꾸지 않는다. 브라우저가 보낸 시간과 모델의 현재 시각 추측을 기준으로 삼지 않는다.

기업명이 ‘삼성’처럼 여러 회사를 가리키거나 ‘그 회사’의 대상을 확정할 수 없으면 확인한다. 화면에서 선택한 기업·사건을 문맥으로 쓸 때는 서버가 대상 ID와 접근 가능 여부를 검증하고 답변에 사용 대상을 표시한다. 현행 기준에서 ‘최근’의 기본 기간은 1개월이고 ‘작년’은 직전 달력 연도다. 질문에 명시한 조건을 선택 문맥보다 우선하며 실제 해석 기간을 고정·표시한다. 기본값 변경은 정책·명세·평가 사례를 함께 갱신하는 변경 절차를 따른다.

비교 대상의 통화·단위·관측 기준을 맞춘다. 차이·비율 등 산술은 서버에서 계산하고 LLM은 결과를 설명한다. 원본 값 또는 비교 기준이 없으면 수치를 생성하지 않는다. Q05의 ‘빠짐’은 선택된 데이터 창이나 회차에서 제외됐다는 뜻이며 사건 종료나 악재 해소로 단정하지 않는다.

### 7.4 출력 검증과 재시도

MCP 호출 전의 커버리지 검증은 실행 계획 검증이고, Luna 생성 후의 출력 검증은 사용자 답변 검증이다. 커버리지 검증에서 누락된 허용 기능을 발견하면 서버가 allowlist와 예산 안에서 계획을 보완하고 다시 확인할 수 있다. 이 단계에서는 아직 사용자 답변이 생성되지 않았으므로 `validation_failed`로 기록하지 않는다. 안전하게 보완할 수 없으면 MCP 호출 전에 `clarification` 또는 `guidance`로 종료한다.

검증기는 인용 ID의 존재, 공개·철회 상태, 주장과 근거의 대응, 숫자·통화·날짜, 개인 접근 범위, 투자 판단 범위와 응답 구조를 검사한다. 챗봇 검증 실패는 `validation_failed`로 처리하고 자동 재생성하지 않는다. 검증 실패를 근거 부족 안내로 바꾸어 성공 처리하지 않는다. 질문 작업의 `ChatFailure.retry`는 서버가 결정한 `rerun / save_only / null`을 따르며, null이면 재시도를 제공하지 않는다.

데이터 생성·공개 검증과 챗봇 답변 검증은 구분한다. 사건·관계 추출의 보류 후보에는 관리자 검수가 개입할 수 있지만, 챗봇은 이미 공개된 버전만 조회하며 개별 답변마다 사람의 사전 승인을 요구하지 않는다. 챗봇 검증은 자동 실행하고, 사람은 출시 전 평가, 표본 품질 점검, 반복 실패 조사, 오류 신고와 사고 대응에 개입한다.

| 검증 대상        | 구현 기준                                                                                            | 실패 처리                                                      |
| ---------------- | ---------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 요구 커버리지    | 고정된 requirementId마다 답변·제한·근거 부족 상태가 있고 허용된 필수 요구가 누락되지 않았는지 검사  | `validation_failed`                                            |
| 응답 구조        | OpenAPI·JSON Schema의 필수 필드, nullable, enum, 배열 조건 검사                                      | `validation_failed`                                            |
| 인용 존재와 결속 | `evidenceId`를 `evidence`에서 찾고 article/version/text artifact와 고정 문맥을 대조                  | `validation_failed`                                            |
| 인용 원문 일치   | 고정 텍스트의 `[start,end)` 구간과 quote를 Unicode code point 기준으로 비교                          | `validation_failed`                                            |
| 공개·철회·버전   | 문서 접근 상태, 분석 상태, graphVersion, 회차, 철회 목록과 현재 접근 권한 검사                       | 노출 차단 또는 `validation_failed`                             |
| 주장과 근거 대응 | 답변을 내부 주장 단위로 만들고 허용 citation을 결속한 뒤 구조·명칭·수치 검사와 독립 의미 판정을 결합 | contradicted는 실패, insufficient는 근거 기반 답변에 사용 금지 |
| 숫자·날짜·통화   | 구조화된 원본 값과 비교하고 산술은 서버에서 계산                                                     | `validation_failed`                                            |
| 그래프 관계      | 고정 공개 스냅샷 버전의 endpoint·유형·방향·hop 수와 간선별 evidence ID, 지도에서 열 수 있는 graphTargets 검사 | `validation_failed`                                            |
| 시점 일치        | 질문의 고정 기간·asOf·회차와 `applied` 및 조회 결과 비교                                             | `validation_failed`                                            |
| 개인정보·권한    | 회원·대화 소유권, 본인 종목 범위와 출력의 타인 식별자 재검사                                         | 노출 차단, `permission_denied`                                 |
| 투자 판단·비밀값 | 규칙 기반 탐지와 보조 분류기를 사용하되 모델 자기평가만으로 통과시키지 않음                          | 답변 차단 또는 허용 범위 안내                                  |

Q02의 일반 LLM 답변은 권위 자료가 없는 상태에서 인용·주장 대응 검증을 통과했다고 기록하지 않는다. 이 경로의 후검증은 응답 구조, 일반 개념 범위, 최신 사실·수치·투자 판단 포함 여부, 관련성, 내부 모순과 명백한 오류의 교차검토다. 두 번째 LLM이 동의했다는 사실만으로 사실 정확성을 증명하지 않는다. 검사를 통과한 답변은 일반 개념 설명으로만 제공하고 Q03~Q08의 근거 기반 답변과 같은 검증 표식을 사용하지 않는다.

| 실패 또는 상태                              | 복구 규칙                                                 | 모델 호출                    |
| ------------------------------------------- | --------------------------------------------------------- | ---------------------------- |
| 챗봇 검증 실패·권한 오류·결과 소실          | 실패 사유 기록, 자동 재생성 금지                          | 자동 재호출 없음             |
| 검증 결과를 보존한 뒤 앱 저장 실패          | 원래 검증 산출물로 save_only, 현재 권한 재확인            | 없음                         |
| 서버가 재실행을 허용한 일시 장애            | 명시적 retry와 원래 고정 문맥 유지, 활성 작업 제약 재검사 | retry=rerun일 때만 허용      |
| 내부 worker 호출 결과 불명                  | reconciling / reconcile_only로 유지, 운영자 정산·확인     | 자동 재전송 없음             |
| 내부 worker 영수증 저장 후 산출물 저장 실패 | 저장 영수증·산출물로 검증·저장 복구                       | 이미 송신한 단계 재호출 없음 |
| worker ready 이후 앱 수입 실패              | 같은 job 결과를 읽어 수입·저장만 복구                     | 없음                         |

내부 worker의 ready는 산출물 준비 완료이며 공개 ChatJob의 completed와 다르다. 챗봇의 검증 결과를 시도별 불변 복구 산출물로 내구 저장하고, 앱 결과 저장과 completed 전환을 같은 트랜잭션으로 처리한다. 완료 결과·최초 문맥은 변경하지 않는다. 내부 worker의 resumeMode와 공개 ChatFailure.retry를 같은 enum으로 취급하지 않는다. 현재 S1 HTTP transport는 문서 세 stage와 기존 briefing-outlook 대상이며, 챗봇 HTTP 실행 계약이 이미 제공된다고 가정하지 않는다.

검증 전 생성 토큰을 사실 답변으로 스트리밍하지 않는다. MVP에서는 ‘자료 확인 중’과 같은 진행 상태만 먼저 전달하고 검증·저장이 끝난 본문을 반환한다. 창 닫기는 취소가 아니다. 취소·로그아웃·계정 전환 후 도착한 챗봇 응답은 서버의 상태·실행 토큰·전달 권한과 화면의 세션을 확인하여 유효하지 않은 결과를 폐기한다.

### 7.5 응답 문구 예시

아래 문구는 형식 예시이며 특정 사건의 실제 조회 결과가 아니다.

- 대상 확인: ‘삼성전자와 삼성SDI 중 어느 기업을 말씀하시나요?’
- 관계 설명: ‘조회 기간의 공개 자료에서는 두 기업이 이 사건에 함께 연결됩니다. 직접 공급계약을 확인할 근거는 현재 조회 범위에 없습니다.’
- 근거 부족: ‘선택한 기간과 공개 자료에서는 이 주장을 확인할 근거를 찾지 못했습니다. 기간을 넓히거나 다른 기업을 선택할 수 있습니다.’
- 투자 판단 제한: ‘특정 종목의 매수·매도 결론은 제공하지 않습니다. 해당 기업의 공개 이슈와 확인할 위험 요인은 근거와 함께 정리할 수 있습니다.’
- 일시 장애: ‘현재 자료 조회가 지연되어 답변을 완료하지 못했습니다.’ 이후의 재시도 또는 저장 복구 안내는 서버가 허용한 동작에 한해 제공한다.

### 7.6 챗봇 조회 자원과 질의 유형 매핑

pgvector는 PostgreSQL의 확장이지 별도 권위 DB로 간주하지 않는다. 현재 ERD v6에는 개념 문서 또는 일반 문서 청크·임베딩 테이블이 구체화되어 있지 않으므로 벡터 검색을 이미 구현된 기능으로 표시하지 않는다. 비공개 파일 저장소는 원문과 불변 산출물을 보관하지만 챗봇이 임의 탐색하지 않고 PostgreSQL의 `artifacts`와 권한 검사를 통해 특정 파일을 읽는다.

| 질의 유형          | 주 조회 자원                                                                                                                 | 적용 조건                                                |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| Q01 서비스 안내    | 버전이 확인된 도움말·화면 명세                                                                                               | 승인된 도움말 자원이 없으면 지원 범위 안내               |
| Q02 금융·산업 개념 | 범용 용어 사전 없이 Luna의 제한된 일반 LLM 설명. ZOOP 고유 개념만 승인된 정책·도움말 문서 조회                               | 일반 개념 설명으로 구분하며 최신 사실에 사용 금지        |
| Q03 기업·사건 사실 | PostgreSQL `companies`, `articles`, `article_versions`, `evidence`, `document_analyses`; 필요한 공개 그래프·외부 시세 어댑터 | 공개·버전·철회 상태와 기간 고정                          |

| Q05 기간 비교      | PostgreSQL `graph_versions`·활성화 이력, 버전별 앱 공개 스냅샷, 서버 차이 계산                                               | 같은 비교 기준과 버전 재현 필요                          |

위 표는 유형별로 가능한 조회 자원의 최대 범위를 나타내며 해당 유형이 선택됐다고 모든 자원을 호출한다는 뜻이 아니다. Jev의 논리 기능 후보와 커버리지 검증 결과를 바탕으로 서버가 명시적 요구를 충족하는 최소 충분 도구 집합을 선택한다. 같은 결과를 제공하는 중복 도구는 제거하고, 한 도구 결과가 다른 도구의 입력일 때만 순차 실행하며 독립 조회는 병렬 실행할 수 있다.

`chat_sessions`와 `chat_jobs`는 질문, 고정 문맥, 상태, 검증된 결과와 복구 정보를 저장한다. 최신 시세·재무는 전용 RDB 테이블이 아니라 승인된 외부 공급자 어댑터를 사용할 수 있으며 공급 실패를 0 또는 자료 없음으로 바꾸지 않는다.

## 8 브리핑과 관계 그래프 운영

브리핑은 공개 데이터의 지정 스냅샷으로 생성한다. 출근·퇴근 회차 ID, 생성 시작 시각, 발행 시각, 데이터 기준 시각, 지표별 관측 시각을 각각 저장한다. 예정 생성 시각을 발행 완료 시각으로 표시하지 않는다.

퇴근 브리핑은 같은 날 출근 회차와 비교하여 신규·이어짐·빠짐을 설명한다. 비교할 출근 회차가 없으면 비교 불가를 표시하고, 존재하지 않는 아침 내용을 만들어 채우지 않는다. 날짜·출근/퇴근 종류별 회차는 하나이며 회차당 발행은 한 번만 가능하다. 발행된 본문·근거·판정·스냅샷은 고정한다. 정정은 원문 밖의 별도 이력으로 추가하며 같은 회차의 새 판 발행이나 덮어쓰기를 허용하지 않는다. 재처리는 미발행 회차에 한정한다. 중대 오류가 있는 회차는 중단 이력을 기록하여 공개 접근을 제한한다.

핵심 이슈는 회차당 최대 3개이며 자료가 부족하면 억지로 채우지 않는다. 개인화는 같은 발행본의 항목과 본인 보유·관심 기업을 교차하여 표시하며 사용자별로 새로운 사건·판정·발행본을 생성하지 않는다. 생성 입력의 검수·규칙 revision을 고정하고 발행 시 현재 revision과 대조한다. 변경됐다면 오래된 생성 결과에 새 revision만 붙이지 않고 정해진 재검증·발행 절차를 수행한다.

브리핑 전체 상태는 미발행·생성 중·발행·실패·중단으로 관리한다. 지표별 정상·지연·사용 불가·실패는 전체 상태와 별도로 관리한다. 환율 등 한 지표가 실패해도 검증된 다른 내용은 유지할 수 있으며, 없는 값을 이전 값으로 대체할 때는 이전 관측 시각과 대체 사실을 명시한다.

이슈 선정 이유는 실제 실행된 규칙과 입력값에서 작성한다. 사건 시각 미상인 항목에 ‘사건 시각이 가장 최근’이라는 설명을 붙이지 않는다. 게시 시각을 대신 사용한 순위라면 게시 시각 기준임을 표시한다. 데이터 시점, 그래프 버전, 화면의 기준 시각이 서로 맞는지 발행 전에 검사한다.

자료의 브리핑 예정 생성 시각은 07:40·18:10 KST이며, 클라우드 계획의 개발 운영 시간은 평일 09:00~18:00다. 현재 승인 범위에서는 이 두 정기 실행을 보장하지 않는다. 개발·시연은 승인 시간 내 수동 실행 또는 시연 회차로 진행하고 실제 정기 운영과 구분한다. 정기 실행은 운영 시간·예산 변경과 작업 완료 시간을 승인받은 후 활성화한다.

## 9 보안과 프롬프트 공격 대응

수집한 뉴스·공시, 검색 결과, 사용자 질문에 포함된 ‘이전 지시를 무시하라’, ‘키를 출력하라’ 등의 문장은 처리 대상 데이터다. 시스템 정책, 도구 권한 또는 관리자 승인으로 해석하지 않는다. 검색 문서는 출처와 경계를 표시한 데이터 영역으로 전달한다.

챗봇의 도구는 정보 조회에 한정한다. 데이터 공개, 검수 승인, DB 수정·삭제, 사용자 권한 변경, 주문·결제는 챗봇 도구에 포함하지 않는다. Jev의 논리 기능 후보와 커버리지 검증 LLM의 계획 평가는 신뢰되지 않은 제안으로 취급하며, typed 스키마를 벗어난 값과 등록되지 않은 논리 기능 ID·MCP 도구·인자·목적지는 서버가 거부한다. 런타임 도구 자동 발견이나 모델 제안만으로 allowlist를 확장하지 않는다. URL 조회가 필요한 기능은 허용된 출처와 네트워크 목적지만 접근하고 내부 주소·클라우드 메타데이터 주소 등은 서버에서 차단한다.

정상적인 금융·보안 개념 질문에 공격 관련 단어가 있다는 이유만으로 일괄 차단하지 않는다. 요청한 행동, 접근 대상과 실제 실행 권한을 판단한다. 입력 필터와 출력 필터 외에도 도구 수준 접근 통제를 검증한다.

보안 시험은 문서 속 악성 지시, 여러 차례 대화에 나눈 우회 요청, 인코딩된 입력, 타인 ID 삽입, 거짓 관리자 주장, 외부 링크를 통한 정보 반출을 포함한다. 사용자에게 내부 프롬프트·키·상세 스택 추적을 노출하지 않고 지원용 요청 ID를 제공한다.

## 10 개인정보와 외부 모델 API

Q01~Q08의 회원 자격을 공통으로 확인하고, Q07은 세션에서 확인된 본인의 보유·관심 종목만 조회한다. 사용자 입력에 다른 사용자 ID가 있더라도 조회 주체를 바꾸지 않는다. 공개 근거로 답할 수 있는 하위 질문은 개인정보 조회 없이 처리할 수 있지만 챗봇 회원 조건은 유지한다.

외부 모델에는 답변에 필요한 기업 ID 또는 명칭과 최소 근거 구간을 우선 전달한다. 이메일, 실명, 연락처, 인증 토큰, 계좌 정보, 불필요한 보유 수량·매입 단가·자산 규모는 제외한다. 기업 목록만으로도 개인과 결합하면 민감한 맥락이 될 수 있으므로 가명 ID와 함께 보내는 것만으로 안전하다고 판단하지 않는다.

모델 제공자별 전송 데이터, 처리 위치, 보관·삭제 조건, 학습 이용 설정, 재위탁 조건, 계정 설정을 확인하여 기록한다. 확인되지 않은 조건을 ‘저장하지 않음’ 또는 ‘학습에 사용하지 않음’이라고 안내하지 않는다. 해당 조건을 확인하기 전에는 실제 개인 데이터의 외부 전송을 활성화하지 않는다.

운영 로그에는 최소한의 가명화된 메타데이터를 남긴다. 원문 질문·전체 답변·검색 문서 전문을 기본 로그로 무조건 저장하지 않는다. 품질 조사에 원문이 필요하면 목적, 마스킹, 접근자와 보관 기간을 정한 제한된 저장소를 사용한다. 사용자의 질문에 포함된 개인정보는 외부 모델뿐 아니라 오류 추적·분석 도구로의 전송에도 같은 기준을 적용한다.

운영 로그의 최소 수집과 서비스 대화 저장은 구분한다. 대화 조회·멱등성·복구에 필요한 질문·고정 문맥·검증된 결과는 chat_jobs 등 정해진 서비스 저장소에 권한과 보관 정책을 적용하여 저장한다. 관리자의 대화록 열람은 `transcript:read` 권한과 목적을 확인하고 마스킹·감사 저장을 완료한 뒤 반환한다. 마스킹 또는 감사 저장에 실패하면 원문을 반환하지 않는다.

보관 기간은 계정·종목, 대화 이력, 원문·근거, 감사 로그, 백업별로 정한다. 삭제 요청이나 보관 기간 만료 시 원본 DB, 벡터 색인, 캐시, 조사 사본과 외부 제공자 경로까지 처리 대상을 추적한다. 백업은 정해진 만료 정책을 따르며 복구 시 삭제·철회 기록을 재적용한다. 클라우드 자원의 견적상 보관 기간을 개인정보 보관 동의나 서비스 정책으로 대신하지 않는다.

## 11 품질 평가와 출시 기준

### 11.1 평가 세트

품질 검증 담당자는 Q01부터 Q08까지의 정상 질문과 경계 사례를 포함한 고정 평가 세트를 관리한다. 각 사례에는 단일 또는 복수 기대 유형, 명시적 하위 요구, 필요한 논리 기능·MCP 도구, 제외 가능한 중복 도구, 허용 상태, 필요한 권한, 기대 근거·기간, 금지 동작과 합격 조건을 기록한다. 모델이 생성한 기대 정답은 사람이 확인한다. Q02에는 안정적 개념, 최신 사실이 섞인 개념, 다의어, 미지원 용어, 잘못된 수치가 포함된 생성 답변과 생성·검증 모델이 같은 오류에 동의하는 사례를 포함한다.

평가에는 모호한 기업, 지시어, 상대 날짜, 한영 혼용, 복합 질의, 자료가 없는 경우, 정정·철회 문서, 서로 충돌하는 기사, 잘못된 그래프 경로, 로그아웃 후 응답, 외부 API 장애와 공격 입력을 포함한다. 대형 기업과 소형 기업, 자료가 많은 기업과 적은 기업을 나누어 확인한다. 자료량 차이를 기업의 중요성이나 투자 가치 차이로 해석하는지 점검한다.

전체 정확도와 함께 유형별 정밀도·재현율, multi-label micro·macro F1, 명시적 요구 커버리지, 필수 유형·기능·도구 누락률, 불필요·중복 MCP 호출률, 호출 수 분포, 커버리지 검증 LLM의 오승인·오차단률, 혼동 행렬, 잘못된 일반 유형 분류와 불필요한 확인 질문 비율을 확인한다. Jev 분류·기능 선택이 서버의 도구 계획으로 정확히 변환되는지, 검증 LLM이 허용 목록 밖 도구·인자·권한으로 확장하지 않는지도 평가한다. 근거 정합성은 인용이 존재하는 비율과 실제로 주장을 지지하는 비율을 나누어 평가한다. 성능 지표는 표본 수, 데이터 버전, Jev 모델·라우터 정책·임계값·MCP 레지스트리·커버리지 검증 모델·프롬프트·Luna 모델·프롬프트 버전과 함께 기록한다.

## 12 모델과 정책 변경 관리

모델, Jev 질문·임계값, 논리 기능 레지스트리, 커버리지 검증 모델·프롬프트·스키마, 논리 기능과 실제 MCP의 매핑, 도구 허용 목록, Luna의 시스템·유형별 프롬프트, 임베딩 모델, 검색 설정, 관계 스키마, 출력 검증 기준과 이슈 선정 규칙을 버전으로 관리한다. 모델 교체 시 같은 이름의 API라는 이유만으로 결과가 동일하다고 가정하지 않는다. 임베딩 변경 시 색인 재생성과 검색 품질도 검증한다.

변경 요청에는 목적, 영향 유형, 데이터 범위, 평가 결과, 알려진 실패, 승인자, 배포·롤백 방법을 기록한다. 개인정보 범위 확대, 새 외부 제공자, 도구 권한 확대, 투자 판단 범위 변경은 책임자와 해당 데이터·보안 담당자의 검토를 요구한다.

출시 전에 고정 평가 세트와 기존 실패 사례를 다시 실행한다. 제한된 환경에서 새 버전의 결과를 확인한 후 적용한다. 불합격이면 이전 코드·프롬프트·정책·데이터 조합으로 돌아갈 수 있어야 한다. 사용자 피드백을 즉시 자동 학습이나 정책 수정에 반영하지 않고 검토 후 평가 사례로 추가한다.

## 13 운영 감시와 감사 기록

챗봇 작업 단위로 요청 추적 ID와 작업 ID, 접수 시각, 가명 회원 식별자, requirementId와 명시적 요구, 내부 Q 유형·확률, 논리 기능 후보, 커버리지 검증 결과, 선택·추가·중복 제거 사유, MCP 레지스트리 버전과 실제 도구·상태, 예약·사용한 호출 수·시간·비용·조회량, 작업 status와 outcome, 정책·모델·프롬프트·데이터 버전, 근거 ID와 검증 실패 코드를 기록한다. 비회원의 거절된 접근은 질문 작업으로 생성하지 않고 필요한 접근 보안 기록으로 구분한다. 상세 내부 추론이나 불필요한 원문은 감사 필수 항목으로 두지 않는다.

실제 모델 호출인 live, 저장된 응답을 사용하는 replay, 저장 복구인 save_only를 구분하여 집계한다. save_only를 새로운 모델 호출로 세지 않는다. 제공자가 보고하지 않은 토큰·비용은 null이며 0으로 바꾸지 않는다. 내부 worker의 호출 전 예산 예약과 호출 영수증은 재시작 이후에도 유지하고, 송신 여부가 불명인 호출의 예약을 임의 해제하지 않는다.

배치 단위로 출처, 수집 범위, 중복 수, 후보 수, 통과·보류·실패 수, 검수 결과, 공개 전환과 롤백 기록을 남긴다. 브리핑은 회차, 선정 규칙 버전, 근거 목록과 정정 이력을 연결한다. 실제 모델의 비결정성 때문에 완전히 같은 문장을 재생성할 수 있다고 보장하지 않되, 어떤 자료와 설정으로 결과가 만들어졌는지는 추적 가능하게 한다.

운영 대시보드는 유형별 요청량, 분류 변경, 명시적 요구 커버리지, 필수 기능·도구 누락률, 불필요·중복 MCP 호출률, 커버리지 검증의 오승인·오차단, 실행 예산 초과, 확인 질문 비율, 근거 부족률, 출력 검증 실패율, 보류 적체, 출처 지연, 응답 시간과 비용을 감시한다. 기준선 대비 악화와 보안·공개 경계 위반을 구분하여 알린다. 수치 경보 임계값은 부하·시연 시험으로 정하고, 중대 권한 위반이나 비밀값 노출은 단일 사건도 즉시 대응한다.

API와 개인화 결과를 공용 캐시에 저장하지 않는다. 캐시가 필요한 내부 기능은 사용자 범위, 정책·데이터 버전, 기간·회차를 키에 반영하고 로그아웃·철회·버전 변경에 따른 무효화를 검증한다. CloudWatch 등 운영 시스템의 로그 접근도 역할별로 제한한다.

## 15 구현 단계별 적용

### 15.1 MVP 필수 범위

MVP에는 Q01부터 Q08까지의 multi-label 분류 계약과 미지원 유형 처리, 권한 검증, 공개 데이터 필터, 읽기 전용 도구, 근거 표시, 출력 검증, 버전 고정, 보류·재검증·공개 전환, 최소 감사 로그, 오류 신고와 중단·롤백을 포함한다. 유형별 실제 데이터나 MCP 도구가 준비되지 않았다면 해당 유형은 미지원 또는 이용 불가로 명확히 표시한다. Q02는 범용 용어 사전 없이 6.1절의 제한된 일반 LLM 경로와 표시·평가 기준을 적용하며 이를 근거 검증 완료 기능으로 소개하지 않는다. ZOOP 고유 개념에는 승인된 도움말·정책·화면 명세만 사용하고 일반 LLM이 내부 규칙을 만들지 못하게 한다.

Jev 라우터와 Q 유형별 MCP 호출은 현재 구현이 아니라 목표 MVP 구성이다. 활성화 전에는 별도 라우터 계약, TypeSafe 전송 승인, multi-label·논리 기능 선택 평가, 커버리지 검증 LLM의 구조화 계약, 논리 도구 ID와 실제 MCP 레지스트리의 매핑, Luna 챗봇 생성 stage, 전체 호출 수·시간·비용 예산과 실패 처리를 구현·시험해야 한다. 이 조건이 준비되지 않으면 기존 결정론적 분기 또는 미지원 안내를 사용하며 S1 의미 검증용 Jev를 라우터로 가장하지 않는다.

UI 고지에는 AI 생성·보조 결과라는 사실, 사건 답변의 기준 시점, 근거 확인 방법과 투자 판단 범위를 포함한다. 고지 문구만으로 검증·권한 통제를 대체하지 않는다. 모든 답변에 긴 경고문을 반복하기보다는 최초 안내와 해당 답변의 한계를 읽기 쉽게 표시한다.

### 15.2 출시 확인 순서

1. 담당 역할과 서비스 허용 범위를 승인한다.
2. 출처 이용 조건, 외부 모델 처리 조건, 개인정보 보관·삭제 방식을 확정한다.
3. 정상 유형·예외 상태·논리 기능 레지스트리·최소 충분 도구 매핑·요구 커버리지 검증·실행 예산을 구현 명세와 맞춘다.
4. 검증·검수·공개 전환과 회차 고정을 시험한다.
5. 11장의 평가와 보안·장애 시나리오를 실행하고 결함을 해결한다.
6. 운영 시간·비용·경보·복구 담당자를 확인한다.
7. 정책 버전, 구현 버전, 시험 결과, 미지원 기능과 승인자를 기록하고 공개한다.

## 17 작성 근거와 변경 이력

### 17.1 프로젝트 자료

- ZOOP 클라우드 사용계획서 TA 반영본 2026년 10월 13일. 서비스 목적, EC2·RDS·Neo4j·S3 역할, 자동 검증과 보류 검수, 재검증, 공개 버전 전환, 개발 운영 시간의 기준으로 사용했다.
- 돈벌레 최종 프로젝트 PDF. 제공 파일은 출퇴근 브리핑과 회차 관계 그래프를 담은 단일 대형 페이지다. 파일 내부의 ‘PDF 46쪽·47쪽’은 화면 설명의 원자료 표기이며 제공 파일의 실제 페이지 번호가 아니다. 회차 불변, 시각 구분, 지표별 상태와 비교 동작의 기준으로 사용했다.
- 2026년 10월 13일 제품 방향. 사용자 질의를 유형별로 분기하고 유형에 따라 답변을 제공하는 방식을 챗봇의 핵심 설계로 반영했다.
- 2026년 10월 16일 제품 논의. Q02의 전용 용어 저장소 부재, 제한된 일반 LLM 경로, multi-hop 오류 전파 통제, 직접·간접 관계의 의미 분리, 간선 근거와 챗봇 자동 검증의 경계를 반영했다.
- 2026년 10월 17일 제품 결정. 범용 금융·산업 용어 사전은 구축하지 않고 일반 개념은 Luna 생성과 자동 검사로 처리하며, ZOOP 고유 정책·도움말 문서는 유지한다. 챗봇 분류는 Jev의 Q01~Q08 typed multi-label 판정과 허용된 논리 기능 선택, Luna의 분리된 coverage-verifier stage, 서버의 동적 MCP allowlist 호출, Luna answer-generator stage로 구성한다. 유형 수는 세 개로 고정하지 않고 필요한 도구를 실행 예산 안에서 호출한다.
- 2026년 10월 17일 v0.7 초기 구현 결정. Jev `0.70/0.35` 선택 기준, Luna 커버리지 최대 2회와 답변 생성 1회, 다섯 MCP 레지스트리 그룹, MCP 12회·동시 4회·추가 1라운드·ChatJob 30초·문서 20개·그래프 3-hop·24k/2k 토큰 상한, Q02 고정 안내와 MVP `PARTIAL` 미지원을 채택했다.
- 2026년 10월 20일 v0.8 설계 검토. 조회 결과로 대상이 정해지는 복합 질문은 호출 전에 되물을 수 없으므로, 계획에 단계와 서버가 평가하는 개수 체크포인트를 선언하고 답변 생성 전까지 `clarification`을 허용했다. 추가 조회를 계획된 단계와 보충 라운드로 구분했다. `answered`에서 답하지 않은 요구를 본문 문장 대신 공개 `ChatResult.limitations`로 구조화하고 출력 검증이 요구 커버리지를 기계적으로 확인하게 했다. Q02 고정 안내·빈 인용이 일반 개념과 근거 기반 사실을 함께 답하는 `mixed` 결과와 충돌했으므로, 본문을 근거 수준별 `sections`로 나누고 Q02 규칙을 `general_knowledge` 구간에 한정했으며 `answerBasis`를 구간에서 계산하게 했다. 구현 계획에서 빠져 있던 챗봇 Jev 의미 검증의 순서(결정론적 검사 후), 대상(근거 구간 claim), 판정 처리(contradicted·금지 조언은 전체 실패, hold는 요구 단위 제외)와 장애 처리를 정했다. 근거 없이 정한 ChatJob 30초를 단계별 잠정 상한과 계획 경로별 실행 기한(최대 60초)으로 바꾸고 실측 보정 규칙을 두었으며, 실행 중 한도 초과를 재실행 가능한 `transient`와 재실행해도 같은 `budget_exceeded`로 나누고 `reason` 코드·재실행 3회 상한·공개 `phase`를 정했다. 챗봇 Q04·Q05가 비공개 AI 투영 저장소인 Neo4j를 읽는 것으로 적혀 있어 지도와 다른 그래프로 답할 위험이 있었으므로, 그래프 도구를 공개 그래프 API와 같은 앱 스냅샷 읽기 경로로 고정하고 소유를 애플리케이션 백엔드로 옮겼으며 hop을 화면 depth 의미로 정의했다. PR 리뷰에서 모델 송신 후 응답 불명 timeout까지 재실행을 허용하면 중복 호출·과금이 생길 수 있다는 지적에 따라, 송신 전 실패와 응답을 받은 확정 실패만 `rerun`하고 응답 불명은 `response_unknown`(retry 없음, `reconcile_only`)으로 분리했다. 같은 리뷰에서 도구 오류를 근거 부족으로 분류할 수 있던 체크포인트 규칙을 `failed` 우선으로 고쳤다. 10월 21일 구현 착수 검토에서 확인 답 작업이 다시 확인 질문을 낼 수 있어 한 질문 사슬의 비용에 상한이 없었으므로, 사슬을 최대 2회로 제한하고 상한에서는 `guidance`로 끝내며 루트 질문과 사슬의 답을 순서대로 합쳐 다시 실행하도록 정했다.
- 저장소 `52b50d0` 기준 [목표 API](api/openapi.yaml)와 [문서 연결 기준](system/links.yaml). 회원 전용 질문, 최초 문맥 고정, 최근 1개월, 작업 상태·결과·오류 분리, 자동 재생성 금지의 기준으로 사용했다.
- [ERD v6](erd/zoop-core-erd-v6.md) 및 [v6 변경 이력](erd/zoop-core-erd-v6-changes.md). 불변 결과·저장 복구, 회차당 단일 발행, 검수 revision, 관리자 복수 대기·단일 실행 규칙을 반영했다. 변경 이력 상단의 2026년 10월 13일 추가 변경이 최초 슬롯 정책을 대체한다.

자료에서 확인된 계약과 본 정책의 추가 요구사항을 구분한다. Q01~Q08 내부 분류, 복합 응답 확장, 출시 수치와 역할별 승인 절차는 설계 제안이다. 공개 응답 필드·상태·오류와 저장 제약은 관련 계약을 따른다. 와이어프레임의 기업·수치·사건이나 authored replay를 실시간 사실·실제 모델 품질·운영 성과의 증거로 사용하지 않는다. 정책 목표에 포함된 전체 철회 전파, 파이프라인 공개 연동 및 정기 운영의 구현 완료 여부는 별도로 확인한다.
