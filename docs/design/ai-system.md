# AI 실행과 문서 공개 계약

## 현재 구현 범위와 설계 논의 적용

**현재 실행 단위는 S1 문서 요약·문서×기업 판정·별도 의미 검증과 기존 회차 outlook이며, S2-1의 독립 오프라인 원문 준비·검사, S2-2의 독립 오프라인 이벤트·SAME·주제 후보 준비, S3의 독립 오프라인 관계·영향 후보 준비와 HOLD 재검증도 구현했다. S4는 저장된 S2/S3 기록에서 변경된 문서·source·grant에 기대는 job과 후보를 찾는 읽기 전용 조회만 구현했고 철회·공개 차단·복구는 구현하지 않았다. 전체 AI 기능이나 FS074–081 전체의 완료를 뜻하지 않는다.** 설계 보고서 `local://ai-contract-design.md`의 §3–6과 §8/S1에서 합의한 worker 소유 경계, camelCase JSON, 불변 영수증, 현재 공개 gate, 무호출 저장 복구를 적용한다. 기존 outlook 생산자를 삭제하지 않는다는 추가 합의도 반영했다. S2-1은 `local://s2-ingestion-contract.md`의 독립 저장소·현재 registry·정확한 원문 좌표 계약을 적용했다. 보고서는 설계 근거이며 실행 증거는 아래 별도로 기록한다.

**2026-10-16 네이티브 수집 경로:** 명시한 URL의 단발 HTTP 수집(`zoop-ai-collect`) → PoC 없는 HTML/PDF 정제·버전·정확 인용 검사(`zoop-ai-ingest`) → Spring 문서 등록까지 로컬 합성 종단 검증을 완료했다. 검색·RSS·DART API 인증·주기 수집·실제 사이트 운영 검증은 포함하지 않는다. 수집은 결정적 검사이며 문서의 의미 판정은 독립 S1 worker가 담당한다.

| 실행 단위 | 현재 상태 | 소유 의미와 후속 범위 |
|---|---|---|
| S1 | 구현: 문서 세 stage + 기존 briefing-outlook 이행 + 실제 JSON CLI + BFF 수입 + Spring operator 문서 분석(PostgreSQL) | 문서의 versioned claim/citation과 기업별 판정을 검증·저장하고, 기존 회차 판정의 생성·발행 고정을 유지한다. |
| S2 | S2-1: 명시 URL 단발 수집·원문 정제·map·불변 버전·재개·정확 인용 검사. S2-2: 오프라인 이벤트·SAME·주제 후보 | `collect`·`ingest`·`extract`는 공개 의존성만으로 동작한다. 검색·API 인증·정기 수집과 실제 공급원 검증은 미완료다. [문서 import](../../api/docs/DOCUMENT_IMPORT.md)는 수집 receipt·실제 수집 시각·날짜 정밀도를 검증해 `artifacts`·`articles`·`article_versions`에 저장한다(분석·evidence 저장은 별도 [문서 분석](../../api/docs/DOCUMENT_ANALYSIS.md)). S2-2는 **네이티브 replay 전용**(`extraction_replay.py`, 어댑터 `zoop-extraction-native-replay-1`, fixture `zoop-analysis-replay-1`)이며 authored replay만 실행한다. 원본 PoC 어댑터 binding으로 저장된 이전 job은 읽기용 기록으로만 남고(`delivery` withheld `analysis_contract_changed`, run/resume 거부) 운영자의 명시 재제출이 필요하다. `submit`·내부 `/internal/v1/extraction-jobs`는 구현됐으나 live 추출·retrieval·승인·게시·주제 승인은 후속이다. |
| S3 | 구현(오프라인 후보 단계): 관계 후보·독립 관계 검증·영향 후보·독립 영향 검증·HOLD 검수 후 재검증 | 공급/경쟁/투자·사건 참여·기업–주제 관계와 영향 방향 라벨, 관계 적격성(eligible/hold/reject)은 영향 불확실성과 분리한다. authored replay만 실행하며 live 모델, 공개·승인, 공개 GraphDB 활성화, 앱 등록, 관리자 화면은 후속이다. 완료된 job 하나를 **비공개** Neo4j version으로 stage하는 `zoop-ai-graph`(FS080 일부, FS081 철회 아님, 활성 공개 상태 없음)는 아래 'S3 → 비공개 Neo4j 버전 projection' 절이다. 등록 전용 CLI `submit`(fixture 없이 freeze만, 실행은 `resume`)을 구현했다. 내부 HTTP는 `ai/service`의 별도 `/internal/v1/relation-jobs` 가족으로 제출·상태·결과·취소·복구와 HOLD 검수(allow/reject)·큐에 넣는 재검증·operation 조회·복구를 노출한다(아래 내부 HTTP 절). 목록 HTTP는 없다. |
| S4 | 일부 구현: S2/S3 읽기 전용 의존 대상 조회. 철회·barrier·복구는 미구현 | 변경된 문서(버전)·source·grant가 기대는 저장 job·후보를 나열만 한다(아래 S4 절). 전체 의존성 철회, 과거 pin·채팅·회차·캐시까지 공개 barrier와 증분 복구는 후속 |
| S5 | 계획, 미구현 | 기업·시장 요약, 중요도 선정, 공통 출퇴근 브리핑 강화. 이미 있는 outlook 생산 능력은 S1 이행으로 보존한다. |
| S6 | 계획, 미구현 | 실제 AI 질문 해석·답변·되묻기와 채팅 작업 seam 이행 |
| S7 | 계획, 미구현 | 개인화 브리핑·소유권·평가·전체 사용량 끝단 |

전체 명세는 요구 범위이며 위 표가 S2–7을 제외하는 결정은 아니다. 실행되지 않는 클래스·echo 응답·빈 디렉터리로 후속 기능을 대신하지 않는다. 원본 PoC는 수정하거나 vendoring하지 않았다. BFF의 pinned PoC 읽기 adapter는 유지한다. S1 worker는 Pydantic·HTTPX만 사용하며, `ai/pipeline`은 collect·ingest·extract·relation·dependents·graph·handoff **전체가 PoC를 import하지 않는다**(`poc` extra·`poc_guard` 제거, 공개 의존성만, CI 토큰 불필요). 이것은 PoC 의존 제거이지 AI 능력 확대가 아니다: 분석은 authored replay이고 라이브 S2/S3, S5–S7, 실제 모델 품질 근거는 없다. 구성·명령은 [ai/pipeline/README.md](../../ai/pipeline/README.md)를 따른다.

### 네이티브 분리 실행 증거 (2026-10-16, 로컬·미커밋)

- 별도 환경(당시 `.venv-public`, 이후 기본 pipeline 환경으로 통합됨)에 private Git 인증 없이 공개 lock 의존성만 설치했고 `investmate`가 없는 환경의 시험 **163개**와 실제 HTTP HTML/PDF 수집→ingest→export가 통과했다. 권한 철회·부분 실패·실제 수집 시각·날짜 정밀도·무재요청 멱등성을 확인했다.
- 보안 검토 4건은 7개 실패 사례로 먼저 재현한 뒤 수정했다. 느린 header/body에도 절대 deadline을 적용하고, robots/redirect 직전과 저장·반환 전 권한을 다시 확인한다. FIFO는 비차단 regular-file 검사로 거절하며 HTML scope 탐색은 선형 candidate membership을 사용한다. 최종 공개 환경 회귀가 모두 통과했다.
- 별도의 로컬 TLS 실험에서 검증된 IP로 연결하면서 원래 Host·SNI·인증서 이름을 유지했고, 신뢰하지 않는 CA·잘못된 hostname·허용되지 않은 redirect·private DNS 답을 거절했다. 임시 CA·서버·파일은 정리했다. 실제 외부 사이트나 조직 인증서 환경의 검증은 아니다.
- (이전 기록) 당시 선택 `poc` extra를 사용하는 전체 pipeline **488개**와 기존 CLI smokes, 서비스의 실제 pipeline 통합 **115개**, 전체 handoff HTTP smoke·OpenAPI 일치 검사가 통과했다. 이 extra는 이후 제거됐고 아래 '네이티브 분석 전환' 항목이 현재 상태다.
- 실제 PostgreSQL 17의 새 시험 DB에서 **10단계·Java import 22회·문서 4개·거절 20건**을 검증했다. 수집 시각은 fetchedAt으로 저장하며 day는 DATE로, 오프셋 없는 시각은 unknown으로 남긴다. 재수입은 행·파일을 다시 쓰지 않는다. 전체 Java 시험 436개 중 19개는 건너뛰었고 실패·오류는 0이었다.
- **네이티브 분석 전환(2026-10-16, 로컬·미커밋, Main 실행 검증).** S2-2를 네이티브 replay 모듈로 옮기고 `investmate` import·`poc` extra·`poc_guard`를 제거했다. 설치 환경에서 PoC와 관련 패키지 23개가 제거됐으며 전체 pipeline **627개**, 서비스 **886개**, 실제 pipeline 통합 **115개**가 통과했다. `Article.version`·요청 preimage·Mention 모양은 이행 전에 고정 PoC에서 한 번 캡처한 literal(`tests/data/native_analysis_golden.json`)과 대조한다. 새 binding은 native adapter와 `zoop-analysis-replay-1`을 쓰며 PoC 검증을 수행했다고 주장하지 않는다. 원장 스키마는 유지하고 옛 adapter job은 원천 registry·fixture를 열기 전에 읽기 전용으로 식별한다. inspect는 이력만, run/submit/resume는 `analysis_contract_changed`로 상태 변경 없이 거절하고 명시적 cancel만 허용한다. 이행 경계 결함은 **45개 실패 사례**로 재현 후 수정해 통과했다. 수집→추출→관계→인계 CLI·S2/S3 HTTP·실제 Neo4j 적재/조회/복구 smoke도 PoC 없는 환경에서 통과했다. 자동 데이터 변환·재분석은 없고 기존 BFF의 별도 PoC 의존성은 유지한다.
- 이 과정에서 비웹 import가 저장 성공 후 종료하지 않는 결함도 확인했다. 실제 thread dump의 non-daemon `scheduling-1`이 원인이어서 `AuthRateCleanup`을 웹 애플리케이션에만 등록하도록 수정했다. 비웹 정상 종료와 웹 서버의 scheduler 유지, 원래 전체 수입 시나리오 통과를 각각 확인했다.

기존 PoC parser profile로 시작한 round는 새 native profile로 몰래 재개하지 않고 `parser_profile_changed`로 거절한다. 저장된 불변 문서·export는 유지하며 새 준비는 새 profile/version으로 수행한다. 수집 receipt는 운영자 소유 bytes·설정의 일치 기록이지 서명된 네트워크 증명이나 이용 허락이 아니다. 실제 데이터 수집·유료 모델 호출·배포·원격 CI는 이번 로컬 검증에 포함하지 않았다.

## 저장소와 공개 seam

- `ai/worker/src/zoop_ai/contracts.py`가 S1 wire 타입을 소유한다. worker 도구 `ai/worker/scripts/export_schema.py`가 생성한 `docs/api/ai-contract.schema.json`과 `ai/worker/fixtures/contracts/synthetic-document/`, `synthetic-outlook/`의 표본(BFF 소유 `prototype/bff/scripts/export_contracts.py`가 생성)은 언어와 독립된 계약이다. 실제 kind는 문서 세 stage와 기존 `briefing-outlook` 네 가지다.
- `provider.py`의 OpenAI-compatible adapter는 실제 `POST chat/completions`를 전송한다. replay adapter는 fixture 순서와 정확한 stage/input/config digest를 대조한다. 불일치·소진은 실패이며 생성 대체값이나 자동 fallback이 없다.
- `store.py`/`runner.py`는 작업, 호출, 영수증, 불변 산출물, 전역 호출 예산 예약을 worker의 별도 SQLite에 저장한다. 앱 SQLite를 공유 쓰기하지 않는다.
- `zoop_bff.ai_worker.AiWorkerClient`는 기존 `LaunchSpec`·process-group 감독 패턴을 재사용하여 설치된 worker 콘솔 명령(기본 `ai/worker/.venv/bin/zoop-ai`, `make worker-install`)과 JSON으로 통신한다. 명령이 없으면 `worker_unavailable`로 닫히고 상대 경로(worker state·grants·replay·명령)는 호출자의 cwd 기준으로 절대화한 뒤 실행하며 BFF 인터프리터나 `PYTHONPATH`로 worker 소스를 읽지 않는다. 앱은 worker DB를 직접 읽거나 쓰지 않는다.
- `DocumentAnalysisStore.import_job()`은 현재 문서 version/hash·기업 연결·synthetic provenance·grant·생성/의미 검증 영수증·인용 ID와 span을 다시 확인한다. 수입과 앱 receipt/사용량 기록은 하나의 짧은 transaction이다.
- `GET /api/companies/{id}/documents`와 `GET /api/evidence/{id}?companyId=...`는 저장 결과만 읽는다. `documentSummary`, `analysisStatus`, `analysisProvenance`, `documentVersion`, `resultVersion`을 제공한다. 기존 `DocumentSentiment`의 모양은 변경하지 않는다.

새 BFF 필드는 항상 직렬화하되 결과가 없으면 nullable이다. 목표 OpenAPI에서는 단계적 소비자를 위해 새 필드를 optional·nullable로 명시한다. `analysisStatus.summary/sentiment`는 각각 `not_requested|pending|failed|withheld|available`이다. 실제 평가를 마쳤으나 방향 근거가 부족한 `sentiment.label=undetermined`와, 판정 산출물이 없는 `sentiment=null`은 다르다. 요약과 판정은 독립 작업이다. 요약의 HOLD/실패가 유효한 기업별 판정을 지우지 않는다. 외부 오류를 판단 보류로 바꾸지 않는다.

`resultVersion`은 공개 요약이 있으면 그 요약 버전, 요약 없이 판정만 있으면 판정 버전이다. summary citation의 document/version/resultVersion과 evidence 응답 문맥을 프론트엔드가 대조한다. JS/Java는 UTF-16 index를 그대로 쓰면 안 된다. `offsetUnit=unicode_code_point`, `end`는 exclusive이고, exact 검증 때 공백·NFC·따옴표를 임의 정규화하지 않는다. S1 합성 표본의 cleaner는 identity이며 raw locator도 명시한다. S2-1은 별도 ingestion 저장소에서 HTML/PDF 정제와 복수 locator를 복원한다. 이 내부 문서를 현재 앱 Dataset에 등록하거나 공개하는 경로는 아직 없다.

## 호출·상태·복구

| 명령/상태 | 실제 동작 | 재호출 규칙 |
|---|---|---|
| `submit` | stdin 요청과 stage 설정을 불변 digest로 저장한다. 같은 job+digest는 기존 작업, 다른 digest는 `job_input_conflict`다. | 모델 호출 0 |
| `run` | grant→durable budget reservation→`outgoingcall.started`→HTTP/replay→`receivedreceipt.saved`→exact→별도 semantic→`artifact.persisted` | 자동 provider retry 없음 |
| `get` | versioned 작업·영수증 메타데이터·산출물을 내부 JSON으로 조회한다. 사용자 API는 이 내부 출력 전체를 노출하지 않는다. | 모델 호출 0 |
| `resume` | 영수증이 저장된 단계는 다시 파싱/검증/저장한다. 아직 송신하지 않은 단계만 실행할 수 있다. | 완료·취소·reconciling은 새 호출 없음 |
| `cancel` | 작업 fence를 올려 늦은 결과의 산출물 저장을 막는다. 발생한 비용/응답 영수증은 보존한다. | 과금 취소를 보장하지 않음 |
| timeout/응답 불명/receipt 저장 전 종료 | `reconciling`, `resumeMode=reconcile_only`로 남는다. 프로세스 종료나 lock 해제는 미청구의 증명이 아니다. | 자동 재실행 금지 |
| receipt 저장 후 산출물 저장 실패 | `persisting`, `resumeMode=save_only`로 보존한다. HOLD/REJECT인 별도 검증 산출물도 작업·kind로 재사용한다. | 저장된 영수증·산출물만 재사용하고 provider는 다시 부르지 않음 |
| worker ready 후 BFF import 실패 | 기존 job `get` 후 import만 반복한다. 앱 transaction은 rollback된다. 동일 attempt는 고정 identity를 확인하고 `started→received→validated` 상태와 처음 확인된 usage만 전진한다. | 새 job/model call·중복 비용 없음 |

네트워크 동안 SQLite write lock은 보유하지 않는다. 모든 live attempt(생성과 의미 검증 포함)는 같은 durable global ledger에서 먼저 예약한다. CLI 재시작이나 두 프로세스 실행으로 ceiling을 초기화하지 않는다. 미확인/송신된 호출의 예약은 임의 해제하지 않는다. 이미 등록된 ceiling을 명령 재실행으로 증가시키지 않는다. Replay/cache는 유료 attempt와 분리한다. provider가 미보고한 input/output/cached/reasoning token과 timeout 비용은 `null`이다. 단가·금액 상한은 미정이며 0원으로 표시하지 않는다.

캐시 identity는 문서 내용/version/source hash, 기업, grant revision, provider/endpoint revision, model, effort, prompt 내용/version, schema 내용/version, policy를 포함한다. 제한 문장 검증을 강화한 현재 정책은 `zoop-document-gate-2`이며 이전 정책 산출물은 raw 이력으로 보존하되 cache hit나 BFF 공개 gate를 통과하지 않고 `document_policy_outdated`로 보류된다. 모델/effort/prompt/policy가 바뀌면 새 작업과 새 cache key다. 이미 제출한 같은 job의 설정을 조용히 바꾸지 않는다. 불변 산출물은 재사용하지만 반환·수입 때 현재 문서/권한/visibility를 대조한다.

## 권한과 공개 gate

source grant는 `enabled`와 `rights`, `allowedOperations`, `recipients`, `purposes`, `evidence`, `expiresAt`을 분리한다. 켜졌다는 사실은 모델 전송 승인이 아니다. read/store/model-send/quote-display 권한과 생성·검증 목적/수신자가 모두 필요하다. unknown·증거 없는 권한·만료는 fail closed다. 모델 전송 전과 회수 후 다시 확인한다. 운영자가 지정하는 `--grants`는 서버 소유 registry이며 job/model 입력이 권한을 발급하지 않는다. BFF도 server-owned registry snapshot 갱신과 worker artifact 수입을 분리한다. artifact에 실린 과거 grant는 실행 영수증일 뿐 현재 권한을 갱신하지 않으며 opaque revision 문자열을 정렬해 최신을 추측하지 않는다.

live 수신자는 단순한 `openai-compatible` 프로토콜 이름이 아니라 `openai-compatible:<providerRevision>`으로 등록한다. `providerRevision`은 승인된 base URL을 포함한 endpoint identity의 digest다. 제출 때 고정한 endpoint와 실제 client endpoint가 다르면 송신 전에 configuration failure로 끝낸다. 다른 업체/endpoint로 조용히 전송하거나 grant를 확대하지 않는다. replay 수신자는 네트워크 없는 `authored-replay`다.

기존 데모는 저장 source의 읽기 계약을 유지한다. 새 live grant를 자동 생성하지 않으며 실제 본문에 authored replay를 수입할 수 없다. [외부 API 조사](../evidence/external-api-candidates-2026-10-08.md)의 NAVER Developers Search 데이터는 AI 입력으로 금지하며 HUB의 별도 허가는 unknown이다. 공개 URL, 키 보유, 관리자 enable을 제3자 전송/요약 게시 권리로 해석하지 않는다.

모든 공개 사실/해석 claim에는 정확한 versioned citation이 필요하다. 공개 `limitations`의 각 문자열도 `assertionKind=limitation` claim과 정확히 대응해야 하며 별도 semantic stage가 사실·해석·제한 claim 전부를 `supported|contradicted|insufficient`로 판정한다. 생성기와 분리된 검증자는 투자 권유·미지원 인과도 검사한다. exact 또는 schema 실패는 공개하지 않는다. semantic HOLD/REJECT 산출물은 worker 내부에서만 보존하고 BFF는 이유와 null을 반환한다.

현재 S1 gate는 두 문서 consumer의 source/context에 적용한다. `document_analysis_visibility`의 explicit deny와 원문 withdrawn은 문서 목록과 direct evidence GET을 차단한다. 저장 raw/모델 영수증과 승인 이력은 worker-private으로 남는다. 공개 응답에는 사용자 디렉터리, key, raw provider reply, private 파일 경로가 없다. 이전 채팅/브리핑/그래프 전체에 대한 의존성 closure까지 구현했다고 주장하지 않는다(S4).

기존 `sentiment_results`와 이미 발행된 회차 payload는 불변 읽기를 유지한다. 예전 BFF provider/client와 `scripts/judge_sentiment.py`의 중복 live 분기는 제거하고, 문서와 기존 회차 생산을 worker로 이행했다. `scripts/judge_outlook.py`는 실제 worker CLI를 통해 비어 있지 않은 미발행 회차의 outlook을 생성하고 원래 발행 경로에 저장한다. 기존 issueIds 정확 참조·금지 표현 검증은 `legacy-outlook-exact-1` 정책이며 `validation.semantic=null`이다. worker의 새 생성 검사뿐 아니라 BFF importer도 미발행 ready/cache 산출물의 한국어 공백 정규화 예측어와 기존 영문·가격·인과 금지 표현을 다시 검사하므로, 이전 약한 검사로 저장된 금지 rationale은 발행되지 않는다. 이미 발행된 불변 payload를 소급 변경하지 않는다. 문서의 별도 의미 검증과 동급으로 검증됐다고 쓰지 않는다. 빈 회차는 모델 호출 없이 outlook null, 발행된 회차는 null까지 그대로 유지한다.

## ERD v6와 AI 저장 책임 대조

[ERD v6](../erd/zoop-core-erd-v6.md)(2026-10-13, [변경 이력](../erd/zoop-core-erd-v6-changes.md))이 PostgreSQL 최신 설계 기준이다. main `91113ce`(PR #18)는 AI 작업 식별·영수증·grant snapshot·검수 원천 버전 규칙을 v6와 공개 OpenAPI에 반영했다. 앱에 적용된 Flyway migration은 인증 스키마(첫 `V20261012210200`과 v6 정렬 `V20261013000000`)뿐이며 AI 저장 테이블(`artifacts`·`document_analyses`·`analysis_jobs`·`ai_executions` 등)의 migration은 아직 없다. AI worker·서비스·pipeline은 계속 자기 SQLite만 쓰고 이 저장소에서 v6 SQL을 실행해 확인한 것도 없다. *(위 문장은 2026-10-13 기준이다. 2026-10-14 로컬 작업으로 문서 쪽 `artifacts`·`articles`·`article_versions`의 migration `V20261014120000`과 operator 문서 import가 추가됐고 소유 담당은 [migration 소유권](../development/api-migration-ownership.md)에서 확정 전이다. `analysis_jobs`(와 챗봇·브리핑 실행 테이블)의 migration은 여전히 없다. 로컬 검증(미커밋·원격 CI 없음·유료 모델 호출 0): Java 157개 시험 통과, 설치된 `zoop-ai-ingest`와 실제 Spring jar·PostgreSQL 17.11 smoke 16단계(JVM 36회)로 article 3·version 5·artifact 5를 확인하고 원본 ledger가 바뀌지 않았으며, SQL 증명(`BEGIN…ROLLBACK`)도 통과했다. compose의 PostgreSQL 16.13은 시험하지 않았고 파일 내구성은 하드웨어·파일시스템의 fsync 준수를 가정한다. 자세한 범위와 한계는 [문서 import](../../api/docs/DOCUMENT_IMPORT.md).)* *(2026-10-14 문서 분석: 같은 날 `document_analyses`·`evidence`·`ai_executions`의 migration `V20261014130000`과 operator 전용 비웹 문서 분석이 로컬로 추가됐다. 로컬 검증(미커밋·원격 CI 없음·유료 모델 호출 0): 전체 Java 시험 301개 통과, 실제 Spring jar·HTTP·`ai/service`·worker·PostgreSQL 17.11 smoke 28단계(JVM 65회)에서 `document_analyses` 16·`ai_executions` 27 = 워커 호출 27·`evidence` 10을 확인하고 원본 ledger가 바뀌지 않았으며, SQL 증명(`BEGIN…ROLLBACK`)도 통과했다. compose의 PostgreSQL 16.13은 시험하지 않았다. 범위·한계는 [문서 분석](../../api/docs/DOCUMENT_ANALYSIS.md).)* 아래는 이 문서의 어휘와 v6의 어휘를 대조해 v6가 정한 것과 닫지 않은 것을 나눈 것이다. 열린 항목은 담당자 합의로 정한다.

> **병합된 분기 기준(2026-10-13, main `91113ce`).** 팀의 `fix/17-erd-v6-alignment`(`af2f0e3`)는 PR #18로 main에 병합됐고, v6와 공개 OpenAPI가 이 대조의 항목 상당수를 **문서로** 정했다. 공개 `analysis_jobs.id`와 내부 AI `jobId`의 분리(`analysis_jobs.checkpoint.aiUnits[]`, `document_analyses.ai_job_id`·`briefing_attempts.stages`가 submit 전에 ID와 불변 요청 artifact를 커밋), 호출 영수증의 `ai_job_id`·`ai_attempt_id`·`receipt_artifact_id`(`UNIQUE(ai_job_id, ai_attempt_id)`로 같은 시도의 중복 집계 금지), 실행 당시 권리 snapshot(`grant_id`·`grant_revision`·`grant_checked_at`·`grant_scope`, 현재 권한이 아님), 그리고 검수 결정의 AI 원천 CAS(`expectedSourceVersion`·`expectedSourceRevision`, 앱 `expectedRevision`과 별개이고 하나라도 다르면 결정·재검증 작업·감사를 만들지 않는 REVISION_CONFLICT)다. (2026-10-13 기준) 이 저장소에서 그 SQL이나 앱 구현을 실행해 확인한 것이 없었고 앱 migration도 인증 스키마뿐이었다. 이후 문서 등록·문서 분석 저장이 추가됐다(위 2026-10-14 주석). 이 저장소의 S3 내부 검수 HTTP는 그 규칙을 내부 계약으로 따른다(아래 ‘S3 관계 job의 내부 HTTP’). 서비스의 `sourceVersion`·`sourceRevision`은 런타임 원천 값이며 앱 revision이 아니다. 아래 표의 ‘열려 있는 것’은 병합된 v6 기준으로 다시 적었다.

## 설정 이행과 재현 명령

실제 모델·effort·예산 운영값은 아직 결정하지 않았다. stage env는 `prototype/bff/.env.example`에 기록한다. 옛 `ZOOP_SENTIMENT_MODEL`/`ZOOP_SENTIMENT_REASONING_EFFORT`의 문서 설정은 `ZOOP_AI_DOCUMENT_SENTIMENT_MODEL`/`ZOOP_AI_DOCUMENT_SENTIMENT_REASONING_EFFORT`로, 회차 설정은 `ZOOP_AI_BRIEFING_OUTLOOK_MODEL`/`ZOOP_AI_BRIEFING_OUTLOOK_REASONING_EFFORT`로 명시적으로 옮긴 뒤 옛 export를 제거한다. 요약은 `ZOOP_AI_DOCUMENT_SUMMARY_*`, 검증은 `ZOOP_AI_VERIFY_*`로 별도 승인한다. 런타임 alias는 없다.

live에는 `ZOOP_AI_LIVE_ENABLED=1`, 양수 `ZOOP_AI_GLOBAL_MAX_CALLS`, 실행하는 stage model, 승인된 current grant와 API 설정이 모두 필요하다. 문서 작업은 생성과 VERIFY 양쪽 모델을 요구하고(VERIFY를 네이티브 Jev로 고르면 `ZOOP_AI_VERIFY_MODEL`/`_REASONING_EFFORT`는 비우고 `TYPESAFE_VALIDATION_MODEL=jev-1.14.0`·`TYPESAFE_API_KEY`를 요구하며 grant에 `typesafe-native:<revision>` 수신자가 따로 필요하다), 기존 outlook은 BRIEFING_OUTLOOK 모델을 사용한다. effort가 비면 요청 필드를 생략한다. 미지원 옵션은 configuration/provider failure로 남기며 조용히 제거하지 않는다. 예산 gate는 durable call ceiling이고(Jev 호출도 같은 상한에서 센다) 실제 단가·금액 상한과 전체 token ceiling의 운영값은 미정이다. 실제 모델/키/.env를 열거나 유료 live를 실행하지 않는다.

저장 상태를 분리한 네트워크 없는 합성 재현은 다음과 같다. 공유 `var`, 기본 8787/5173을 사용하지 않는다.

```sh
ZOOP_SNAPSHOT_PATH="$PWD/ai/worker/fixtures/contracts/synthetic-document/snapshot.json" \
ZOOP_COMPANY_CATALOG="$PWD/ai/worker/fixtures/contracts/synthetic-document/snapshot.json" \
```

BFF 수입 재시도와 source deny는 다음 명령을 사용한다. 두 명령 모두 모델 호출이 없다.

```sh
  --state-dir /tmp/zoop-ai-doc-bff-demo --document-id doc-synthetic-s1 --reason '합성 문서 공개 철회'
```

import도 실행할 때 위와 동일한 synthetic `ZOOP_SNAPSHOT_PATH`/catalog를 지정한다. 일반 앱의 실제 source/state에 합성 응답을 섞지 않는다. schema 재생성은 `ai/worker/scripts/export_schema.py`(`make worker-schema-check`), fixture 재생성은 BFF 소유 `prototype/bff/scripts/export_contracts.py`(`make worker-contracts-check`), 검증은 `ai/worker/scripts/validate_contracts.py`로 수행한다. export는 기존 BFF 환경의 pinned PoC Article.version/evidence ID 규칙을 fixture 생성에만 재사용하며 원본에 쓰지 않는다. worker만 배포할 때 fixture/schema는 별도 계약 파일로 함께 전달한다.

### 기존 outlook 생성·빈 회차·불변 발행 재현

```sh
prototype/bff/.venv/bin/python prototype/bff/scripts/replay_outlook_fixture.py \
  --worker-state /tmp/zoop-ai-doc-outlook-worker \
  --bff-state /tmp/zoop-ai-doc-outlook-bff \
  --empty-bff-state /tmp/zoop-ai-doc-outlook-empty
```

driver는 실제 `scripts/judge_outlook.py --replay ... --grants ... --source-id ... --grant-id ... --grant-revision ... --round ...`를 실행한다. `--synthetic-now`는 합성 replay에서만 가능한 재현용 Clock hook이다. actual/live 자료의 clock을 바꾸지 않는다. 합성 2026-10-08 저녁 회차는 이슈 1개로 판정을 생성하고, 같은 회차 재실행은 발행값을 그대로 반환하며 새 worker 작업이 없다. 같은 문서가 아직 들어오지 않은 출근 회차는 0개·outlook null·worker 명령 0개다. 실제 BFF 조회는 해당 snapshot/state를 읽는 `/api/briefings?date=2026-10-08&edition=evening`으로 확인한다.

기존 admin 생성 권한·발행 후 409·immutable payload trigger를 유지한다. replay는 실제 자료에 적용하지 못하고, 현재 grant가 unknown/disabled/만료이거나 목적·수신자가 맞지 않으면 생성하지 않는다. 저장된 worker artifact를 가져온 뒤 원래 round에 commit하기 전에 graph/review/rule pin을 다시 확인한다. configured worker의 실패를 근거 부족의 undetermined나 정상 발행 null로 위장하지 않는다. 모델 전송 불명은 reconciling으로 보존한다.

### 잠금 파일과 독립 worker 환경

`ai/worker/uv.lock`은 기존 BFF와 같은 Pydantic 2.13.5·HTTPX 0.28.1과 dev pytest 9.1.1을 고정한다. 새로운 외부 패키지나 private PoC 의존성을 worker 런타임에 추가하지 않았다.

### 실제 AI 환경 준비 (2026-10-15)

`zoop-ai config-check`는 현재 프로세스의 환경변수만 검사하며 키 값은 출력하지 않는다. grant·원장 파일을 읽거나 provider 요청을 보내지 않는다. 설정 유효성(`configValid`), live 필수 조건(`liveEnvironmentReady`), 비용 승인·계정 모델 접근 가능 여부를 구분한다. 기본 프로필은 모든 단계를 OpenAI 호환 adapter로, `--profile native-jev`는 `semantic-verification`을 네이티브 Jev로 기대하며 어긋나면 오류다. 실제 계정·키는 검증하지 않았다(이전 기록: worker 시험 76개와 4개 합성 CLI 시나리오는 Jev 어댑터 도입 전 상태의 결과다).

사용자 결정으로 LLM은 **`gpt-6-luna`·`reasoning_effort=high`**, Jev는 **`jev-1.14.0`**으로 고정한다. 모델 선택은 확정됐지만 실제 호출·비용 집행은 하지 않았다. 문서 요약·감성 생성과 briefing-outlook은 Luna/high chat stage이고, **S1 `semantic-verification`은 `ZOOP_AI_VERIFY_PROVIDER=typesafe-native`를 명시한 때만 네이티브 Jev `/v1/systemone`**로 간다(기본은 기존 chat 검증기, 저장된 job은 submit 때 고정한 설정대로만 실행). Jev를 OpenAI 호환 endpoint로 보내지 않는다. 판정은 claim별 Choice와 독립 Noul 두 개의 확률을 Zoop 코드가 `VerificationAnswer`로 바꾸는 규칙이고(Choice 승리 확률 ≥ 0.90 **그리고** confidence ≥ 0.80, Noul ≥ 0.90 / ≤ 0.10, 중간은 `hold`), 이 임계치는 **잠정 공학값이며 보정·검증되지 않았다**. 원문 응답은 receipt로 먼저 남기고 형식·모델·분포가 틀리면 재시도 없이 닫힌 채 실패한다. 생성과 검증은 서로 다른 수신자이며 grant는 각각의 `provider:revision`을 요구한다. Responses API 도구 호출은 미구현이며 S2/S3는 replay 전용이다. [런타임 준비 가이드](../development/ai-runtime-setup.md)(§8에 네이티브 계약, §7에 로컬 smoke)에 환경 분리·키 등록 위치·호출 수 상한·최초 합성 smoke 승인 조건을 정리했다.

**Jev 1.14 공식 자료 확인(2026-10-15).** [10월 14일 발표](https://typesafe.ai/blog/jev-1-14)는 전반적인 소폭 개선, 특히 다국어에서 가장 큰 개선을 기대한다고 설명한다. 이는 공급자 설명이며 한국어 금융 문서의 정확도 개선 수치를 검증한 결과는 아니다. 발표의 `jev-latest` 전환 예정과 무관하게 고정 ID `jev-1.14.0`을 사용하고 실제 응답 모델도 기록한다.

## S2-1: 독립 오프라인 원문 준비와 검사

`ai/pipeline/src/zoop_ai_pipeline/ingestion_cli.py`는 설치된 `ai/pipeline` interpreter로 실행하는 **내부 JSON 프로세스**다. FastAPI route, admin job, S1 명령이나 앱 문서 등록 API가 아니다. 명시한 전용 `--state-dir`의 `ingestion.sqlite3`만 쓰며, 앱/S1 상태와 섞인 디렉터리는 거부한다. 디렉터리는 0700, DB·lock은 0600이고 SQLite WAL·FULL commit·foreign key와 OS 독점 잠금을 사용한다. 원본 응답과 문서 바이트는 같은 DB의 SHA-256 content-addressed BLOB에 저장하므로 checkpoint가 미게시 파일을 가리키는 문제가 없다. 원본 PoC checkout은 import하지 않고 기존 pinned 설치본의 URL 검증·HTML scope/noise/access 검사·PDF decoding/preflight helper만 한 adapter에서 재사용한다. 의존성이나 lock 변경은 없다.

### 명령과 권한

wire schema는 `zoop-ingestion-s2-1`이다. 알 수 없는 필드·버전은 거부하며, `ingestion_contracts.py`의 strict 모델이 실행 계약을 소유한다. stdout은 JSON 한 객체다. 등록 전 오류는 `{schemaVersion,error:{code}}`와 종료 코드 2를 반환하고, 등록 이후 운영 실패는 `state=incomplete`와 저장된 `failure.code`를 반환한다. `state=complete`는 원문 준비 회차의 완료이며 분석·게시 성공이 아니다.

| 명령 | stdin 필드 | 별도 파일 |
|---|---|---|
| `run` | `schemaVersion,roundId,sourceId,scopeId,window,checkpointRevision,fixtureManifestHash,cleanerVersion` | `--sources`, `--fixture-manifest` |
| `resume` | `schemaVersion,roundId,sourceId` | 새로 읽는 현재 `--sources` |
| `inspect` | `schemaVersion,roundId,sourceId`; 선택적으로 정확한 `documentId,documentVersion` | 현재 `--sources` |

`window`는 null 또는 timezone이 있는 `{from,through}`다. `cleanerVersion`은 현재 `exact-copy-1`만 지원한다. `inspect`의 메타데이터는 `offset,limit`(기본 50, 최대 100)으로 안정적인 페이지/후보 순서를 나누고, 본문은 정확한 문서·버전 하나를 선택한 경우에만 반환한다. 좌표 해석에는 추가로 `locatorId,start,end`를 보내며, clean interval과 겹치는 원문 span을 산술로 계산한다. 같은 문자열을 원문에서 검색해 위치를 추정하지 않는다.

registry는 `{schemaVersion,revision,sources}`의 **현재 완전한 snapshot**이다. source는 `sourceId,adapter="authored-files",inputRoot,allowedHosts,scopes,grant`를 가진다. scope는 `scopeId,selection,initialCursor,articleXPath,timestampLimitations`를 고정한다. grant는 기존 `grantId,revision,sourceId,enabled,rights,allowedOperations,recipients,purposes,evidence,expiresAt` 어휘를 보존한다. 수집/정제에는 read·store가 필요하고, 내부 본문 검사에는 read, 원문 인용 span 검사에는 read·quote-display가 필요하다. model-send를 요구하거나 저장 권한에서 추론하지 않는다. 누락·disabled·unknown·만료·권한 근거 부재는 거부한다. raw 접근·내용 commit·checkpoint·본문 반환 직전에 현재 파일을 다시 대조하며, 실행 중 atomic 교체가 일어나면 rollback/중단하고 명시적 resume에서 새 snapshot을 읽는다. 과거 실행의 registry hash/BLOB이 현재 권한을 복구하지 않는다.

fixture manifest는 권한 파일이 아니다. `{schemaVersion,sourceId,scopeId,pages,documents}`를 가지며 모든 응답은 `{file,sha256}`로 고정한다. page는 `pageId,cursor,response,status,nextCursor,terminal,coverageThrough`를 선언하고, 저장하는 discovery JSON은 `{items,more,nextCursor}`다. item은 supplier ID·원래 URL·본문 ref·media type·제목·published/modified/source revision을 구별한다. `documents`는 body ref에서 응답 파일로 연결한다. 입력은 source의 명시적 absolute namespace 안의 상대 파일만 읽는다. traversal·절대 경로·URL·symlink·device/FIFO·hash 불일치를 거부하며, 파일이 없어도 HTTP로 전환하지 않는다. JSON은 2 MB, raw 문서는 10 MB, 추출 text/source representation은 500,000 code point로 제한한다. node/segment 수에도 상한이 있다.

### 영속성과 좌표의 의미

- source-local supplier ID가 우선이며, 없으면 pinned PoC의 최소 canonical URL을 쓴다. query 순서를 바꾸거나 tracking parameter를 삭제하지 않는다. URL fallback 뒤 유일하고 충돌 없는 supplier ID가 확인되면 기존 document ID에 alias를 붙인다. 경쟁하는 URL identity는 조용히 합치지 않으며, supplier를 확정할 수 없는 후보는 raw를 보존하고 identity hold로 남긴다. 같은 이벤트·같은 본문이어도 다른 supplier/source 문서는 별개다.
- `rawHash`는 수신 바이트의 SHA-256이고, S1 `sourceHash`는 canonical JSON string의 digest다. raw revision에는 안정적인 문서 metadata를 포함하되 observed time·round·grant revision은 제외한다. parser/cleaner·text hash·mapping digest를 포함한 `documentVersion`과 locator는 불변이다. 같은 입력은 재사용하고 바이트만 바뀌어 정제 text가 같아도 raw/text lineage를 새로 보존한다.
- 현재 adapter의 동적 본문 선택 설정인 `articleXPath`도 `parserProfile`에 고정하고 preparation key·`documentVersion`에 포함한다. 서로 다른 selector는 정제 text가 같아도 별도 준비 버전이다. scope ID·grant revision 같은 권한 이력을 원문 identity/raw revision으로 섞지 않는다. selector가 바뀐 새 scope는 이전 scope의 text나 parse hold를 재사용하지 않으며, selector binding이 없는 옛 profile의 본문 조회는 `preparation_profile_unbound`로 거부한다.
- raw save·정제 결과/hold save·page/checkpoint commit은 독립적인 복구 경계다. 저장된 입력은 resume 때 파일 없이 재사용하고, 아직 저장하지 못한 응답만 원래 hash의 파일이 필요하다. 페이지의 모든 raw·text 결과 또는 reasoned hold가 durable해야 연속 cursor를 옮긴다. 부분 discovery·항목 오류·누락 body는 페이지를 끝내지 않는다. 유효한 zero와 비영(非零) discovery의 버전 재사용은 counts/completion으로 구별한다.
- 여러 supplier 후보가 같은 body hash를 가리키면, 현재 권한을 다시 확인한 뒤 **동일 source/round slice에서 실제로 저장한 문서 BLOB**을 재사용한다. 다른 source/round의 global BLOB을 hash만으로 가져오지 않는다. 첫 후보의 raw commit 뒤 입력 파일이 없어져도 다음 후보를 이어 준비하며, supplier별 document/raw/text identity는 별개로 유지한다.
- 성공한 조회 범위는 모든 페이지와 terminal coverage가 확인된 경우만 이동한다. `more=true`에서 fixture가 끝나면 incomplete다. 마지막 transaction에서도 checkpoint revision을 비교하므로 오래된 round가 새 checkpoint를 덮지 못한다. 완료된 과거 round는 현재 checkpoint 문맥과 자신의 완료 revision을 함께 반환한다.
- HTML 위치는 원래 parsed DOM의 절대 path·text/tail slot과 저장된 **decoded node string**의 Unicode `[start,end)`다. entity 확장·HTML repair 뒤의 위치이며 markup byte offset은 아니다. inline node를 잇는 인용은 각 원래 span을 보존하고, 제거한 noise의 surviving tail도 원래 slot을 유지한다. 삽입한 block/noise separator에는 좌표를 만들지 않는다.
- PDF는 최대 30초로 감독하는 disposable child에서 PoC의 raw/page/decoded/aggregate/filter 예산과 encrypted/external decoder 거부를 유지한다. 각 page의 수정하지 않은 추출 문자열·page hash·1-based page number를 저장한다. 모든 page가 비어 있어 `no_usable_body` hold가 된 경우에도 frozen page table을 private preparation에 보존하고, bounded 후보 metadata에 page/empty-page 수와 representation hash를 반환한다. output limit이면 hold하며 잘린 text를 성공으로 반환하지 않는다. 좌표는 page-extracted text의 code point이지 PDF byte·glyph·bounding box·OCR·시각적 읽기 순서 보장이 아니다.
- 내부 S1 `Document` projection은 최대 연속 mapped run만 `rawLocators`로 제공한다. 생성 separator나 PDF page 경계를 가로지르는 인용은 기존 `exact()`에서 거부된다. S1 schema·exact 규칙·권한 검사는 변경하지 않았다. 이것은 앱 Dataset 문서나 PoC `Article.version` 등록이 아니므로 기존 BFF importer를 우회하지 않는다. 기업 연결·현재 문서 소유권·public registration·publication·유료 semantic validation은 이 실행에 없다.

## S2-2: 오프라인 이벤트·SAME·주제 후보 준비

`ai/pipeline/src/zoop_ai_pipeline/extraction_cli.py`는 설치된 `ai/pipeline` interpreter로 실행하는 **내부 JSON 프로세스**다. FastAPI route, S1 명령, 앱 문서 등록·게시, 스케줄러, GraphDB writer가 아니다. wire schema는 `zoop-extraction-s2-2`이며 S1 schema의 alias가 아니다. 결과는 후보일 뿐 ALLOW·승인·게시가 아니고, **authored replay는 독립 AI 추론이 아니다.** replay는 사람이 작성한 응답을 이 저장소의 엄격한 네이티브 계약(`extraction_replay.py`, 원본 PoC 코드·프롬프트 없음)으로 검증하는 방법이며 의미 품질을 증명하지 않는다. live mode는 `live_mode_unsupported`로 거부하고 fake fallback을 두지 않는다.

| 명령 | stdin | 파일 인자 |
|---|---|---|
| `run` | `{schemaVersion,jobId,provenance,promptVersion,incoming,catalogue,snapshot,topic}` | `--replay` 필수, `--topic-replay` 선택 |
| `submit` | `run`과 같은 요청 | `--replay` 필수, `--topic-replay`는 `fixture_not_allowed`. 등록(`queued`)만 하고 `inspect` 결과를 반환한다 |
| `resume` | `{schemaVersion,jobId}` | 선택적 같은 `--replay`/`--topic-replay` |
| `inspect`, `cancel` | `{schemaVersion,jobId}` | 없음 |

**`submit`(등록 전용, CLI).** `run`에서 **등록 절반만** 분리한 명령이다. 이 명령 자체는 CLI이고, 호출자가 본문·fixture를 고르지 못하는 선택적 HTTP 가족(`ai/service`, 아래 S2 HTTP 절)이 서버 승인 요청으로만 감싼다. 구현은 `Extractor.freeze`이고 `run`은 같은 함수 뒤에 `resume`하므로 등록 경로는 하나다. 필수 `--replay`는 헤더(format·synthetic·recordingKind·promptVersion·analysisVersion)만 검증해 파일 hash를 입력 digest와 binding에 고정하고, 문서 binding·snapshot member의 정확 인용을 검증한 뒤 같은 transaction에서 현재 권한을 다시 확인하고 `queued`를 저장한다. fixture 레코드 조회, stage 실행, 호출 예약·`calls` 행, 후보 쓰기, 네트워크는 없다(`calls=[]`, `usage.replayCalls=0`). record 단위 결함(중복 record 등)은 등록에서 보지 않고 첫 `resume`의 `replay_fixture_invalid`로 드러난다(`run`과 같다). `--topic-replay`는 job에 고정되지 않으므로 `fixture_not_allowed`이고 live provenance는 `live_mode_unsupported`다. 같은 `jobId`와 같은 입력은 queued·stopped·ready·cancelled 어느 상태에서도 **저장된 job을 `inspect`처럼 보고만 한다**. resume·재고정·stopped 초기화·호출이 없고 현재 권한은 반환 `delivery`에만 적용된다(철회·grant revision 변경이면 `withheld`와 종료 코드 2이며 binding은 그대로다). 다른 입력·다른 replay bytes는 쓰기 없이 `job_input_conflict`다. 잘못된 fixture를 고정했다면 같은 jobId로 고칠 수 없고 새 jobId가 필요하다. 이후 `resume`은 권한·binding을 다시 검사하므로 submit 뒤 철회·grant revision 변경은 호출 없이 `stopped`다. 이 문서의 시험·smoke 수치는 submit 추가 이전 기록이며 submit 회귀 시험과 smoke(12단계)의 통과는 최종 실행 결과로만 기록한다.

공통 인자는 `--state-dir`(전용 `extraction.sqlite3`·`extraction.lock`만 허용), `--ingestion-state-dir`(읽기 전용 입력), `--sources`(S2-1과 같은 현재 완전한 registry)다. 알 수 없는 필드·schema/format/ledger 버전, app·S1·ingestion·원본 PoC 디렉터리, 겹치거나 알 수 없는 파일이 있는 mixed root는 거부한다. `incoming`과 snapshot member는 정확한 관측 `{roundId,sourceId,page,ordinal,documentId,rawVersion,documentVersion}`이다. snapshot은 운영자가 얼린 **whole-event 목록**이며 각 member는 이 계약의 `Mention` JSON(snake_case, 이전 결과의 `mention`)이다.

### 정확한 입력 export와 binding

S2-1에 좁은 additive 명령 `ingestion_cli export`와 `Ingestor.export`를 추가했다. 정확한 관측(round/source/page/ordinal/document/rawVersion/documentVersion)만 받아 현재 read·quote-display 권한을 확인하고 기존 S1 `Document` projection과 별도로 서버 소유 URL·title·publishedAt·modifiedAt·sourceRevision·mediaType·page observedAt·grant ID/revision을 반환한다. 클라이언트가 보낸 metadata는 신뢰하지 않는다. 이 소비자 접근(`Store(existing=True)`)은 **실제 읽기 전용**이다. 디렉터리·파일 mode/소유권 보정(chmod), 생성, schema/PRAGMA/WAL 쓰기 없이 `immutable=1` 읽기 전용 SQLite로 열고, 시험이 일부러 0750/0640/0440으로 바꾼 mode·bytes·mtime·파일 목록이 export와 extraction 실행 전후 같음을 확인한다. lock 정책은 기존 `ingestion.lock`에 대한 **shared non-blocking flock**이다. reader끼리는 공존하고, 활성 writer가 있으면 reader가 `ingestion_busy`, reader가 있으면 새 writer도 `ingestion_busy`다. 비어 있지 않은 `-wal`(중단된 writer가 남긴 commit)은 reader가 무시하거나 복구할 수 없으므로 `ingestion_recovery_required`로 거부하고, 운영자가 ingestion `resume`으로 복구한 뒤 다시 읽는다. 없는 namespace는 만들지 않고 `ingestion_state_missing`이다. 기존 `inspect` 결과는 같은 helper로 옮겼지만 출력이 같고 `test_ingestion.py` 43개가 통과한다.

job은 replay 호출 전에 다음을 불변 binding으로 먼저 저장한다. 네이티브 `Article`(publisher는 알 수 없어 빈 값, origin_id null, language는 adapter 상수 `ko`, `allow_model_send=false`)과 **진짜 계산된 `Article.version`**(collected_at 없이 12개 필드의 digest), 문서별 raw/representation/mapping/locator/metadata/parser digest, grant 이름·revision, 어댑터 `{version zoop-extraction-native-replay-1, candidate, fingerprint}`(fingerprint = 어댑터·후보 버전·`promptVersion`·`analysisVersion`·catalogue digest), replay 정체 `{format zoop-analysis-replay-1, synthetic, recordingKind, promptVersion, analysisVersion}`와 파일 hash, 회사 catalogue digest, snapshot digest와 개별 event digest다(원본 PoC commit·prompt 지문·settings digest는 없다). 같은 jobId에 다른 입력·replay bytes를 보내면 `job_input_conflict`, resume에서 다른 replay bytes를 보내면 `replay_fixture_changed`다. 누락된 extract/compare 응답은 실패이며 fixture를 고쳐 같은 job에 붙이지 않고 새 job을 만든다. `Article.version`은 documentVersion을 대체하지 않는다. raw만 바뀌어 `Article.version`이 같아도 documentVersion·mention/event candidate ID·job 입력이 달라진다. 같은 comparison에 같은 Article.version이 두 documentVersion으로 묶이면 SAME/FOLLOWS evidence는 최신/첫 항목을 고르지 않고 HOLD다. **이전 build가 PoC 어댑터 binding으로 저장한 job**은 같은 원장에 남지만 `binding.adapter.version`이 다르므로 읽기용 기록이다: inspect는 저장된 상태·binding·호출 요약만 보이고 `delivery`는 withheld `analysis_contract_changed`이며 후보·원천을 읽지 않는다. run/resume은 어떤 상태에서도 원천 읽기·호출·상태 쓰기 전에 같은 코드로 거부하고, S3/graph/handoff upstream으로는 쓸 수 없으며, `cancel`은 유지하고 자동 변환·재분석은 없다.

### 추출·비교·주제 stage

- **추출/비교**: `extraction_replay.py`의 순수 함수만 호출한다(요청 preimage·digest, 인용 해석, 엄격한 parser, SAME 규칙). `Pipeline`, Repository, graph, B0–B4 retrieval, 원본 PoC는 쓰지 않는다. whole-event 목록의 모든 event를 비교하며 이것이 retrieval 완전성이라고 주장하지 않는다. raw `PairDecision`은 보존하고, 별도 effective decision은 SAME 규칙을 다시 적용한다. SAME인데 member 하나라도 period/assertion/event_time이 알려진 값으로 충돌하면 DIFFERENT, SAME/FOLLOWS의 exact evidence 부재와 FOLLOWS의 incoming evidence 부재는 HOLD다. 알 수 없는 값은 날짜나 identity를 만들지 않는다. SAME 둘 이상이거나 HOLD/CONFLICT가 있으면 선택하지 않고 `held`이며 transitive union은 없다.
- **ID**: `mentionCandidateId`(`mc-`)는 정확한 문서 binding·extract request key·fingerprint·로컬 mention ID에서, `eventCandidateId`(`evc-`)는 mention candidate에서 파생한 별도 ID다. documentId, snapshot의 event ID, mention ID, topic ID(`tp-`)는 서로 다른 namespace이며 snapshot event ID가 `mc-`/`evc-`/`tp-`로 시작하면 거부한다.
- **인용**: `Evidence.matches`만 믿지 않는다. 구간은 정확히 하나의 mapped locator run 안에 있어야 하고(S1 `exact`와 같은 규칙), ingestion inspect의 source resolver로 재구성한 원문 segment 합이 quote와 같아야 한다. 생성된 separator를 가로지르면 mention은 `rejected/raw_locator_mismatch`로 남고, 응답의 offset은 인용이 정확히 선택하는 정수일 때만 유지되며 그렇지 않으면 본문에서 유일한 quote로 다시 구하고 반복·부재 quote는 응답을 영구 거부한다. snapshot member의 모든 evidence도 job을 저장하기 전에 같은 규칙(mapped run + resolver)으로 검사하며 실패하면 `snapshot_member_unmapped`로 거부해 SAME 비교 입력이 되지 않는다. 비교 응답이 member 문서의 separator span을 인용하면 effective decision은 HOLD다. 시험은 실제 S1 `exact`로 accept/reject를 대조한다.
- **주제**: PoC에는 topic 호출이 없으므로 별도 prototype producer 계약 `zoop-topic-request-1`/`zoop-topic-response-1`/`zoop-topic-replay-1`을 둔다. 요청은 event candidate와 snapshot event, 문서 목록이며 응답은 label·criteria·rationale·명시적 membership·정확한 문서 citation이다. 모든 member와 citation을 frozen 요청과 대조하고 알 수 없는 member, 중복 member, 요청에 없는 문서, 부정확한 quote는 received 영수증에 거부 verdict를 남기고 topic을 만들지 않는다. 사건이 없으면 producer 호출도 빈 topic도 만들지 않는다. topic은 `status=candidate, approved=false`다.

### 영속성·복구·권한

stage의 후보와 완료 marker는 한 transaction에서 commit한다. provider 영수증은 `started→received`로 분리하고 응답/request digest/fixture hash는 변경할 수 없다. replay fixture는 호출 예약 전에 전체 레코드를 엄격한 `AnalysisReplay` 계약으로 검증하며(중복 `(stage,requestDigest)`·잘못된 단계/형식·추가 키는 `replay_fixture_invalid`), 잘못된 fixture는 receipt가 되지 않는다. 순수 parser가 통과한 응답만 `received`로 저장하고, 계약을 위반한 응답은 영수증을 보존한 채 거부 verdict를 붙여 영구히 사용할 수 없다. topic membership/citation 같은 후속 검증의 응답 결함도 같은 방식이며 권한·환경 실패는 유효한 receipt를 그대로 두어 다음 resume이 다시 검증한다. resume은 저장된 receipt를 새 호출 없이 production parser로 다시 검증한다. 응답 저장 뒤·후보 저장 전 프로세스가 죽어도, stage commit 뒤에 죽어도 replay 파일 없이 재개하며 추가 호출은 0이다. `started`만 있고 receipt가 없으면 replay라도 `reconciling/reconcile_only`로 남기고 자동 재전송하지 않는다. 모든 문서는 read 전, 응답 뒤, stage commit 직전, 결과 전달 직전에 현재 registry를 다시 읽어 read+quote-display, exact binding을 확인한다. 철회·만료·registry 제거·grant revision 변경 뒤에는 `delivery=withheld`와 종료 코드 2이고 후보·인용·본문이 출력되지 않으며 이전 결과가 권한을 복구하지 않는다. `model-send`·recipient·purpose는 offline replay가 외부로 전송하지 않으므로 검사하지 않으며, live 전송을 도입하면 별도 검사가 필요하다. 이 단계는 cross-job 결과 cache를 두지 않는다. 재사용은 같은 job의 영수증뿐이다.

남은 범위: 실제 모델 추출·SAME 품질, B0–B4 retrieval 연결과 현재 event/topic 저장소, 앱 등록·게시·GraphDB, S4 전체 철회 closure, 사람 승인 topic은 구현·검증하지 않았다. S3 후보 단계의 소비자를 위해 이 ledger에는 **읽기 전용 export seam**만 추가했다. `Store(existing=True)`(shared non-blocking flock·`immutable=1`·비어 있지 않은 WAL은 `extraction_recovery_required`·없으면 `extraction_state_missing`·활성 writer면 `extraction_busy`)와 `Extractor.export(job_id)`(ready이고 binding·권한이 현재 검증된 job의 frozen 요청과 전달 결과만 반환, 아니면 `upstream_not_ready` 또는 withheld 코드)다. 정확한 인용 로직은 `extraction.cite_exact`로 꺼내 S2-2와 S3가 같은 코드를 쓴다. `test_downstream_export_seam_…` 회귀가 mode/bytes/mtime 불변, 미완료·철회 job 거부, 읽기 전용 SQL 거부를 확인한다.

## S3: 오프라인 관계·영향 후보와 HOLD 재검증

`ai/pipeline/src/zoop_ai_pipeline/relation_cli.py`는 S2와 같은 **내부 JSON 프로세스**다. FastAPI route, 공개 OpenAPI, 새 관리자 화면, S1 명령, 앱 문서·관계 등록, GraphDB writer가 아니며(비공개 Neo4j stage는 이 job을 읽기 전용으로 소비하는 별도 CLI `zoop-ai-graph`다) wire schema는 `zoop-relation-s3`이다. 입력은 **완료된(ready) S2 job 하나의 정확한 `{jobId,inputDigest}`**뿐이다. 호출자가 후보 JSON을 보낼 수 없으며(wire는 닫혀 있다) event 후보·topic 후보·catalogue·문서 binding은 모두 위의 읽기 전용 export seam이 서버 소유 registry로 다시 검증한 snapshot에서만 온다. snapshot digest가 job binding에 고정되며 단계마다 다시 읽어 바뀌면 `upstream_changed`로 멈춘다. authored replay는 **독립 AI 추론이 아니며** producer fixture(`--replay`: relation/impact)와 **독립된** verifier fixture(`--verifier-replay`: verify-relation/verify-impact)를 따로 둔다. 결과는 후보일 뿐 `approved=false`이며 `eligible`은 자동 증거 gate 통과이지 승인·게시가 아니다. live mode는 `live_mode_unsupported`다.

| 명령 | stdin | 파일 인자 |
|---|---|---|
| `run` | `{schemaVersion,jobId,provenance,upstream:{jobId,inputDigest}}` | 선택적 `--replay`, `--verifier-replay`. 없으면 해당 단계에서 `*_replay_required`와 `requestDigest`를 남기고 멈춘다 |
| `submit` | `run`과 같은 요청 | 없음. `--replay`·`--verifier-replay`는 `fixture_not_allowed`다. 등록(`queued`)만 하고 `inspect` 결과를 반환한다 |
| `resume` | `{schemaVersion,jobId}` | 선택적 같은 fixture |
| `inspect`, `cancel` | `{schemaVersion,jobId}` | 없음 |
| `review` | `{schemaVersion,jobId,relationCandidateId,expectedRevision,decision:allow\|reject,reviewer,note}` | 없음 |
| `revalidate` | `{schemaVersion,jobId,relationCandidateId,expectedRevision}` | 새 시도에는 `--verifier-replay`가 필요하다(없으면 `verifier_replay_required`와 `requestDigest`). 이미 저장된 receipt를 복구할 때는 fixture가 필요 없다. 새로 eligible이 된 관계의 영향 producer는 선택적 `--replay` |

**`submit`(등록 전용, CLI).** `run`의 등록 절반이다(`Engine.freeze`. `run`은 같은 함수 뒤에 `resume`한다). 이 CLI 자체는 HTTP가 아니며, 내부 HTTP는 `ai/service`의 별도 `/internal/v1/relation-jobs` 가족이 제출·상태·결과·취소·복구와 검수·재검증 operation을 노출한다(아래 내부 HTTP 절). 완료(ready)되고 현재 권한·binding이 검증되는 S2 job이 있어야 하며(`upstream_not_ready`, 위조 digest는 `upstream_input_mismatch`, 권한 문제는 S2의 withheld 코드) 거부되면 job은 생기지 않는다. 성공하면 upstream identity·`upstream.digest`·provenance를 고정한 `queued`를 같은 transaction의 upstream 재검증과 함께 저장하고 `inspect` 결과를 반환한다(`calls=[]`). **fixture를 받지 않는다.** S2와 달리 S3 binding과 입력 digest에는 replay 파일이 들어가지 않고 producer/verifier fixture는 호출별로 `calls.fixture_hash`에만 기록되므로, 이후 `resume`/`run`/`revalidate`가 단계마다 fixture를 준다. 이 비대칭은 기존 동작이며 바꾸지 않았다. 같은 `jobId`와 같은 입력의 재제출은 어떤 상태에서도 저장된 job을 `inspect`처럼 보고만 하며 resume·재고정·stopped 초기화·호출·pending HOLD 검토 반영(재검증)을 하지 않는다. 다른 입력(다른 upstream 포함)은 쓰기 없이 `job_input_conflict`다. 이후 `resume`은 upstream·권한·binding을 다시 확인하므로 submit 뒤 S2의 권한·grant revision이 바뀌면 호출 없이 `stopped`다. queued는 `cancel`로 호출 전에 취소한다. 이 문서의 시험·smoke 수치는 submit 추가 이전 기록이며 submit 회귀 시험과 smoke(13단계)의 통과는 최종 실행 결과로만 기록한다.

공통 인자는 `--state-dir`(전용 `relation.sqlite3`·`relation.lock`만 허용, extraction/ingestion/앱/worker/원본 PoC 디렉터리와 겹치거나 알 수 없는 파일이 있으면 `state_namespace_conflict`), `--extraction-state-dir`, `--ingestion-state-dir`(둘 다 읽기 전용), `--sources`다. 이 ledger만 쓰며 S2·ingestion DB의 bytes/mode/mtime/파일 목록은 시험과 smoke에서 실행 전후 같다.

### 관계 후보(FS078)

- **어휘**(FS055 공통 계약이 확정되기 전의 보수적 임시 선택): `SUPPLIES`(공급자→고객), `INVESTS_IN`(투자자→피투자), `COMPETES_WITH`(대칭, 정렬된 쌍으로 정규화), `PARTICIPATES_IN`(기업→**명시적 event**), `RELATES_TO_TOPIC`(기업→**실제 bound topic 후보**). event와 topic은 서로 다른 endpoint kind이며 event ID를 topic/issue 별칭으로 쓰면 `event_id_not_topic`으로 reject, 종류가 맞지 않으면 `endpoint_kind_invalid` reject다. `SAME`·`FOLLOWS`·`SHARES_ISSUE`·`CO_MENTION`·`INVOLVES`·`STRUCTURALLY_RELATED_TO`는 관계 근거가 아니어서 `non_relationship_basis` hold이고 그 밖의 유형은 `relation_type_unsupported` hold다. 같은 문서에 두 기업이 함께 언급됐다는 사실만으로는 어떤 관계도 확정되지 않는다(독립 verifier가 `insufficient`이면 hold).
- **정규화·보존**: 방향 관계는 제시된 출발→도착을 유지하고 뒤집지 않는다. 대칭 관계는 (kind,ref)로 정렬하고 같은 key의 중복(순서만 다른 쌍)은 한 후보로 합치며 근거만 합집합이다. relation key는 유형·endpoint·사업 범위·제품 범위·유효 기간 값·직접/간접·경로·국가에서 계산하므로 같은 기업 쌍이라도 유형이나 사업/제품 범위가 다르면 서로 덮어쓰지 않는다. 후보 ID는 `rc-`(관계)·`ic-`(영향)로 `evc-`/`tp-`/문서/mention ID와 별도 namespace다.
- **직접/간접과 경로**: 직접 관계는 자체 인용이 필요하고(`evidence_missing`), 간접 관계는 `SUPPLIES`/`INVESTS_IN`에서 정확히 2단계 경로만 허용한다. 각 단계는 알려진 기업이며 인용돼 있고(`path_step_uncited`) 같은 유형이고(`path_step_type_mismatch`) 출발에서 도착까지 이어져야 한다(`path_disconnected`, `path_incomplete`, `path_too_long`). 어느 하나라도 어긋나면 경로 전체가 비공개 hold이며 부분 근거로 통과하지 않는다.
- **유효 기간·국가**: 시작/종료는 인용으로 확인한 값만 가진다. 근거 없는 날짜는 `validity_uncited` hold, 순서가 틀리면 reject이고 값이 없으면 `unknown` 상태로 남는다(날짜를 만들지 않는다). 국가는 선언한 값이 S2 mention의 국가와 충돌하면 `country_context_conflict` hold이며 `context.market`(domestic/international/unknown)과 `context.check`(pass/unverified/unknown/conflict)를 결과에 명시한다.
- **인용**: 모든 인용은 S2와 같은 `cite_exact`(정확한 code point 구간·단일 mapped run·ingestion resolver)를 통과해야 한다. 위조 span, UTF-16/byte 오프셋, 생성된 separator는 `citation_invalid` reject이고 후보에 오류 코드와 함께 남는다. event/topic 관계의 인용은 그 target의 문서에 속해야 한다(`citation_not_target_evidence`). 알 수 없는 endpoint는 `target_unknown` 비공개 hold다.

### 독립 관계 검증과 적격성(FS079)

verifier 요청은 후보에서 만든 **고정 사실**(유형·방향·endpoint 이름·범위·유효 기간·국가·경로)과 **정확한 quote 및 `claims`(claimId→허용 quoteIds)**뿐이다. 생성기의 사유·후보 ID·형제 후보는 들어가지 않으며 시험이 요청 digest가 생성기 문구에 영향받지 않음을 확인한다. 응답은 claim마다 `supported/contradicted/insufficient`(방향 claim과 경로 단계는 `reversed`도 가능)이며 claim 집합이 정확히 같아야 하고 근거 quoteIds는 요청의 부분집합이어야 한다. 규칙은 fail-closed다. 하나라도 `contradicted`(wrong target 포함)면 reject, `reversed`·`insufficient`면 hold, **모든 claim이 supported이고 모든 결정적 검사를 통과한 경우만 `eligible`**이다. 응답 형태 위반·모르는/중복/누락 claim·요청에 없는 quote ID는 그 후보를 `verification_reply_invalid`로 영구 reject하고 영수증에 verdict를 남기며 재호출하지 않는다. 관리자 allow나 높은 확신도는 이 gate를 대체하지 않는다.

### 영향 후보와 라벨

eligible 관계마다 별도 producer 호출 하나가 후보를 만든다. 각 영향은 관계의 기업 endpoint(`impactedCompanyId`) 하나와 supporting/opposing 인용을 갖는다. 대상이 관계 endpoint가 아니거나 인용이 위조·미결합이면 `impact_target_invalid`/`citation_invalid`로 reject하되 **관계 eligibility는 바뀌지 않는다**. 인용이 모두 정확하면 별도 verifier가 대상 일치(`target`)와 quote마다 `positive/negative/neutral`을 매핑하고, 라벨은 이 매핑에서만 계산한다. 양쪽 모두 근거가 있으면 `mixed`, 한쪽이면 그 방향, 매핑된 근거가 없거나 대상이 `insufficient`이거나 인용이 없으면 `undetermined`다. 이 라벨은 인용 문장의 텍스트 방향이며 가격 방향·확률·예측이 아니다. producer가 제시한 방향은 `agreement`로 비교만 한다. 대상이 `contradicted`면 그 영향만 reject다. 영향 producer/verifier의 응답 결함은 그 영향만 기록하고 relation은 eligible로 남는다.

### HOLD 검수와 재검증

각 relation은 append-only 이벤트 사슬(결정적 verdict·verifier verdict·검수)을 갖고 `revision`은 이벤트 수다. `review`는 현재 `hold`인 관계에만, `expectedRevision`이 맞을 때만 기록한다(`review_revision_conflict`, `review_target_not_hold`, `review_already_pending`). `allow`는 **재검증 요청만** 기록하며 eligibility를 바꾸지 않고 공개와도 무관하다. `reject`는 제외만 한다(`admin_rejected`). `revalidate`는 요청된 hold에 대해 새 시도를 한다. 새 시도는 별도 `attempt`(종류·순번·재검증 정책 버전·직전 verdict digest)와 request digest·receipt를 갖고 고정된 저장 후보를 입력으로 독립 verifier를 다시 호출한다. 결정적 hold(알 수 없는 endpoint, 경로 결함 등)는 verifier 호출 없이 같은 사유로 다시 hold가 된다. 이전 hold/reject verdict는 history에 그대로 남고 relation을 자동 재생성하지 않는다. 새로 eligible이 된 관계는 영향 producer 호출이 별도로 필요하다. CLI를 직접 쓸 때 reviewer는 운영자가 붙인 이름일 뿐 인증된 관리자 신원이 아니다. 내부 HTTP(아래)는 이 CLI를 operation으로 감싸 reviewer를 인증된 principal로, `note`를 operation marker로 채운다.

### 영속성·복구·권한

S2와 같은 방식이다. 후보와 완료 기록은 한 transaction이며 provider 영수증은 `started→received`로 분리되고 request digest·응답·fixture hash는 변경할 수 없다(trigger). 호출 전에 fixture 전체를 엄격히 검증하며(중복 record·잘못된 role/stage·알 수 없는 필드는 `relation_replay_invalid`, provenance 불일치는 `replay_provenance_conflict`) 잘못된 fixture는 receipt가 되지 않는다. 계약을 위반한 응답은 영수증과 거부 verdict를 보존하고 더 나은 fixture가 나중에 와도 쓰지 않는다. 응답 저장 뒤 프로세스가 죽어도 fixture 없이 재개하며 추가 호출은 0이고 `started`만 있으면 `reconciling/reconcile_only`로 재전송하지 않는다. 읽기 전용 snapshot은 호출 예약 전, 응답 뒤, 저장 transaction 직전, 결과 전달 직전에 다시 읽으며 철회·만료·grant revision 변경·상위 job 변경 뒤에는 `delivery=withheld`(종료 코드 2)이고 본문과 후보가 출력되지 않는다. 명시적 상한은 관계 100·문서 50·인용 20·경로 4단계·영향 2이며 초과는 거부된다.

### 실제 재현 결과

저장소 루트에서 다음 명령을 실행했다.

```sh
PYTHONDONTWRITEBYTECODE=1 ai/pipeline/.venv/bin/python -m pytest ai/pipeline/tests/test_relation.py ai/pipeline/tests/test_extraction.py ai/pipeline/tests/test_ingestion.py -q -p no:cacheprovider
PYTHONDONTWRITEBYTECODE=1 ai/pipeline/.venv/bin/python ai/pipeline/scripts/relation_smoke.py
```

첫 명령은 **142 passed, 1 warning**(`test_relation.py` 52 + `test_extraction.py` 47 + `test_ingestion.py` 43, 기존 Starlette warning)이었고 `relation_smoke.py`는 `status=passed, providerCalls=0, modelCalls=0`이었다. 재검증 receipt가 저장된 뒤 verdict commit 전에 프로세스가 죽거나 권한이 사라지면(`running`/`ready`로 남은 job 포함) `resume`·`revalidate`가 fixture 없이 저장된 receipt에서 verdict를 append하고 추가 호출은 0이다. 이 경우 수정 전에는 `ready`인데 `reviewPending`인 채로 남았음을 재현했다. ready job은 **저장된 재검증 receipt가 있을 때만** 재진입하며 새로 `allow`만 된 검수는 자동 실행되지 않는다. 관리자 reject나 cancel이 먼저 오면 남은 receipt는 사용되지 않는다. smoke는 authored HTML을 실제 ingestion 프로세스로 수입하고 실제 S2 extraction으로 event·snapshot·topic 후보를 만든 뒤 relation CLI 프로세스(소켓 audit hook)로 방향 뒤집힘 hold, 경쟁 쌍 정규화·중복 병합, 같은 쌍의 다른 유형·범위 보존, 경로 단계 누락·알 수 없는 endpoint hold, 직접 대 2단계, mixed/positive/undetermined 영향과 eligibility 분리, event/topic/SHARES_ISSUE/공동언급 처리, 한글·emoji·entity 정확 인용과 위조·separator 거부, HOLD allow→재검증과 그 receipt 뒤 중단 복구, receipt 뒤 중단 복구와 started-without-receipt, 위조 upstream·fixture·live·철회를 확인했다. 시험은 거기에 영향 결함, 잘못된 verifier 응답 7종, 국가 검사, 응답 뒤 권한 상실, namespace 충돌, 읽기 전용 seam, immutable trigger를 더했다. 모든 상태는 실행 뒤 제거했다.

남은 범위: 실제 모델의 관계·영향 품질(replay는 의미 품질을 증명하지 않는다), FS055 공통 계약에 맞춘 유형·키·필수 속성 확정, 기업/이슈 canonical ID(FS077)와 retrieval, 앱 등록·공개 version과 FS021/FS022/FS024 소비(GraphDB는 아래 비공개 stage까지만), 관리자 검수 화면과 인증된 검수자 신원, S4 전체 철회 closure는 구현·검증하지 않았다.

## S3 → 비공개 Neo4j 버전 projection (FS080 일부, 게시·FS081 철회 아님)

**범위.** `zoop_ai_pipeline.graph_projection_cli`(설치 명령 `zoop-ai-graph`, wire `zoop-graph-projection-1`)는 **완료되어 현재 전달 가능한 S3 job 하나**를 **불변 Neo4j version 하나**로 stage한다(`init`·`freeze`·`project`·`recover`·`inspect`·`read`·`focus`). `ai/service`의 읽기 전용 내부 HTTP는 아래 별도 절을 따른다. 공개 활성화(FS059)·앱 등록·Spring 클라이언트·증분 갱신·영향 라벨 projection·두 기업 사이 경로 조회·live provider·모델 호출은 없고, S1·S2·S3·ingestion·앱 상태와 PoC 코드·상태는 바꾸지 않는다. `ready`는 "stage되고 전체 검증됨"일 뿐이며 결과의 `publication`은 항상 `not-published`다. 어떤 노드·간선에도 `active`/`public`/`approved` 속성이 없다. FS081의 철회 구현이 아니다: gate가 닫히면 `read`가 withheld할 뿐 version을 삭제·비활성화·purge하지 않는다.

**소유 경계.** pipeline의 이 CLI가 Neo4j의 유일한 writer이고 Spring은 Neo4j write 자격을 갖지 않는다. `ai/service`는 설치된 CLI의 `read`·`focus`만 고정 명령으로 호출하며, pipeline을 import하거나 원장을 직접 열지 않는다. 대상 Neo4j는 이 원장 하나에 묶인 **별도의 빈 database**여야 하며 PoC Neo4j나 내용이 있는 database는 채택하지 않는다. 관계·감성 PoC의 변경 writer(`investmate.graph`)는 쓰지 않는다. `neo4j==6.3.1`은 직접 의존성이다(이미 lock에 있던 같은 버전, 새 다운로드 없음). 관계/의존 모듈은 graph 모듈이나 `neo4j`를 import하지 않는다.

**서버 소유 입력(stdin에는 없다).** (1) 연결: `init --graph-uri`와 `preflight --graph-uri`에서만 받고(`bolt://` loopback 또는 인증서 검증 TLS `bolt+s://`, 명시 포트, userinfo·path·query·`neo4j://`·`bolt+ssc://`는 `graph_uri_invalid`) `init`만 한 번 원장 `meta.store`에 묶는다. 이후 명령은 원장에 묶인 URI·database만 쓰고 다른 명령에 `--graph-uri`를 주면 설정 오류다. 자격은 환경(`ZOOP_GRAPH_AUTH=none|basic`, `ZOOP_GRAPH_USER`, `ZOOP_GRAPH_PASSWORD`)에서만 읽고(원격 TLS는 basic 필수) 어떤 출력에도 싣지 않는다. 사설 CA의 `bolt+s` 대상은 명령마다 환경 `SSL_CERT_FILE=<공개 CA pem>`으로 신뢰를 준다(드라이버는 `bolt+s`에서 기본 시스템 CA를 쓰고 `TrustCustomCAs`·`ssl_context`는 쓰지 않으며 인증서·호스트 이름 검증을 끄는 경로는 없다). **`preflight`**는 `init`과 같은 stdin·`--graph-uri`에 의도한 `--state-dir`을 받는 후보 점검이다: 원장을 만들거나 열거나 잠그거나 chmod하지 않고(디렉터리 목록만 읽음), DDL·쓰기 transaction이 없으며 어댑터의 닫힌 읽기 문장(`probe()`)만 쓴다. `init`과 같은 순수 규칙(`refuse_unbound_target`)으로 비어 있는 Neo4j 5 database인지 보고 `{preflight:{result:"eligible-empty-target", ddlPermission:"unverified", tls, ledger:"absent", server, database, dbId, counts, schemaObjects}}`만 낸다(URI·경로·자격·owner 없음). 원장이 이미 있으면 `graph_store_already_bound`로 거절하며(바인딩 재확인은 멱등 `init` 재실행) DDL 권한과 이후 상태 불변은 증명하지 못한다: eligible은 `init` 성공 보장이 아니다. (2) canonical registry(`--canonical`, `zoop-graph-canonical-1`): 닫힌 JSON, 최대 2,000,000B·20,000건이며 항목은 **정확한 S2 upstream `(jobId, inputDigest)`**와 `kind(company|event|topic)`·S3 endpoint `ref`에 묶인 `canonicalId`·`decisionRef`다(grant revision은 키에 넣지 않는다. grant 현재성은 모든 명령이 따로 검사한다). 이 파일이 canonical ID의 유일한 권위이며 S2 catalogue ID·SAME·후보 ID에서 추론하지 않는다. 여러 ref가 한 canonical ID로 합쳐질 수 있다(별칭). 이 결정은 공개 승인·S2 SAME·topic 승인이 아니다. 매 명령이 파일을 새로 읽고 디스크 cache를 쓰지 않으므로 철회·변경된 결정은 다음 명령에서 즉시 적용된다. (3) grant: 기존 `Authority`를 S3 `Engine.inspect()`를 통해서만 쓴다.

**`freeze`(SQLite만, Neo4j 접촉 없음).** `{versionId, relation:{jobId, inputDigest}}`. S3 job은 기존 읽기 전용 seam(`relation.Store(existing=True)`, 출력까지 shared lock)으로만 읽으며 owner가 S2 job·grant·rights·정확한 후보 집합을 현재 기준으로 다시 검증한다. ready·현재 전달·`inputDigest` 일치여야 하며 아니면 S3의 withheld 코드를 그대로 낸다. 고정하는 것은 S3 `inputDigest`, S2 upstream digest(grant revision 포함), 전체 review 상태 digest(`[rcId, relationKey, 상태, reviewPending, revision]`), 사용한 canonical 결정 전부와 그 digest, 정책 버전이다. eligible이고 review pending이 아닌 후보만 projection하며 HOLD·REJECT·pending·review 대기는 **개수만** 감사 기록(`s3Relations`, `eligibility`, `reviewPending`, `projectedCandidates`, `canonicalMerges`, `impactCandidatesNotProjected`)에 남기고 내용은 남기지 않는다. 투영 대상 endpoint(주체·객체·경로 단계) 중 하나라도 registry 결정이 없으면 `canonical_mapping_unresolved{total, unresolved(최대 50)}`로 **전체 freeze가 실패**하고 아무것도 쓰지 않는다(투영하지 않는 후보의 endpoint는 결정이 필요 없다). 대칭 유형(`COMPETES_WITH`)은 canonical 쌍을 `(kind, id)`로 다시 정렬하고, 자기 자신 관계나 2단계 경로의 세 기업이 합쳐지면 `canonical_mapping_conflict{self_relation|path_collapsed}`로 전체 실패한다. 별칭으로 canonical 내용이 같아진 후보는 한 간선으로 합치고 근거와 후보 ID는 합집합이다. 투영 대상이 0건이어도 유효한 빈 version이다. 같은 `versionId`에 같은 요청은 그대로 돌려주되 **그때마다** S3 현재성·고정된 upstream digest·사용한 canonical 결정이 아직 현재인지 다시 검사하고(요청이 바이트 단위로 같아도 grant가 바뀌었으면 `grant_revision_changed`), 다른 요청은 `version_input_conflict`로 아무것도 쓰지 않는다.

**저장 형태.** 모든 식별자가 version을 키에 포함하므로 version 사이에 노드가 공유되지 않고 삭제도 없다. 노드는 `:ZgCompany|:ZgEvent|:ZgTopic {vk: "<version>|<id>", v, id}`(ID 문자 집합에 `|`가 없어 키가 모호하지 않고 `version|id`로 왕복 검증한다), 간선은 `ZG_SUPPLIES|ZG_INVESTS_IN|ZG_COMPETES_WITH|ZG_PARTICIPATES_IN|ZG_RELATES_TO_TOPIC`에 `vk, v`와 `id, direction, connection, businessScope, productScope, validFrom, validUntil, countries, pathCompanyIds, evidenceIds, validityEvidenceIds, step1EvidenceIds, step2EvidenceIds, sourceRelationCandidateIds`(null·빈 목록은 쓰지 않고 읽을 때 복원)다. 관계 ID는 `rel-`+canonical 끝점·유형·범위·유효기간·경로의 digest이고 근거는 S2의 정확 인용 ID(`ev-…`)다. **quote·제목·URL·모델 rationale·검수 메모는 그래프·plan·출력 어디에도 없고** 근거 기록은 `{evidenceId, documentId, documentVersion, rawVersion, start, end}`뿐이다. 마커는 `:ZgVersion {versionId, schema, storeId, payloadDigest, graphDigest, nodeCount, edgeCount}`, 저장소 마커는 `:ZgStore {slot, storeId, schema, owner}`다. 한도는 간선 100·노드 300·근거 8,000·plan 2,000,000B(`version_limit_exceeded`)다. 모든 Cypher는 모듈 상수이고 데이터는 전부 파라미터이며 `run()`이 등록되지 않은 문장을 서버에 보내기 전에 거부한다. 삭제·MERGE·APOC·관리 문장은 없다.

**`init`.** 의도(무작위 owner 포함)를 SQLite에 먼저 commit한 뒤 DDL을 보낸다. 빈 database(노드·관계·기대하지 않은 제약/인덱스 없음, Neo4j 5.x)만 받아들이며 어긋나면 `graph_store_not_empty`/`graph_server_unsupported`다. 유일성 제약 10개(노드 5개: store slot·version ID·세 label의 `vk`, 관계 5개: 유형별 `vk`)와 label별 `v` range 인덱스 3개(소유 인덱스 포함 RANGE 13개)를 `IF NOT EXISTS`로 각자 explicit transaction에서 만들고 `db.awaitIndexes`로 기다린다. `:ZgStore`는 노드가 하나도 없을 때만 만들고 slot 유일성이 동시 두 번째 생성자를 막는다. 같은 원장의 재실행은 멱등이며, 이전 `init`이 중간에 죽었으면 **그 원장의 owner를 가진 마커 하나뿐**인 database만 이어받는다. 다른 원장·다른 `storeId`·내용이 있는 database는 채택하지 않는다.

**서버 경고 알림 방지.** 스키마(와 token)가 아직 없는 database에는 Zg label·관계 유형·속성 이름을 질의에 쓰지 않는다. 서버가 처음 보는 이름을 질의에 쓰면 UnknownLabel 경고 알림을 보내고 driver logger가 이를 stderr로 출력하기 때문이다. 그래서 `init`의 probe와 이후 모든 store 마커 조회는 label 이름 없이 `labels()` 술어로 찾고, DDL 이전에는 이름 없는 질의(`count`, `db.info`, `SHOW`)만 쓴다. 간선 endpoint 조회는 `WITH`로 질의 단계를 나눠 cartesian product 경고도 만들지 않는다. 알림을 숨기려고 logging이나 assertion을 끄지 않는다(smoke는 모든 CLI 프로세스의 stderr가 비어 있음을 확인한다).

**소유 열거·경합 안전 존재 검사·스키마 정의 preflight(독립 검토 R1–R4 반영).** (1) 한 version의 검증은 그 version의 노드에 붙은 간선만이 아니라 **그 version을 주장하는 모든 것**을 센다. 노드는 **label과 무관하게**(label이 없거나 마커 label `ZgVersion`·`ZgStore`여도) `v` 또는 `version|` 키 접두로, 간선은 `v` 또는 `vk` 접두로 주장하며(간선은 어디에 붙어 있든) 다른 version의 노드 사이에 걸린 소유 간선, 키는 이 version인데 `v`가 다른 노드, 데이터 label(`ZgCompany`·`ZgEvent`·`ZgTopic`) 정확히 하나가 아닌 label로 이 version을 주장하는 노드, 이 version의 노드에 붙은 다른 version 소유 간선은 모두 불일치이며 상한이 있다(`READ_OWNED_NODES`, `READ_OWNED_EDGES`, 기존 incident `READ_EDGES`). 같은 소유 열거를 마커·노드 부재 확인에도 쓰므로 마커도 노드도 없이 소유 간선이나 마커 label 노드만 남은 version은 "데이터 있음"이다. (2) read transaction은 snapshot이 아니라 read-committed라서 두 문장 사이에 늦은 commit이 보일 수 있다. version은 노드·간선·마커를 **한 원자적 append-only transaction**으로 쓰므로 commit된 데이터에는 항상 마커가 따라온다. 그래서 존재 검사는 마커→데이터→(처음에 마커가 없었으면) 마커를 다시 읽는 순서이며, 그 사이에 commit이 들어오면 '마커 없는 데이터'가 아니라 마커로 보인다(`recover`는 전체 검증, 쓰기 guard는 `unknown`). 마지막 마커 재조회에서도 마커가 없는데 데이터가 있으면 손상이다(유효한 commit은 둘을 원자적으로 쓴다). 마커가 보이면 이미 commit된 불변 version이므로 `recover`는 전체 그래프를 한 번 검증해 일치하면 ready, 불일치하면 종결 상태 `failed graph_version_corrupt`이며 재시도나 대기 휴리스틱은 없다. 상세 읽기의 `observe`는 끝에서 마커를 다시 읽어 바뀌지 않았음을 확인하고 바뀌었으면 불일치로 본다(계약 밖의 동시 변경 탐지). (3) `init`은 database에 이미 있는 제약·인덱스를 이름만이 아니라 **정의**(유형·대상·label/관계 유형·속성, 인덱스는 POPULATING|ONLINE)까지 기대값과 비교해 어긋나면 의도(SQLite binding)·DDL·store 마커보다 먼저 `graph_store_schema_mismatch`로 거부한다. 기대 이름을 가진 **LOOKUP 인덱스**도 정의 불일치다(투영은 LOOKUP을 정의하지 않는다). 기대 이름이 아닌 database 기본 token-lookup 인덱스만 스키마 밖으로 본다. 올바른 정의의 부분 스키마(중단된 init)와 동시 init의 멱등성·slot 유일성은 그대로다. (4) `focus`의 기업 존재 여부는 검증된 version의 **노드 집합** 기준이다(경로 중간 기업도 found, 자신만 distance 0, 간선 없음). 인접은 투영된 간선에서만 만들고 경로 단계 간선을 합성하지 않는다.

**`project`(단일 explicit unmanaged transaction, 자동 재시도 없음).** 현재 gate(S3·S2 권한과 고정된 upstream digest, **전체** review digest 일치(`review_revision_changed`), 사용한 canonical 결정 동일(`canonical_mapping_changed`))와 store binding(Neo4j 5·같은 database id·마커 하나·Zg label/type만·정확히 기대한 제약과 ONLINE 인덱스)을 통과하면 시도를 SQLite에 `reserved`로 **먼저 commit**한 뒤에야 쓴다. 트랜잭션 안에서 database·store 마커와 이 version의 흔적 부재를 다시 확인하고(마커가 이미 있으면 쓰지 않고 `unknown`, 마커 없는 version 노드는 `failed graph_version_corrupt`), 노드→유형별 간선→마커를 쓰며 매 문장의 반환 건수를 행 수와 대조하고(조용히 버려진 `MATCH`를 잡는다), **같은 트랜잭션에서 전체를 읽어** digest·건수를 대조한 뒤, commit 직전 gate를 다시 돌리고(registry 파일 바이트 포함) commit한다. `commit()` 호출 전 실패는 아무것도 commit하지 않았으므로 `frozen`으로 돌아가고(`graph_unavailable`/`graph_write_failed`/`graph_write_mismatch`/gate 코드) 시도는 `not-committed|rolled-back`이다. `ConstraintError`와 `commit()`에서 나온 모든 예외(`IncompleteCommit` 포함)는 `unknown`(`graph_commit_unknown`)이다. 상태는 `frozen → reserved → ready`이며 `ready`·`failed`는 종결이고(SQLite trigger), 시도는 version당 5회다. 타임아웃은 연결 5초·획득 10초·트랜잭션 30초·pool 2다.

**`recover`(읽기만, 쓰기·재생성·모델 호출 없음).** `reserved`/`unknown`만 대상이다. 마커가 있고 속성이 기대와 같으면 **전체 그래프**를 검증해 `ready`(시도 `confirmed`) 또는 `failed graph_version_corrupt`, 마커 속성이 다르면 `failed graph_version_conflict`(version ID를 태운다), 마커도 노드도 없으면 `frozen`으로 돌려 **명시적** `project`로만 다시 시도하게 하고, 마커 없는 노드가 있으면 `failed graph_version_corrupt`다. 그 사이 `project`는 추측하지 않고 `graph_commit_unknown`이다.

**`read`/`focus`(원장 읽기 전용, 무쓰기).** `ready`만 대상이다. 모든 gate가 현재여야 하고(실패하면 내용 없는 `withheld {schemaVersion, versionId, state, publication, delivery{status,code}, usage}`와 exit 2), store binding을 다시 확인한 뒤 **전체 그래프**를 한 읽기 transaction에서 가져와(문장마다 상한) 마커 속성·노드 label/키/왕복·간선 유형/키/끝점 label과 끝점 소속·중복 없음·digest·건수를 검증한다. 마커만으로는 신뢰하지 않으므로 누락·추가·변경된 노드·간선·속성은 `graph_version_corrupt`로 withheld다. 마커가 없으면 빈 결과가 아니라 withheld다. 빈 version은 `graph.nodes=[]`와 `verification`이 있는 정상 결과로 읽기 실패와 구별된다. `current.s3ReviewDigestMatches`는 제외 후보를 포함한 review 상태가 freeze 때와 같은지만 알린다(더 새로운 review는 새 version의 사유이며 불변 version을 withheld하지 않는다). `focus`는 검증이 끝난 version(간선 ≤100)을 메모리에서 무방향 BFS해 깊이 1·2·3의 노드(`distance`)와 간선을 돌려주고, 없는 기업은 `found:false`·빈 목록·exit 0이다. 가변 길이 Cypher를 쓰지 않으며 S3 생산 경로 길이(`MAX_PATH=2`)와 무관한 읽기 한도다.

**오류와 개인정보.** 모든 명령은 stdout에 canonical JSON 하나를 쓴다(`{schemaVersion, error:{code[,detail]}}`, exit 2). 주요 코드: 설정·상태(`input_or_configuration_invalid`, `command_input_limit`, `graph_state_missing|invalid`, `graph_busy`, `graph_recovery_required`, `state_namespace_conflict|invalid`), 저장소(`graph_uri_invalid`, `graph_auth_unconfigured|failed`, `graph_unavailable`, `graph_store_not_empty|already_bound|unbound|identity_mismatch|foreign_data|schema_mismatch`, `graph_server_unsupported`), 원천(S3/S2 코드 그대로, `relation_not_ready`, `review_revision_changed`), canonical(`canonical_registry_invalid|changed`, `canonical_mapping_unresolved|conflict|changed`, `relation_type_unsupported`, `relation_payload_invalid`, `evidence_record_conflict`), version(`version_not_found|not_frozen|not_ready|input_conflict|limit_exceeded`, `attempt_limit_exceeded`, `recovery_not_required`, `graph_commit_unknown`, `graph_write_failed|mismatch`, `graph_version_conflict|corrupt`). 예기치 않은 예외는 메시지·경로·URI 없이 `graph_internal_failure`이고 Neo4j 오류는 클래스나 상태 코드만 `detail`에 남긴다.

### 비공개 그래프의 내부 HTTP 조회

`ai/service`에 `GET /internal/v1/graph-versions/{versionId}`와 `GET /internal/v1/graph-versions/{versionId}/focus?companyId=&depth=1..3`를 추가했다. 별도 `graph.read` scope와 서버 소유 principal별 버전·digest 허용 목록을 사용한다. 허용되지 않은 버전은 존재 여부와 관계없이 child 실행 전에 403이며, 실행 대기·결과 수신·내용 반환 직전에 허용 상태를 다시 확인한다. graph 자격은 graph child에만 전달한다.

상태 조회에는 노드·간선·근거 내용이 없다. focus는 현재 원천 권한·canonical 결정·검수 revision·Neo4j 전체 그래프 검증과 digest 일치를 모두 통과할 때만 내용을 반환한다. withheld는 내용 없는 200, 원장 busy·Neo4j 장애는 503이며 빈 그래프로 위장하지 않는다. 공개 활성화·앱 상태 모델 매핑·Java 클라이언트는 포함하지 않았다. 계약·설정·백엔드 연결 주의점은 [그래프 조회 인수 문서](../../api/docs/GRAPH_READ_HANDOFF.md)를 따른다.

**관측한 검증(2026-10-15, 로컬 작업 트리).** `make service-test` 650개, `make service-pipeline-test` 105개, 내부 OpenAPI 재생성 일치 검사를 통과했다. 권한이 gate 대기 중 철회되면 child를 실행하지 않고 403이며, child 반환 중 철회되면 current·withheld·오류 여부와 무관하게 결과를 숨기는 회귀 시험을 포함한다. 실제 HTTP → 설치 CLI → 격리된 Neo4j 5.26 smoke도 권한 분리·digest·1~3홉·source 철회·canonical 변경·변조·busy·deadline·정보 노출 점검을 통과했다. 원천 원장은 불변, provider/model 호출은 0이었다. 첫 smoke의 정상 요청 에코 오판은 시험에서 수정했고 서비스의 반환 규칙은 완화하지 않았다. 임시 컨테이너와 소유 시험 상태는 정리했다. `public-check`는 생성물 275개 drift 0·hard error 0·문서 회귀 21개 통과였으며, 기존 원문 경고·프로토타입 차이는 유지했다. 운영 인증/TLS·실제 데이터 부하·원격 CI·Java 공개 API는 검증하지 않았다.

## S2/S3 → 공개 그래프 handoff bundle (AI 측 생산물, 앱 import·활성화는 백엔드 소유)

**범위와 한계.** `zoop_ai_pipeline.handoff_cli`(설치 명령 `zoop-ai-handoff`, wire `zoop-ai-handoff-1`, bundle `zoop-graph-handoff-bundle-1`)는 운영자 manifest가 고정한 **둘 이상일 수 있는 S3 relation job**과 각 S2 upstream을 기존 owner seam(비공개 그래프와 같은 gate: S3 `inspect`가 S2 job·grant·rights·후보 집합을 현재 기준으로 재검증)으로 읽어 **공개 이슈 중심 projection 하나**를 불변 artifact(`<state>/bundles/<sha256>.json`)로 저장한다. Neo4j·비공개 그래프 원장은 입력이 아니다. 앱 DB·공개 route·활성화·asOf 정책·evidence 등록·GraphDB 상태는 하지 않고, 모델·provider·네트워크 호출은 0이며 어떤 원천 원장도 쓰지 않는다. bundle은 앱의 `graphVersion`이 아니고 `readiness`가 항상 `{app:"import-pending", evidenceRegistration:"not-registered", publicActivation:"none", graphDb:"none"}`다. 원래 WBS 이슈(#61·#68·#78·#88 등)를 닫지 않는다.

**명령.** `freeze`(manifest 고정→원천 재검증→plan→엄격 검증→`reserved`→artifact 기록→`ready`), `inspect`(원장+artifact 무결성, 내용 없음), `recover`(`reserved`를 **저장된 artifact만**으로 정산: 원천을 읽지도 재생성하지도 않는다. artifact가 없거나 변조되면 그 ID는 `failed`(종료)이고 운영자는 **새 handoffId**로 freeze한다), `export`(artifact 검증 + **현재 권한 재검증** 뒤에만 bundle 출력). 같은 `handoffId`+같은 입력은 멱등(원천·파일이 아직 현재일 때만 에코), 다른 입력은 `handoff_input_conflict`다. 쓰기 명령은 배타 lock, 읽기 명령은 shared lock이며 writer가 잡고 있으면 `handoff_busy`(원천은 `relation_busy` 등) **오류**이지 빈 bundle이 아니다.

**운영자 입력(모두 정확한 파일 hash로 manifest에 고정).** (1) `zoop-graph-canonical-1`(기존): S3 endpoint(`company`/`event`)→canonical ID, 정확한 S2 upstream `(jobId,inputDigest)`에 묶임. (2) `zoop-public-decisions-1`: `companies`(canonical→앱 `companies.id`+label), `issues`(canonical→공개 issue id, **geography 필드 verdict**, 선택적 representative), `structural`(이슈·기업·S3 SUPPLIES basis ≤2 + **수동 applicability 단언**), `follows`(명시 순서 결정). (3) `zoop-app-document-bindings-1`: `(documentId,documentVersion)`→`(articleId,articleVersion)`+앱 텍스트 `textSha256`+`offsetUnit`. manifest의 `sourceKind`는 **선언**이며 모든 S3·S2 관측 provenance와 같아야 하고(synthetic을 actual로 올릴 수 없음) bundle에 `declaredSourceKind`/`observedSourceKind`가 따로 남는다.

원천 issue member의 동일성은 `(upstream, kind, event ref, mentionId, documentId, documentVersion, exact observation)` 전체로 정한다. S2의 `mentionId`는 문서 간 전역 식별자가 아니므로 다른 문서의 같은 값도 별도 member다. `sourceEvents[]`, geography 근거, 대표 member 결정과 구조 적용성 `bindingDigest`에 이 식별자를 그대로 사용한다. source가 여러 S3 job에 재사용돼도 완전히 같은 member tuple만 중복 제거한다.

**공개 관계의 의미와 근거.** `INVOLVES`: eligible·review 대기 아닌 S3 `PARTICIPATES_IN`(company→event, 독립 verifier가 모든 claim 지지)만, canonical event→issue와 company→공개 company 결정이 모두 있을 때, **방향을 뒤집어** issue→company로. `STRUCTURALLY_RELATED_TO`: S3는 이슈별 적용성을 산출하지 않는다(영향 후보는 relation별 텍스트 라벨이고 이슈 연결·적용성 필드가 없다). 그래서 **운영자의 독립 검토 단언**을 정확한 issue source event·basis relation(S3 review revision 포함)·decision version에 묶은 `bindingDigest`로만 받아들이며, bundle에는 `provenance.origin="manual-operator-review"`, `s3SemanticValidation="none"`으로 표시한다(S3가 의미를 검증했다고 주장하지 않음). 기계 검사는 basis가 eligible·직접(`connection=direct`)·`SUPPLIES`(PoC 구조 basis 집합과 겹치는 유일한 S3 유형)이고 참여 기업에서 대상 기업으로 이어지는 ≤2 경로이며, 이벤트 시각이 basis 유효기간 안(시각이 일 단위보다 거칠면 증명 불가)이고 basis 국가가 이슈 국가를 포함하는지다. `FOLLOWS`: S2 비교의 effective `FOLLOWS`(증거가 incoming 기사에 있고 정확 인용)에 운영자 순서 결정이 `groupDigest`로 묶인 경우만, 뒤 이슈→앞 이슈. 근거 없는 company–company 유형·topic·`SHARES_ISSUE`(소비자가 권한·시간 필터 뒤 파생)는 내보내지 않고, 적격하지만 공개 간선이 아닌 S3 유형은 `sources[].audit.eligibleNotPublicByType` 개수로만 남긴다.

구조 basis가 유효기간(`validFrom`/`validUntil`)을 제시하면 별도의 `validity.citations`도 직접 관계 인용과 똑같이 재해석하고 앱 문서 바인딩을 확인한다. 양쪽 인용의 합집합을 `basis.evidenceIds`에 담고 그 전체에서 `sourceArticles`를 만든다. 유효기간 근거 문서가 바인딩되지 않거나 앱 텍스트 hash가 일치하지 않으면 구조 간선을 제외하며 날짜만 남기지 않는다. 각 basis는 S3의 `relationKey`도 기록하므로 수신 측이 구조 간선 ID를 독립적으로 검증할 수 있다.

**geography.** 이슈마다 `domestic|international` 필수. S2/S3는 국가 필드를 **검증하지 않으므로**(mention `countries`는 모델 출력일 뿐) 운영자의 field verdict(`countries`, 이슈 자신의 문서 span ≤20개 — 좌표와 본 텍스트 `quoteSha256`)가 유일한 검증이다. 생산자는 verdict 국가 집합이 well-formed, 분류와 일치(정확히 `["KR"]`→domestic, 하나라도 비KR(KR+타국 포함)→international), **모든 source mention의 국가 필드와 같고** span이 해당 이슈 문서의 정확 텍스트인지 검사한다. 필드 없음→`geography_unproven`, 불일치→`geography_countries_disagree`/`geography_decision_mismatch`로 제외되고 미상을 international로 매핑하지 않는다. 회사 국가·티커·거래소·언어 휴리스틱은 쓰지 않는다. 정책 `zoop-public-projection-policy-1`, verdict의 `decisionRef`/`decisionVersion`이 bundle에 남는다.

**근거와 앱 매핑.** evidence id = `ev-`+sha256(canonical JSON `{kind:"graph-body-span", articleId, articleVersion, start, end}`)(앱 `Canonical.digest`와 같은 규칙, S1 `{analysisId,evidenceId}`·S2 `ev-`+32hex와 충돌·별칭 없음, 같은 문서 span이 다른 문서·버전이면 다른 id). 각 근거는 owner 재해석(`cite_exact`: 정확 span·whole mapped run·ingestion resolver)으로 **지금** 검증하고 `quoteSha256`·`rawLocatorIds`·source 좌표(`documentId`/`documentVersion`/`rawVersion`/S2 `ev-…`)만 싣는다(인용문·본문 없음). 바인딩의 `textSha256`이 원천 텍스트 sha256과 다르면 그 문서에 기대는 항목은 `app_binding_text_mismatch`로 제외되고, 바인딩이 없으면 `app_binding_missing`이다(임의 매핑을 앱 검증됨으로 보고하지 않음). **생산자가 확인한 것**과 **앱 import가 해야 할 것**은 bundle의 `checks.producerConfirmed`/`checks.appImportPending`에 분리돼 있다. evidence id는 "준비됨"이지 등록·공개된 것이 아니며 기존 `getEvidence`는 등록되지 않은 graph evidence를 제공하지 않는다.

한 `(documentId,documentVersion)`에 여러 정확한 관측이 있어도 모두 유지하며, 같은 관측만 중복 제거한다. 공개 기사 하나로 만들기 전에 각 관측의 제목·URL·발행 시각이 모두 같은지 검사하고 차이가 있으면 `article_metadata_conflict`로 freeze를 중단한다. backend용 bundle 검증기는 source 정책·감사, member·대표, 관계 유형별 provenance·sourceRefs, basis의 기사·근거 참조, 제외 상세와 관계 ID 공식까지 닫힌 형식으로 확인한다. `contentDigest` 재계산만으로 중첩 의미 검증을 대체하지 않는다.

**시각.** `articles[].publishedAt`(+`publicationPrecision` datetime|day|unknown, 자정 날조 없음; `day`는 수집으로 날짜만 선언된 문서의 `YYYY-MM-DD`), `articles[].observations[].observedAt`, `issues[].eventTime`(+형식으로만 정한 `timePrecision`), `basis[].verifiedAt`(S3 verdict 시각)은 서로 다른 시계로 따로 보존하고, 필터 정책(asOf)은 단언하지 않는다. freeze 시각은 receipt의 `frozenAt`, export 확인 시각은 `delivery.checkedAt`이며 bundle 자체는 결정적이다.

**현재 권한과 복구.** export는 저장된 `ready`여도 (1) 세 운영자 파일이 manifest 고정 hash와 같고(아니면 `canonical_mapping_changed`/`decisions_changed`/`bindings_changed`, 파싱 불가도 withheld), (2) **내용을 내지 않은 구성 원천까지 포함해** 각 S3 job이 ready·현재 전달·고정 upstream(grant revision 포함)이며, (3) bundle이 쓴 relation의 review revision이 그대로이고(`review_revision_changed`), (4) 다시 만든 content digest가 같아야 한다. 출력 직전에 S3 읽기 잠금 아래 모든 구성 원천과 세 운영자 파일을 다시 확인한 뒤 응답을 직렬화한다. 하나라도 어긋나면 `{schemaVersion, handoffId, state, publication, delivery{withheld,code}, usage}`뿐인 withheld(exit 2)이고 **bundle·개수·제외 항목 id가 나가지 않는다**. 제외 항목(`exclusions.items`)은 id·코드만이며 current export의 bundle 안에서만 나간다. freeze는 전체 review 상태를 정확히 고정하고, export는 사용하지 않은(제외된) 후보의 review 변화로는 withheld하지 않으며 `delivery.reviewDigestMatches`로만 알린다. 기존 디렉터리·DB는 chmod·mkdir·원장 DDL 전에 읽기 전용으로 네임스페이스와 소유 표식·구조를 확인하고, 미확인 상태는 채택하지 않는다. 앱 저장소와 이 원장·원천은 원자적이지 않다. 잠금이 보호하지 않는 권한·운영자 파일은 마지막 확인 직후에도 변경될 수 있고, 응답과 앱 import 사이 철회도 막지 못하므로 앱의 import 시점 권한 재확인이 필요하다.

## S4 일부: S2/S3 의존 대상 조회 (읽기 전용)

**범위.** `zoop_ai_pipeline.dependency_cli`(설치 명령 `zoop-ai-dependents`, wire `zoop-dependency-s4`)는 변경된 문서·source·grant **하나**를 stdin으로 받아 이미 저장된 ingestion·S2·S3 원장에서 그 변경에 기대는 job과 후보를 나열한다. **보고 전용**이다. 철회·withheld 처리·재검증·재생성·게시·GraphDB 변경, 현재 registry·권한·delivery 판정, 모델·provider 호출, 쓰기를 하지 않는다. 실제 권한 철회, 공개 barrier, 과거 채팅·브리핑·pin·캐시 차단과 증분 복구(S4의 나머지)는 구현하지 않았다. 공개 route·OpenAPI·앱 DB는 바꾸지 않았고 HTTP로 열지 않았다.

```sh
zoop-ai-dependents --ingestion-state-dir DIR --extraction-state-dir DIR [--relation-state-dir DIR] < query.json
```

stdin은 100,000B 이하의 닫힌 JSON이다(알 수 없는 키·다른 `schemaVersion` 거부, null을 허용하는 키도 생략할 수 없다). 변경은 세 모양 중 하나다. `{"kind":"document","documentId","documentVersion":hex|null,"rawVersion":hex|null}`, `{"kind":"source","sourceId"}`, `{"kind":"grant","grantId","revision":str|null}`. null은 **묶여 있는 모든 값(과거 포함)** 이며 "최신"으로 해석하지 않는다. `--relation-state-dir`를 생략하면 보고서의 `relation`과 `counts.relation`은 `[]`·0이 아니라 `null`이다.

**무엇과 일치시키나.** S2 job을 만들 때 고정한 binding의 관측(`roundId/sourceId/page/ordinal/documentId/rawVersion/documentVersion`)과 같은 자리에 고정된 grant(`grantId/revision`)다. 현재 registry와 권한이 아니므로 권한이 철회돼 owner의 `inspect`/`export`가 withheld인 job도 같은 모양으로 보고한다. queued·running·stopped·reconciling·cancelled·ready 모든 상태의 job을 읽는다(`state`는 읽은 시점의 원장 값이지 delivery 상태가 아니다). 한 job의 인용 가능한 문서는 incoming 문서와 snapshot member뿐이라(`_context`) 일치하는 관측이 없는 job은 영향이 없다.

**따라가는 관계(기록된 연결만).** S2 job → `snapshotEvents`(member 문서) · `eventCandidates`(incoming이면 `extracted_from`, 영향받는 snapshot event와 비교됐으면 `disposition_input`) · `comparisons`(`incoming_document`, `target_event_member`, 인용 `cites`) · `topicCandidates`(`member_event`, `cites`). S3 job은 자신이 고정한 upstream `(jobId, inputDigest)`와 `upstream.digest`로 연결한다. `inputDigest`는 요청·replay만 덮고 고정된 grant는 덮지 않으며 관계 binding은 어느 extraction 원장을 읽었는지 기록하지 않으므로, 같은 job ID·같은 입력이 다른 grant revision으로 고정된 원장은 `inputDigest`만으로 구별되지 않는다. reader는 저장 행에서 owner의 전달 projection(고정 binding과 event/topic 후보)을 다시 계산한 digest를 S3의 `upstream.digest`와 비교하고, upstream이 스캔한 원장에 없거나(`upstream_not_in_scanned_ledger`), 입력 digest가 다르거나(`upstream_input_mismatch`), ready가 아니거나(S3는 ready job에서만 만들어지고 ready는 종료 상태다) digest가 다르면(`upstream_binding_mismatch`) 영향 여부를 판단하기 **전에** 버리지 않고 `unresolved`로 나열한다. 영향받는 upstream의 relation job은 `relationCandidates`(영향받는 event/topic를 **종류가 맞는** endpoint로 가리키는 `endpoint_event`/`endpoint_topic`, `citations`·`validity`·`step:N`의 `cites`; 이벤트 ID를 topic처럼 쓴 endpoint는 의존이 아니다)와 `impactCandidates`(부모 `relation`, `supporting`/`opposing` `cites`)를 직접 항목으로 갖고, 각각 저장된 chain의 `eligibility`(pending/eligible/hold/reject)와 `verdictStatus`를 함께 낸다. **`jobScope`는 job 전체의 개수**다. owner delivery가 job의 모든 문서를 다시 검증하므로 권리·binding 변경은 job 전체를 withheld로 만들고, 직접 목록은 그 가운데 생산·근거로 연결된 부분집합이다.

**출력과 개인정보.** 하나의 canonical JSON 객체(`changed` 정규화 echo, `identity{bound,recordedInIngestion}`, `basis`, `consistency`, `notCovered`, `extraction{ledgerVersion,scannedJobs,jobs}`, `relation`, `counts`, `effect`, `usage{providerCalls:0,modelCalls:0}`)이고 목록은 결정적 순서다. 담는 것은 ID·digest·관측 좌표·grant·상태·eligibility·reason 코드뿐이며 원문·quote·제목·URL·mention·topic label/criteria·관계 유형/범위·impact label/direction·회사명·파일 경로·원 응답은 없다. `notCovered`는 항상 ingestion 원장 기록·S1 worker·앱 상태·게시 브리핑·채팅·pin·캐시·GraphDB·PoC 저장소·스캔하지 않은 extraction/relation 원장을 명시한다. 완전성은 **스캔한 원장에 한정**되며 전체 철회 closure가 아니다.

**정합성과 닫힘.** 원장은 ingestion → extraction → relation 순서로 기존 `Store(existing=True)`(shared non-blocking flock·`immutable=1`·비어 있지 않은 WAL은 `*_recovery_required`·없으면 `*_state_missing`·활성 writer면 `*_busy`)로 연다. relation `Store`에도 같은 읽기 전용 모드를 추가했고 생성자 시그니처는 `Store(root, *upstream_roots, existing=False)`이므로 기존 호출은 그대로다. shared lock은 첫 읽기부터 출력이 끝날 때까지 모두 유지하고 pipeline writer는 모두 exclusive non-blocking lock을 쓰므로 읽는 동안 어떤 원장도 바뀌지 않고 그동안 시작하는 writer는 `*_busy`다. 오류는 부분 출력 없는 `{"schemaVersion","error":{"code"[,"detail"]}}`와 exit 2다. `command_input_limit`, `input_or_configuration_invalid`, `state_namespace_conflict`/`state_namespace_invalid`/`state_ownership_unconfigured`, `ingestion|extraction|relation_{state_missing,busy,recovery_required,state_invalid}`, `ledger_version_unknown`, `dependency_record_invalid`(`detail{ledger[,jobId]}`: 저장된 binding·request·payload가 파싱되지 않거나 키가 없거나 citations·path·topic members 같은 의존 container가 배열이 아니면 빈 값으로 읽지 않고 보고서 전체 실패), `changed_identity_unknown`, `dependency_report_limit`(`detail{entries,limit}`: 항목 10,000 초과를 자르지 않고 거부, 프로토타입 상한이며 실측값이 아니다), `persistence_failed`, `dependency_internal_failure`가 있다. 일치하는 관측이 없어도 변경 ID가 ingestion 원장에 기록돼 있으면 `bound:false`의 확인된 빈 결과(exit 0)이고, 어느 쪽에도 없으면 성공-빈 결과가 아니라 `changed_identity_unknown`이다.

**한계.** ingestion은 resume 때 적용한 문서별 grant revision을 기록하지 않아 grant 일치는 extraction이 고정한 값만 쓴다(ingestion 원장은 빈 결과를 확인할 때 round 등록 때 고정한 registry에서만 읽는다). "현재 버전" 포인터는 어디에도 없어 해석하지 않는다. 인용에는 sourceId·grant가 없으므로 source/grant 변경은 같은 job의 일치한 관측을 거쳐서만 인용에 닿는다(문서 ID는 source-local이라 안전하다). 관계 binding이 읽은 extraction 원장의 위치는 기록돼 있지 않으므로 일치는 위치가 아니라 S3가 고정한 upstream digest로만 판단한다. 현재 코드에서 ingestion 문서를 소비하는 곳은 S2→S3뿐이며(`grep` 확인: `ai/pipeline` 밖에서 `zoop_ai_pipeline`·S2/S3 원장을 쓰는 코드 없음) 그 밖의 저장소와의 연결은 기록돼 있지 않아 보고하지 않는다. 한 쌍의 extraction/relation 원장만 스캔하며 다중 원장 위상은 미정이다.

구현은 `dependency_contracts.py`(wire·일치 규칙·상한·배열 검증), `dependency_cli.py`, 그리고 원장 소유 모듈의 읽기 전용 reader(`ingestion.recorded`, `extraction.dependents`, `relation.dependents`, 공유 `relation.chain`)다. 정상 결과와 S4의 digest가 같은 코드를 쓰도록 extraction 소유 `candidate_rows`/`project_candidates`(전달 projection, 권한 gate 뒤의 `Extractor.result`와 읽기 전용 reader가 공유)와 `upstream_digest`(relation이 이를 가져다 쓴다)를 두었다. 시험 `ai/pipeline/tests/test_dependency.py`는 실제 ingestion·S2·S3 원장을 authored replay로 만들고 snapshot member/incoming 문서별 traversal 차이, 이벤트·topic endpoint 종류 구분, 고정된 grant와 현재 registry의 분리, 같은 job·입력이 다른 고정 grant revision이거나 ready가 아닌 upstream의 `upstream_binding_mismatch`, 모든 상태 job 포함, 알 수 없는 ID·손상·hot WAL·busy·버전 불명·구조 불일치·배열이 아닌 의존 container의 닫힘, 잠금 유지, 출력의 개인정보 부재와 결정성, 원장 바이트·mode·mtime 불변을 검사한다. `ai/pipeline/scripts/dependency_smoke.py`는 같은 흐름(같은 입력·다른 고정 grant revision 포함)을 실제 CLI subprocess로 실행하며 소켓과 상태 루트 쓰기를 감시 hook으로 막는다.

실행 증거(10/13, `72219db` 이후 최종 로컬 작업 트리): `uv sync --offline --project ai/pipeline --frozen --group dev`로 설치했고, `ai/pipeline/.venv/bin/python -B -m pytest ai/pipeline/tests -q -p no:cacheprovider`에서 **208 passed**를 확인했다. `ai/pipeline/.venv/bin/python -B ai/pipeline/scripts/dependency_smoke.py`도 **status=passed, providerCalls=0, modelCalls=0**이었다. 실제 CLI 프로세스에서 문서·source·grant별 전파, 권한 철회 뒤 동일한 메타데이터 결과, 미등록 ID·없는 원장·hot WAL 거부, 원문·경로 미노출, 원장 파일·권한·수정시각 무변경을 관측했다. 특히 같은 job·입력이라도 고정 grant revision이 다른 원장을 연결하면 `upstream_binding_mismatch`로 보고하며 원래 원장의 정상 연결은 유지함을 확인했다.

독립 검토에서 발견한 upstream binding 비교 누락과 잘못된 배열 형식의 빈 목록 오인을 수정했다. 추가 회귀 15건은 최종 모두 통과했다. 수정 전에는 13건이 실제 동작 결함을 재현했고, 대조 1건은 통과했으며, 다른 grant의 ready 원장을 만드는 1건은 fixture 오류로 본 검증에 도달하지 못했다. 해당 fixture를 올바르게 구성한 뒤 테스트와 실제 CLI 양쪽에서 다른 grant 연결의 거부를 확인했다. 이 변경은 아직 커밋·푸시하지 않았으며 이전 원격 CI의 검증 범위에 포함되지 않는다.

## 내부 HTTP transport (S1, S2, S3)

**위치와 범위.** `ai/service`(`zoop_ai_service`, FastAPI/uvicorn)는 S1 네 kind(`document-summary`, `document-sentiment`, `semantic-verification`, `briefing-outlook`)를 `/internal/v1/analysis-jobs` 아래, 그리고 별도 가족으로 S2 추출 job을 `/internal/v1/extraction-jobs` 아래(기본 꺼짐, 아래 S2 절)와 S3 관계 job을 `/internal/v1/relation-jobs` 아래(기본 꺼짐, 아래 S3 절) 제출·상태·결과·취소·복구(S3는 검수·재검증 포함)로 노출한다. 설치된 `zoop-ai` CLI의 `submit/run/get/resume/cancel`(S3는 `zoop-ai-relation`의 `submit/inspect/resume/cancel/review/revalidate`)만 고정 argv로 호출하며 `zoop_ai`·pipeline·BFF를 import하지 않고 worker의 `worker.sqlite3`와 pipeline 원장을 열지 않는다. 런타임 원장이 작업 상태의 유일한 출처이고 서비스 원장(`service.sqlite3`, S2는 `extraction-jobs.sqlite3`, S3는 `relation-jobs.sqlite3`)은 소유자·멱등·(S2는) 고정된 승인 신원·dispatch 상태만 갖는다. **로컬 준비 상태이며 배포·SG/프록시/TLS는 확인하지 않았고 승인되지 않았다. 원격 CI는 `5cf208e`의 [실행 38226220631](https://github.com/Donbug/zoop/actions/runs/38226220631)에서 8개 작업이 모두 통과했고 여기에는 실제 Java 클라이언트 → 이 서비스 → 설치된 `zoop-ai` replay 종단 시험이 포함된다(S2·S3 가족은 그 이후 로컬 추가분이며 원격에서 실행되지 않았다). Spring 전송 클라이언트(`api/src/main/java/com/zoop/ai`)가 S1·S2·S3 세 가족의 HTTP를 소비한다(`AiAnalysisClient`·`ExtractionClient`·`RelationClient`, 가족별 기본 비활성; S2·S3는 실제 서비스와 설치된 pipeline replay 종단 gate `api/scripts/ai_pipeline_gate.py`로 로컬 검증). 공개 앱의 인증·사용자 격리·공개 endpoint·배포는 아직 없다. 앱 DB 저장과 AI 결과 import는 S1 문서 요약·기업 판정에 한해 operator 전용 비웹 실행([문서 분석](../../api/docs/DOCUMENT_ANALYSIS.md))으로만 있고 S2·S3·`briefing-outlook` 결과 import는 없다. 프로토타입 BFF는 이 HTTP를 소비하지 않고 CLI를 직접 호출한다.** S2-2(`zoop-ai-extract`)는 hash가 job 입력 digest에 들어가는 운영자 소유 `--replay` 파일을 요구하므로, 호출자가 스냅샷·카탈로그·fixture를 보내는 모델이 아니라 **서버가 사전 승인한 정확한 요청을 digest로 참조하는** 별도 가족(`/internal/v1/extraction-jobs`, 아래 S2 절)으로만 열었다. S2-1은 운영자 파일 입력이라 HTTP 대상이 아니다. 계약은 생성 문서 [`internal-ai-openapi.yaml`](../api/internal-ai-openapi.yaml)/`.json`(요청·복구 예시 포함)이며 `Submit`/`JobResult`는 [`ai-contract.schema.json`](../api/ai-contract.schema.json)을 참조한다. 공개 `docs/api/openapi.yaml`은 바꾸지 않았다. 운영·설정·토큰 절차는 [`ai/service/README.md`](../../ai/service/README.md)다. S4 의존 대상 조회(`zoop-ai-dependents`)도 이 HTTP로 열지 않았다.

### 접수·소유 결속·dispatch

| 단계 | 동작 | 불변식 |
|---|---|---|
| 인증·검증 | operator 발급 bearer token의 SHA-256 digest를 설정된 **모든** digest와 `hmac.compare_digest`로 대조한다. scope(`analysis.submit/read/cancel/recover`)→헤더(`Idempotency-Key`==`body.jobId`, content-type)→본문(2,000,000B, 엄격 UTF-8·중복 키 거부, 최상위 키 집합)을 이 순서로 확인한다. | 요청이 경로·명령·환경·URL·모델·fixture를 고를 수 없다. 서비스는 비밀을 생성하지 않는다. |
| 소유 의도 | 서비스 원장에 `owner+jobId+요청 digest`를 `reserved`로 **먼저** durable 기록한 뒤 `zoop-ai submit`(모델 호출 0)을 실행한다. | 응답 전 충돌로 런타임에만 등록된 고아 job을 다른 principal이 가져갈 수 없다(409 `job_id_unavailable`). 예약은 시간으로 청소하지 않고, 런타임이 **첫 시도에서 명확히 거절**한 경우(입력 검증·`job_input_conflict`·모델/effort/provider 설정·grant registry 코드)에만 지운다. |
| 접수 | 런타임 등록이 확인되면 `accepted`(런타임 `inputDigest`)와 dispatch 의도를 한 transaction으로 기록하고 202. 같은 key·본문 재전송은 200. | 202는 승인·예산·모델 호출을 뜻하지 않는다. 다른 본문은 409 `idempotency_conflict`이며 런타임을 호출하지 않는다. |
| dispatch | 한 스레드·한 child가 가장 오래된 pending을 `in_flight`로 확정하고 `run`/`resume`을 실행한다. 이름 없는 임시 파일 stdin, stderr 폐기, 자기 세션, 데드라인 30초(제출·조회·취소)/300초(실행). | replay ordinal이 ledger 전체 순서이므로 직렬이다. 서비스 종료는 child를 기다리거나 죽이지 않는다. |
| 상태 | 요청마다 `zoop-ai get`을 실행해 만든다. 서비스가 기억한 값은 dispatch 행뿐이다. | POST가 돌려준 `queued`가 오래 남지 않으며 cache hit은 자기 호출 0(`unreceiptedAttempts=0`)으로 보고한다. |

| 런타임 결과 | dispatch 갱신 |
|---|---|
| 자동 재dispatch(재시작·비정상 child·busy 폴링) | worker `--initial-only`(런타임 job lock 안에서 판정)로 실행한다. 호출 기록이 없는 job만 시작하고, 기록이 있으면 저장된 receipt 저장만 하며 reserve/송신/provider 생성이 없다. 일부 단계 receipt만 있는 job(예: 생성 receipt 뒤 검증 reserve 전 중단)은 `idle`+`needs_recover`이며 제한 없는 명시적 recover만 이어 간다. started/unknown은 기존대로 `reconciling` |
| exit 0, `queued`/`running` | 다른 프로세스가 잡고 있다는 뜻이므로 지수 backoff(≤60초)로 `pending` 유지, `busy` |
| exit 0, `persisting`+`save_only`+**필요한 모든 단계의 receipt가 이미 저장됨** | 즉시 `resume`(CLI가 provider를 만들지 않으므로 송신 불가), 이후 다시 `persisting`이면 `idle` |
| exit 0, 그 밖의 `persisting`, `failed`(`unsent_only` 포함), `ready`, `cancelled`, `reconciling` | `idle`. 미송신 단계 재개는 **명시적 recover만** 한다 |
| exit 2 + 코드 | `idle`, `runtime_error`, `lastRuntimeCode`(예 `replay_fixture_invalid`). job은 `queued`로 남고 `next=recover` |
| 데드라인·signal·비정상 종료·불가해 출력 | `transport_unknown`, 같은 job을 런타임에 다시 맡김(최대 3회, 이후 `idle`). 서비스는 결과를 판정하지 않으며 응답을 잃은 호출은 런타임이 `reconciling`으로 만들고 재송신하지 않는다 |
| spawn 실패·stdout 16MiB 초과 | `idle`, `runtime_unavailable` |
| 서비스 시작 때 `in_flight` | `pending`, `service_restarted` |

대기+실행 중 dispatch 상한(1,000, in_flight 포함)은 접수와 명시적 recover의 트랜잭션 안에서 원자적으로 확인하며(coalesce는 자리를 쓰지 않음, claim된 job의 재대기는 자리가 이미 예약돼 있음), 상한을 넘는 `Content-Length`는 즉시 413으로 답하고 응답 뒤 제한된 시간·양만 버려 읽는다. child가 끝난 뒤 dispatch 결과의 원장 쓰기가 일시적으로 실패하면 그 결과를 보관해 **쓰기만** 재시도한다(worker 재실행 없음). `next`는 순수 규칙이다: dispatch pending/in_flight→`wait`, ready→`fetch_result`, reconciling→`operator_reconcile`, cancelled 또는 `resumeMode=none`인 failed→`none`, 나머지→`recover`. 내부 `ready`는 공개 `completed`가 아니다. 런타임 `input_or_configuration_invalid`는 클라이언트 입력과 서버 I/O 오류가 섞여 있어, 서버 입력(grant registry·worker 명령·worker state)을 제출 전후로 확인해 깨끗하고 같은 registry였을 때만 422이며 아니면 안정적인 503 `service_configuration_invalid`다.

### 취소·결과 전달·개인정보

- 취소는 런타임 fence를 올리고 pending dispatch를 끝낸다. 진행 중 child는 죽이지 않으므로 늦게 온 응답은 receipt로 저장되어 사용량에 남고, artifact 저장과 verify 송신만 막힌다. 환불 보장은 없고 `reconciling`은 어떤 명령도 정산하지 못해 운영자 판단(공급자 측 사용량 증거)이 필요하다.
- `result`는 런타임 `get` 출력을 **허용 목록 View**로 다시 직렬화한다(알 수 없는 키 제거, 누락 키는 실패, 자유 문자열 `phase`/`failure.code`/`calls[].error`는 기계 코드가 아니면 `redacted`). `input`·`artifacts`는 worker 계약 타입의 잎까지 필드 단위로 투영한다(계약에 없는 필드 제거, 필수 필드 누락·타입 오류는 닫힘; 필드 일치는 `zoop_ai` 계약과 시험으로 비교하며 서비스는 import하지 않는다). 그 위에서 서버가 **현재** grant registry를 직접 읽어 권리·revision·source·만료·operation·purpose·recipient를 확인하고(런타임이 echo한 grant는 실행 시점 스냅샷일 뿐이다), 막히면 `delivery.state=withheld`와 내용 없는 `receipts`만 돌려준다. live job은 필요한 모든 단계의 호출 기록이 있어야 recipient를 증명할 수 있으므로 그 전에는 `reason=recipient_unproven`으로 막는다(대기 큐로 내용이 새지 않음). 모델 호출이 없는 live 빈 회차 outlook도 기록이 없어 같은 이유로 막힌다(실패 시 닫힘, 가짜 출력 없음). registry를 읽을 수 없으면 503이다. 앱은 여전히 자체 현재 권한·visibility로 수입 gate를 다시 적용한다.
- 오류 envelope에는 message·stack·stderr·argv·경로·환경 문자열이 없고, stdout 로그는 요청마다 안정 필드(requestId, principal, 라우트 템플릿, jobId, status, 런타임 exit/code, 소요 시간)만 낸다. 런타임의 stderr는 읽지 않고 버린다.

`service-test`는 **208 passed**(실제 uvicorn 프로세스+설치된 `zoop-ai`+repository-authored 합성 replay; 114.5초)였다. 증명 범위: 설정 실패 닫힘(exit 78, 값 미출력, listener 없음, 두 번째 인스턴스·worker 원장 binding 거부); 401 동일 응답·403·`/docs` 404·타 principal 404/409와 런타임 무변경; 멱등 202/200·key/본문 불일치·크기/형식/중복 키·live·replay 불가·동시 중복 요청 정확히 1회 등록·1회 dispatch; 문서 4건+outlook(빈 회차 무호출 포함)+단독 semantic-verification 모두 ready(`replayCalls` 총 10, `providerAttempts` 0)이며 `result.job`이 직접 `zoop-ai get` 출력과 **동일**; 소유 의도·런타임 등록·응답 전·dispatch claim 후 SIGKILL 뒤 재시작이 중복·고아 탈취 없이 완료; 차단된 replay fixture는 `queued`+`runtime_error`+`next=recover`로 보고되고 recover 뒤 ready; loopback provider의 요청 수로 서비스 kill/재시작 재송신 없음, child kill·데드라인 kill은 `reconciling`(요청 1회)이며 재시작 뒤에도 유지, 소진된 예산은 자동 재개 없이 명시적 recover도 새 호출 없음; 취소 중 receipt 보존·verify 미송신·대기 job 미송신; grant 철회·변경·만료·registry 손상 시 content withheld/503; 응답·헤더·로그·`service.sqlite3`에 비밀·경로·문서 본문·stderr 없음. `service-smoke`는 `replay: status=passed, kinds=4, providerAttempts=0, replayCalls=10`, `recover: status=passed`, `cancel: status=passed, loopbackRequests=1`, `restart: status=passed, loopbackRequests=2`를 출력했고 소유한 서버·임시 상태를 정리했다. `service-openapi-check`는 생성 JSON/YAML drift가 없음을 확인했다.

live 경로 시험의 provider는 `127.0.0.1`의 표준 라이브러리 HTTP 서버(요청 수만 센다)이며 실제 모델·외부 네트워크가 아니다. 프로세스 충돌 시험은 `tests/launcher.py`가 실제 컴포넌트를 감싸 정해진 경계에서 SIGKILL하며 프로덕션 코드에는 그런 hook이 없다.

### S3 관계 job의 내부 HTTP (`/internal/v1/relation-jobs`)

같은 서비스 프로세스의 **별도 리소스 가족**이며 S1의 `zoop-ai-internal-1` 와이어·상태 기계·원장과 섞이지 않는다(S1 `runtime._interpret`는 모든 exit 2를 `error.code`가 있는 오류로 보지만 pipeline은 전달이 withheld인 완전한 결과도 exit 2로 내고, pipeline에는 S1 worker의 under-lock `--initial-only` 표지가 없다). 스키마 `zoop-ai-internal-relation-1`, scope `relation.submit|read|cancel|recover|review`, 설치된 `zoop-ai-relation`을 고정 argv와 이름 없는 stdin으로만 호출하며(submit·inspect·cancel·review는 fixture 없음, `resume`·`revalidate`만 서버 소유 fixture) `zoop_ai_pipeline`을 import하지 않고 pipeline 원장을 열지 않는다. 서비스 lock에 private 의존성은 추가하지 않았다. 계약은 `internal-ai-openapi.{json,yaml}`에 같은 생성기로 들어간다. **목록 라우트는 없고 후보 승인·게시 workflow가 구현됐다고 주장하지 않는다.** upstream은 운영자가 준비한 S2 job이거나 별도 S2 가족(아래 S2 절, 서버 사전 승인 요청 digest만 받음)이 만든 job이며, 어느 쪽이든 S3 upstream 허용은 운영자 allowlist가 따로 정한다.

- **설정.** 전부 있어야 켜지는 그룹(`ZOOP_AI_SERVICE_RELATION_COMMAND`, `ZOOP_AI_RELATION_STATE_DIR`, `ZOOP_AI_EXTRACTION_STATE_DIR`, `ZOOP_AI_INGESTION_STATE_DIR`, `ZOOP_AI_SERVICE_SOURCES`, `ZOOP_AI_SERVICE_RELATION_REPLAY`, `ZOOP_AI_SERVICE_RELATION_VERIFIER_REPLAY`, `ZOOP_AI_SERVICE_RELATION_UPSTREAMS`와 `ZOOP_STATE_DIR`). 없으면 relation 라우트는 인증 뒤 409 `execution_unavailable`, 일부만 있거나 잘못되면 시작 거부. 요청은 경로·registry·fixture·command·live를 고를 수 없다. 서비스는 relation 원장의 유일한 writer이고 ingestion은 운영자가 쓴다. extraction 원장은 운영자 CLI 또는(S2 그룹을 켠 경우) 이 서비스의 S2 child가 쓰며, S3는 둘 중 누가 썼든 읽기 전용으로만 열고 S2 결과가 S3 upstream 허용을 자동으로 만들지는 않는다(운영자가 allowlist에 명시).
- **upstream 권한.** 호출자가 적은 `{jobId,inputDigest}`는 권한이 아니다. 서버 소유 allowlist가 principal별 정확한 쌍만 허용하고 목록에 없으면 존재 여부와 무관하게 같은 403을 ledger·child 이전에 돌려준다. 파일은 사용할 때마다 다시 읽고 읽을 수 없으면 닫힌다.
- **소유와 멱등.** job은 제출한 principal의 것이고 다른 principal에게는 없는 job과 같은 404다(검토한 ‘모든 principal이 읽는다’는 공유 읽기 모델은 채택하지 않았다). `reserved`(소유 의도, durable)→`zoop-ai-relation submit`→`accepted`+초기 dispatch 1개를 한 transaction으로 기록한다. pipeline `submit`은 이미 있는 id에 저장된 job을 보고만 하므로 첫 시도에서 먼저 `inspect`로 부재를 확인해 운영자가 만든 job의 채택을 막는다. `submit`이 결과를 못 주면 같은 gate 안에서 `inspect`로 등록 여부를 확인해 등록 시 이어 가고, 부재가 증명되면 예약을 풀고, 아니면 예약을 유지한다.
- **자동 재실행 없음.** 최초 dispatch는 한 번 claim한다. timeout·비정상 종료·읽을 수 없는 출력, 죽은 서비스의 in-flight 행은 모호하므로 `idle`(`transport_unknown`/`service_restarted`, `next=recover`)로 끝나고 명시적 `recover`만 이어 간다. 유일한 자동 재시도는 pipeline이 락을 열 때(효과 이전) 내는 `relation_busy`의 제한된 backoff다. reserve됐으나 응답이 기록되지 않은 호출은 pipeline이 `reconciling`으로 만들고 재전송하지 않으며 recover는 409 `reconcile_required`다. pipeline 원장 락이 대기하지 않으므로 서비스가 한 번에 하나의 child만 실행하고 점유 중인 읽기는 오래된 값 대신 503 `runtime_busy`다.
- **취소.** 취소된 job은 멱등 200. ready는 409 `job_already_terminal`이다(pipeline `cancel`은 ready job도 영구 withheld로 바꾸므로 서비스가 상태를 먼저 읽고 ready를 넘기지 않는다). 가짜 성공은 없다.
- **전달 gate.** 소유자, pipeline `ready`+`delivery.status=current`(매 호출 source registry·ingestion·S2 export 재확인), 서버 allowlist의 현재 항목, 허용 목록 투영의 엄격한 통과가 모두 같은 응답 시점에 성립해야 후보가 나간다. 아니면 `delivery.state=withheld`와 사유 코드와 내용 없는 receipt만 돌려준다. 상태·오류·로그에는 후보·인용·digest·경로가 없다. **TOCTOU 한계:** gate는 서로 다른 시각의 읽기이므로 그 뒤의 철회는 보이지 않고 이미 전달한 내용은 회수할 수 없으며, `available`은 앱 import의 현재 권한 재확인을 대신하지 않는다.
- **검수와 원천 버전·revision.** `POST …/{jobId}/reviews`(scope `relation.review`)는 본문 `{relationCandidateId, expectedSourceVersion, expectedSourceRevision, decision}`만 받고 `Idempotency-Key`가 안정적인 operation id다. reviewer는 항상 인증된 principal이며 요청으로 보낼 수 없다. 앞의 병합된 분기 기준(main `91113ce`의 v6·공개 OpenAPI)이 정한 ‘앱 `expectedRevision`과 별개인 AI 원천 기대값’ 규칙을 내부 계약으로 따른다. 내부 값은 `sourceVersion`=S3 job의 `inputDigest`(S2 upstream digest가 아니며 job마다 불변), `sourceRevision`=해당 relation 후보의 이벤트 사슬 revision(이벤트 수)의 10진 문자열이고 `GET …/result`의 relation마다 나온다. **앱의 대상별·전역 검수 revision과는 다른 값이며 서비스는 그것을 받지도 전달하지도 않는다.** 새 결정은 두 값이 정확히 일치해야 한다(version은 예약 전에 원장 값과, revision은 pipeline `review`의 `expectedRevision`으로 append transaction 안에서). 하나라도 다르거나 후보가 HOLD가 아니거나 job이 취소됐으면 아무것도 기록하지 않고(409 `source_version_conflict`·`source_revision_conflict`·`review_target_not_hold`·`review_already_pending`·`job_cancelled`, 404 `relation_candidate_not_found`) 그 key는 다시 쓸 수 있다. 같은 key·본문은 relation이 그 사이 앞으로 갔어도 기존 operation(200), 다른 본문은 409 `idempotency_conflict`, 다른 principal의 key는 409 `operation_id_unavailable`이다.
- **모호한 append의 조정.** operation 예약(소유자·job·후보·결정·두 기대값, durable)을 child보다 먼저 기록한다. 이벤트의 `reviewer`=principal, `note`=operation id에서 만든 marker이므로 ‘내 append가 반영됐는가’는 추측이 아니라 사슬 조회다. 이전 시도가 있었거나 child가 모호하게 끝나면 **쓰기 전에 읽고**, 이벤트가 `seq=expected+1`과 reviewer·decision·expectedRevision·effect·marker까지 모두 같을 때만 채택하며 pipeline이 적은 `createdAt`을 함께 기록한다. 일부만 같으면 모순(500 `runtime_binding_mismatch`)으로 채택하지 않는다. **이전 시도가 있었던 재시도에서는 pipeline의 거절도 부재의 증명이 아니다.** review child는 별도 세션이라 서비스가 죽어도 살아남을 수 있고, 아직 원장 락을 잡기 전인 child가 재시도의 읽기와 쓰기 사이에 같은 operation의 정확한 이벤트를 append하면 재시도의 child는 `review_revision_conflict`로 거절된다(이 창은 크래시 seam만으로는 만들 수 없고 실제 orphan child로 시험한다). 첫 시도의 거절만 확정이고, 재시도의 거절은 체인을 다시 읽어 정확한 이벤트가 있으면 채택하고, 읽을 수 없거나 모순이면 예약을 유지하며, 체인이 expected를 지났는데 marker 이벤트가 없을 때(운영자의 이벤트 등)만 풀어 키를 현재 revision에서 다시 쓸 수 있게 한다. 체인·job 상태만으로 정해지는 거절(`review_target_not_hold`·`review_already_pending`·`job_cancelled`·`relation_candidate_not_found`)은 체인에 우리 이벤트가 없으면 풀고, 후보 없음이 읽은 체인에서도 확인되면 풀며, 사슬을 읽을 수 없으면 503 `review_unconfirmed`로 예약을 유지해 같은 요청의 재시도가 이어 가게 한다. 운영자 CLI가 쓴 이벤트는 marker가 없어 어떤 operation도 채택하지 않는다. 증거가 없으면 가짜 성공 대신 명시적 실패다.
- **operation 상태와 재검증.** `GET …/reviews/{operationId}`는 서비스 원장만 읽어(pipeline이 바빠도, 크래시 뒤에도) operation·후보·결정·reviewer·두 기대값을 그대로 돌려주고 acceptance(`review`: `applied`/`unconfirmed`)·verification(`revalidation`: `queued`·`running`·`verified`+verdict·`superseded`·`interrupted`·`failed`·`cancelled`)·publication(항상 `not_published`)을 따로 보여 준다. 확정된 allow는 재검증 dispatch 1개를 같은 dispatcher·gate·FIFO·상한에서 한 번 실행하고, 그 직전에 소유자의 upstream allowlist를 다시 읽는다(아니면 child 없이 `upstream_not_allowed`로 끝난다). 모호하게 끝난 child와 재시작이 남긴 in-flight 행은 자동으로 다시 실행하지 않고 `POST …/reviews/{operationId}/recover`만 이어 간다. recover는 **사슬을 먼저 읽는다**: 뒤따르는 verdict가 있으면 `verified`, 뒤따르는 reject가 있으면 `superseded`로 확정하고 아무것도 보내지 않으며, relation이 review가 남긴 revision에서 기다릴 때만 재큐한다. 확정은 write-once 종결 상태이므로 그것에 쓰이는 모든 읽기(dispatcher의 `inspect` probe와 `revalidate` 결과, recover의 `inspect`)는 claim의 job·`inputDigest`·upstream에 묶인 뒤에만, 그리고 delivery가 current일 때만 쓰인다. relation 후보 id는 같은 upstream을 쓰는 job들 사이에서 반복될 수 있으므로 다른 job·입력·upstream의 유효한 사슬은 같은 verdict를 보여 주어도 확정하지 못하고 `runtime_binding_mismatch`의 `failed`(미확정, recover 가능)로 남는다. pipeline은 attempt마다 호출을 한 번만 만들고 시작된 호출을 다시 보내지 않으므로 저장된 receipt는 fixture 없이 마무리되고 응답 없는 호출은 409 `reconcile_required`다. 대기 중인 allow는 뒤의 reject를 덮어쓰지 못한다(`superseded`). 재검증 중에는 job이 `running`이라 결과 전달이 withheld다.
- **호환·마이그레이션.** 서비스 원장 스키마 `zoop-ai-relation-jobs-ledger-1`→`-2`(테이블 `relation_operations`와 job·재검증이 공유하는 dispatch 순서·상한)는 열 때 앞으로만 제자리 이전하고 이후·외부 스키마는 거절한다. **pipeline은 이 slice에서 바꾸지 않았다**(marker·CAS·이벤트 기록이 `review`·`revalidate`·`inspect`에 이미 있다). 호출자에게 보이는 변경은 additive다(scope `relation.review`, 라우트 3개, result relation의 `sourceVersion`·`sourceRevision`, 오류 봉투의 선택 필드 `operation`). 팀 분기가 main(`91113ce`)에 병합됐으므로 앱 쪽 영속화(`review_targets`·`review_decisions`)는 병합된 v6·공개 OpenAPI에 이 계약을 맞춰 구현할 수 있고 아직 구현하지 않았다. Spring 전송 클라이언트(`RelationClient`의 `review`·`operation`·`recoverOperation`)는 로컬에서 구현·종단 검증했다: AI 원천 `expectedSourceVersion`·`expectedSourceRevision`만 전달하고 앱 revision을 넣을 필드가 없으며 operation 응답을 요청·job에 결속해 검증한다([api AI 연동](../../api/docs/AI_INTEGRATION.md#s2-추출s3-관계-클라이언트)).
- **시험.** `make service-test`(pipeline 불필요: 설정·allowlist·정책·원장·투영·비활성 라우트·Gateway catch-all의 family별 envelope, 그리고 `test_relation_review_unit.py`의 모의 child 검수 결정 트리와 `-1`→`-2` 이전)와 별도 `make service-pipeline-test`·`service-pipeline-smoke`(실제 uvicorn + 설치된 `zoop-ai-relation` + 새 운영자 ingestion/S2 세계, 설치된 pipeline이 없으면 skip이 아니라 실패. 검수 allow→재검증→새 revision, reject, stale 거절, 중복 key, 다른 principal, 철회, review 반영 직후 크래시, verifier receipt 저장 뒤 크래시를 포함)다. 기존 `ai-pipeline` CI job의 자격 증명 범위는 바꾸지 않았다. 이 추가분이 원격 CI에서 실행된 결과는 관측하지 않았다.
- **관측한 최종 실행(10/13, 로컬 작업 트리, Main 실행).** 검수·재검증 slice와 독립 검토가 찾은 두 지적(R1: 재시도의 거절 뒤 체인 재조회, R2: probe의 job·`inputDigest`·upstream 결속)을 반영한 뒤 `make service-test` **403 tests**, `make service-pipeline-test` **59 tests**, 실제 `make service-pipeline-smoke`가 통과했다. smoke는 검수 allow→재검증으로 `sourceRevision` 1→2→3(verifier 호출 1회, 게시 없음), 서비스를 SIGKILL한 뒤 락을 잡기 전에 살아남은 실제 orphan review child가 재시도의 읽기 뒤에 append한 정확한 이벤트의 marker 채택(이벤트 1개, 재검증 1회), 운영자 이벤트(foreign) 대조에서의 예약 해제와 revision 2에서의 키 재사용, verifier receipt 저장 뒤 크래시의 추가 호출 0을 확인했다. OpenAPI 재생성 뒤 drift는 0이었고 `make public-check`는 생성물 275개 차이 없음·하드 오류 0·문서 시스템 테스트 21개 통과였다. 이전 이력: Gateway 수정 뒤 `service-test` 291 tests·`service-pipeline-test` 24 passed(이 slice 이전), 첫 전체 실행의 로그 allowlist 실패와 독립 검토가 찾은 Gateway catch-all의 relation 경로 S1 envelope 오류는 각각 고쳤고 후자는 회귀 시험으로 먼저 실패를 확인했다. 이 관측 당시에는 커밋·푸시·원격 CI·배포를 하지 않았다. 당시 팀 분기 `fix/17-erd-v6-alignment`(`af2f0e3`)는 병합 전이었고 이후 main `91113ce`(PR #18)로 병합됐다. 병합은 `ai/`를 바꾸지 않았고 이 시험들은 병합 뒤 다시 실행하지 않았다. **S3 검수·재검증과 S2 추출 job HTTP는 로컬에서 완료·검증했고 목록 라우트는 아직 없다.**

### S2 추출 job의 내부 HTTP (`/internal/v1/extraction-jobs`)

S3와 같은 서비스 프로세스 안의 **별도 가족**(응답 스키마 `zoop-ai-internal-extraction-1`, scope `extraction.*`, 서비스 원장 `extraction-jobs.sqlite3` 스키마 `zoop-ai-extraction-jobs-ledger-1`, 기본 꺼짐)이다. 설치된 `zoop-ai-extract`의 `submit/inspect/cancel/resume`만 고정 argv로 호출한다(`run`은 쓰지 않는다: 등록과 실행은 별도 명령·권한). 계약과 설정은 [`ai/service/README.md`](../../ai/service/README.md#s2-추출-job-internalv1extraction-jobs)가, 생성된 OpenAPI가 기계 판독 계약이 된다.

- **호출자는 참조만 보낸다.** 본문은 정확히 `{schemaVersion, jobId, approvedRequestDigest}`다. 서버 소유 승인 파일이 `principal+jobId+digest`를 정확한 S2 `Submit` 본문과 producer·(선택) topic fixture의 SHA-256에 대응시키고, 서비스는 정규 JSON digest·`jobId` 일치·replay 전용 provenance·topic 요청과 topic pin의 짝을 검증한다. 호출자 스냅샷·카탈로그·incoming 관측·경로·fixture는 알 수 없는 필드로 거절된다. 승인은 pipeline의 source registry가 허용하는 것을 **좁히기만** 한다(registry는 내용을 다루는 모든 명령에서 다시 읽힌다).
- **고정된 신원과 같은 job id의 재결속 금지.** 예약은 `submit` 전에 승인 digest·producer digest·topic digest와 서비스가 승인 바이트로 계산한 `inputDigest`를 불변 열로 영속한다(pipeline이 보고하는 `inputDigest`가 이 값과 같아야 `accepted`). 정확한 재전송은 고정 값을 유지하고, 같은 job에 다른 요청은 409, 승인·fixture가 바뀌면 409 또는 withheld이며 고치려면 새 jobId를 승인해야 한다.
- **모든 내용 사용에서 권한 재확인.** 승인 파일을 다시 읽고 fixture를 다시 해시하는 시점은 submit·매 dispatch(최초 포함)·recover·전달이다. 전달은 pipeline `ready`+`delivery=current`, 승인이 예약된 것과 같음, fixture가 고정 바이트, **모든 receipt가 그 바이트로 응답됨**, 엄격한 허용 목록 투영 통과가 모두 같은 응답 시점에 성립할 때만 나간다. 사건 후보·비교·disposition·토픽 후보는 이름을 적은 필드만 보존하고 pipeline이 더하는 artifact·locator·digest·binding과 인용으로 뒷받침되지 않은 생성 텍스트는 내보내지 않으며, 검증 실패는 원문 fallback 없이 `projection_invalid`다.
- **fixture 파일의 TOCTOU.** child가 직접 읽는 파일이라 서비스의 digest 확인은 원자적이지 않다. 사후에 닫는다: 등록 중 교체는 `inputDigest` 불일치(500 `runtime_binding_mismatch`, 예약만 남고 dispatch 없음), 실행 중 교체는 receipt hash 불일치(dispatch `fixture_changed`, 파일을 되돌려도 전달 withheld). 어떤 경로(오류 포함)에서도 네트워크는 없다.
- **자동 재전송 금지.** 모호한 dispatch(timeout·비정상 종료·재시작)와 pipeline이 `stopped`로 기록한 job(실행 도중 `ingestion_busy` 포함)은 명시적 recover만 이어 가며 pipeline은 바꾸지 않았다. 어떤 효과도 일어나기 전의 `extraction_busy`·`ingestion_busy` 오류만 자동 재시도(최대 8회)한다. reserve된 호출의 무응답은 `reconciling`이고 다시 보내지 않는다. `submit`이 모호하면 같은 gate 안의 `inspect`로 조정하고 `submit`을 다시 보내지 않는다. 취소는 queued·running·stopped·reconciling을 `cancelled`로 끝내고(멱등) ready는 409 `job_already_terminal`로 남긴다(S2 pipeline `cancel`은 ready를 건드리지 않는다).
- **S2→S3.** S2 결과는 S3 권한을 넓히지 않는다. S3 upstream은 운영자가 별도 allowlist 파일에 명시적으로 적어야 하고, 두 가족은 단일 gate 뒤에서 child를 한 번에 하나씩 실행한다(S3가 읽는 S2 원장을 S2 child가 쓴다). 두 가족의 권한(S2 승인, S3 allowlist)은 서로를 바꾸지 않으며 공유 source registry는 둘 모두를 withheld로 만든다.
- **상태.** 구현과 시험(`tests/test_extraction_unit.py`, `pipeline_tests/test_extraction_{flow,authority,recovery,chain}.py`, `scripts/extraction_service_smoke.py`)은 아래 관측으로 검증했다. 관측(10/13, 로컬 작업 트리, Main 실행): `make service-test` 461 tests, `make service-pipeline-test` 96 tests(설치된 pipeline 통합), 실제 `make service-pipeline-smoke`(S2 → S3)가 통과했다. smoke는 저장된 receipt가 stage 완료 전에 남은 경우의 재사용(추가 호출 0), 승인·source 철회와 fixture 회전의 withheld, 크래시 뒤 중복·유실 없음, 그리고 S2 HTTP ready → 운영자의 명시적 S3 upstream 허용 → S3 HTTP ready(관계 2개, S2 replay 3회, S3 replay 5회, provider 호출 0, 자동 권한 상승 없음)를 확인했다. OpenAPI 재생성 뒤 drift 0, `make public-check`는 생성물 275개 차이 없음·하드 오류 0·문서 검사 21개 통과였다. 이 관측 당시에는 커밋·푸시·원격 CI·배포를 하지 않았고 replay는 authored 응답이라 실제 모델 품질의 증거가 아니다. 당시 팀 분기 `fix/17-erd-v6-alignment`(`af2f0e3`)는 병합 전이었고 이후 main `91113ce`(PR #18)로 병합됐다. 병합은 `ai/`를 바꾸지 않았고 이 시험들은 병합 뒤 다시 실행하지 않았다. 이후 Spring 전송 클라이언트(`ExtractionClient`·`RelationClient`, [api AI 연동](../../api/docs/AI_INTEGRATION.md#s2-추출s3-관계-클라이언트))가 로컬에서 이 두 가족의 실제 서비스·설치된 pipeline 종단 gate(`api/scripts/ai_pipeline_gate.py`)를 통과했다(원격 CI 미실행, 앱 DB·결과 import·사용자 격리·공개 endpoint는 없음). 남은 범위: S2 목록 라우트, 앱 영속화, 승인 항목의 운영 절차(누가 어떤 요청을 어떤 digest로 승인하는가), 직렬 gate의 처리량·`resume` 소요 시간 측정, live S2 전의 under-lock initial-only 표지와 목적·수신자 검사.
- **Spring 전송 클라이언트 종단 관측(2026-10-14, 로컬 작업 트리, Main 실행).** 전체 Java 시험 187개 통과(실패 0, skip 0)와 `assemble`, 실제 `api/scripts/ai_pipeline_gate.py`는 `AiPipelineContractTest` 13개 통과·서비스 6개·provider 호출 0·네트워크 시도 0·운영자 ingestion·extraction 상태 변경 없음, S1 gate는 9개 통과했다. 이 실행에서 서비스·pipeline 코드는 바뀌지 않았고 `service-test`·`service-pipeline-test`는 다시 실행하지 않았다. 독립 읽기 전용 검토 지적 4건(영수증 개수 상한, 변경 성공 응답 phase, operation `next` 규칙, READY가 아닌 job의 `available`)은 수정·회귀 시험으로 닫았고, `recover_operation` 202가 gate를 놓은 뒤 만들어져 이미 진행된 phase를 보일 수 있다는 경합은 소스 검토로 찾아 수정했으며 수정 뒤 시험만 있다(수정 전 실패 실행 없음). 커밋·푸시·원격 CI·배포 없음, replay는 authored 응답이다.

남은 범위: 배포 환경의 SG/route/프록시/TLS 실관측(WBS 6.11.2/8), Spring 전송 클라이언트 위의 S2·S3·`briefing-outlook` 결과 가져오기(import)·앱 DB 저장(S1 문서 요약·기업 판정은 operator 전용으로 구현됨, [문서 분석](../../api/docs/DOCUMENT_ANALYSIS.md))과 공개 인증·읽기 경로·BFF 전환 결정, 운영 토큰 digest 발급·교체 절차 실행, S2·S3 목록 라우트와 앱 영속화(S2·S3 Spring 전송 클라이언트와 그 실제 서비스 종단 gate는 로컬에서 구현·검증됨), 직렬 dispatcher의 처리량·`resume`·`revalidate` 소요 시간 측정, 정산 불가 `reconciling`의 공급자 측 증거 절차는 구현·검증하지 않았다. 실제 S2·S3를 열기 전에는 pipeline에 under-lock initial-only 표지와 purpose·recipient 검사가 필요하다. 매달린 orphan child는 서비스가 pid를 몰라 종료하지 않는다.
